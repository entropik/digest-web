Fin du P1 backend et WooCommerce service

Le premier travail a été de terminer la suite logique du P1 backend.

Après pricing, assets et print jobs, backend/src/routes/woocommerce.ts a été allégée en sortant le workflow métier dans backend/src/services/woocommerce-service.ts.

Le service porte maintenant les use cases importants :

  • création de commande checkout depuis un projet ;
  • consommation de token de lancement Woo ;
  • webhook de commande confirmée ;
  • reprise, duplication et suppression de projets client ;
  • lock de checkout pour éviter les doubles commandes.

La route reste responsable du HTTP : schémas, status codes, headers, auth intégration et cookies. Les décisions métier sont dans le service.

Ce lot a aussi réparé des migrations d’attributs atelier et de processus MISKISS qui bloquaient les contrats Prisma. Ce n’est pas glamour, mais c’est essentiel : une bêta ne peut pas dépendre d’un historique Prisma approximatif.

Le P1 backend a ensuite été merge sur dev via PR.

Better Auth : socle bêta et Google OAuth

Le gros chantier du milieu de journée a été l’authentification.

L’objectif n’était pas de remplacer brutalement l’ancien /api/auth. Le choix a été plus prudent : ajouter Better Auth sur une surface isolée /api/auth-v2/*, puis construire un pont vers la session KEREDIT existante.

Ce qui a été posé :

  • models Prisma better_auth_* ;
  • configuration backend/src/lib/better-auth.ts avec adapter Prisma ;
  • Google OAuth optionnel ;
  • route /api/auth-v2/keredit/session pour convertir une session Better Auth valide en session KEREDIT ;
  • route de config OAuth pour masquer Google quand les secrets ne sont pas présents ;
  • preflight local pnpm auth:preflight ;
  • documentation dans docs/architecture/auth-roadmap-better-auth-2026.md.

Le test local Google a fait apparaître un state_mismatch, puis le parcours a été corrigé côté environnement/cookies jusqu’à obtenir une connexion fonctionnelle.

Sur le VPS, il a fallu ajouter explicitement les variables Better Auth dans le compose. Le login Google backoffice a ensuite été validé en live sur ooblik.keredit.com.

Décision produit importante : pendant la bêta, la création publique de compte reste fermée. Les comptes sont créés depuis le backoffice. Le bouton Creer un compte a donc été retiré, et le public signup Better Auth est rejeté côté backend.

Utilisateurs admin : enfin un vrai outil

Le backoffice Utilisateurs était trop pauvre pour administrer KEREDIT sérieusement.

Le chantier a ajouté une vraie gestion opérationnelle :

  • liste avec recherche, filtres, tri et sélection multiple ;
  • édition utilisateur ;
  • changement de rôle ;
  • reset ou initialisation de mot de passe ;
  • rattachement et lecture des projets accessibles ;
  • suppression protégée ;
  • actions batch ;
  • vraie implémentation reset password, pas un placeholder bêta.

L’UX a été revue pendant la session :

  • champ recherche corrigé ;
  • drawer latéral remplace par une modale centrée ;
  • projets présentes de façon plus compacte ;
  • ouverture des projets client dans un nouvel onglet ;
  • confirmation de suppression via notre modale, pas window.confirm.

Ce lot a aussi clarifié une règle produit : KEREDIT est l’admin des clients qui utilisent l’application. OOBLIK est le premier client, mais l’interface doit rester capable de gérer d’autres comptes, rôles et projets.

Le pont OOBLIK : corriger un projet client depuis KEREDIT

Une question produit a structuré la suite : si un client OOBLIK commande une carte postale puis signale une faute, où doit-on corriger ?

La décision retenue : la correction du projet se fait dans KEREDIT, pas dans WordPress. WordPress/WooCommerce reste le canal commerce, commande et paiement. KEREDIT reste l’atelier de création, correction et support.

Le code a donc ajouté un pont support :

  • backend/src/services/admin-project-support-service.ts ;
  • contexte support Woo dans les routes admin projets et commandes ;
  • liens visibles dans les pages admin KEREDIT ;
  • metabox KEREDIT dans les commandes WooCommerce quand une commande porte _keredit_project_id.

Le but est simple : depuis une commande Woo, OOBLIK doit pouvoir ouvrir le projet KEREDIT correspondant et corriger rapidement.

Éditeur : prix visible et bouton Commander

La fin de journée produit a touché l’éditeur.

Le panneau de propriétés affichait encore un mini récap prix redondant. Le prix total a été remonté dans le header, à côté de l’action de commande.

Le nouveau flux :

  • le header montre Total XX,XX EUR ;
  • le bouton principal est Commander ;
  • Sauvegarder quitte le header et passé dans la ligne de menu, aligne à droite ;
  • le panneau de propriétés gardé format, nom, quantité et options, mais plus le récap panier.

Plusieurs corrections UX ont suivi :

  • bouton Commander invisible au hover ;
  • état disable trop blanc ;
  • libellé qui clignote entre Sauvegarder et Sauve ;
  • alignement et contraste terracotta ;
  • suppression du tooltip inutile Commander ce projet.

Le hook frontend/src/hooks/useEditorCheckout.ts centralise maintenant devis, options par défaut et action checkout. Le bouton appelle /api/projects/:id/add-to-cart, puis redirige vers WooCommerce.

En local, le checkout échouait avec une erreur 500 parce que les credentials Woo locaux étaient des placeholders. Ce n’était pas un bug du code : le VPS devait être testé avec les vrais secrets.

Déploiement VPS et warning Prisma/OpenSSL

Un déploiement VPS a été lancé pour tester le parcours en production.

Source de vérité :

  • branche dev ;
  • SHA f05bd66ad959, puis 97efe7f91479 après correctif Docker ;
  • version 0.6.37, puis 0.6.38.

Le deploy nominal deploy/manual-vps-local.sh a construit les images sur le VPS, applique Prisma, seed, redémarre backend/worker/frontend et vérifié :

  • https://ooblik.keredit.com/ ;
  • https://krampouz.ooblik.com/ ;
  • /api/health ;
  • /api/theme.

Un avertissement Prisma/OpenSSL est apparu dans les conteneurs Node. Il aurait été facile de le repousser à “après bêta”. Marc a refusé, à raison.

La correction a installé openssl et ca-certificates dans les stages Docker Node :

  • Dockerfile.backend stage deps ;
  • Dockerfile.backend stage runtime ;
  • Dockerfile.frontend stage deps, car le build frontend installe aussi le workspace backend et déclenche prisma generate.

Validation :

  • build Docker local backend/frontend ;
  • npx prisma generate dans l’image runtime sans warning ;
  • redéploiement VPS ;
  • logs backend/worker relus sans prisma:warn, failed to detect ou openssl.

Plugin WordPress : la procédure devait devenir exécutable

Le plus gros rappel à l’ordre de la journée est venu du plugin WordPress.

Le code plugin avait été modifié pour le support commande Woo, mais aucune mise à jour n’apparaissait dans le backoffice OOBLIK.

Cause initiale : le plugin source était reste en version 0.1.20. Si le manifest public dit déjà 0.1.20 et que WordPress à 0.1.20, WordPress ne proposera jamais d’update.

Cause réelle plus profonde : ooblik.com utilisait encore l’ancien slug installe krampouz-connector, alors que la publication récente visait surtout keredit-connector. On publiait le mauvais canal pour l’installation active.

La correction a été volontairement plus dure qu’un patch :

  • création de pnpm plugin:publish ;
  • lint PHP ;
  • build ZIP ;
  • alignement manifest/checksum ;
  • upload sur updates.ooblik.com ;
  • publication du canal canonique keredit-connector ;
  • publication du canal legacy krampouz-connector tant que le site live n’a pas migré ;
  • vérification checksum public ;
  • purge caches WordPress ;
  • vérification WP-CLI.

Le script de deploy VPS contrôle maintenant les changements sous wordpress-plugin/keredit-connector/. Si le plugin à change sans version publiée, le déploiement refuse de continuer.

AGENTS.md, le skill .codex-skills/wp-plugin-release, le guide WooCommerce et BIBLIOTHEQUE.md ont été mis à jour : une modification plugin n’est plus une simple édition source, c’est une release.

Incident de migration plugin et correction 0.1.23

En activant la nouvelle version, WordPress a affiché :

Desole, vous n’avez pas l’autorisation d’accéder à cette page.

La page ouverte était admin.php?page=krampouz-editor.

Le problème n’était pas le compte utilisateur. C’était un slug admin legacy non déclaré par le nouveau plugin. Après la migration, WordPress gardait ou ouvrait encore l’ancienne URL, mais le plugin ne l’enregistrait plus.

La version 0.1.23 a restauré les alias :

  • page=krampouz-editor redirige vers page=keredit ;
  • page=krampouz-connector redirige vers les réglages techniques ;
  • les options live ont été migrées vers keredit_connector_settings ;
  • le plugin actif sur ooblik.com est maintenant keredit-connector, version 0.1.23.

Vérification WP-CLI finale :

keredit-connector,KEREDIT,active,0.1.23,none

Complément tardif : test live et quantité Woo/KEREDIT

Après le close-out initial, un test en situation sur le produit OOBLIK test krampouz a révélé un autre problème de contrat commerce.

Le produit n’était pas perdu. Il existait toujours côté WordPress, mais son permalink courant était :

https://ooblik.com/impressions/test-krampouz/

L’ancienne URL /produit/test-krampouz/ redirigeait vers ce nouveau slug, et le produit restait marqué en visibilité catalogue cachée. Les metas legacy _krampouz_connector_* et les nouvelles metas _keredit_connector_* étaient présentes, donc le changement Krampouz/KEREDIT n’avait pas efface le mapping.

Le vrai bug était ailleurs : le lancement WooCommerce créait un projet KEREDIT avec selected_quantity = 1, puis l’éditeur appelait :

/api/projects/:id/pricing?...&quantity=1...

Or le produit KEREDIT Carte postale impose une règle de quantités :

min = 8
default = 8
values = [8, 16, 24, 48, 100, 200, 500]

Le 400 Bad Request était donc logique : KEREDIT refusait une quantité invalide. La faille était dans l’alignement produit : WooCommerce envoyait sa quantité de ligne par défaut (1) comme si c’était la quantité d’exemplaires atelier.

Décision de contrat prise en fin de soirée :

  • KEREDIT est la source de vérité des quantités imprimées ;
  • le produit WooCommerce doit recevoir les quantités autorisées depuis KEREDIT ;
  • le plugin doit synchroniser automatiquement la règle quantité du produit KEREDIT ;
  • la fiche produit Woo ne doit plus laisser partir 1 si KEREDIT attend 8, 16, 24, etc. ;
  • le backend KEREDIT doit rester défensif et refuser ou corriger toute quantité Woo invalide.

Un correctif local a été commencé sur cette base :

  • nouvelle route backend /api/woocommerce/products/:productId/config pour exposer la config produit KEREDIT au plugin ;
  • nouveau module plugin class-product-sync.php pour synchroniser et cacher la règle de quantité sur le produit Woo ;
  • transformation du champ quantité Woo en liste des valeurs KEREDIT autorisées ;
  • protection backend pour ne plus créer un projet depuis Woo avec selected_quantity=1 quand la règle produit demande 8 ;
  • correction frontend pour rebasculer les anciens projets invalides vers une quantité autorisée.

État au moment de l’interruption poste :

  • version locale préparée : application 0.6.40, plugin 0.1.24 ;
  • ZIP plugin keredit-connector-0.1.24.zip construit localement ;
  • manifest local 0.1.24 mis à jour avec checksum ;
  • upload vers updates.ooblik.com interrompu avant publication ;
  • aucun commit ni deploy VPS effectué après a14b027.

Ce complément change la conclusion produit : le parcours client complet ne doit pas seulement vérifier bouton, éditeur et checkout. Il doit aussi vérifier que la fiche WooCommerce et KEREDIT parlent exactement la même langue sur les quantités, les formats, les options et le prix.

Auto-critique

La journée montre deux choses.

D’abord, les gros chantiers avancent bien quand les frontières sont explicites : route/service, auth provider/session KEREDIT, WordPress commerce/KEREDIT atelier, deploy app/release plugin.

Ensuite, une procédure dans la doc n’est pas une procédure fiable. Tant que le deploy pouvait passer alors qu’un plugin avait changé sans release, le système était fragile. Le bon correctif n’était pas de “penser à le faire”. Le bon correctif était de faire échouer le script.

Le même principe vaut pour les migrations legacy : on ne peut pas supposer que le live à déjà le nouveau slug. Tant que ooblik.com portait encore krampouz-connector, le canal legacy devait rester vivant.

État pour demain

Le socle est meilleur qu’au matin :

  • Better Auth est posé et Google backoffice fonctionne ;
  • la création publique de compte est fermée pour la bêta ;
  • l’admin utilisateurs devient utilisable ;
  • l’éditeur sait afficher prix et commander ;
  • le VPS sert 0.6.38 aujourd’hui, et le repo local est préparé en 0.6.39 ;
  • le plugin WordPress est actif en 0.1.23 sur ooblik.com ;
  • le release flow plugin est maintenant exécutable et bloqué les oublis.
  • un nouveau lot local 0.6.40 / 0.1.24 est en cours pour aligner les quantités WooCommerce sur les quantités KEREDIT.

La suite logique est de reprendre le parcours client complet en live : produit WooCommerce, création, édition, sauvegarde, commande, retour commande, support backoffice et correction projet.

Il faudra aussi choisir si on termine et publie d’abord le correctif quantités 0.6.40 / 0.1.24, puis si on redeploie le VPS pour un test contrôle sur le produit test-krampouz.

Et surtout : demain, repartir avec la fatigue en moins. Aujourd’hui, il faisait environ 30 degrés dehors et la journée a été longue.
