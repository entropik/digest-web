Day 73 – Stabilising the editor whilst GOF takes shape

KEREDIT: making the beta less fragile

The first KEREDIT focus of the day is direct uploads and diagnostics.

The commit 6ed046c added an R2 probe script, two reference CORS configurations, deployment notes and a more explicit upload specification. The bug report button has also been streamlined to better capture what matters rather than generating noise.

It’s a subtle but crucial issue for the beta: if a client or tester uploads a photo and the asset doesn’t appear, we need to know whether the problem lies with the browser, R2, the backend, the frontend poll, the worker or the thumbnail. Without diagnostics, every test looks like a system-wide failure.

Assets: quickly see what you’ve just imported

The rest of the day revolved around the asset contract.

The commits 1d4f0e0, 652b68a and, most importantly, 40bbab6 have tightened up several layers:

  • refreshing the preview after upload;
  • creation of a preview key for imported photos;
  • asset contract backend helpers;
  • audit and repair scripts;
  • backend tests for the asset contract;
  • corrections to the pipeline worker;
  • front-end formatting of assets;
  • thumbnails in the options panels;
  • consistency between upload status, preview and editor display.

The key point is this: for the beta, ‘uploaded’ and ‘preview_ready’ are the statuses that must instil confidence in the user. ‘print_ready’ remains a production concern, but it must not block visibility in the editor.

This day has therefore refocused attention on the right thing: the user must be able to see their image, understand that it is available, and continue editing without having to wait for the entire production pipeline to have finished processing.

Save, autosave and visible action

Commit f1a25b6 completed the move of the save button to the global header.

This detail had already been refined through screenshots: size, line style, legibility, and ensuring there were no duplicates in the toolbar. This isn’t just cosmetic. For a client-side editor, the save button must be where the eye naturally looks for it, and it must not compete with style controls.

The commit b97124c addressed a more fundamental issue: autosave freezes during dragging.

The Postcard beta needs basic gestures to remain fluid. Moving a photo, text or decorative element must not give the impression that the application has frozen because it is persisting too aggressively at the wrong moment. The fix is a step in the right direction: less friction during interaction, with persistence at the right pace.

Text and editing controls

The commit 6548090 has fixed the text style controls.

It added common components for colour swatches and font selection, dedicated helpers for text styles, and tests for the font catalogue and controls. The text panel and toolbar have been realigned.

This issue is important because, whilst text is not the main area to be reopened before the beta, it must remain stable. A text tool that loses its font, displays colours incorrectly, or shows inconsistencies between the panel and the toolbar immediately gives the impression of an unfinished editor.

So today’s work didn’t mark the relaunch of a typographic ambition. Instead, it consolidated what already exists to ensure that the controls already on display remain consistent.

Woo launch and round logo

The late afternoon also saw fixes to visible details relating to the Woo launch and the logo.

The commits ddabd28 and 341540f refined the splash screen, the admin user query and the round logo on the splash page. The commit 7e12d3e adjusted the fit icon for the photo frame.

The approach remains the same as in previous days: minor visual inconsistencies are not mere details when preparing for a closed beta. They are indicators. KEREDIT must give the impression of a polished tool, even if the entire production workflow is not yet finalised.

Local runtime: adapting the workstation

The final KEREDIT commit of the day, 1e71664, adapted the local runtime for Mac.

It affected the dev scripts, the local DB bootstrap, the backend reset, the status, the start/stop commands and the workstation recovery guides. A helper scripts/dev-runtime-lib.sh was added to centralise part of this logic.

This is less product-related, but very important for the future: a beta cannot be properly prepared if the development workstation misrepresents its purpose. So 3 June was also a day spent making the environment more reliable.

GOF: a clean start for the forge

On the GOF front, 3 June is even more straightforward.

At 08:34, the commit ‘ccfb2d6’ established the initial baseline for the build system: Node app, Dockerfile, Docker Compose, Postgres, Redis, worker, dashboard, storage, queue, PDF renderer, installation scripts and operational documentation.

The GOF folder thus ceased to be merely a collection of notes. It became a repository.

The main components are:

  • an app gof-forge-app;
  • a rendering worker;
  • a BullMQ queue;
  • a Postgres database;
  • local storage and R2;
  • a basic low-level PDF renderer using pdf-lib and sharp;
  • an operator dashboard;
  • documentation on installation, security, HTTPS exposure and operations;
  • a synchronisation script to the workshop machine.

The commit `8f9dcc8` then cleans up the repository by ignoring local backups and Playwright artefacts. This is a clean-up commit, but it’s important: a workshop forge must not begin its Git life with local backups as a source of noise.

Client-side reverse proxy and workshop exposure

The commit 621f1a1 documents the client-side reverse proxy installation.

It adds docs/reverse-proxy-installation-client.md and connects README.md, docs/exposition-https-autonome.md and the Ubuntu runbook. This is already a real-world issue: GOF must reside within the workshop, but certain services must be properly accessible from the outside or from KEREDIT, depending on the traffic flows.

This isn’t yet the pairing session scheduled for 4 June. It’s preparation for the demonstration: how to make the forge accessible without turning every client into a system administrator.

GOF back office: view jobs

The commit 3c6c49c, made at the end of the day, adds a full-screen modal for displaying job details.

It modifies `app/src/server.js`, updates the dependencies and enhances the operations/runbook documentation. This is a strong product signal for GOF: the operator must not only know that a job exists, but must be able to open it, read its payload, its artefacts and its events in a user-friendly interface.

A PDF forge is not a black box. It must explain what it received, what it produced, and where it failed.

What 3 June tells us about 4 June

The post from 4 June describes the entire workflow:

WooCommerce -> KEREDIT -> GOF -> Accurio Flux -> atelier

The 3 June post, on the other hand, covers the preparation for this workflow.

KEREDIT works on user inputs: uploads, assets, autosave, text, launch, local runtime.

GOF is working on the production environment: Git repository, Docker stack, worker, renderer, dashboard, reverse proxy, operations.

The following day, these two worlds began to communicate more openly with one another regarding Accurio. But without 3 June, 4 June would have meant less. First, each side needed to be a bit more organised.

What’s holding up

By the end of the day, several things are more robust:

  • uploads have better diagnostics;
  • asset previews have a clearer specification;
  • thumbnails reappear more quickly in the interface;
  • autosave causes fewer issues with interactions;
  • text controls are better modularised and tested;
  • saving is handled in the global header;
  • the local runtime is better suited to the workstation;
  • GOF exists as a Git repository and as a Stack Atelier;
  • the GOF back office has started to provide visibility to operators.

The keredit-site repository, however, shows no Git activity on 3 June. The KEREDIT day visible in the logs is therefore driven by the Krampouz/KEREDIT monorepo, not by the separate showcase site or WordPress site.

What remains fragile

The main vulnerability remains the end-to-end workflow.

Each component has progressed, but the whole is not yet a beta workflow that can be smoothly replayed. Assets must remain visible without having to wait for production. Autosave must remain seamless during interaction. GOF must be accessible from the right locations, not just from the dev workstation. And the future Accurio link must not blur the division of responsibilities: KEREDIT for the project and the order, GOF for the forge and the operator, Accurio for production.

Resumption

The logical next steps after 3 June are straightforward:

  1. re-run a photo import and check that the preview becomes visible without having to wait for ‘print_ready’;
  2. test a long drag with autosave enabled;
  3. check the text controls displayed in the toolbar;
  4. confirm that the dev scripts correctly indicate that the runtime has loaded;
  5. open GOF, create or inspect a job, and check that the operator details are legible;
  6. prepare the KEREDIT → GOF bridge without making GOF an opaque dependency.

3 June wasn’t a spectacular day in terms of a single major deliverable. It was better than that: a day of fine-tuning. The publisher is becoming less anxious, the assets are becoming more predictable, and GOF has moved from the draft stage to the start of production.
