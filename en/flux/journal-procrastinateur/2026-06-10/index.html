Day 80 – Templates become format families

Audit of the KEREDIT-GOF JSON contract, TLS hardening, photo placeholder, live stabilisation of multi-format templates and seamless photo replacement in image blocks.

Post prepared during the live tests on Wednesday 10 June 2026. The status described here corresponds to the code pushed and deployed up to KEREDIT 0.6.102.

Brief conclusion

The day began with a contractual issue: why do the KEREDIT publisher, the transmitted JSON, GOF and the PDF still diverge when the fields appear to exist somewhere?

It ended with another, more business-related issue: a template can no longer be thought of as a single layout that is stretched across different formats. A template becomes an editorial family, with a variant for each format, and the client can switch from 10x15 to 10x10 without losing the photo that has already been placed.

In between, we also fixed a TLS security issue, made the photo placeholder sharper, and then traced several live bugs from WordPress to WooCommerce to KEREDIT back to their true source: not the plugin itself, but the continuity between template variants, created projects, client permissions, format changes and client content.

Morning: auditing the KEREDIT → GOF JSON contract

The first KEREDIT commit of the day, 298cde9, carries out a full audit of the KEREDIT → GOF JSON contract.

This work stems from a painful but useful realisation: guessing field by field is no longer enough. Image, text, clipart and shape blocks must have an explicit decision regarding:

  • field to be persisted and rendered;
  • field deliberately ignored;
  • field not supported but deferred;
  • field missing from the payload and therefore requiring correction.

The audit adds traceable documentation to docs/audits/keredit-gof-json-contract-2026-06-10.md, strengthens the backend tests for the export payload and verifies that important fields survive all the way to KereditPdfForgePayloadV1.pages.

On the GOF side, 4249b81 implements the same logic: the renderer is better equipped to audit KEREDIT canvas fields, and the fixtures for the sensitive commands 1075752 and 1075753 act as safeguards.

The method point is important: when the editor and the PDF do not match, the problem must be treated as a contract bug, not as a blind rendering tweak.

Security: remove the GOF TLS bypass

The commit 8feb9ef fixes a targeted security issue in the KEREDIT-side GOF client.

The GOF configuration helper was disabling TLS validation via rejectUnauthorized: false. Even though the current live configuration uses a GOF HTTP LAN, this flaw posed a risk to any future HTTPS instances: GOF bearer tokens, the Accurio catalogue and cached responses must not pass through a channel that silently accepts an invalid certificate.

The fix is deliberately minimal:

  • removal of the unconditional TLS bypass;
  • addition of a check to prevent its silent reintroduction;
  • retaining the current HTTP LAN behaviour;
  • no new global bypass flag.

The result is more robust: if an HTTPS GOF has a faulty certificate, the certificate will need to be fixed, not KEREDIT weakened.

Placeholder photo: sharper first impression

The commit ea77ae1, followed by part of ac5e85f, address a very noticeable issue: the empty photo placeholder.

Before the fix, the icon and the text “Add a photo” could appear blurry or become out of sync with the frame during interactions. This isn’t just an aesthetic issue: it’s the first thing a customer sees before adding their photo.

The placeholder rendering now remains vector-based, rather than being cached as a blurry bitmap, and its sub-elements are tagged to follow the frame during resizing and dragging:

  • placeholder background;
  • icon;
  • labelling;
  • block border.

The `test:photo-placeholder` test locks in this behaviour. The aim is simple: even before the client-side image loads, the slot must look clean.

The real challenge: multi-format templates

The commit 3bbe914 switches the template model.

The old implicit approach was too limited: a template had a pages_data, and then that layout was adapted to another format. This works for simple cases, but it doesn’t reflect the business requirements. A 10x15, a 10x10, a 13x18 or a 20x20 may require different layouts.

The new template introduces TemplateFormatVariant:

  • template_id ;
  • the name and dimensions of the format;
  • pages_data specific to that format;
  • a thumbnail, if applicable;
  • is_default marker.

Template.pages_data Compatibility remains temporary, but the variants become the nominal source. The builder knows how to load the exact variant, create a new one by adapting it when it does not exist, and then save only the variant for the current format.

Creating a standard project from a template follows the same rule: the exact variant if available, otherwise adaptation from the default variant.

WordPress -> WooCommerce -> KEREDIT: following the actual path

Live tests subsequently showed that the front end was not synchronised with the variants, even though they had been saved.

The first instinct might have been to blame the WordPress plugin. However, the logs revealed something else:

  • WordPress was indeed sending template_id;
  • it was also sending the format requested within the KEREDIT context;
  • the backend was creating a project linked to the correct template;
  • but some paths were still reading Template.pages_data or adapting the pages locally.

The commit ac5e85f fixes project creation from the WooCommerce launch. backend/src/services/woocommerce-service.ts now resolves template pages via TemplateFormatVariant, exactly like the standard project route.

The actual integration test verifies that a WooCommerce launch using a template utilises the exact variant, not the old legacy pages_data.

The next pitfall: changing the format in the client editor

Once the Woo creation had been corrected, another discrepancy appeared in the editor.

The project was indeed derived from the template, but the frontend did not retain enough information to recognise that a format change required the exact variant. It simply did:

pages courantes -> adaptPagesToFormat(...)

The commit 7469656 therefore adds the minimum necessary logic: a project generated from a template retains its sourceTemplateId on the store editor side. When the client changes the format, RightPanel calls the API /templates/:id with the target format.

If the API returns variant_source: "exact", the publisher applies this variant. Otherwise, it retains the existing adaptive fallback.

This fix has resolved the main bug visible in production: switching to the 10x10 format now finally loads the 10x10 layout saved in the builder, rather than stretching the 10x15 layout.

The overlooked issue: retaining the client’s photo

The final discovery of the day is the most business-specific.

Yes, the layout must change when switching from 10x15 to 10x10. But if the client has already placed a photo in the slot, that photo must not disappear. The target variant must replace the composition, not reset the project to blank.

The commit e041449 adds this merge:

  • the target variant provides the block’s geometry, position and permissions;
  • the current project provides the client content that has already been placed;
  • for a photo block of the same id, KEREDIT retains the assetId, original aspect ratio, crop, pan, zoom, internal rotation, flip and image enhancements;
  • for a text block with the same ‘id’, KEREDIT preserves the rich text content.

The test:template-format-variant test explicitly verifies this scenario: a 10x10 variant with an empty placeholder retrieves the client’s photo placed at 10x15, whilst retaining the geometry 10x10.

This is probably the most important product rule of the day: variants drive the design, but the project drives the client’s work.

The contradiction in template permissions

Following the multi-format deployment, a very specific bug emerged on the product Carte postale, using the Postal theme: on 10x15, the block correctly displayed “Add a photo”, but the client was unable to drag and drop a photo into it. Switching to other formats seemed to restore normal behaviour.

The cause was neither a drag-and-drop issue nor a WooCommerce issue. The template contained two contradictory messages:

  • the image block was an empty, editable and unlocked placeholder;
  • the template’s global permissions prohibited ‘canReplaceAsset’.

The front end therefore adhered to the global permission and silently refused the replacement, whilst the interface promised a usable photo slot.

The commits 0052ab0 and afcd1d3 resolve this issue. On the backend, a project derived from a template can no longer be published with an empty, editable but non-replaceable photo block. The rule applies to standard project creation, to creation via the WooCommerce launch screen, and to project saving, to prevent an already open tab from reverting to the previous state via autosave.

The live data has also been corrected for tpl_postcard_postal: the template has reverted to consistent client permissions, and the affected draft has been restored to canReplaceAsset: true without reopening the other actions.

Replacing a photo should be a natural action

Last UX tweak of the day: once an image block already contains a photo, the client must be able to replace it without deleting the block, without recreating a layout and without losing the frame.

The commit 4efe897 adds this behaviour:

  • dragging a photo onto an empty block: immediate placement;
  • dropping a photo onto a block that is already filled: “Replace the photo?” confirmation;
  • clicking on a photo whilst an image block is selected: same confirmation;
  • same photo as the one already present: no action;
  • non-replaceable block: no action, no silent behaviour, no addition elsewhere.

After confirmation, KEREDIT retains the block’s geometry: position, size, rotation, permissions, mask and decorative frame. However, the new photo starts afresh in ‘cover’ mode, with cropping, panning, zooming, internal rotation and image enhancements reset to zero. This is the right balance for a customer service solution: the block remains the editorial container, whilst the replaced photo starts from a readable state.

Documentation and observability

Two documentation commits accompanied the day’s work:

  • 1eaa675 implements a beta observability design centred on OpenReplay and VictoriaMetrics;
  • 143cfee adds an implementation plan.

The commit bc466d7 also updates AGENTS.md, BIBLIOTHEQUE.md, docs/HOME.md and CHANGELOG.md with the new multi-format contract.

This documentation is useful because the subject is subtle: it is no longer enough to simply say “adapt the pages to the format”. Three things must be distinguished:

  • exact template variant;
  • adaptive fallback;
  • merging of client-side content already entered.

Closure decision

The day has reinforced an important product strategy: KEREDIT cannot simply be a publisher that adapts rectangles. It must retain a business purpose.

For multi-format templates, this focus is now clearer:

  • the design team can prepare a layout for each format;
  • the client can change the format within the same product;
  • the project retrieves the exact variant where one exists;
  • content already added by the client survives the change.

This is not merely a convenience feature. It is what makes changing formats commercially viable: the client can explore another format without feeling that KEREDIT is taking away their work.

A point to bear in mind for the future: this logic must remain valid beyond the simple photo block. Rich text, recoloured clipart, frames and masks must follow the same philosophy: a variant for the layout, a project for the client’s content.

Another point to bear in mind: each permission template must be conceived as an interface promise. If the screen says ‘Add a photo’, the project contract must make this action possible. Otherwise, the client will see it as a bug, even if technically the code ‘complies’ with a permission.
