La décision du jour : un seul moteur PDF

La journée met fin à une ambiguïté qui traînait depuis la naissance de GOF : KEREDIT avait encore un moteur PDF historique dans son backend, pendant que GOF devenait la vraie forge atelier.

Techniquement, les deux moteurs partaient du même objet central : le payload versionné construit par buildKereditPdfForgePayload(). C’est pratique pour démarrer, mais mauvais comme architecture durable. Deux moteurs qui rendent le même JSON, c’est deux endroits ou les textes, les images, les polices, les formes, les masques, les rapports et les optimisations peuvent diverger.

Le choix du jour est donc clair :

KEREDIT = editeur, commande, produit, prix, JSON maitre, suivi
GOF     = forge PDF unique, pre-presse, artefacts, cockpit atelier

Ce n’est pas un recul de KEREDIT. Au contraire, c’est une clarification de responsabilités. KEREDIT ne doit pas être à la fois l’éditeur, le backoffice commercial, le connecteur WooCommerce, le chef d’orchestre Accurio et une forge PDF concurrente. Il doit produire une donnée propre, complète, stable, puis laisser GOF faire le métier de forge.

Sortir le doublon sans casser la chaîne

Le commit 4be70ab commence à traduire cette décision dans le code : la génération est deleguee a GOF. KEREDIT garde la queue, le suivi, les routes admin et le lien avec les jobs de production, mais le PDF final n’est plus cense être fabrique par un moteur local parallèle.

La documentation bc3d26c pose ensuite l’analyse proprement dans docs/analyse/opt-generation-pdf.md et la synthèse HTML associée. Elle nomme le doublon, liste les fichiers concernes et propose l’ordre prudent :

  1. decoupler le declencheur GOF du vieux pdf_key local ;
  2. repurposer le worker KEREDIT en dispatch/suivi GOF ;
  3. rebrancher les téléchargements, rapports et packages sur les artefacts GOF ;
  4. supprimer le moteur local seulement après validation de parité.

Ce point est important : on ne jette pas brutalement une brique qui sert encore de filet. On la rend inutile d’abord, puis on la retire quand GOF couvre les produits et les rapports attendus.

KEREDIT reste le maître, mais pas la forge

La bonne frontière devient plus nette.

KEREDIT continue de savoir ce qu’est un produit, un projet, une commande, une quantité, une option, une couverture, un cahier, un asset client et un mapping atelier. Il continue aussi de produire le JSON maître. C’est la partie qui ne doit pas bouger vers GOF, parce que GOF ne doit pas lire les tables internes KEREDIT ni devenir un second backoffice métier.

Le reste de la journée KEREDIT va dans ce sens. Le commit 80ee02a renforce le contrat livre : les couvertures intérieures sont persistables et l’export peut produire une couverture deux pages. Les correctifs 4be1d23 et 9de2782 protègent aussi le flux projet : les sauvegardes doivent rester lisibles, et les corrections support doivent viser les assets client sans toucher aux assets structurels ou verrouilles.

Ce n’est pas le même sujet que le PDF, mais c’est la même discipline : distinguer ce qui appartient au projet client, ce qui appartient au template, ce qui appartient au moteur d’édition, et ce qui doit être transmis à la production.

GOF prend le poids pre-presse

Pendant que KEREDIT retire le doublon, GOF avance exactement dans le sens attendu.

Le matin commence par des gestes très opérateur : relancer une pièce PDF sans perdre le contexte, stabiliser le changement d’aperçu, renommer l’action en Relancer PDF, puis streamer les gros aperçus avec des requêtes range. Ce sont des détails d’usage, mais ils disent que GOF n’est plus seulement une API : c’est un poste de travail.

Le commit cd90c85 aligne ensuite GOF avec le travail livre/zine : une couverture scindee peut être rendue en deux pages. Cela répond directement au contrat KEREDIT : si le produit distingue couverture, cahier et surfaces intérieures, GOF doit rendre ces pièces sans les mélanger.

Le commit 43c8371 pousse le cœur forge : artefacts optimises, post-traitement, poids de sortie mieux maîtrise. Le résultat concret de la session est très parlant sur le dossier 1075781.

Avant optimisation sérieuse, la révision 3 pesait 482,5 Mo :

  • couverture : 12,5 Mo ;
  • cahier : 470,1 Mo.

Après optimisation, la révision 7 pèse 19,4 Mo :

  • couverture : 0,7 Mo ;
  • cahier : 18,8 Mo.

Le gain total est donc de 463,1 Mo économises, soit 95,97 % de réduction. Le PDF devient environ 24,8x plus léger. Ce n’est pas une micro-amélioration ; c’est le passage d’un artefact difficile a manipuler à un fichier réellement exploitable dans un flux atelier.

Le gros gain vient du cahier : il passe d’environ 470 Mo a 18,8 Mo. La couverture, elle, descend d’environ 12,5 Mo a 681 Ko.

Les leviers documentes dans la synthèse expliquent pourquoi le gain est aussi fort : éviter d’embarquer toutes les photos en PNG quand le JPEG print suffit, réduire les images à la résolution utile du cadre, garder les avertissements pre-presse quand le DPI devient limite, puis laisser les passes structurelles comme qpdf et mutool compacter le PDF sans recréer une deuxième logique dans KEREDIT.

Puis ef435e9 expose des métriques pre-presse. La suite de la soirée transforme ces métriques en lecture opérateur : progression de dossier plus claire, ordre stable des pièces livre, inspector qui garde son scroll, métriques image pre-presse mieux nommees.

Le dernier ajustement GOF, 3675b62, ferme une nuance importante : une image sous le seuil recommande ne doit pas bloquer toute la production si elle reste au-dessus du seuil critique. GOF garde donc une alerte opérateur avec page, asset, élément et DPI effectif, mais ne bloque vraiment que les cas asset.image_dpi_critical. C’est exactement le bon type de règle pre-presse pour l’atelier : ne pas laisser passer l’inacceptable, sans transformer chaque avertissement en arrêt machine.

Autrement dit, GOF commence à prendre le poids que KEREDIT doit justement arrêter de porter : qualité PDF, artefacts, taille, contrôle, preflight, lisibilité du dossier.

Le vrai gain : moins de magie, plus de chaîne

La décision “un seul moteur PDF” est moins spectaculaire qu’une nouvelle fonctionnalité, mais elle vaut probablement plus pour la suite.

Avant, on pouvait avoir cette situation mentale :

KEREDIT rend un PDF local
GOF re-rend un PDF atelier
Accurio consomme une sortie
et personne ne sait plus exactement lequel fait foi

Après clarification :

KEREDIT produit le projet et le JSON
GOF forge le PDF et les rapports
Accurio reçoit la piece validee par GOF

Ce flux est plus simple a expliquer, plus simple à tester, et surtout plus facile a faire évoluer. Les optimisations lourdes ne se font qu’une fois. Les métriques pre-presse vivent au même endroit que les artefacts. Les écarts écran / JSON / PDF deviennent des bugs de contrat entre KEREDIT et GOF, pas une bataille entre deux renderers.

Le passage 400 Mo -> 19 Mo rend cette architecture beaucoup moins théorique. Si l’optimisation vit dans GOF, elle profite a tous les produits qui passent par la forge : zine, livre, photo print, tirage d’art, demain d’autres formats. Si elle reste dispersee entre KEREDIT et GOF, chaque amélioration de poids, de codec, de DPI ou de rapport doit être rejouée deux fois.

Risques encore ouverts

La prudence reste indispensable.

Avant de supprimer physiquement le vieux moteur PDF KEREDIT, il faut vérifier la parité GOF produit par produit. Les points sensibles restent ceux qui font mal en web-to-print : formes non rectangulaires, cliparts SVG, masques, ombres, polices, rapports, packages de livraison, et références de téléchargement dans l’admin.

Le bon objectif n’est pas “supprimer du code pour supprimer du code”. C’est : ne garder qu’un moteur quand le moteur retenu couvre vraiment les cas atelier.

Suite logique

La suite courte devrait rester très étroite :

  1. rejouer un projet livre/zine complet dans KEREDIT ;
  2. envoyer le payload vers GOF ;
  3. vérifier couverture, cahier, pièces et ordre de dossier ;
  4. regarder les métriques pre-presse GOF ;
  5. valider téléchargement, rapport et package depuis les surfaces admin ;
  6. seulement ensuite, retirer les fichiers du moteur PDF local devenu inerte.

Le cap du jour est sain : moins de duplication, plus de responsabilités explicites. KEREDIT garde le métier et la mémoire du projet. GOF devient l’atelier PDF.
