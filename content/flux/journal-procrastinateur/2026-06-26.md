## Lecture globale

La journée a commencé dans le prolongement direct de la nuit precedente :
l'éditeur fonctionnait de nouveau, mais la confiance était abimee. Plusieurs
correctifs avaient réparé des gestes visibles tout en exposant d'autres contrats
implicites : remplissage automatique, doubles pages, calques, mini-menu photo,
déplacement de la photo dans son bloc, pages de couverture non éditables.

Le fil du jour a donc été double :

- continuer à rendre le **remplissage automatique** exploitable pour les carnets
  photo ;
- réparer la chaîne **commande WooCommerce -> KEREDIT -> GOF -> Accurio** sans
  écraser les artefacts print par le nouveau livrable PDF web.

Le point important n'est pas seulement technique. La séquence a montré une fois
de plus que les bugs les plus dangereux ne sont pas les erreurs visibles au
premier clic, mais les mauvais partages de contrat : deux surfaces utilisent le
même identifiant, le même élément ou la même page, mais pas pour la même raison.

## Remplissage automatique : V1 utile, V2 a structurer

Le remplissage automatique est devenu une vraie surface produit.

La V1 permet de partir d'une bibliothèque de photos chargées, de choisir le
nombre de photos par page, la marge, l'écart, le nombre de pages du cahier, et
de visualiser un aperçu de double page. Elle traite aussi la 1re de couverture a
part : elle peut recevoir une photo, mais ne doit pas devenir un spread qui
déborde sur toute la couverture.

Plusieurs détails UX ont été ajustes :

- bouton **Remplissage automatique** dans le menu principal ;
- fermeture de la modale après lancement ;
- sliders homogenes pour photos/page, marge et écart ;
- marge jusqu'a 30 mm ;
- possibilité d'ajouter des pages si le cahier est plein, dans la limite produit ;
- preview plus grande, avec flèches de navigation ;
- bouton de remise a zéro pour les tests ;
- modale accessible aussi en plein écran.

La limite produit a été reclarifiee : pour le Zine, le cahier va de **20 a 60
pages**, avec **32 pages incluses** et un pas de **4 pages**. Les pages de
couverture ne doivent pas être additionnees pour inventer un "64 pages produit".

Le document `docs/produit/remplissage-automatique-roadmap.md` reste la base de
la suite : templates réutilisables par nombre de photos, panneau Templates utile
après un premier jet automatique, changements de gabarit page par page, marge,
écart et redistribution sans repasser par tout le flux.

## Régressions editor : contrat, pas intuition

La journée a aussi continue à solder la cascade de régressions Fabric.

Les contrats critiques rappeles et durcis :

- en vue livre, une double page affiche deux pages propriétaires, mais les
  actions doivent toujours cibler la vraie page de l'élément ;
- la 2e et la 3e de couverture sont des surfaces non éditables, gris léger, avec
  libellé explicite ;
- une image ne doit pas déborder sur la page non éditable voisine ;
- le drag normal d'un bloc photo déplacé le cadre ;
- la croix centrale déplacé la photo à l'intérieur du cadre ;
- les calques doivent lister les éléments visibles des deux pages du spread ;
- les actions de calques doivent modifier l'ordre local de la page propriétaire ;
- les vignettes de calques ne doivent pas dépendre de la page courante de la
  bibliothèque Photos.

La correction des vignettes de calques a révélé un cas local/VPS piegeux :
localement, l'asset était souvent déjà présent dans le store photos ; sur le VPS,
le projet pouvait afficher l'image dans le canvas sans que l'asset correspondant
soit encore charge dans `useAssetStore.assets`. Le panneau Calques doit donc
résoudre l'URL par `assetId`, puis utiliser un fallback
`thumbnail -> preview -> display -> original`.

## Commande Zine 1075789 : le print n'avait pas disparu

Le test de commande **Zine - hwkrhc35**, WooCommerce **#1075789**, a donne le
symptôme le plus inquiétant : le PDF web apparaissait dans GOF, mais plus les
PDF HD **Couverture** et **Cahier**.

L'analyse a montré que les artefacts print n'étaient pas perdus.

Dans GOF, deux jobs existaient bien pour la même commande :

- job print `f3646088-31be-4386-9d75-62fd712f7ed4` :
  `cover_pdf` + `cahier_pdf`, statut `approved` ;
- job PDF web `4c8d5bca-2340-4813-afbd-59f5b53fb146` :
  `web_preview_pdf`, statut `completed`.

Le bug était dans la logique de dossier courant. Le job PDF web gardait
`order_ref=1075789`, ce qui est nécessaire pour le rattacher visuellement à la
commande. Mais GOF utilisait encore cet `order_ref` comme identité de versioning.
Résultat : un rendu web pouvait prendre la place visible du rendu print dans le
dossier courant.

Le contrat correct est maintenant :

```text
order_ref        -> regrouper les pieces d'une meme commande dans le dossier
external_job_id  -> versionner un rendu PDF web issu du partage
project_id       -> versionner le rendu print HD du projet editeur
```

GOF `0.1.84` applique ce contrat : le PDF web est groupe avec la commande, mais
ne peut plus superseder le job print `cover_pdf/cahier_pdf`.

Vérification directe dans le conteneur GOF pour `1075789` :

- **Couverture** : `cover_pdf`, 1 page, 2,86 Mo ;
- **Cahier** : `cahier_pdf`, 60 pages, 78,33 Mo ;
- **PDF web** : `web_preview_pdf`, 64 pages, 9,50 Mo.

Le chiffre **64 pages** du PDF web correspond au PDF de consultation avec les
surfaces de couverture/non-éditables visibles ; ce n'est pas une nouvelle limite
produit. Le cahier produit reste bien limite a **60 pages** pour le Zine.

## Ce que cette journée doit laisser

Le point de méthode est simple et doit rester visible :

```text
un meme identifiant peut servir a regrouper sans servir a versionner
```

`order_ref` est utile pour afficher un dossier client cohérent. Il ne doit pas
devenir, par facilite, l'identité technique qui decide quel rendu est "courant"
quand plusieurs types de rendus cohabitent.

La même logique vaut cote éditeur : une double page peut être une surface
visuelle commune, mais les éléments restent propriétaires de leur page ; une
photo peut être dans un bloc, mais le bloc et le contenu interne ne partagent
pas le même geste.

La prochaine étape doit rester sobre : transformer ces contrats en tests
nommes, proches des helpers, et refuser les patchs qui corrigent un symptôme en
deplacant silencieusement la source de vérité.
