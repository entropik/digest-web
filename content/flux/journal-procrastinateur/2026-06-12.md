## Plugin WordPress : contraste des actions projet

Les commits `a0ae6e3` et `239a5c0` prolongent le travail de la veille sur l'espace projets client WooCommerce.

Le sujet n'est pas seulement esthétique. Dans une liste projet, `Modifier`, `Dupliquer` et `Supprimer` n'ont pas le même poids. Compacter l'interface ne doit pas rendre la suppression trop discrète ou ambiguë.

La correction touche le CSS front du plugin, le header de version, le `readme.txt` et le manifest d'exemple. Cela rappelle une règle du repo : tout changement sous `wordpress-plugin/keredit-connector/` est une release plugin, pas une simple retouche locale.

## Documentation : ne plus compter sur la mémoire

Le commit `536ef3c` ajoute le vrai changement de méthode.

La skill `.codex-skills/doc` existait déjà, mais elle était trop générale. Elle sait maintenant déclencher un audit court, puis orienter l'agent vers les bons fichiers :

- `AGENTS.md` pour l'état repo et les règles de travail ;
- `CHANGELOG.md` pour les jalons versionnes ;
- `BIBLIOTHEQUE.md` et `docs/HOME.md` pour la carte du repo ;
- les docs produit pour roadmap, bêta et objectifs ;
- les guides de reprise et commandes ;
- le journal quotidien quand une journée significative n'a pas encore son entrée.

Le script `node .codex-skills/doc/scripts/audit-docs.mjs` donne les faits avant d'écrire : branche, HEAD, versions des quatre packages, drift eventuel, derniers commits, dernier billet et ligne de temps cumulé.

## Pourquoi c'est important

Le problème n'était pas l'absence de documentation. Le repo en a beaucoup. Le problème était la cadence : après un correctif live, un bump de version, un deploy VPS ou une retouche plugin, il est trop facile d'oublier la partie documentaire.

La skill ne remplace pas le jugement. Elle force simplement le premier geste utile :

- vérifier les faits actuels ;
- voir si une doc est en retard ;
- corriger petit ;
- dire explicitement quand aucun bump, roadmap ou changelog n'est nécessaire.

## Session de nuit : marque et aperçu final

Les commits `6f3f3b1` et `c2b42e0` retouchent le wordmark KEREDIT dans l'éditeur. Ce n'est pas un chantier produit large, mais un détail de finition : l'entête doit donner une impression stable, pas bricolage, surtout quand l'interface commence à être montree hors du poste de dev.

Le commit `5734f11` ajoute le mode **Aperçu final** dans le menu `Affichage`.

Jusqu'ici, le bouton `Fond perdu` pilotait surtout un repère visuel. Le canvas, lui, restait construit sur la page complète, avec fond perdu. Le nouveau mode change la surface d'affichage effective :

- en édition, la surface reste `format + fond perdu` ;
- en aperçu final, la surface devient le **format fini**, avec `bleed=0` ;
- les coordonnées projet restent relatives au format coupe ;
- l'aperçu est volontairement en lecture seule : pas de sélection, pas de poignées, pas de grille, pas de règles, pas de drag-and-drop, pas d'édition texte inline.

Ce choix évite de créer une deuxième géométrie d'édition. On ne modifie pas le JSON projet pour regarder le produit fini. On change seulement la surface de rendu.

## Décision de clôture

La petite leçon de la session est double.

Si une tâche revient souvent et qu'elle dépend de discipline, il faut l'encoder dans le repo.

Si un client doit comprendre ce qu'il va recevoir, il faut pouvoir lui montrer le produit fini sans les marques de fabrication.

La documentation Krampouz a maintenant un point d'entrée concret. Quand la version, la roadmap, le changelog ou le journal risquent de dériver, l'agent peut lancer l'audit au lieu de repartir au feeling.

Et l'éditeur carte postale gagne un mode plus humain : moins atelier, plus objet fini. à 1h30 du matin, c'est une bonne limite de clôture.
