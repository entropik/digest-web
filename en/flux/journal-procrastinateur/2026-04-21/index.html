Jour 38 — Remise a zéro du VPS, re-alignement sur dev et retour à une chaîne lisible

Le VPS a été rase, remis sur une stack unique, puis rebranche sur `dev` via un vrai chemin Git local -> VPS. La journée a aussi corrigé la CSP R2 et le faux blocage `processing` cote admin photos.

Ce qui s’est passé vraiment

Après la restauration de la veille, la conclusion devient impossible à éviter : la stack VPS est devenue illisible. Trop de chemins de deploy se sont superposes, trop de répertoires ont coexiste, trop d’images locales et GitHub se sont melees. La seule sortie propre est donc radicale : tout effacer et repartir depuis la seule chose qui tienne encore debout, c’est-a-dire le local valide.

Le VPS est d’abord purge complètement :

  • plus de conteneurs krampouz
  • plus de volumes krampouz
  • plus de reseaux krampouz
  • plus de répertoires /opt/[chemin privé]
  • plus de backups gardes sur place

Ensuite la doctrine change vraiment. Le runtime nominal n’est plus “GitHub Actions + GHCR + SSH + magie Prisma”. Il devient d’abord :

  1. un local valide ;
  2. un redéploiement manuel explicite vers /opt/[chemin privé] ;
  3. un build VPS ;
  4. un bootstrap explicite (prisma migrate deploy puis seed) ;
  5. une stack unique krampouz.

Ce premier retour en ligne remet bien l’application debout, mais révèle encore deux erreurs de remise en service :

  • l’upload navigateur vers R2 est bloqué par la CSP publique (connect-src 'self') ;
  • l’admin Photos peut afficher un faux processing persistant alors que le pipeline a déjà fini.

Le premier problème vient du proxy : le backend sait presigner, R2 accepte bien le PUT, mais le navigateur public n’a tout simplement pas le droit de parler a *.r2.cloudflarestorage.com. La correction de la CSP remet les uploads en route.

Le deuxième problème est plus pervers : le pipeline assets marche, les lignes en base passent bien a ready, mais l’interface admin se rafraîchit encore selon un signal trop partiel (thumbnail_pending). Il faut donc corriger le refresh de Photos pour suivre aussi les statuts transitoires preview_status et print_ready_status.

En fin de journée, une dernière incoherence apparaît : le local a été repasse sur dev, alors que le VPS tourne encore sur un ancien snapshot issu d’une branche temporaire. C’est exactement le type d’entropie qu’il fallait justement faire disparaître.

La correction finale est donc structurelle, pas cosmétique :

  1. garder dev comme branche de travail testée en local ;
  2. pousser dev ;
  3. cesser de déployer le VPS comme un snapshot rsync opaque ;
  4. installer un vrai dépôt Git bare sur le VPS (/opt/[chemin privé]) ;
  5. pousser dev dedans ;
  6. reconstruire le worktree applicatif /opt/[chemin privé] depuis ce dépôt ;
  7. builder ensuite les images Docker sur le VPS à partir de ce checkout.

La fin de journée vaut enfin quelque chose de concret :

  • upload OK
  • lecture publique asset OK
  • insertion image OK
  • déplacement/rotation des blocs image OK
  • local sur dev
  • VPS sur dev

Le vrai gain du jour

Le gain n’est pas seulement d’avoir “repare deux bugs”. Le gain, c’est d’avoir enfin retrouve une ligne de causalité simple :

  • un seul répertoire VPS
  • un seul dépôt Git VPS
  • une seule stack
  • une seule procédure
  • une seule branche de vérité de travail : dev

Après deux jours de confusion, cette lisibilité vaut presque autant que les correctifs eux-mêmes.

Décisions qui restent vraies après coup

  • le VPS ne doit plus être traité comme un “snapshot opaque” ;
  • le chemin manuel local valide -> push dev -> deploy Git bare sur le VPS reste la seule procédure autorisée tant que la chaîne CI/CD n’est pas reconstruite proprement ;
  • le seed et Prisma doivent rester explicites, jamais caches dans le boot des conteneurs longs ;
  • avant toute autre feature, il fallait retrouver un état fonctionnel simple et racontable. C’est enfin le cas.

Ce que la journée laisse ouvert

La prochaine étape n’est pas une nouvelle feature spectaculaire. C’est la stabilisation :

  • figer la documentation sur cette procédure réelle ;
  • nettoyer les branches et worktrees parasites ;
  • garder dev comme vérité de travail tant que main n’est pas repassée dans un circuit propre ;
  • ne reintroduire de l’automatisation qu’après plusieurs deploys manuels sans surprise.
