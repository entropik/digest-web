Day 79 – Sharper images, more cautious plans, JSON contract fixed

Improvements to image rendering in the editor, improved zoom functionality, more conservative WooCommerce projects, followed by the GOF 0.1.49 fix for the KEREDIT JSON contract/image rendering.

Post finalised following GOF correction 0.1.49 regarding the image mismatch between the KEREDIT JSON and the GOF PDF output.

Brief conclusion

The day began with efforts to make the editor more visually credible: improved preview resolution, a configurable splash image, better-loaded original photos, a sharper adaptive grid, followed by smoother panning and scrolling within the canvas.

The focus then shifted to a more product-related issue: WooCommerce client projects need to be handled with greater care. A project that has already been commissioned must not be re-edited as an open draft; duplication is now the standard procedure for resuming work without compromising the order history.

The end of the day wrapped up the trickiest issue: image alignment between KEREDIT and GOF. KEREDIT had strengthened its rendering freshness contract; GOF 0.1.49 can now render KEREDIT’s image adjustments with the correct rotation origin and the same direction of rotation as the editor.

This morning: making the editor look sharper

The main focus of the day was very clear: the editor had to stop looking blurry or flimsy as soon as you looked at a real photo.

The reference commits on the KEREDIT side show the progress:

  • a569076 adds a configurable splash screen;
  • 89c395e adds configurable effects to this screen;
  • 411039c increases the resolution of the editor previews;
  • b6962fe then 67e32f2 makes the launch preview image more reliable;
  • 8402bf3 improves the comfort zoom in the Postcard editor.

This isn’t just a cosmetic update. In the beta, the user needs to understand that they are working on a printable object, not a rough thumbnail. The zoom function, sharpness, loading time and stability of the canvas are all key to building trust in the product.

Photos: keep the original as the definitive version, speed up the display

The major technical overhaul of the image handling then resumed the previously documented approach: the original remains the production standard, whilst the adaptive raster remains a temporary on-screen cache.

KEREDIT now loads original photos more efficiently into the canvas (44905a2), keeps photos attached whilst dragging (272fd34 / 35d99e6), makes adaptive rasters sharper (be46fcf), maintains their correct fit (7881b03), and then defers computationally intensive tasks so as not to block user interactions (5eb7146).

The key point is the trade-off: the editor must respond immediately when a photo is moved or resized, but it must not sacrifice the quality of the exported output. The day therefore further clarified the division of responsibilities:

  • rapid on-screen feedback during interaction;
  • a browser cache to avoid re-reading the original with every action;
  • a persistent contract that continues to refer to the source image, not the cache.

Overlays and editor gestures

The commit b865919 refines overlay interactions. This is consistent with the rest of the day’s work: now that images are larger and sharper, we must ensure that guides, selections and toolbars do not give the impression of being pasted on or lagging behind.

This work remains within the beta track: we won’t reopen the stable typography branch, but we’ll remove visible friction around image manipulation.

WooCommerce: resuming the order without breaking it

The other half of the day focused on the customer journey and the WooCommerce plugin.

The commit 854f288 imposes a precautionary rule: a project that has already been ordered must be duplicated before it can be resumed. This is an important business requirement. An order placed constitutes a commercial and production record; reopening it as an editable draft would be dangerous.

The next set of changes improves the user experience:

  • 281d7ac loads client projects progressively;
  • c379067 simplifies validation checks;
  • 456b5c4 clarifies bulk selection;
  • fbfbd09 refines batch actions.

The expected outcome for clients is simpler: finding their projects, understanding which ones have been commissioned, duplicating them when they need to start again, and avoiding ambiguous actions.

Bug fixed: KEREDIT and GOF are reading the same image contract

The end of the day was the point of tension.

KEREDIT has an explicit commit, ‘0beb905’ (Fix image render contract freshness), which affects page validation, the GOF payload, PDF/print job routes, PDF administration and project persistence. The message is clear: the image rendering contract needed to be updated and made more explicit before renderings were sent or reused.

On the GOF side, the fix was carried out in three stages:

  • 9f33865 (Render Keredit image adjustments in GOF) adds the rendering of KEREDIT image adjustments in app/src/pdf-renderer.js with an associated test;
  • 7756fb5 (Fix GOF image block rotation origin) corrects the rotation origin of the image blocks;
  • 347a563 (Mirror editor image rotation in GOF PDFs) aligns the GOF rotation direction with that of the editor.

The bug was therefore not simply a visual difference in the PDF. It was a contract bug between:

  • the editor’s persistent JSON;
  • the payload exported by KEREDIT;
  • the GOF interpretation;
  • the final PDF rendering.

GOF0.1.49 documents the resolution of this issue: KEREDIT image adjustments, the rotation origin and the direction of rotation are now rendered on the same side of the string.

Closure decision

The day ends on a better note than it began: the image editor is now more user-friendly, the WooCommerce project workflow is less fraught, and the KEREDIT → GOF bridge resolves a specific discrepancy between JSON and PDF.

Point to bear in mind for the future: whenever a PDF rendering does not match the editor, the correct approach remains to follow the full contract rather than patching the final rendering based on intuition. The pipeline must be checked in this order: persistent JSON, exported payload, GOF interpretation, generated PDF.
