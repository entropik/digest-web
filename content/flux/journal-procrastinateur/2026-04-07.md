## Des agents disent « fini », le disque dit non

Les agents Claude Code lances en parallèle pour créer les fichiers blog n'ont pas tous écrit sur le disque. Le premier et le deuxième lot (19 fichiers) ont du être relances — les agents confirmaient la création mais les fichiers n'atterrissaient pas. Probablement un problème d'isolation ou de worktree implicite. Le troisième lot a fonctionne du premier coup. Leçon : vérifier les fichiers après chaque batch d'agents.

Le skill `/blog` n'est pas immédiatement reconnu par Claude Code après création — il faut relancer la session pour qu'il soit indexe. On a du exécuter le workflow manuellement pour cette première fois.

Décision importante pour le template : ajout d'une section "Conversations et décisions" qui capture les échanges de la session Claude Code. C'est la partie la plus precieuse du blog car elle disparaît à la fermeture de la conversation. Le git log reste accessible indéfiniment, les débats et raisonnements non.

La suite de la journée a bascule sur un vrai chantier de remise en ordre Git. Une PR texte paraissait encore en conflit dans GitHub alors que localement le merge de `origin/main` était déjà fait. On a vérifié le `merge-base`, confirme que la branche était bien descendante de `main`, puis compris que GitHub affichait un état stale cote navigateur. Rafraîchissement complet : le faux conflit disparaît.

Deuxième complication plus sérieuse : GitGuardian signale un secret sur la PR texte. Le secret n'était plus présent dans les fichiers courants, mais dans l'historique ancien de la branche, hérite d'une branche fourre-tout (`fix/snaping`). On a donc reconstitue la branche PR proprement depuis `origin/main`, rejoue le diff final en commit squashe, puis force-pushe la branche propre. Le lint a ensuite cassé sur `OptionsPanel`, puis plusieurs commentaires de review ont été corrigés un par un sur la nouvelle branche propre.

Enfin, gros ménage de branches, worktrees et refs distantes. Le dépôt finit la journée avec une seule branche locale utile (`main`), un worktree propre, et seulement `origin/main` cote remote. Les vieilles branches `dockhand`, la branche `fix/snaping`, la branche texte et la branche blog ont toutes été supprimées après merge. C'est la première fois depuis longtemps que le repo redevient vraiment lisible.

- **Approche hybride jour/semaine** — l'utilisateur demande pourquoi seulement 25 fichiers sur 2 mois. Explication : 25 jours de commits sur 58 jours calendaires. Décision de créer des fichiers hebdomadaires pour les intervalles
- **Résume des conversations** — l'utilisateur veut capturer les échanges Claude Code, pas seulement le git log. Ajout de la section "Conversations et décisions" au template et au skill
- **Stabilisation texte** — 3 commits sur le bloc texte avant de basculer sur le blog
- **Git et branches** — longue session pédagogique sur les branches locales, les PRs, `main`, les worktrees, les stashes et le ménage du repo
- **Conflits GitHub fantômes** — vérification que la PR texte était bien mergeable malgré un affichage stale dans le navigateur
- **GitGuardian / CI** — suppression d'un historique pollue dans la PR texte, puis correction des retours de review et du lint frontend
- **Blog dans `main`** — décision explicite de traiter le blog comme une vraie documentation du projet, pas comme un carnet prive hors repo

### Décisions prises ensemble
- **Un fichier par jour de commit + fichiers hebdomadaires** pour les pauses — compromis entre exhaustivité et pertinence
- **Nommage `YYYY-MM-DD.md`** pour le tri naturel et la compatibilité SSG
- **Frontmatter avec `day_number`, `type`, `commits`, `tags`** pour le filtrage et l'affichage
- **Marqueur `<!-- Reconstitue à partir du git log -->`** sur les entrées historiques pour la transparence
- **Section "Conversations et décisions"** ajoutée au template — ne peut être remplie que pendant la session vivante
- **Taxonomie de tags fixe** : scaffold, ci, auth, canvas, pdf, woocommerce, docker, admin, éditeur, docs, upload, photos, infra, performance, snapping, texte, sécurité, ux, réflexion, produit
- **Le blog a sa place dans `main`** — on l'assume comme mémoire projet durable
- **Une branche = un sujet** — le vrai cadre mental retenu pour l'utilisateur
- **`origin/main` est la vérité, `main` local est juste une copie a réaligner** — distinction importante comprise pendant la session
- **Pour une PR polluee par de vieux commits, recréer une branche propre depuis `origin/main` puis squash le diff** — stratégie retenue contre GitGuardian
- **Ménage final radical** — ne laisser que `main` en local et `origin/main` a distance une fois les sujets merges

### Tentatives abandonnées
- **Un fichier par jour calendaire (~58 fichiers)** — trop de fichiers vides, rejeté au profit de l'hybride jour/semaine
- **Numérotation `jour-01.md`** — rejeté, `YYYY-MM-DD.md` est plus naturel et triable
- **Essayer de "sauver" la vieille branche `fix/snaping` comme telle** — abandonne après constat qu'elle était complètement absorbée ailleurs
- **Pousser directement sur `main`** — non retenu, le repo impose de rester sur un workflow propre par branche/PR
- **Considérer le conflit GitHub comme réel sans vérifier le `merge-base`** — abandonne au profit de la preuve Git locale

## Apprentissages du jour

- Une branche n'est pas un "service temporaire" : c'est juste un nom qui pointe vers une ligne de commits.
- Une branche peut exister longtemps en local sans être la branche courante.
- `main` local n'est pas la vérité ; `origin/main` est la référence, et `main` local doit juste être realignee.
- Un worktree sale ne veut pas dire "du code casse" : parfois il y a juste un autre sujet en cours qu'il faut isoler.
- Un stash bien nomme vaut mieux que trois `WIP on main` incomprehensibles.
- GitHub peut afficher un état stale d'une PR ; il faut vérifier localement avant de paniquer.
- GitGuardian peut bloquer sur l'historique d'une PR, même si le fichier courant est déjà propre.
- Quand une branche est devenue fourre-tout, le bon mouvement n'est pas de la merger "au courage", mais d'en extraire proprement ce qui vaut encore la peine.
- "Aligner les etoiles aux planetes" en Git, ici, a voulu dire : un sujet = une branche, une PR = une branche vivante, puis suppression après merge.

## Repères : SSG, pull request et worktree

- `SSG` — static site generator : outil qui transforme des fichiers Markdown en site statique.
- `PR` — pull request : proposition de changement revue avant merge dans `main`.
- `worktree` — second dossier de travail Git branche sur le même dépôt, utile pour isoler un sujet.
- `stash` — rangement temporaire de modifications Git non committées.
- `GitGuardian` — outil qui détecte les secrets exposes dans le code ou l'historique Git.
