## Ce qui s’est passé

Journée fondatrice. On part de zéro et on pose tout le socle en une seule session massive : 23 commits, 6 pull requests mergées, un monorepo fonctionnel.

L'idée est simple mais ambitieuse : un éditeur web-to-print SaaS où les clients conçoivent leurs produits imprimés (albums photo, cartes postales, posters) dans le navigateur et génèrent des PDF print-ready. On commence avec le produit le plus simple : la carte postale.

Le scaffold initial pose un monorepo pnpm avec trois packages (`shared`, `frontend`, `backend`), Docker Compose pour l'infra locale (PostgreSQL, Redis, MinIO), et un pipeline CI GitHub Actions. Le frontend démarre avec React 18, Vite, et Fabric.js pour le canvas. Le backend avec Fastify et Prisma.

On enchaîne immédiatement avec le Phase 1 MVP : 38 fichiers, 4500+ lignes. Le canvas Fabric.js affiche des éléments, le store Zustand gère l'état, les routes Fastify servent les données. C'est brut mais ça tourne.

Puis on corrige : CI qui casse parce que Prisma generate n'est pas lancé avant typecheck, auth plugin mal encapsulé avec fastify-plugin, crash sur `assets.map` parce que la route retourne un objet au lieu d'un array. Six PRs corrigent six problèmes en rafale.

La journée finit avec les images réelles chargées sur le canvas Fabric.js (avec un cache module-level), un guide de setup, un CHANGELOG, et la décision ferme que tout passe par des PRs — plus jamais de push direct sur main.

## Complications et décisions

Le CI a cassé 3 fois dans la journée. D'abord le build `shared` pas lancé avant typecheck, puis Prisma generate manquant, puis le lockfile désynchronisé. Classique d'un monorepo pnpm avec des dépendances cross-packages — il faut que `shared` soit build avant que le reste puisse typecheck.

Le crash `assets.map` était un piège basique : la route Fastify retournait `{ assets: [...] }` au lieu de `[...]`. Le frontend faisait `.map()` sur un objet. Type checking aurait dû le capter mais les types shared n'étaient pas encore assez stricts.

Décision importante : on impose le workflow PR-only dès le jour 1. Ça ralentit un peu la boucle solo, mais ça structure le git log et ça force à décrire ce qu'on fait.

## Opinions et réflexions

23 commits en une journée, c'est beaucoup. Avec Claude Code, le ratio "ce qu'on pense / ce qui s'écrit" est complètement différent. On passe plus de temps à vérifier et corriger qu’à taper. Le risque c'est d'aller trop vite et de poser des fondations bancales — mais au moins on a un socle testable immédiatement.

Fabric.js est un choix fort. La lib est puissante mais sa documentation est… créative. On verra si ça tient la route pour un usage web-to-print sérieux.

## Mini-lexique

- `CI` — intégration continue : vérification automatique du code à chaque push ou PR.
- `MVP` — version minimale mais utilisable d'un produit, suffisante pour valider l'usage.
- `PR` — pull request : proposition de changement revue avant merge dans `main`.
- `Fabric.js` — bibliothèque canvas qui sert de moteur d'édition visuelle dans Krampouz.
- `MinIO` — stockage objet local compatible S3, pratique pour le dev et les tests.
