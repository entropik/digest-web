Jour 31 — Le blog Zola force un retour à la simplicité

16 commits : publication du devblog Zola, faux départ Pages CMS, retour a Decap et nettoyage du périmètre blog.

Horaires de session

  • Agent utilisé : Codex, transition depuis Claude Code
  • Première trace git du jour : 15:34 CEST
  • Dernière trace git du jour : 18:42 CEST
  • Amplitude minimale observée : 3h08
  • Temps cumulé :128h19+, non recalcule dans ce billet historique

Zola publie, l’admin complique tout

La journée a commencé comme un vrai chantier blog : Zola est installé dans le repo, les billets migrent, le devblog sort enfin en statique sur devblog.ooblik.com, Pagefind s’indexe proprement, et un panneau d’admin apparaît. Sur le papier, c’est une belle avancée.

Le problème, c’est que le mot “simple” n’avait pas la même définition cote technique et cote usage. Le passage vers Pages CMS paraissait léger en infra, mais il ajoutait un service externe alors que le besoin réel était beaucoup plus terre a terre : des fichiers .md, un /admin heberge chez nous, et basta.

Le reste de la journée a donc été une longue correction de trajectoire. On a poussé feature/blog-zola vers main, nettoyé le périmètre du blog, diagnostique les échecs GitHub Actions lies au deploy blog et au deploy conteneurs, puis surtout remis le sujet d’aplomb : ne plus mélanger le blog Zola avec le deploy principal de l’app Krampouz. La fin de session revient à l’essentiel avec un vrai retour a Decap pour l’admin blog.

Un blog statique, indexé et administrable

  • Projet Zola branche dans le monorepo avec contenu blog rendu depuis docs/blog/
  • Recherche Pagefind intégrée et validée sur le build statique
  • devblog.ooblik.com publie et reserve au blog
  • Branche feature/blog-zola poussée puis mergée dans main
  • Portail Pages CMS teste puis retire du flux blog
  • Admin Decap remis en place avec config.yml cible main
  • Worker OAuth cms-auth.ooblik.com remis dans le repo comme référence claire du setup
  • Rediffusion manuelle du blog sur [serveur de production] pour remettre un /admin cohérent

« Simple » ne veut pas dire ajouter un service

La principale erreur du jour, ce n’est pas un bug de code. C’est une erreur de cadrage. Le besoin était “un panneau d’admin simple pour des fichiers Markdown”, mais la solution intermédiaire a introduit un nouvel acteur externe et de la confusion mentale. Techniquement défendable, produitement mauvaise.

Autre friction : plusieurs workflows GitHub en échec se sont mis a parler en même temps. Le deploy du blog demandait juste ses secrets VPS_USER, VPS_HOST, VPS_BLOG_PATH, tandis que le deploy conteneurs de l’app cassait ailleurs sur des questions de git fetch, de sync vers le VPS, puis d’owner GHCR. Deux sujets différents, mélanges trop longtemps.

La bonne décision prise en fin de journée est nette :

  • le blog reste un sujet autonome ;
  • Zola + Decap est le bon couple pour l’usage vise ;
  • le deploy blog doit viser uniquement [serveur de production] ;
  • on ne laisse plus l’infra de l’app principale polluer la lecture du sujet blog.

Compter les surprises plutôt que les fichiers

Cette journée rappelle un truc brutal mais utile : “simple” ne veut pas dire “moins de fichiers”. Ça veut dire “moins de surprises pour la personne qui s’en sert”. Un lien qui ouvre un nouveau service inconnu au lieu d’un vrai panneau admin, même si c’est propre en architecture, reste une mauvaise simplification.

L’autre leçon, c’est qu’un monorepo rend les glissements de contexte très faciles. Quand plusieurs workflows cassent à la fois, on peut vite passer du blog à la prod applicative sans même s’en rendre compte. Le bon réflexe, c’est de redecouper les perimetres avant de continuer a patcher.

Zola, Decap et le faux départ CMS

Sujets abordes

  • publication du site statique Zola sur devblog.ooblik.com
  • choix de l’outil d’édition pour les billets
  • clarification des pannes réseau, DNS et logs serveur
  • nettoyage du périmètre entre blog et deploy principal de Krampouz

Décisions prises ensemble

  • garder Zola pour le blog ;
  • abandonner Pages CMS pour cet usage ;
  • remettre Decap derrière /admin ;
  • traiter le deploy blog comme un flux indépendant du deploy conteneurs.

Tentatives abandonnées

  • faire de Pages CMS le panneau d’admin principal du blog ;
  • laisser croire qu’un portail /admin vers un service externe valait un vrai backoffice simple ;
  • raisonner les échecs blog et les échecs conteneurs comme un seul problème.

Les pièces du devblog

  • blog/static/admin/config.yml
  • blog/infra/oauth-worker/worker.js
  • .github/workflows/blog.yml
  • deploy/blog-deploy.sh

Un admin sans mode d’emploi

Quand un panneau d’admin demande un mode d’emploi, ce n’est déjà plus un panneau d’admin.

Automatiser le blog puis ne plus y toucher

Finaliser un deploy blog automatique vraiment minimal sur [serveur de production], avec les bons secrets GitHub, puis ne plus toucher à l’admin tant qu’il ne redevient pas invisible à l’usage.

Repères : Zola, Decap CMS et Pagefind

  • Zola — generateur de site statique qui transforme les fichiers Markdown en pages HTML.
  • Decap CMS — panneau d’édition Git pour modifier des fichiers Markdown via une interface web.
  • Pagefind — moteur de recherche statique embarque directement dans le site genere.
  • OAuth — mécanisme d’authentification deleguee utilise ici pour connecter GitHub au panneau admin.
  • SSG — static site generator : outil qui produit un site statique à partir de contenu source.
  • VPS — serveur prive virtuel loue chez un hébergeur.
