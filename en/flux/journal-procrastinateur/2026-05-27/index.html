Progress: KEREDIT takes back control

The first block corrected a significant contractual error.

WooCommerce was still launching projects with a quantity of `1`, whereas the KEREDIT product `Carte postale` had started at `8 exemplaires`. The price therefore logically failed with `400 Bad Request`.

The fix has aligned the data flow:

  • the WooCommerce product reads the authorised quantities from KEREDIT;
  • the editor starts with a valid quantity;
  • the WooCommerce basket displays the quantity printed by KEREDIT;
  • the standard WooCommerce quantity is locked for KEREDIT lines;
  • the customer can return to edit their order from the basket, change the format or quantity, and then place the order again.

This point is central to the beta. It prevents a dangerous discrepancy between the product page, editor, price and basket.

Product data: export/import to avoid confusion between code and database

The live test highlighted another point of confusion: the deployment included the code, but not the local data on prices, formats, paper types and workshop attributes.

On ooblik.keredit.com, some products were therefore empty or incomplete even though the local system was correctly configured.

The Produits & Prix back office now features an export/import workflow to transfer product and workshop data:

  • export of local product data;
  • import to the VPS;
  • correction of the admin refresh after import;
  • correct populating of workshop attributes in the product record;
  • compatibility with the old paper=invercote_300 setting.

After import and redeployment, the price went live again. This was the first real e-commerce hurdle of the day.

Woo integrations: the client will be able to configure their keys

The Intégrations back office has been enhanced so that the WooCommerce integration can be utilised by a KEREDIT client.

What has changed:

  • Woo REST credentials configurable via the KEREDIT admin panel;
  • encryption of secrets via INTEGRATION_SECRET_ENCRYPTION_KEY;
  • Woo connection test;
  • explicit activation of the WooCommerce command;
  • UX distinction between mandatory REST keys and optional webhook secrets.

The key point: KEREDIT must not depend on any invisible manipulation carried out by us via SSH. The back office must explain and manage the configuration.

WooCommerce basket: the first customer cycle works

The ‘Commander’ button in the editor now calls KEREDIT, which adds the line to the WooCommerce basket and then redirects to OOBLIK.

The workflow has been validated in production:

  1. open an OOBLIK product;
  2. launch the KEREDIT editor;
  3. create/edit a postcard;
  4. calculate the price;
  5. place an order;
  6. add it to the OOBLIK basket;
  7. view the KEREDIT line item showing the design, format, print run and paper type;
  8. click on ‘éditer’ from the basket;
  9. change the format or quantity;
  10. return to the basket with the updated price.

The basket should no longer display the WooCommerce quantity selector on these lines. The business-specific quantity is managed by KEREDIT.

Admin commands and support fixes

The Commandes page in the KEREDIT back office can now be used to track projects with a WooCommerce order.

Today’s additions:

  • search;
  • filters;
  • sorting;
  • pagination;
  • dynamic search without pressing Enter;
  • fix for the focus bug that prevented users from typing more than one letter;
  • opening the project in support edit mode.

Support mode has also been secured in terms of assets.

Problem encountered: when opening a client project from the admin panel, certain images displayed:

/api/assets/:id/url 404 Asset non trouvé

Cause: the support admin could open the project, but could not necessarily resolve the URL of the client asset attached to the project.

Fix:

  • admin/editor access authorised for assets linked to a project within the same tenant;
  • Live verification of an asset URL via 200;
  • ‘Commander’ button hidden in support correction mode;
  • retention of Sauvegarder and Régénérer PDF.

Product decision: when the workshop corrects a client project, it must not place an order on the client’s behalf.

Useful issues

The day mainly revealed discrepancies in the terms and conditions:

  • Woo quantity 1 versus KEREDIT quantity 8;
  • local product data not present in production;
  • Woo integration not sufficiently clear in the back office;
  • Woo shopping basket still attempting to modify a business quantity;
  • a support fix that opened the project but not always the assets;
  • order filter that lost focus with every keystroke.

These issues are positive signs ahead of the beta: they arose during a real customer journey, not in an abstract scenario. And they have been resolved in line with the product’s design, not by workarounds.

Beta update on the evening of 27 May

Yes, we’re in a much better position for the 1 June beta.

We’re not yet at the stage of a wide public launch. However, a controlled ‘friends and family’ beta is now a realistic prospect:

  • the ‘produit -> éditeur -> prix -> panier’ shopping journey exists;
  • the customer can return to edit their order from the shopping basket;
  • the workshop can view orders in KEREDIT;
  • support can open and amend a customer project;
  • quantities and prices are now managed by KEREDIT;
  • product data can be transferred correctly between the local system and the VPS.

What remains to be validated before launch:

  • re-run a complete, error-free workflow, from the OOBLIK product through to the Woo order;
  • check the PDF regeneration for support on a live project;
  • confirm the order/webhook status if we wish to use it in the beta;
  • document the product data import runbook before each thorough test;
  • keep the launch limited to a few friendly clients, no more.

My recommendation: proceed with caution for 1 June, provided the review on 29–31 May confirms a full cycle without any blocking incidents. The appropriate scope is postcard + Woo basket + support fixes. No marketing expansion, no multi-product promises.

Back to work tomorrow

Short-term priorities:

  1. re-run the full end-to-end live user journey;
  2. check PDF/support regeneration;
  3. check that production product data is saved and exportable;
  4. clear the latest non-blocking warnings that interfere with playback;
  5. prepare the beta announcement for partner clients.

Today, it was still around 32 degrees outside. We’re certainly feeling the strain, but the product has reached a significant milestone: the sales journey is no longer just a theoretical concept.
