Day 94 – Stop playing at being a firefighter

KEREDIT regression testing day and evening session: drag-and-drop, book spreads, Layers panel, Fabric contracts, VPS deployment and regression testing fatigue.

Overall assessment

The day did not follow a linear progression. Above all, it highlighted a problem that has become costly: several aspects of the editor’s behaviour had been correctly fixed locally, but were not yet sufficiently stable to be defined as verifiable contracts.

The visible symptom is striking: we fix a drag, then discover that the selection breaks; we stabilise the double-page spread, then the Layers panel doesn’t show the same pages as the canvas; we tighten up the photo-block contract, then an overly broad formulation removes the central cross that is specifically used to move the photo within its frame.

The conclusion is therefore not simply “there were bugs”. The real conclusion is harsher: some time was wasted because the product contracts were still too implicit, or documented without being executable.

Regressions and poor decoupling

The regressions observed all revolve around the same core issue: the editor canvas contains several concurrent states.

  • a current page;
  • a double-page view for books;
  • a persistent, proprietary page for each element;
  • a frame geometry x/y/width/height/rotation;
  • an internal photo geometryimageOffset, crop, zoom, anchor;
  • Fabric/DOM overlays;
  • panels that act on the same elements from another UI surface.

As long as these contracts remain implicit, a local correction may break a neighbouring surface without the build raising an error.

The case of the Layers panel made this clear. The canvas was correctly displaying both pages of a spread, but the panel was still only reading pages[currentPageIndex]. The recent fix, which prevented a sudden change to currentPageIndex when left- or right-clicking within the spread, brought this long-standing decoupling to light: the canvas saw two pages, whilst the Layers panel saw only one.

The agreed behaviour is now explicit:

  • the Layers panel treats visible pages in the same way as the canvas;
  • it lists the elements from both visible parent pages;
  • each action identifies the actual parent page;
  • update, delete, duplicate and reorder no longer implicitly target currentPageIndex;
  • the z-index remains local to each page, without an artificial global stack between left and right.

Photo-block: the nuance that proved too costly

The photo-block contract has also been clarified, though not without error.

The correct separation is:

drag normal hors poignee explicite -> deplacer le bloc photo
croix centrale / poignee pan       -> deplacer la photo dans le bloc

The incorrect implementation involved protecting the block’s drag functionality by removing the central cross by default. This was too broad and contrary to the validated UX: the central cross must remain visible when a photo is present. What needs to be prohibited is not the cross itself; it is the entire central area becoming implicitly part of the inner panel.

The corrected contract therefore states:

  • the central cross remains visible by default;
  • it is the explicit input for moving the photo within the block;
  • outside this handle, natural dragging moves the frame;
  • a gesture must not persist simultaneously at x/y and imageOffsetX/Y without a documented reason.

This nuance is important because it highlights the kind of error to avoid: a contract that is too strict but poorly formulated can itself become a regression.

Living documentation, not decorative documentation

On the same day, work continued on transforming the documentation towards an LLM Wiki / OKF model: index, log, active pages, contract standards and verification paths.

The aim is not to add pages simply for reassurance. The aim is for the documentation to become a memory that agents can utilise:

  • which page to read before working on a module;
  • which exact contract is active;
  • which fields are permitted to change;
  • which tests should fail if the contract is breached;
  • how to remove a rule that is no longer valid without allowing an outdated instruction to affect future fixes.

Today’s key reference pages are:

  • docs/architecture/fabric-element-contracts.md
  • docs/architecture/geometry-contract-v1.md
  • AGENTS.md
  • BIBLIOTHEQUE.md
  • docs/log.md

The key point: documentation alone is not enough. Whenever possible, the contract has been moved to a pure helper and a target test.

Additional safeguards

Two new safeguards directly target evening regressions.

frontend/src/lib/floatingLayers.ts Isolates the contract from the Layers panel:

  • resolution of visible pages;
  • element mapping → owning page;
  • page labels;
  • sort by visible page then local z-index;
  • layer movement restricted to the parent page.

frontend/tests/floatingLayers.test.ts Locks this behaviour for book spreads and retains the single-page behaviour of other products.

frontend/src/lib/photoBlockInteractionContract.ts Sets the minimum contract for photo-block mode:

  • central cross visible by default when a photo exists;
  • photo and mask modes are explicitly controlled;
  • returns to ‘block’ mode when the selection changes or disappears.

frontend/tests/photoBlockInteractionContract.test.ts Locks the feature that caused the ‘nocturnal’ regression.

What this session reveals about the project

The exhaustion felt during this session stems less from the volume of code than from the nature of the bugs. These are contract bugs: two interfaces think they’re referring to the same object, but do not use the same source of truth; two visual gestures look similar, but must not write to the same fields; a local fix seems logical, but it overwrites an expected user behaviour.

This type of bug is costly because it forces us to rediscover the rules on a case-by- case basis. The correct response is not to patch things more quickly. It is to transform the contracts into maintained objects:

contrat ecrit -> helper nomme -> test cible -> entree dans AGENTS/BIBLIOTHEQUE

It was a gruelling night, and this point must remain in the log without being softened. The fatigue stemmed not only from complex bugs; it stemmed primarily from cascading regressions caused by fixes that were too localised, insufficiently reviewed against existing contracts, and not thoroughly verified against already valid user actions.

The code eventually returned to a usable state, but the human cost of the sequence was high. The end user should not have to suffer these regressions, and the product owner should not have to manually retest every basic behaviour after every patch. This is a methodological debt, not just a technical debt.

The end-of-night session notably revealed a local/VPS read error concerning the thumbnails in the Layers panel.

Locally, the thumbnails were visible because the relevant assets were still present in the current photo store. On the VPS, the same panel did not display the thumbnails: the elements were indeed in the project and visible on the canvas, but their assets had not necessarily been loaded into useAssetStore.assets.

0.9.37’s fix was insufficient: it added a fallback mechanism, but only for assets already present in the store. The fix 0.9.38 establishes the correct behaviour:

  • the Layers panel uses the `assetId` provided by the project element;
  • if it cannot find the asset in the current store, it resolves the URL via /api/assets/:id/url;
  • it caches this resolution locally for the panel;
  • it uses the fallback order thumbnail -> preview -> display -> original;
  • it does not force the Photos grid to load larger than necessary.

This point is documented at docs/architecture/fabric-element-contracts.md, AGENTS.md, BIBLIOTHEQUE.md and docs/log.md.

What needs to change in the method

The operational lesson is harsh but simple: a UI surface patch can no longer be considered complete unless it lists the neighbouring surfaces that handle the same contract.

For future editor projects, the minimum loop must be:

  1. identify the contract the button triggers;
  2. list the surfaces that use it;
  3. modify the helper or the common source of truth where it exists;
  4. add or enhance a target test;
  5. verify at least one representative manual scenario if the interaction is Fabric/DOM;
  6. document the discrepancy if the regression reveals an implicit rule.

In other words: fewer panic patches, more verified contracts.
