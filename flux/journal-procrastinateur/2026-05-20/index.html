Carnet de fabrication · 2026.05.20

Jour 61 - Refaire simple après la crise des prix

Une journée de crise utile autour du calcul de prix : trop de couches exposées, confusion MISKISS/grilles/variables, recentrage radical sur la fiche produit, bibliothèques atelier séparées, et point de sauvegarde avant simplification.

Horaires de session

  • Agent utilisé : Codex, transition depuis Claude Code
  • Branche de travail : feat/miskiss-pricing-v0
  • État de départ : le chantier prix avait avancé techniquement, mais l’interface et les concepts étaient devenus trop disperses pour être compris simplement.
  • État de clôture : le menu visible recentre Produits & Prix sur la fiche produit, l’onglet Prix contient le calcul du produit, et /admin/pricing devient une surface discrète Bibliotheques atelier
  • Version repo : 0.6.29
  • Commit de sauvegarde cree avant simplification : 3d93bcd checkpoint: save pricing prototype before product simplification
  • Travail local final : refonte UX produit/prix, bibliothèques atelier, correction du vocabulaire visible et documentation de l’état
  • Temps de session estime : environ 5h00
  • Objectif du jour : sortir de la complexité prix sans jeter les données utiles. La journée a été inconfortable, mais nécessaire. Le sujet n’était pas un bug isole. Ce n’était pas seulement un bouton mal nomme, un accent oublie, ou un champ mal place. Le vrai problème était plus profond : l’interface de prix avait commencé à exposer directement la tuyauterie technique. Et quand l’interface expose la tuyauterie, l’atelier ne voit plus son métier.
  • Temps cumulé :303h30+

Le symptôme : Claire et Marc ne comprennent plus le prix

Le moment de bascule a été très clair : Claire et Marc ne comprenaient plus la logique entre :

  • Grilles tarifaires ;
  • Liaisons produits ;
  • Variables ;
  • MISKISS ;
  • Recette de prix ;
  • Bibliotheques papier ;
  • produits ;
  • options ;
  • paliers ;
  • fabrication.

Chaque mot avait une raison technique. Mais tous ensemble, ils formaient une carte mentale inutilisable.

On était exactement à l’inverse du KISS attendu.

Le paradoxe est classique : pour rendre le prix générique, versionne, réutilisable et propre, on avait commencé à nommer toutes les couches internes. Mais l’utilisateur métier n’a pas besoin de voir toutes les couches. Il a besoin d’ouvrir un produit et de comprendre :

  • quels choix le client peut faire ;
  • comment on le fabrique ;
  • combien cela coûte ;
  • combien on le vend ;
  • quels paliers sont disponibles ;
  • quels papiers, formats, finitions ou reliures sont autorisés.

Tout le reste est implémentation.

Première hésitation : sauver MISKISS ou le cacher ?

MISKISS avait une vraie valeur : il portait l’idée d’un calcul atelier lisible, notamment pour une carte postale SRA3 avec :

  • poses par feuille ;
  • recto / verso ;
  • clics couleur ou N&B ;
  • papier ;
  • gâche ;
  • temps atelier ;
  • marge ;
  • prix conseille.

Le problème n’était pas le calcul. Le problème était de l’avoir transforme en entrée séparée, comme si l’utilisateur devait apprendre un logiciel dans le logiciel.

La correction de vocabulaire a commencé par des choses concrètes :

  • Machine devait devenir Imprimante ;
  • les procedes atelier devaient être modifiables ;
  • les modèles de coût ne devaient pas être des valeurs cachées ou en dur ;
  • les accents français devaient être visibles dans l’interface ;
  • les papiers devaient venir d’une bibliothèque, pas de champs libres recopies partout.

Ces corrections étaient justes. Mais elles ne suffisaient pas.

Même corrige, un écran MISKISS sépare continuait a dire à l’atelier : “le prix est ailleurs”.

Deuxième hésitation : les bibliothèques sont indispensables

La réaction inverse aurait été de tout mettre dans le produit sous forme de champs libres.

Cela aurait été plus simple pendant dix minutes, puis catastrophique.

Si chaque produit resaisit son papier, son format, sa finition et son fournisseur en texte libre, on refabrique le chaos :

  • Invercote 300g ici ;
  • Invercote 300 g ailleurs ;
  • Invercote SRA3 dans une recette ;
  • un prix fournisseur dans Fine Art ;
  • un autre coût papier dans Carte postale ;
  • une option WooCommerce qui ne correspond plus a KEREDIT.

La bonne direction est donc double :

  1. les bibliothèques atelier existent comme sources communes ;
  2. le calcul du prix se fait dans chaque produit.

Autrement dit : les variables ne disparaissent pas, mais elles ne sont plus le centre de l’UX.

Le revirement principal : le prix vit dans le produit

Le cap final du jour est plus radical :

Toute la logique de prix visible doit être dans la fiche produit.

La fiche Carte postale doit porter ses formats, papiers, paliers, options, règles de fabrication et prix. La fiche Carnet photo portera ses pages, finitions, reliures, couverture, paliers et prix.

On ne doit pas devoir ouvrir Liaisons produits, Grilles, Variables ou MISKISS pour régler le prix d’un produit.

Les anciens concepts restent sous le capot parce qu’ils contiennent déjà de la structure utile :

  • routes existantes ;
  • tables Prisma ;
  • matrices tarifaires ;
  • référentiel papier ;
  • recettes de calcul atelier ;
  • compatibilité avec les produits existants.

Mais l’interface visible doit parler produit.

Ce qui a été implémente aujourd’hui

Un point de sauvegarde a d’abord été créé avant de casser le modèle mental existant :

3d93bcd checkpoint: save pricing prototype before product simplification

Ce checkpoint garde le prototype papier/MISKISS en sécurité avant simplification.

Ensuite, l’admin a été recentre :

  • le menu Produits devient Produits & Prix ;
  • /admin/products devient la surface centrale ;
  • chaque produit garde ses onglets métier ;
  • l’onglet Prix contient maintenant directement :
    • prix de base ;
    • prix de page supplémentaire ;
    • paliers ;
    • prix par palier ;
    • aperçu calcule ;
    • formats et suppléments ;
    • sélection papier depuis la bibliothèque ;
    • options de prix ;
  • le bouton qui renvoyait vers un autre écran Produits & Prix a été supprimé ;
  • /admin/pricing est renomme Bibliothèques atelier ;
  • cet écran ne doit plus être compris comme l’endroit ou l’on règle le prix du produit.

C’est un changement important : le prix redevient une propriété du produit, pas une chasse au tresor entre cinq écrans.

L’état exact ce soir

Ce qui est mieux :

  • Claire peut maintenant partir de Produits & Prix, choisir un produit, ouvrir Prix, et voir les composants du calcul au même endroit.
  • Carte postale montre ses formats, ses papiers, ses paliers et son onglet prix.
  • Les paliers carte postale ont été recentres sur 25 / 50 / 100 / 250 / 500.
  • Les papiers viennent d’une bibliothèque active, pas d’une recopie libre dans l’onglet prix.
  • Les anciennes surfaces techniques sont cachées ou renommees dans l’UX visible.
  • Le vocabulaire visible se rapproche de l’atelier : Imprimante, Papier, Bibliotheques atelier, Prix par palier, Formats et supplements.

Ce qui reste volontairement imparfait :

  • les anciennes routes et anciens composants existent encore pour compatibilité ;
  • les bibliothèques Formats, Imprimantes, Finitions, Reliures et Operations atelier ne sont pas encore toutes des CRUD complets ;
  • la fabrication fine doit encore être reliee proprement au produit, au lieu de rester en grande partie issue du prototype MISKISS ;
  • l’onglet prix porte maintenant la logique visible, mais il faudra encore durcir le modèle de données pour que toutes les bibliothèques soient vraiment referencees par identifiant stable ;
  • l’interface est fonctionnelle, mais il reste à la tester avec Claire sur une vraie carte postale et un vrai carnet.

Auto-critique

L’erreur du jour n’a pas été de vouloir des données propres. C’était nécessaire.

L’erreur a été d’exposer trop tôt les noms techniques :

  • une grille tarifaire est une implémentation ;
  • une liaison produit est une implémentation ;
  • une variable est une implémentation ;
  • MISKISS est un moteur de calcul, pas forcément un écran principal ;
  • un modèle de coût est une ressource atelier, pas un concept que Claire doit deviner.

La bonne interface doit partir de la question métier :

Je vends une carte postale. Qu’est-ce que le client choisit ? Comment je la fabrique ? Combien je la vends ?

Si l’écran ne répond pas a cette question en moins de quelques secondes, il est trop complique.

Le moment de crise a donc été utile. Il a cassé l’illusion que le modèle devenait clair parce que le code devenait plus structure.

Le code peut être structuré et l’usage rester incompréhensible.

Vérifications

Les contrôles techniques ont été relances après la refonte :

  • pnpm --filter frontend typecheck : OK
  • pnpm --filter backend typecheck : OK
  • pnpm lint : OK, avec avertissements attendus sur les anciens composants caches
  • pnpm build : OK
  • pnpm dev:status : OK
  • vérification navigateur sur /admin/products :
    • menu Produits & Prix visible ;
    • menu Bibliotheques atelier sépare ;
    • fiche Carte postale ouvrable ;
    • onglet Prix avec sections de calcul visibles.

État pour la suite

Le prochain bon geste n’est pas de rouvrir une grande architecture.

Il faut prendre un seul produit :

  1. Carte postale ;
  2. formats autorises ;
  3. papiers autorises ;
  4. recto / recto-verso ;
  5. imprimante ;
  6. SRA3, poses, gâche, temps ;
  7. paliers ;
  8. prix final.

Et vérifier avec Claire que tout se comprend sans prononcer :

  • MISKISS ;
  • liaison ;
  • matrice ;
  • variable ;
  • grille.

Si la carte postale tient, on fera le carnet photo avec ses pages, sa couverture, ses finitions et sa reliure.

La lumière du jour est la :

KEREDIT doit garder les bibliothèques pour ne pas dupliquer les données, mais le prix doit se régler dans le produit, la ou l’atelier pense déjà.

Ce soir, le cap est moins ambitieux en apparence, mais beaucoup plus juste.
