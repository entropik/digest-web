## Lecture courte

La journée part d'une frayeur banale : une fiche produit modifiée dans KEREDIT
ne s'affiche pas correctement cote WooCommerce. Ralage immédiat. Puis la
mémoire revient : la fiche Woo n'avait jamais été resynchronisee — il fallait
ouvrir le produit dans WooCommerce et cliquer sur « Synchroniser ». Le bug
n'était pas dans le code, il était dans le geste.

Plutôt que de s'habituer au geste, la journée le supprime. Le soir, une
sauvegarde dans l'admin KEREDIT met à jour la fiche Woo toute seule, en
quelques secondes, prouve sur ooblik.com.

## Le diagnostic avant le code

L'exploration confirme d'abord ce qui existe : la synchro est un pull, le
plugin WordPress vient lire la config produit via l'API KEREDIT. Deux
declencheurs automatiques existent déjà — la sauvegarde de la fiche cote Woo
et un rafraîchissement paresseux à l'affichage, borne à une heure. Le trou est
précis : modifier la fiche dans l'admin KEREDIT ne previent personne.

Trois options sont posées sur la table : un push webhook temps réel, un pull
simplement durci, un cron cote WordPress. Le choix va au push, parce que le
cas vécu est exactement « je viens de modifier, je teste tout de suite ».

## Les décisions qui comptent

Première décision : pas de migration Prisma pour le secret. Le backend ne
stocke que le hash du secret d'intégration, il ne peut donc jamais le renvoyer
au plugin. Les variables d'environnement `WOO_SITE_URL`,
`WOO_INTEGRATION_KEY` et `WOO_INTEGRATION_SECRET` suivent le précédent
`AUTH_EMAIL_WEBHOOK_*` — doublon assume, mono-tenant pilote oblige.

Deuxième décision : la notification est fire-and-forget. Timeout cinq
secondes, erreur journalisee en warn, jamais d'échec remonte à la sauvegarde
admin. Un site Woo injoignable ne doit pas faire échouer une fiche produit.

Troisième décision : cote plugin, la réponse HTTP part immédiatement et la
vraie synchro est planifiee via `wp_schedule_single_event`. Le backend
n'attend pas WordPress.

## Le stress habituel du « faire les choses bien »

La configuration reclame les credentials de production. Ils vivent dans les
réglages du plugin, cote serveur ooblik.com. WP-CLI avec PHP 8.3 explicite —
le binaire par défaut pointe vers un PHP trop vieux et ment sur les versions —
permet de les relire proprement, de renseigner le `.env` local et celui du
VPS, et de valider le rendu du compose avant tout redémarrage. Le backend
n'est pas redémarre dans la foulée : l'ancien code tourne encore, les
variables attendront le déploiement.

Le déploiement impose son propre rituel : la 0.17.0 est déjà servie, il faut
une 0.17.1, donc une branche de release, une PR, une CI verte, un merge. Puis
le script nominal, le SHA servi vérifie, et seulement après cela le test.

## La preuve, deux fois

Le premier test end-to-end échoue — la meta `_keredit_connector_synced_at` ne
bouge pas. Quelques secondes de doute, puis l'évidence : la sauvegarde de test
est passée pendant le redéploiement, sur l'ancien code. Le canal est prouve a
la main depuis le conteneur (200, `scheduled: true`), l'utilisateur
reenregistre, et la meta avance toute seule. La deuxième fois est la bonne.

Le bouton « Synchroniser » reste affiche dans WooCommerce. Il ne sert plus,
mais on ne retire pas une rampe de secours le jour ou l'on installe
l'ascenseur.
