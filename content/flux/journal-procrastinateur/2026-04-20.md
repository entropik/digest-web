## Note de reconstruction

Ce billet est reconstruit à partir des traces d'exploitation, des commandes executees sur le VPS et du diagnostic formule pendant l'incident. Il n'y a pas de commit représentatif de cette journée : le travail s'est fait presque entièrement en investigation et en restauration.

## Ce qui s'est passe

La journée a été monopolisee par un constat brutal : la prod `krampouz.ooblik.com` ne servait plus les vraies données métier. Les assets clients avaient disparu de l'interface, et l'état de la base active ressemblait à une base seedee plutôt qu'à une base de production vivante.

Le diagnostic fini par tomber sans ambiguïté :

- `assets = 0`
- `users = 2`
- `projects = 1`
- présence typique des comptes seed (`[compte OOBLIK retiré]`, `[compte OOBLIK retiré]`)

Autrement dit : la prod ne pointait plus vers une vraie base métier, mais vers une base reconstruite/bootstrappee après les ennuis Prisma. Le deploy "reussi" visible dans GitHub n'était pas la cause directe de la disparition ; le dommage était déjà la, dans la séquence de régularisation precedente.

La journée a ensuite change de nature. Il ne s'agissait plus d'améliorer le workflow, mais de sauver les données. Un backup du `2026-04-02` a été retrouve sur le VPS. Il contenait encore les vraies données :

- `assets: 1562`
- `users: 1525`
- `projects: 547`

La restauration a d'abord été faite dans une base témoin. Cette base restauree n'avait pas `_prisma_migrations` et ne pouvait pas simplement repartir en `migrate deploy`. Il a fallu :

1. mesurer le diff exact avec le schéma courant ;
2. appliquer uniquement le diff additif nécessaire ;
3. enregistrer l'historique Prisma ;
4. vérifier ensuite que `prisma migrate deploy` ne voulait plus rien changer.

Une fois la base témoin rendue compatible, le cutover réel a été fait vers la vraie base `krampouz`. Les comptes, projets et assets du backup ont alors reapparu en prod, y compris le compte `[compte OOBLIK retiré]` et ses données liées.

## Ce qui a été confirme

- la prod active était bien tombee sur une base seedee
- le volume Docker Postgres n'avait pas simplement été recree "par hasard"
- aucune preuve d'un `DELETE assets` dans les migrations elles-mêmes
- le problème venait d'un chemin d'exploitation trop dangereux autour de Prisma et du seed
- la restauration depuis backup était possible
- la base restauree pouvait être rendue compatible avec le schéma courant

## Décisions de la journée

La décision la plus importante n'est pas seulement la restauration. C'est la remise en question du workflow lui-même. à partir de ce moment-la, plusieurs règles deviennent evidentes :

- plus de seed possible en prod sans action explicite exceptionnelle ;
- plus de régularisation Prisma "intelligente" dans le flux nominal ;
- un deploy doit échouer si la base est ambiguë, pas tenter de la "réparer" tout seul ;
- la prod client ne doit plus jamais servir de terrain de régularisation legacy.

## Réalité de la session

Cette journée ne produit aucune feature. Elle consomme presque tout son temps a :

Le sentiment de temps perdu est réel, mais la sortie utile l'est aussi : les données clients reviennent et la dette Prisma cesse d'être une abstraction.

## Ce que la journée laisse ouvert

La restauration sauve la situation immediate, mais elle ne règle pas encore la cause racine de fond : une procédure de deploy trop complexe, trop ambiguë, trop capable de deriver hors du chemin nominal.

Le lendemain devra donc faire plus que "continuer" : il faudra remettre a plat la provenance du runtime lui-même.
