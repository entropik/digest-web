OOBLIK — thematic feature

FOCUS - After the IDE, here comes the ADE

For thirty years, the development environment was designed around a developer working with files. Claude Code and Codex have changed this unit of work. A new generation of tools — Orca, Superset, Emdash — no longer seeks to help us write code: it organises agents to write it for us.

L’IDE classique organise des fichiers, un éditeur, un terminal et un debugger. L’ADE organise désormais des agents. Ce changement de vocabulaire signale une transformation plus profonde : l’unité de travail n’est plus seulement le fichier ouvert par un développeur, mais la tâche confiée à un agent dans un environnement isolé.

La thèse de cette édition tient en une phrase : le prochain outil essentiel du développeur IA ne sera peut-être ni le modèle, ni l’éditeur. Ce sera l’orchestrateur.

De l’IDE à l’ADE

Pendant trente ans, l’environnement de développement intégré a rassemblé dans une même fenêtre ce dont un humain avait besoin pour programmer : arborescence de fichiers, éditeur, terminal, debugger, recherche et contrôle de version. Les assistants de code ont d’abord pris place dans cette architecture sous la forme d’une autocomplétion plus intelligente ou d’un panneau de conversation.

Claude Code, Codex, OpenCode et les autres agents de terminal déplacent maintenant le centre de gravité. Ils lisent le dépôt, modifient plusieurs fichiers, lancent les tests, inspectent les erreurs et préparent parfois eux-mêmes le commit ou la pull request. L’humain ne manipule plus chaque ligne : il distribue des problèmes, surveille l’exécution et juge les résultats.

Le workflow dominant prend alors une autre forme :

Projet → tâches → worktrees Git → agents indépendants → supervision → diff et revue → fusion

L’ADE — Agentic Development Environment — devient moins un éditeur qu’un poste de contrôle. Son rôle est de lancer plusieurs agents, de leur fournir le bon contexte, d’isoler leurs modifications, de signaler ceux qui attendent une décision et de présenter leurs propositions de façon comparable.

Le worktree comme primitive commune

La plupart de ces outils convergent vers la même brique : le worktree Git. Une tâche reçoit une branche et un répertoire de travail distincts. Claude Code peut corriger une régression pendant que Codex prépare une fonctionnalité et qu’OpenCode explore une troisième solution, sans que leurs modifications se mélangent immédiatement.

Cette isolation ne résout pas tout. Les agents peuvent encore modifier les mêmes concepts sur des branches différentes, échouer à installer le projet ou produire des changements incompatibles au moment de la fusion. Mais le worktree transforme une cacophonie de processus concurrents en unités observables, comparables et, si nécessaire, jetables.

Il devient à l’ADE ce que le fichier était à l’IDE : l’objet concret autour duquel l’interface organise le travail.

La couche stable au-dessus des modèles

Les modèles resteront inégaux. Claude excellera sur une tâche, Codex sur une autre, Gemini ou un modèle local sur une troisième. Leurs performances, leurs tarifs et leurs fenêtres de contexte évolueront rapidement. Miser tout le workflow sur un seul d’entre eux revient à confondre le moteur du moment avec le véhicule.

L’ADE propose une couche plus stable : projet + contexte + worktrees + agents + supervision + validation + historique. Le modèle devient un exécuteur interchangeable que l’on choisit selon le problème, le coût ou les contraintes de confidentialité.

Cette promesse reste en partie à démontrer. Les agents n’exposent pas tous les mêmes événements, formats de session ou mécanismes de reprise. Changer de modèle ne signifie pas encore transporter proprement sa mémoire et son raisonnement. Mais l’orientation est claire : l’environnement cherche à absorber ces différences pour offrir un workflow cohérent au développeur.

Trois projets qui définissent la catégorie

Orca — le cockpit le plus complet

Orca assume le plus directement l’idée de flotte. Il exécute des agents CLI côte à côte, chacun dans son worktree, puis réunit dans une seule interface les terminaux, les fichiers, les diffs, GitHub, Linear, les machines distantes et les notifications. Son compagnon mobile permet également de surveiller ou de relancer une exécution loin du poste de travail.

Sa fonction la plus révélatrice consiste à envoyer le même problème à plusieurs agents isolés, puis à comparer leurs solutions. Le développement devient presque une expérimentation concurrente : plusieurs implémentations sont produites, testées et mises en regard avant que l’humain ne choisisse ou ne fusionne.

Sous licence MIT et porté par une très forte dynamique communautaire, Orca est aujourd’hui le meilleur point d’entrée pour comprendre ce que peut devenir un ADE généraliste.

Emdash — le choix open source agnostique

Emdash se définit explicitement comme un environnement de développement agentique open source. Sa licence Apache 2.0 et son indépendance à l’égard des fournisseurs en font le candidat le plus net pour construire un workflow durable sans l’attacher à un seul agent.

Son approche suit la chaîne de production réelle : un ticket provenant de GitHub, GitLab, Linear, Jira ou Asana est confié à un agent dans un environnement isolé ; viennent ensuite les modifications, la revue, les tests, la pull request et la CI. Les agents peuvent aussi travailler sur une machine distante par SSH tandis que l’interface reste locale.

Emdash est moins spectaculaire qu’Orca, mais sa neutralité et son articulation avec les outils de projet en font probablement le choix open source le plus cohérent de cette sélection.

Superset — l’IDE agentique intégré

Superset reprend la même primitive — une tâche, un workspace isolé, un agent — avec une ambition plus proche du successeur direct de l’IDE. Il conserve les sessions grâce à un daemon, signale les agents qui réclament une intervention, affiche les diffs et permet d’ouvrir les workspaces dans d’autres éditeurs.

Le projet annonce pouvoir orchestrer plus de cent agents. Ce chiffre décrit surtout une capacité architecturale : aucun humain ne peut raisonnablement examiner cent flux complexes à la fois. Il pose néanmoins la bonne question, celle de l’attention. Quand dix agents travaillent simultanément, le problème n’est plus de les lancer mais de savoir lequel est bloqué, lequel a terminé et lequel nécessite une décision.

Une distinction éditoriale est indispensable : Superset publie son code sous Elastic License 2.0. Il peut être utilisé, modifié et auto-hébergé, mais cette licence n’est pas reconnue comme open source au sens strict par l’OSI. Superset est donc source-available, pas open source strict.

L’autre école : rester dans le terminal

Agent Deck refuse l’idée qu’un cockpit d’agents doive nécessairement devenir une grande application graphique. Écrit en Go et construit autour de tmux, il rassemble les sessions, leurs états, les notifications, les groupes et les worktrees dans une interface terminal.

Cette approche répond au même problème avec les primitives Unix existantes. Elle parlera davantage aux développeurs qui vivent déjà dans tmux et veulent superviser plusieurs agents sans installer un nouvel IDE Electron. Agent Deck montre surtout que l’ADE est une fonction avant d’être une forme graphique.

Deux jeunes projets à suivre

OpenADE, sous licence MIT, défend une séquence plus disciplinée : planifier, réviser, puis exécuter. La planification peut être confrontée entre plusieurs agents avant qu’un seul n’applique les modifications. L’environnement reste local et réunit terminal, fichiers, recherche, diff, gestion de processus et snapshots Git autour de Claude Code et Codex.

ADE porte littéralement le nom de la catégorie. Encore jeune, ce projet AGPL rassemble une application macOS, une CLI, un runtime local persistant — le « brain » — et un compagnon iOS. Chaque tâche vit dans son propre worktree et les différentes interfaces se connectent au même état d’exécution. Sa traction reste limitée, mais son architecture illustre bien l’idée d’un environnement durable auquel plusieurs surfaces viennent se rattacher.

Après l’orchestration, la mémoire du projet

Frame déplace la question vers un problème que les cockpits ne résolvent pas encore bien : comment conserver l’intention du logiciel ? Lancer cinq agents en parallèle ne sert à rien si chacun doit redécouvrir l’architecture, les décisions passées et les critères d’acceptation.

Son approche spec-driven transforme la planification, les notes d’architecture, la structure et les tâches en contexte persistant, lisible par les agents futurs et versionné avec le projet. Frame est moins un gestionnaire de flotte qu’une tentative pour construire la mémoire collective dont cette flotte aura besoin.

Cette piste pourrait devenir aussi importante que l’orchestration elle-même. L’ADE mature ne devra pas seulement répondre à « quel agent travaille sur quelle branche ? », mais aussi à « que sait-il du projet, pourquoi cette décision a-t-elle été prise et comment prouver que son travail respecte l’intention initiale ? »

Agent, ADE, organisation : trois couches distinctes

La confusion avec les « OS agentiques » disparaît si l’on sépare les couches :

Agent — Claude Code, Codex, OpenCode, Gemini CLI : exécuter une tâche de développement.

ADE — Orca, Emdash, Superset : isoler, lancer, superviser, comparer et valider plusieurs agents.

Orchestration organisationnelle — Paperclip et les systèmes multi-agents : distribuer objectifs, responsabilités, budgets et gouvernance à l’échelle d’une organisation.

Paperclip cherche à devenir l’OS d’une entreprise d’agents. Orca ou Emdash cherchent à devenir l’OS de son atelier logiciel. Ils sont voisins, parfois appelés à se connecter, mais ils ne résolvent pas le même problème.

Mon classement éditorial

Orca constitue aujourd’hui l’ensemble le plus complet et le projet qui définit le mieux la catégorie. Emdash est le choix open source le plus propre pour un workflow agnostique. Superset porte peut-être la vision produit la plus proche du futur IDE, avec la réserve importante de sa licence source-available.

Viennent ensuite Agent Deck pour l’école terminal, OpenADE pour la discipline de planification, Frame pour la mémoire et le contexte, puis ADE pour son architecture locale, persistante et mobile encore expérimentale.

Le véritable test ne sera pourtant pas le nombre d’agents affichés dans une interface. Ce sera la capacité à les rendre remplaçables, à reprendre leur travail après un échec, à conserver l’intention du projet et à ramener cent propositions concurrentes vers une décision humaine vérifiable.

L’IDE aidait le développeur à écrire du code. L’ADE doit maintenant l’aider à diriger ceux qui l’écrivent.
