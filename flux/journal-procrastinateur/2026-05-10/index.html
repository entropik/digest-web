Jour 51 - Le pont devient un produit

Une journée dense ou le chantier auth/Woo est passé du prototype au flux client presque naturel : même onglet, retour boutique, reprise des projets, vignettes, suppression confirmée et plugin WordPress mis à jour en live.

Horaires de session

  • Branche de travail : dev, après merge de dev-auth
  • SHA de départ notable : 4e0c0d7 (feat: add dev auth foundation and woo plugin)
  • Merge de dev-auth vers dev : 8df3c5e
  • Dernier SHA pousse du jour au moment du billet : ed7a472 (feat: confirm customer project deletion)
  • Version app déployée en live : 0.6.12
  • Version plugin WordPress publiée : 0.1.7
  • Déploiements VPS Krampouz du jour : 0.6.3 -> 0.6.12, par petites marches vérifiées
  • Déploiements plugin ooblik.com : 0.1.5 -> 0.1.6 -> 0.1.7
  • Amplitude minimale observée : grosse journée de test live et d’itération produit
  • Objectif produit du jour : transformer le lancement WooCommerce en expérience client réutilisable, pas seulement en preuve technique Il y a des jours ou le code avance. Et puis il y a des jours ou le produit change de nature. Aujourd’hui fait partie de la deuxième catégorie. Ce matin, le pont entre ooblik.com, WooCommerce et l’éditeur Krampouz était encore un assemblage prometteur : plugin, tokens signes, sessions, lancement dans l’éditeur. Ce soir, il commence à ressembler à un vrai parcours client : on clique, on édite, on revient, on retrouve ses projets, on reprend, on duplique, on supprime avec confirmation. La phrase du jour pourrait être : le tunnel technique est devenu une surface produit. Et oui, la sensation est un peu vertigineuse. Ce qui avait pris des semaines, parfois des mois, avec une intégration externe traditionnelle, s’est mis a sortir en quelques heures. Pas par magie. Pas parce que tout est facile. Mais parce que le terrain était devenu favorable.
  • Temps cumulé :249h+

Pourquoi ça va si vite maintenant

La réponse courte : oui, la codebase documentée et cadrée change tout.

La réponse plus juste : la vitesse vient de la combinaison de plusieurs choses.

1. Le produit est suffisamment clair

On ne part plus d’une idée vague comme “faire un éditeur web-to-print”. On sait maintenant que le cœur bêta est :

  • un client WooCommerce ;
  • un produit configurable ;
  • un bouton Creation ;
  • une session éditeur signée ;
  • une sauvegarde fiable ;
  • une reprise de brouillon ;
  • un retour boutique compréhensible.

Quand le produit est flou, chaque ligne de code ouvre dix questions. Quand le produit est net, le code peut avancer sans debattre à chaque bifurcation.

Aujourd’hui, par exemple, la décision “même onglet plutôt que nouvel onglet” est venue du test utilisateur, pas d’une préférence abstraite. Les utilisateurs étaient perdus par le nouvel onglet. On a donc corrige l’architecture d’expérience : navigation top-level dans la même fenêtre, pas d’iframe, pas de cookie tiers, pas de chrome WordPress force autour de l’éditeur.

C’est une petite phrase cote utilisateur. Techniquement, c’est une vraie décision d’architecture.

2. La documentation donne une mémoire au projet

Les specs, la roadmap, BIBLIOTHEQUE.md, le changelog et les billets precedents évitent de redécouvrir le projet à chaque session.

Ce n’est pas de la documentation décorative. C’est une infrastructure cognitive :

  • elle rappelle pourquoi les tokens Woo sont one-shot ;
  • elle dit que Google Photos vient après le plugin ;
  • elle garde la séparation entre réglages techniques Woo et futur dashboard métier ;
  • elle garde le contexte CloudPanel / PHP 8.3 / WP-CLI ;
  • elle évite de mélanger local, VPS, WordPress et backend Krampouz.

Sans ça, chaque accélération serait dangereuse. Avec ça, on peut aller vite sans perdre le fil.

La documentation ne remplace pas les tests. Mais elle évite les mauvais tests, les faux problèmes et les retours en arrière inutiles.

3. La codebase a maintenant de bons points d’appui

Les features du jour n’ont pas été ajoutées dans le vide. Elles se sont branchées sur des fondations déjà présentes :

  • Fastify pour les routes API ;
  • Prisma pour les relations client/projet/session ;
  • cookies HttpOnly et CSRF pour l’auth moderne ;
  • credentials d’intégration pour WooCommerce ;
  • tokens de lancement Woo signes, hashes et expirables ;
  • pipeline asset existant ;
  • editor JSON déjà persiste ;
  • plugin WordPress déjà structure en classes ;
  • update prive par manifest ZIP.

La grande différence avec une intégration “from scratch”, c’est que chaque pièce nouvelle a pu réutiliser une pièce stable.

La reprise des projets client, par exemple, n’a pas invente un stockage parallèle dans WordPress. WordPress demande une liste paginee. Krampouz répond avec des métadonnées. Le gros JSON éditeur reste cote Krampouz. C’est sain, scalable, et cohérent avec le futur multi-client.

4. Les tests live ont été immediats

Le cycle du jour a été très court :

  1. coder ;
  2. vérifier localement ;
  3. versionner ;
  4. déployer VPS ;
  5. publier le plugin ;
  6. tester dans WordPress ;
  7. corriger l’UX observée.

C’est la que l’assistance IA devient vraiment efficace : pas seulement écrire du code, mais traverser la chaîne entière sans perdre le contexte.

Un exemple simple : WordPress voyait encore un vieux manifest 0.1.5 à cause d’une URL avec query ?v=013. Le symptôme était “pas d’update”. La correction n’était pas de recompiler dix fois le plugin ; c’était de vérifier l’option active, le manifest HTTP, le transient WordPress, puis de remettre l’URL propre.

Ce genre de résolution rapide est possible parce que le système est assez observable.

Le parcours WooCommerce a changé de catégorie

Au début de la journée, on avait surtout un lancement signe. à la fin, on a une vraie boucle client.

Même onglet

Le lancement WooCommerce ne part plus dans un nouvel onglet.

Le bouton Creation navigue dans la même fenêtre vers Krampouz. L’utilisateur quitte visuellement la boutique, mais il ne perd pas son contexte navigateur. C’est beaucoup plus compréhensible.

On a volontairement écarte l’iframe en v1 :

  • cookies plus compliques ;
  • CSP et frame-ancestors ;
  • responsive fragile ;
  • dépendance trop forte au CMS ;
  • portabilite future moins bonne.

Le compromis retenu est simple : même onglet, top-level navigation, domaine Krampouz visible pendant l’édition. Pour une bêta, c’est le meilleur ratio simplicité / sécurité / expérience.

Retour boutique

L’éditeur affiche maintenant un bouton Retour, place pres de Sauvegarder, et le logo/nom peut aussi ramener vers la boutique.

C’est un petit détail, mais il change la sensation de sécurité. L’utilisateur sait qu’il peut revenir. Il n’est plus “avale” par l’éditeur.

Reprise des projets

Le gros manque était la persistance cote client.

Avant : je cree un projet, je reviens sur ooblik.com, je relance Creation, je repars a zéro. Frustrant, donc dangereux.

Maintenant :

  • Krampouz expose des endpoints Woo serveur-a-serveur pour les projets client ;
  • WordPress affiche Mon compte > Projets ;
  • le client voit ses brouillons ;
  • Modifier relance l’éditeur sur le même projet ;
  • Dupliquer cree une copie ;
  • Supprimer archive/supprime prudemment selon les verrous production ;
  • l’éditeur a aussi son menu Projets.

La décision importante : WordPress ne reçoit jamais le gros pages_data. Il reçoit seulement des métadonnées : nom, produit, format, pages, quantité, dates, vignette. C’est bon pour la sécurité, bon pour les performances, et bon pour les milliers de clients a venir.

Vignettes

Le premier affichage était fonctionnel mais un peu triste : des rectangles “Aperçu”.

On a donc ajoute une vignette projet :

  • capture légère du canvas pendant la sauvegarde ;
  • stockage cote Krampouz dans le bucket applicatif ;
  • clé stable en base (thumbnail_key) ;
  • URL publique signée et courte generee à la lecture ;
  • retour via thumbnail_url dans les listes de projets.

Le plugin n’a pas eu besoin d’une grosse modification pour ça : il savait déjà afficher une image si thumbnail_url existait. C’est l’API Krampouz qui devait enfin la fournir.

Confirmation de suppression

Dernier frottement du jour : supprimer un projet sans confirmation était trop brutal.

Le plugin passe donc en 0.1.7 avec une modale de confirmation dans Mon compte > Projets.

Le point important : la modale améliore l’UX, mais ne remplace pas la sécurité. La suppression reste une action formulaire WordPress protégée par nonce, puis vérifiée cote API par tenant, credential, client et ownership.

Sécurité : ce qui tient maintenant

La journée a aussi montré que le chantier auth n’était pas seulement théorique.

Pièces en place :

  • sessions serveur ;
  • cookies HttpOnly ;
  • CSRF pour mutations cookie ;
  • compat Bearer temporaire ;
  • credentials Woo serveur-a-serveur ;
  • secrets jamais exposes au JavaScript WordPress ;
  • return_url allowlistee ;
  • tokens launch one-shot ;
  • expiration courte ;
  • hash des tokens en base ;
  • séparation claire entre client Woo et compte Krampouz ;
  • suppression projet vérifiée cote backend.

Le plus rassurant : les corrections UX n’ont pas contourne ces garde-fous. Le même onglet n’a pas cassé l’auth. Le bouton retour n’a pas cassé la session. La reprise projet n’a pas expose le JSON éditeur a WordPress. La vignette ne stocke pas une URL signée expirante en base.

C’est exactement le genre de détail qui compte avant une bêta.

Humeur

Il y à une joie particulière dans cette journée, parce qu’elle corrige une vieille fatigue.

Pendant longtemps, l’intégration web-to-print a été un territoire ou tout semblait lourd : plugins approximatifs, allers-retours lents, dépendances opaques, semaines d’attente pour obtenir une expérience encore fragile.

Aujourd’hui, le contraste est brutal.

On n’a pas seulement empile des tickets. On a transformé une conversation produit en architecture, puis l’architecture en code, puis le code en test live, puis le test live en correction UX, dans la même journée.

Ce n’est pas parce que l’IA “sait tout faire”. Elle ne sait rien faire correctement si le projet n’a pas de nord.

Ce qui fonctionne ici, c’est le trio :

  • un produit qui devient clair ;
  • une codebase qui accepte les extensions sans casser ;
  • une documentation qui garde la mémoire de ce qu’on a décidé.

Le résultat donne parfois une impression de vitesse presque indecente. Mais ce n’est pas une accélération gratuite. C’est le rendement d’un terrain prépare.

Ce que ça dit de la suite

La suite logique n’est pas de partir dans tous les sens.

Priorités probables :

  1. tester encore le flux client Creation -> edition -> retour -> Mon compte > Projets -> reprise ;
  2. observer les vignettes sur plusieurs vrais projets ;
  3. nettoyer l’UX de l’espace projets si besoin ;
  4. renforcer le dashboard plugin Editor pour produits/options/formats ;
  5. seulement ensuite rouvrir Google Photos.

Google Photos reste important. Mais aujourd’hui a confirme une chose : avant d’importer encore plus d’images, il faut que le client retrouve déjà parfaitement ce qu’il a créé.

État de clôture

État fonctionnel :

  • lancement WooCommerce en même onglet valide ;
  • retour boutique visible dans l’éditeur ;
  • autosave après lancement Woo stabilise ;
  • reprise projet client disponible cote WordPress et cote éditeur ;
  • duplication et suppression disponibles ;
  • confirmation avant suppression ajoutée ;
  • vignettes projets generees et servies par Krampouz ;
  • plugin update prive opérationnel.

Risques a surveiller :

  • les anciens projets sans nouvelle sauvegarde peuvent rester sans vignette jusqu’a leur prochaine modification ;
  • la suppression doit rester prudente dès que commande, PDF ou production entrent en jeu ;
  • l’UX mobile de Mon compte > Projets devra être testée sur vrai téléphone ;
  • le nom public du produit reste ouvert.

Ce soir, la bêta a gagné quelque chose de plus important qu’une feature : elle a gagné une continuité.

Le client ne tombe plus dans un éditeur isole. Il entre, travaille, revient, retrouve, reprend. C’est exactement le genre de boucle qui donne confiance.
