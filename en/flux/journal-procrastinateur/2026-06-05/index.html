Today’s feed

The thread remains the same as the one that appeared yesterday:

WooCommerce -> KEREDIT -> GOF -> Accurio Flux -> atelier

But today, this thread has started to carry some weight.

KEREDIT has learnt to automatically push data to GOF from completed orders. GOF has learnt to render assets and fonts more effectively, to synchronise KEREDIT’s Google Fonts, to display validation errors, to allow an operator to override certain warnings, and then to prepare for automatic submission to Accurio.

Accurio is no longer just a ‘future connector’. It is beginning to impose its exact constraints:

  • mandatory quantities;
  • available runtime in the GOF worker;
  • readiness prior to auto-submit;
  • distinction between operator warnings and hard blocks;
  • PDFs and assets accessible from the correct location;
  • fonts consistent with what KEREDIT sold to the client.

So the day didn’t just add features. It turned intentions into operational realities.

KEREDIT is pushing towards GOF

The first milestone on the KEREDIT side is clear: 1545705 automates GOF dispatch from completed orders.

This is a significant change, because it moves GOF from being a “tool that can be called” to being a “natural part of the order workflow”.

The commit adds:

  • an automatic dispatch option in the GOF configuration;
  • an associated Prisma field;
  • the PDF worker-side call;
  • worker tests;
  • a section in the PDF back office.

In short: when the order reaches the correct status, KEREDIT can prepare the GOF stage without waiting for any further manual intervention.

This is not yet a promise of zero supervision. It’s better than that: it’s a promise of a ‘workshop-first’ approach. The system proceeds automatically whenever possible, but the checkpoints remain visible.

GOF is learning to operate like KEREDIT

On the GOF side, it’s been a very busy day.

The commit b73afac fixes the PDF rendering of assets and fonts. This isn’t just a cosmetic change. If GOF is to become the PDF engine, it must reproduce exactly what the publisher displayed, not produce a vaguely similar interpretation.

The commit f55efb2 then adds synchronisation of KEREDIT’s Google Fonts within GOF. This is exactly the sort of detail that reveals the true contract:

  • the client selects a font from KEREDIT;
  • KEREDIT persists this choice;
  • GOF must be able to resolve it locally;
  • the PDF must remain consistent;
  • Accurio must not discover a font substitution at the last minute.

The GOF dashboard has also become more sophisticated:

  • details of rendering events;
  • print validation blocks;
  • progress whilst a job is open;
  • selection and deletion of jobs;
  • a better-integrated jobs panel;
  • a cleaner sidebar.

GOF is becoming less of a hidden API and more of a proper operator console.

Accurio is establishing its own terminology

Today’s work on Accurio was very practical.

The GOF commit 44dc9d9 converts the imposition quantities for Accurio orders. On the KEREDIT side, e9fa741 adds the corresponding mappings to the exports and the admin panel.

This is an important point: printer quantities are not always the same as gross commercial quantities. The print shop sells an order, but production may be subject to imposition, batch, sheet or service logic.

The system has now therefore started to account for this difference rather than hiding it.

The latest GOF commits (3e2e126, b72a19f) also enhance Accurio readiness. Auto-submit must not be a dangerous toggle. The runtime must be available in the worker, and the minimum conditions must be met before anything is sent.

This is the right approach: automate, yes; send blindly, no.

Deployment is also becoming a product development focus

KEREDIT has also made progress on the deployment pipeline.

The morning commits pave the way for GHCR:

  • modernised GitHub Actions runtime;
  • beta deployment pipeline set up;
  • dev images published from CI;
  • workflow token for GHCR pull requests;
  • normalised proxy host health.

15d003c then adds a more robust safeguard: the security of business data during deployment.

The deployment script now takes a snapshot of the business data before and after, and rejects any unexpected changes unless there is explicit opt-in. This is exactly the sort of protection that matters when you start handling orders, products, mappings and production flows.

Deployment is no longer just about “restarting containers”. It becomes a contract of trust.

A fire in production: the photos disappear

The end of the day was a bit of a fire-fighting session.

In the live editor, the photos were no longer appearing. The console was displaying a continuous loop of ‘403’ messages:

/api/assets/public/.../thumbnail
/api/assets/public/.../preview
/api/assets/public/.../original

The diagnosis was quite clear: the signed URLs for the assets had expired, but the Photos panel was holding onto the old URLs for too long. It wasn’t a missing image, nor a grid rendering issue. It was a lifecycle contract.

The fix 9b261a1 adds a front-end helper that reads the expires from the URLs /api/assets/public/..., then schedules a silent refresh before they expire. It also refreshes when focus is regained if the URLs are already too close to expiry.

The version was updated from 0.6.65 to 0.6.66, then urgently deployed to the VPS via the manual path from local to VPS.

Post-deployment verification:

  • .deploy-sha VPS: 9b261a19f1db950d81d292eba66bbba7b464a178;
  • VPS packages: 0.6.66;
  • Public API health OK;
  • Public frontend OK;
  • Public bundle served via 0.6.66;
  • script smoke checks OK.

Important point: the fix is narrow in scope. It does not arbitrarily extend the lifetime of signed URLs. It adheres to the security model and corrects the client-side refresh.

Addendum – The fixes that followed

The first fix for photos resolved the issue of images disappearing in the editor, but live testing immediately revealed a second, more subtle problem: the Google Photos import.

In the console, the following call returned an error:

/api/google-photos/picker-sessions -> 401

At first glance, this looked like a lost KEREDIT session. In reality, the VPS logs told a different story: immediately after this `401`, `/api/auth/me` responded with `200`. The client was therefore still connected to KEREDIT.

The problem lay in our error handling logic: when Google Photos could no longer be reconnected properly, or when the Google token had expired or been revoked, the route /picker-sessions would return 401. This status triggered both a mental and technical misdiagnosis. We assumed there was an invalid KEREDIT session, whereas the real issue was the Google Photos connection.

The commit 7dda00c corrected this behaviour:

  • the KEREDIT session remains distinct from the Google login;
  • an expired or rejected Google Photos token now returns `409`;
  • the message is now actionable: Google Photos must be reconnected;
  • this scenario is covered by an integration test.

Then, one final UX pitfall emerged. The modal displayed the message correctly, but it only offered Réessayer. For a user, this creates an absurd loop: they click, the Picker call restarts, Google Photos responds again with 409, and nothing progresses.

The commit 805fbf0 therefore changed the screen:

  • in the event of 409, the modal displays a main ‘Reconnect Google Photos’ button;
  • this button clears the old Google link on the KEREDIT side;
  • it opens the Google OAuth flow directly;
  • the customer no longer needs to realise that they first had to click ‘Déconnecter’, return to the previous screen, and then reconnect.

These two fixes have been deployed to the VPS as a hotfix in the same version as 0.6.66.

The final SHA verified following these changes is:

805fbf0edd4f54d70de0fef80504a85a861c842a

In between, the f365618 commit also closed a number of clean-up follow-ups: documented structural debt, completed clean-up audit, PDF/email/script adjustments, and updated tracking documentation. This wasn’t the most visible work from the client’s perspective, but it forms part of the same effort: keeping the project readable whilst production demands rapid fixes.

Cleaning up whilst things are heating up

The day wasn’t all about workflows and incidents.

1162f44 It also involved a comprehensive clean-up review and the removal of dead code from the toolbar. It’s easy to underestimate this on a day like this, but it’s important.

When GOF, Accurio, WooCommerce, webhooks and deployment are all changing at the same time, there’s a risk of letting dead code accumulate. The audit and documentation clean-up kept the map clear:

It’s not spectacular, but it’s what stops you from losing the thread when production starts pulling on all the strings.

What’s holding up tonight

Tonight, several things are holding up better than yesterday.

KEREDIT can now automatically push to GOF from completed jobs. GOF renders assets and fonts better. KEREDIT fonts can be synchronised in GOF. Print warnings are now visible and can be managed by an operator. Accurio receives a model that better aligns with its constraints, particularly regarding imposed quantities. The deployment is better protected against unexpected changes to business data.

And above all, the KEREDIT VPS has weathered a genuine production incident with a quick fix that was tested and deployed properly.

The system is not trouble-free, but it is more robust.

What remains fragile

Vulnerability remains throughout the entire workflow.

We now have many components capable of functioning:

  • WooCommerce can notify KEREDIT;
  • KEREDIT can maintain context and dispatch;
  • GOF can render, validate and prepare Accurio;
  • Accurio can receive a structured command;
  • the VPS can be redeployed with safeguards in place.

However, a workflow is only validated if it runs end-to-end with a real order and a deliberately simple product.

Areas to monitor:

  • exact consistency between the KEREDIT sales quantity and the quantity set in Accurio;
  • public or LAN availability of PDFs from Accurio’s perspective;
  • effective font resolution on the GOF machine;
  • distinction between a ‘forceable warning’ and a ‘hard block’;
  • status of the GOF job after auto-submit;
  • behaviour of the editor after long open sessions, now that the signed URLs have been refreshed.

It’s been a tough day because it affected the entire chain. But that’s also what makes it worthwhile: KEREDIT is no longer just a web-to-print editor. It’s starting to become a workshop system linked to production.
