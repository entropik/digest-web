Day 78 – Lock down the beta before scaling up

Re-establishment of publisher connections, tightening of WooCommerce security, public beta audit and strict enforcement of the PDF contract between KEREDIT and GOF.

Session timetable

  • System used: Codex
  • Date: Monday 8 June 2026.
  • Environments: Krampouz/KEREDIT at dépôt local krampouz, GOF at dépôt local gof, KEREDIT VPS.
  • KEREDIT branch: dev.
  • End-of-day KEREDIT SHA: 6eeb30a.
  • End-of-day KEREDIT version: 0.6.78.
  • GOF SHA observed at the end of the day: 6c9ffd7.
  • KEREDIT commit amplitude: 08:59 -> 17:49.
  • GOF commit amplitude: 10:36 -> 18:15.
  • Minimum cumulative time since the start of the log: approximately 427h14+.

Brief conclusion

8 June marked the milestone for the ‘friends and family’ beta. The day was not about opening things up widely. Rather, it tightened the security measures: more recoverable publisher access, a more robust splash screen, a protected WooCommerce webhook, a written security audit, and, above all, a much stricter PDF contract between KEREDIT and GOF.

The practical conclusion is a cautious one: the beta can move forward, but not whilst leaving grey areas in order flows, webhooks or PDFs.

The editor login must allow users to log back in

The morning begins with ‘2b719d8’: the editor’s launch screen must allow users to log in again. This point stems from a very real scenario: a user might arrive from WooCommerce, have an expired session, or encounter an intermediate state during launch.

The previous behaviour could leave the user facing a splash screen that simply waits, with no clear course of action. The fix adds a cleaner exit:

  • the splash screen now distinguishes more clearly between waiting, error and re-login;
  • ProtectedRoute and the application bootstrap works more seamlessly;
  • the wording avoids mentioning unnecessary technical details;
  • the package versions are aligned for deployment.

Reference commit: 2b719d8 (fix: allow reconnect from editor launch splash).

Splash: making recovery more robust, not just improving the appearance

The commit f99b27e continues this work with a more comprehensive hardening of recovery. The application receives a proper RouteErrorBoundary, the bootstrap becomes more explicit, and the launch store better preserves the state required to handle errors.

This is a trust-building fix: a beta version cannot expect a user to understand whether a frozen screen is caused by a session, a frontend chunk, a route, or a WooCommerce launch. It must offer a simple action: reload, log in again, or resume.

Security: the WooCommerce webhook must not be public

The commit 48f5f1d is today’s most visible security measure: the WooCommerce webhook now requires a key. This is no minor detail. A webhook route that accepts order events must be authenticated, even in a closed beta.

The fix:

  • removes the dangerous default resolution on the credentials side;
  • enforces a webhook key at the endpoint;
  • adds integration tests;
  • documents the behaviour in the plugin guide;
  • writes the ‘docs/audits/2026-06-08-audit-securite-beta-publique.md’ audit.

The message is simple: testing can be carried out with a small number of clients, but public endpoints must not be left open simply for convenience.

Reference commit: 48f5f1d (fix(security): require WooCommerce webhook key).

PDF text: the contract becomes stricter

The biggest technical task of the day is still the text. 7 June established the contract; 8 June made it stricter.

KEREDIT first added c23432a, a clearer documentation of the KEREDIT-GOF text contract. Then d4616fb locks this contract on the backend:

  • stricter page validation;
  • text field diagnostics;
  • enriched export payload;
  • updated JSON project schema;
  • tests on the validator and the payload.

Nextaa22062, issues a strict text layout contract in the PDF export. shared/src/utils/richText.ts sets out the standardisation more clearly, and the rich text tests cover cases that should no longer depend on local interpretations.

Finally, 6eeb30a explicitly declares the PDF font synthesis policy. This is a subtle but important point: if the system synthesises italics or bold text due to the lack of an exact variant, this must be a decision visible in the contract, not a hidden behaviour of the rendering engine.

Reference commits:

  • c23432a (docs: verrouiller le contrat texte KEREDIT GOF) ;
  • d4616fb (fix(pdf): verrouille le contrat texte GOF) ;
  • aa22062 (fix: emit strict PDF text layout contract) ;
  • 6eeb30a (fix: declare PDF font synthesis policy).

GOF: from glyph to regression guardrail

GOF is progressing at the same pace:

  • b0b16ca corrects the deterministic rendering of ligatures;
  • ebfdfcc fixes text shaping at the glyph level;
  • 0df3422 adds text contraction diagnostics;
  • 526e221 displays the bleed guide in the PDF preview;
  • f6688c3 and dd778fc adds PDF download and command-linked filenames;
  • f9e49c1 applies the KEREDIT text layout contract;
  • c98d3f4 synthesises italics for exact variants;
  • 2de371b maintains the compact line height of rich text;
  • 4d9d48b includes the renderer version in job reuse;
  • 6c9ffd7 documents PDF regression safeguards.

It is no longer simply a matter of ‘creating a PDF’. It is about making the PDF inspectable, downloadable, versioned, and sufficiently deterministic to enable comparison between the screen preview and the final output.

The 8 June beta becomes a controlled launch

The production notes already stated that 8 June was to remain a limited release for selected clients, not a wide-scale launch. Today’s work confirms this approach.

What has been reinforced:

  • a more reliable editor launch;
  • a secure WooCommerce webhook;
  • written beta security audit;
  • PDF contract text documented and tested;
  • GOF better equipped to diagnose rendering discrepancies;
  • 0.6.78 of the advanced KEREDIT version.

What has not yet been given the all-clear:

  • each Woo -> editor -> basket path must continue to be tested in a real product context;
  • projects opened outside the product sheet may exist, but must not be confused with orderable projects;
  • PDFs must continue to be compared using realistic text examples;
  • customer messages must remain understandable without technical jargon.

What is solid this evening

  • KEREDIT ends the day at 6eeb30a, version 0.6.78.
  • The WooCommerce webhook is protected by a key.
  • The public beta security audit of 8 June has been documented.
  • The editor launch splash screen now displays cleaner output.
  • The PDF text contract is more rigorous, documented and shared.
  • GOF adds diagnostics, bleed previews, PDF downloads and regression safeguards.

What remains to be monitored

The danger is no longer just the obvious bug. It lies in the intermediate states: an expired session, a project resumed from ‘My Projects’, a PDF file reused when the renderer has changed, the exact font missing, or a misconfigured webhook. Today’s session has reduced these grey areas, but it also shows that the beta still requires ongoing support.

The right approach remains: few clients, real-world workflows, and careful verification of the transitions between WooCommerce, KEREDIT, GOF and the workshop.
