Lecture globale

La journée n’a pas ressemble à une progression linéaire. Elle a surtout mis en évidence un problème devenu coûteux : plusieurs comportements de l’éditeur étaient bien corrigés localement, mais pas encore assez fixes comme contrats vérifiables.

Le symptôme visible est brutal : on corrige un drag, puis on découvre que la sélection casse ; on stabilise la double page, puis le panneau Calques ne regarde pas les mêmes pages que le canvas ; on durcit le contrat photo-block, puis une formulation trop large supprime la croix centrale qui sert justement a déplacer la photo dans son cadre.

Le bilan n’est donc pas seulement “il y a eu des bugs”. Le vrai bilan est plus dur : une partie du temps a été perdue parce que les contrats produit étaient encore trop implicites, ou documentes sans être exécutables.

Régressions et mauvais decouplages

Les régressions observées tournent autour du même noyau : le canvas éditeur porte plusieurs vérités simultanees.

  • une page courante ;
  • une vue double page pour les livres ;
  • une page propriétaire persistante pour chaque élément ;
  • une géométrie de cadre x/y/width/height/rotation ;
  • une géométrie interne photo imageOffset, crop, zoom, anchor ;
  • des overlays Fabric / DOM ;
  • des panneaux qui agissent sur les mêmes éléments depuis une autre surface UI.

Tant que ces contrats restent implicites, une correction locale peut casser une surface voisine sans que le build proteste.

Le cas du panneau Calques l’a rendu clair. Le canvas affichait bien les deux pages d’un spread, mais le panneau lisait encore seulement pages[currentPageIndex]. La correction récente qui evitait de changer brutalement currentPageIndex lors d’un clic gauche/droite dans le spread a fait apparaître ce vieux decouplage : le canvas voyait deux pages, les calques une seule.

Le contrat retenu est maintenant explicite :

  • le panneau Calques résout les pages visibles comme le canvas ;
  • il liste les éléments des deux pages propriétaires visibles ;
  • chaque action retrouve la page propriétaire réelle ;
  • update, delete, duplicate et reorder ne visent plus implicitement currentPageIndex ;
  • le z-index reste local à chaque page, sans pile globale artificielle entre gauche et droite.

Photo-block : la nuance qui a coûte trop cher

Le contrat photo-block a aussi été clarifié, mais non sans erreur.

La séparation correcte est :

drag normal hors poignee explicite -> deplacer le bloc photo
croix centrale / poignee pan       -> deplacer la photo dans le bloc

Le mauvais durcissement a consisté à protéger le drag du bloc en supprimant la croix centrale par défaut. C’était trop large et contraire à l’UX validée : la croix centrale doit rester visible quand une photo existe. Ce qu’il faut interdire, ce n’est pas la croix ; c’est que toute la surface centrale devienne implicitement du pan interne.

Le contrat corrige dit donc :

  • la croix centrale reste visible par défaut ;
  • elle est l’entrée explicite pour déplacer la photo dans le bloc ;
  • hors de cette poignée, le drag naturel déplacé le cadre ;
  • un geste ne doit pas persister à la fois x/y et imageOffsetX/Y sans raison documentée.

Cette nuance est importante parce qu’elle montre le type d’erreur à éviter : un contrat trop strict mais mal formule peut devenir lui-même une régression.

Documentation vivante, pas documentation décorative

La même journée a continue la transformation de la documentation vers un modèle LLM Wiki / OKF : index, log, pages actives, normes de contrat et chemins de vérification.

L’objectif n’est pas d’ajouter des pages pour se rassurer. L’objectif est que la documentation devienne une mémoire exploitable par l’agent :

  • quelle page lire avant de toucher un module ;
  • quel contrat exact est actif ;
  • quels champs ont le droit de changer ;
  • quels tests doivent casser si le contrat saute ;
  • comment supprimer une norme devenue fausse sans laisser une vieille consigne contaminer les prochains correctifs.

Les pages de référence importantes du jour sont :

  • docs/architecture/fabric-element-contracts.md
  • docs/architecture/geometry-contract-v1.md
  • AGENTS.md
  • BIBLIOTHEQUE.md
  • docs/log.md

Le point clé : la doc seule ne suffit pas. Chaque fois que possible, le contrat a été déplacé vers un helper pur et un test cible.

Garde-fous ajoutes

Deux nouveaux garde-fous ciblent directement les régressions du soir.

frontend/src/lib/floatingLayers.ts isole le contrat du panneau Calques :

  • résolution des pages visibles ;
  • mapping élément -> page propriétaire ;
  • labels de page ;
  • tri par page visible puis z-index local ;
  • cible de déplacement de calque limitée à la page propriétaire.

frontend/tests/floatingLayers.test.ts verrouille ce comportement pour les spreads livre et garde le comportement page simple des autres produits.

frontend/src/lib/photoBlockInteractionContract.ts fixe le contrat minimal du mode photo-block :

  • croix centrale visible par défaut quand une photo existe ;
  • mode photo et mode mask contrôles explicitement ;
  • retour au mode block quand la sélection change ou disparaît.

frontend/tests/photoBlockInteractionContract.test.ts verrouille la nuance qui a provoque la régression nocturne.

Ce que cette session dit du projet

La fatigue de cette session vient moins du volume de code que de la nature des bugs. Ce sont des bugs de contrat : deux surfaces pensent parler du même objet, mais n’utilisent pas la même source de vérité ; deux gestes visuels se ressemblent, mais ne doivent pas écrire les mêmes champs ; une correction locale semble logique, mais elle efface un comportement utilisateur attendu.

Ce type de bug coûte cher parce qu’il force à redécouvrir les règles au cas par cas. La réponse correcte n’est pas de patcher plus vite. Elle est de transformer les contrats en objets maintenus :

contrat ecrit -> helper nomme -> test cible -> entree dans AGENTS/BIBLIOTHEQUE

La nuit a été pénible, et ce point doit rester dans le journal sans être adouci. La fatigue ne venait pas seulement de bugs complexes ; elle venait surtout de régressions en cascade provoquees par des correctifs trop locaux, trop peu relus contre les contrats existants, et pas assez vérifiés contre les gestes utilisateur déjà valides.

Le code a fini par revenir dans un état exploitable, mais le coût humain de la séquence est mauvais. Le client final n’a pas a subir ces régressions, et le porteur produit n’a pas a retester manuellement chaque comportement de base après chaque patch. C’est une dette de méthode, pas seulement une dette de code.

La fin de nuit a notamment expose une erreur de lecture local/VPS sur les vignettes du panneau Calques.

En local, les vignettes étaient visibles parce que les assets concernes étaient encore présents dans le store photos courant. Sur le VPS, le même panneau ne montrait pas les vignettes : les éléments étaient bien dans le projet et visibles sur le canvas, mais leurs assets n’étaient pas forcément charges dans useAssetStore.assets.

La correction 0.9.37 était insuffisante : elle ajoutait une logique de fallback, mais seulement pour les assets déjà présents dans le store. La correction 0.9.38 fixe le vrai contrat :

  • le panneau Calques part de l’assetId porte par l’élément du projet ;
  • s’il ne trouve pas l’asset dans le store courant, il résout l’URL via /api/assets/:id/url ;
  • il cache cette résolution localement pour le panneau ;
  • il utilise l’ordre de fallback thumbnail -> preview -> display -> original ;
  • il ne force pas la grille Photos a charger plus large que son besoin.

Ce point est documenté dans docs/architecture/fabric-element-contracts.md, AGENTS.md, BIBLIOTHEQUE.md et docs/log.md.

Ce qui doit changer dans la méthode

La leçon opérationnelle est dure mais simple : un patch de surface UI ne peut plus être considère termine s’il ne liste pas les surfaces voisines qui manipulent le même contrat.

Pour les prochains chantiers editor, la boucle minimale doit être :

  1. identifier le contrat produit touche ;
  2. lister les surfaces qui l’utilisent ;
  3. modifier le helper ou la source de vérité commune quand elle existe ;
  4. ajouter ou renforcer un test cible ;
  5. vérifier au moins un scénario manuel représentatif si l’interaction est Fabric/DOM ;
  6. documenter l’écart si la régression révèle une règle implicite.

Autrement dit : moins de patchs de panique, plus de contrats vérifiés.
