The actual flow emerges

The crux of the day can be summed up in a single line:

WooCommerce -> KEREDIT -> GOF -> Accurio Flux -> atelier

Up to this point, each segment already had substance.

KEREDIT was able to receive a project, maintain client context, expose a back-office system, and send a job to a PDF renderer. GOF was able to act as the local renderer, generate artefacts, and keep a production log. Accurio was the industrial ecosystem we needed to integrate with, with its API, catalogue, printers, services and network constraints.

Today, the task has been to pass real data across these boundaries.

This isn’t just a minor UI tweak. It’s a fundamental shift: we’re no longer just testing an editor; we’re testing a production line.

Accurio is part of the contract

The first KEREDIT project of the day extended the GOF export payload for Accurio.

The payload no longer simply states “here is a project to be delivered”. It now carries the expected production details:

  • client context;
  • order context;
  • Accurio product name;
  • target printer;
  • order prefix;
  • delivery type;
  • Accurio services selected from the KEREDIT options.

On the GOF side, the commit 729c4ba added the Accurio production connector. The workflow in GOF establishes an important rule: Accurio receives a document POST /api/createOrder that is already compliant. For this workflow, no Accurio transformation script should become the central workaround.

This is precisely the right approach to accountability:

  • KEREDIT remains the business authority: customer, order, product sold, options, mapping.
  • GOF prepares the PDF, keeps it available and submits the order.
  • Accurio manages production and printing.

The difficulty arises when words need to be translated into precise terms: Accurio product, Accurio printer, Accurio services, PDF URL accessible from the Accurio server.

GOF becomes configurable

GOF has evolved significantly today.

The forge is no longer just a local app with a PDF pipeline. It now features a usable configuration interface:

  • Accurio connector;
  • client configuration UI;
  • session-based back-office login instead of plain browser authentication;
  • built-in configuration help;
  • customer documentation;
  • simplification of the KEREDIT synchronisation process;
  • clean removal of old automatic API tokens;
  • full reading of the Accurio catalogue from GOF;
  • API errors returned in a readable format.

The GOF documentation produced today also sends an important signal:

  • docs/flux-keredit-gof-accurio.md sets out the technical specifications;
  • docs/procedure-client-configuration-keredit-gof-accurio.md provides a non-technical customer procedure;
  • docs/architecture-gof-memo-2026-06-04.html and .pdf set out the architectural intent;
  • docs/operations-gof.md whilst docs/backoffice-gof.md handle the operational side.

GOF therefore assumes its role as a workshop: not a hidden library, but a configured, visible, testable local machine, with an operator at the centre.

KEREDIT is learning to connect to GOF

On the KEREDIT side, the back-office GOF Flux has become much more tangible.

Two migrations have been added:

  • 20260604113000_add_gof_integration_config ;
  • 20260604124500_add_gof_pairing_code.

These allow the GOF configuration to be stored, followed by a temporary login code. The principle is simple for the client:

  1. KEREDIT generates a login code.
  2. GOF receives this code on its configuration screen.
  3. GOF creates a technical token.
  4. GOF sends this token to KEREDIT.
  5. KEREDIT stores it in encrypted form and tests the connection.

This is much better than a field saying “paste a secret token somewhere”, because the customer’s action becomes clear: connecting two tools, not handling a technical key.

The KEREDIT back office also displays the connection status, GOF tests and the Accurio catalogue read status more clearly.

A policy issue was rectified this afternoon: KEREDIT must not read the Accurio catalogue directly. The Accurio catalogue is read by GOF, because GOF is installed in the workshop and can connect to the Accurio Flux server. KEREDIT then utilises this data via GOF.

This detail may seem minor, but it prevents an unstable architecture. Accurio belongs to the workshop network, not the KEREDIT VPS.

WooCommerce closes the loop

By the end of the day, WooCommerce had been brought back into the loop.

This isn’t a separate issue. The GOF/Accurio workflow requires both the order context and the customer context. Without these, the production team receives a PDF, but not enough business logic to process it.

The end-of-day commits therefore dealt with:

  • the preferred Woo customer context for GOF exports;
  • reusing the WooCommerce cart lock for updates from the editor;
  • the automation of the WooCommerce webhook configuration;
  • checkout repair via the admin panel.

We can see the same logic here as with GOF: real-world testing reveals hidden contracts. An editor project does not exist in isolation. It must remain consistent with the shopping basket, the order, the webhooks and the client identity.

Bugs aren’t just noise

The quote of the day could be: “I’m uncovering issues everywhere whilst testing”.

Yes. And that’s probably a good sign, even if it’s tiring.

Problems crop up everywhere because testing now crosses the system’s boundaries:

  • browser/back-office boundary;
  • the KEREDIT/GOF boundary;
  • the VPS/development machine boundary;
  • public URL / LAN URL boundary;
  • readable token / encrypted technical token boundary;
  • Accurio catalogue / KEREDIT product mapping boundary;
  • publisher project / WooCommerce order boundary;
  • boundary between generated PDF and printable order.

As long as each component was tested in isolation, these issues remained hidden. Live testing brings them to light. This is not a single regression with a simple cause. It is the gradual discovery of the true production contract.

The correct response, therefore, is not to reopen everything. It is to turn every surprise into a contract:

  • who is the authority for this data?
  • Who is authorised to call which service?
  • Which URL must be accessible from which machine?
  • Which status should be visible to the customer or the operator?
  • Which error should halt the flow rather than giving the impression that everything is fine?

What’s already in place

Tonight, there are some solid foundations.

KEREDIT and GOF are both on dev, clean, up to date, with a consistent commit history. The KEREDIT versions have been realigned to 0.6.61. The back office now has a proper start to its interface at GOF Flux. Code pairing provides a more robust customer experience. GOF reads Accurio from the correct location. Client and operator documentation is in place. WooCommerce continues to move closer to the production environment.

Most importantly: the architecture has retained the correct distribution.

KEREDIT is not becoming a remote Accurio machine. GOF does not read KEREDIT’s internal tables as the primary contract. Accurio is not becoming the place where KEREDIT data is corrected. Each tool is starting to find its place.

What remains fragile

The vulnerability does not yet lie in a single file. It lies in the entire workflow.

We still need to calmly test a minimal workflow:

  1. Check that the KEREDIT VPS is indeed serving the expected SHA before any live testing.
  2. Open GOF and validate its Accurio configuration.
  3. From the Accurio server, check that the GOF URL for the PDFs is accessible.
  4. Connect KEREDIT to GOF using a temporary code.
  5. Test GOF from KEREDIT.
  6. Read the Accurio catalogue via GOF.
  7. Map a single KEREDIT product to a single Accurio product.
  8. Send a known project to GOF.
  9. Check the PDF in GOF.
  10. Send to Accurio.
  11. Note down each error along with its exact boundaries.

This walkthrough must remain concise. One product, one order, one PDF, one printer. Not the whole shop, not all formats, not all business scenarios.

What this tells us about the beta

The postcard beta is no longer just about a nice-looking, stable editor.

It’s becoming a matter of workshop trust:

  • can the customer place an order?
  • Does KEREDIT retain the correct context?
  • Does GOF produce a controllable artefact?
  • Does Accurio receive a usable job?
  • Does the operator know where to look when something breaks?

It was an impressive day because it brought this level of detail to light.

There are still lots of moving parts, but they’re starting to form a chain. It’s not comfortable, but it’s more realistic than reassuring. And for a workshop-first project, this is probably the right step.

Back to work tomorrow

Tomorrow, don’t try to ‘test everything’.

Aim to test a single story from start to finish:

un produit postcard -> une commande Woo -> un projet KEREDIT -> un job GOF -> un PDF contrôle -> un envoi Accurio

If this story works, even with some tweaks, today’s work will take on a new significance: it will no longer be an overwhelming jumble, but the moment when the pieces began to come together as a flow.
