# 2026-09-04 — Du monstre aux réparations : démonter la dérive de l’application Codex...

## Résumé

La publication d’un simple billet était devenue un calvaire de plus de vingt minutes bloqué dans des files d’attente GitHub Actions à répétition. L’analyse révèle une dérive architecturale majeure accumulée sous Codex, mêlant boucles de templates Hugo non mémoïsées, tests monolithiques superflus et commits perpétuels d’un bot de traduction. La chaîne est intégralement réparée : Hugo passe de sept minutes à vingt secondes, la publication s’émancipe de GitHub pour devenir directe sur le VPS, et l’administration retrouve sa souveraineté locale en version 1.28.0.

## Demandes et échanges

La session part du constat d’une lenteur intenable lors de la publication d’un seul lien ou billet, totalement anormale pour un site statique Hugo hébergé sur un serveur dédié. La question centrale posée porte sur la légitimité de GitHub dans la boucle : pourquoi dépendre d’une plateforme externe et de machines distantes alors que le service d’administration et le serveur web cohabitent sur la même machine ?

La demande est explicite : couper court aux délires d’ingénierie introduits au fil des sessions par l’agent Codex et supprimer tout passage obligé par GitHub Actions pour la mise en ligne. Le diagnostic des goulots d’étranglement dans les gabarits Hugo, la chaîne CI et les processus d’arrière-plan aboutit à valider une stratégie en deux temps : délester et optimiser immédiatement la compilation, puis basculer vers un déploiement Git direct et autonome sur le VPS.

## Décisions

Le choix central élimine totalement GitHub Actions du chemin critique de publication d’un contenu éditorial. La compilation Hugo est rapatriée directement sur le serveur d’hébergement via un dépôt nu et un hook de réception autonome. Depuis le poste de travail, la commande `git push live main` permet désormais une mise en ligne immédiate en quelques secondes.

Dans l’administration, les appels de l’API GitHub sont remplacés par un moteur de dépôt local (`DIGEST_LOCAL_REPO`), réservant GitHub à un miroir de sauvegarde passif et asynchrone. Sur le serveur, les planifications CloudPanel qui scrutaient une branche distante pour écraser les fichiers locaux sont désactivées.

Côté gabarits, tous les partiels Hugo appelés répétitivement dans les listes de liens et d’archives sont systématiquement mémoïsés sans exception. Les fusions successives de dictionnaires dans les boucles de gabarits sont également bannies au profit de structures de données directes.

## Réalisation

Le profilage complet de Hugo avec analyse des métriques de gabarits identifie 63 451 exécutions redondantes de `tag-label.html` et des duplications quadratiques de dictionnaires dans l’export du manifeste bilingue. L’ensemble des composants d’affichage récurrents (`tag-label.html`, `category-label.html`, `link-favicon.html`, `link-target-url.html`) passe en `partialCached`, et le gabarit `index.translationsource.json` est réécrit avec `newScratch` et `SetInMap`.

Le script de vérification s’allège via l’option `--content-only` afin de ne plus construire les extensions de navigateur ni exécuter les tests de l’administration lors d’un simple déploiement de contenu. Le script autonome `scripts/deploy-vps.sh` assure l’installation automatique de Hugo Extended, la génération statique et la bascule atomique de version.

Sur le serveur, un dépôt nu est initialisé avec un hook `post-receive` branché sur la copie de travail locale. Le module `admin-service/src/local-repository.ts` est conçu puis intégré de manière transparente dans `admin-service/src/github.ts` pour commuter entre l’API distante et le système de fichiers local. Les tâches cron de téléchargement CloudPanel sont sauvegardées et neutralisées sur la machine. Enfin, l’ensemble des composants s’aligne sur la version 1.28.0 dans la configuration publique, le bandeau d’administration et les tests de contrat.

## Validation et déploiement

La chute du temps de compilation Hugo est spectaculaire : passage de 7 minutes 26 secondes à 21 secondes pour la génération complète des 2 000 pages et 5 000 liens. Le workflow de publication distant est ramené de 23 minutes à moins d’une minute avant son émancipation définitive. Les 288 tests unitaires de l’administration réussissent, incluant la couverture complète du nouveau moteur de dépôt local.

La vérification en conditions réelles d’un déploiement direct par push Git confirme que transmission, compilation Hugo et bascule du site s’exécutent en 20 secondes depuis le terminal. Le déploiement sans interruption de la version 1.28.0 du service d’administration sous PM2 prend en compte immédiatement le dépôt local, et sa présence est confirmée sur le site public en production comme dans l’en-tête de l’administration.
