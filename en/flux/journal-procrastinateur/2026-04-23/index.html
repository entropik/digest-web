Jour 40 — Arrêter les patches sur les blocs lies et poser enfin un noyau canonique

La journée n'a pas servi a ajouter une feature de plus, mais a arrêter une dérive : trop de patches locaux sur les blocs texte lies. Le vrai progrès est d'avoir formalise le contrat produit et commence la remise a plat autour d'un document canonique unique par chaîne.

Ce qui s’est passé vraiment

La journée est partie d’un constat assez usant mais finalement sain : le sujet des blocs texte lies n’était plus un “bug à corriger”, c’était un sous-système qui commençait a se contredire lui-même.

Les symptômes s’accumulaient :

  • texte duplique ou mal coupe après le + ;
  • style du bloc pollue par la première portion de texte ;
  • justification ou typographie qui partent pendant un resize ;
  • comportement incohérent après changement de format ;
  • bloc 2 qui peut se recouvrir ou repartir à un endroit non voulu ;
  • dérive générale des fragments de texte après plusieurs manipulations.

Le point important de la journée n’est donc pas d’avoir “encore patché un peu”. Au contraire, la vraie avancée a été d’accepter que le modèle courant n’était plus défendable tel quel, puis de remettre de l’ordre avant de continuer.

Les décisions produit explicites fixées aujourd’hui

La conversation du jour a surtout servi a sortir les attentes réelles du flou implicite. Ce contrat est beaucoup plus important que n’importe quel patch local :

  1. pendant le resize, le reflow doit être visible en live pour montrer ou le texte va couper ;
  2. l’action + cree un nouveau bloc à droite, même gabarit, avec un écart physique fixe ;
  3. si un bloc lie est supprimé, le texte doit revenir dans la chaîne d’origine sans changer la géométrie du bloc source ;
  4. le style appartient au texte, pas au bloc ;
  5. une nouvelle ligne ajoutée dans le bloc d’origine doit pousser le texte dans le bloc lie ;
  6. le changement de format ne doit pas recalculer automatiquement les blocs texte ;
  7. le système doit pouvoir aller vers 2, 3, X blocs et pas seulement un duo fragile.

La décision structurante du jour est celle-ci :

  • il faut une source de vérité unique par chaîne ;
  • le texte complet ne doit pas être “possède” par chaque bloc séparément ;
  • les blocs lies sont des cadres d’ecoulement, pas des propriétaires concurrents du contenu.

Autrement dit, on sort enfin d’un modèle “chaque bloc stocke son petit morceau et on réécrit tout à chaque interaction”.

Le vrai chantier technique du jour

Une fois le contrat clarifie, la journée a servi à lancer une remise a plat du noyau.

Le repo gagne d’abord un document de cadrage dédié :

  • docs/architecture/linked-text-contract.md

Ce document pose noir sur blanc :

  • la séparation entre contenu riche, style de bloc et géométrie ;
  • les invariants de conservation du texte ;
  • la matrice de validation edition / + / resize / suppression / changement de format ;
  • les pannes déjà observées ;
  • la direction technique cible.

Ensuite, le code commence à converger vers cette architecture :

  • shared/src/types/index.ts reçoit de nouvelles métadonnées de chaîne (linkedTextRootId, linkedTextCanonicalRichText, linkedTextRangeStart, linkedTextRangeEnd) ;
  • shared/src/utils/richText.ts gagne une primitive de remplacement de range dans un document riche ;
  • frontend/src/lib/textFrame.ts devient le centre du sujet avec la logique de document canonique, de redistribution des fragments, d’append de bloc, de reflow de chaîne et de suppression ;
  • frontend/src/components/text/TextFrameEditor.tsx est recable sur cette logique ;
  • frontend/src/components/canvas/EditorCanvas.tsx relance le reflow live depuis le document canonique ;
  • frontend/src/stores/editorStore.ts passe par la logique partagée pour la suppression d’un bloc lie.

La conséquence conceptuelle est nette :

  • le document canonique de la chaîne est conservé sur le bloc racine ;
  • les blocs visibles n’affichent que des fragments dérives ;
  • le +, l’édition, le resize et la suppression ne doivent plus se battre sur plusieurs “vérités” concurrentes.

Ce qui a été vérifié aujourd’hui

La journée ne s’est pas arretee au cadrage. Un test navigateur cible a aussi été monte sur l’extrait Lorem Ipsum utilise pendant la session.

Vérification outillée :

  • pnpm typecheck
  • pnpm --filter frontend lint
  • pnpm exec playwright test e2e/tmp-linked-text-debug.spec.ts --reporter=line

Le test ne prouve pas encore que tout le sujet est “termine”. En revanche il valide un point crucial :

  • avant le +, le store contient bien le texte complet ;
  • après le +, le document canonique conserve toujours le texte complet ;
  • les blocs visibles reçoivent des fragments cohérents dérives de ce document ;
  • on ne perd plus la vérité du texte au moment du split.

Ce point est essentiel parce qu’il change la nature du problème restant. On n’est plus en train de courir après un texte casse à la source. On est en train de fiabiliser la redistribution et le rendu autour d’une vérité déjà saine.

Fin de journée : Playwright MCP enfin opérationnel

La fin de journée a aussi servi a régler un point de méthode qui comptait pour la suite : rendre le debug navigateur plus direct dans Codex lui-même.

Le premier constat a été utile : l’échec du test Playwright de la session n’était pas un échec produit, mais un échec d’environnement. Le même test cible est passé hors sandbox, ce qui a permis d’isoler proprement le problème.

Ensuite, le poste a été configuré pour utiliser un vrai serveur Playwright MCP dans Codex. Le point bloquant n’était pas le repo Krampouz, mais le runtime navigateur cherche par défaut par le serveur MCP. Au lieu d’installer un Chrome système en force, la configuration a été recalée pour pointer vers le Chromium déjà présent dans le cache Playwright local.

Le résultat est concret : un test MCP a été mene directement sur l’éditeur local.

Vérification réelle en fin de journée :

  • ouverture du navigateur MCP ;
  • chargement de l’éditeur local ;
  • authentification locale par l’API puis injection du token ;
  • navigation vers le projet cmoa8r7070001pfvt229apbrh ;
  • lecture du store frontend et des blocs texte lies ;
  • lecture des erreurs console réelles de la page.

Le MCP a vu l’état attendu :

  • un bloc racine avec document canonique ;
  • un bloc lie dérive ;
  • linkedTextPrevId / linkedTextNextId cohérents ;
  • linkedTextRootId commun ;
  • un document canonique porte uniquement par le bloc racine.

Ce n’est pas juste un confort annexe. Pour les prochains retours sur le texte, cela change la vitesse de diagnostic :

  • on peut observer le DOM et le store dans la même session ;
  • on peut rejouer un + ou un resize sans écrire un test complet à chaque fois ;
  • on peut vérifier si un bug est géométrique, store, ou rendu.

Autrement dit, la journée se termine avec une meilleure base de debug qu’au départ : pas seulement un noyau linked-text plus propre, mais aussi un outil plus direct pour voir ce qu’il fait vraiment dans le navigateur.

Ce qui a été discute explicitement, et pourquoi c’est important

La valeur de la journée vient aussi de la discussion elle-même. Plusieurs remarques utilisateur ont poussé a sortir des demi-solutions :

  • “il faut coder proprement” ;
  • “on doit avoir un code solide et unifie, pas des patches a rallonge” ;
  • “le style est lié au texte, pas au bloc” ;
  • “le reflow doit être visible pendant le drag” ;
  • “le changement de format ne doit pas recalculer les blocs texte”.

Dit autrement : la conversation du jour a force une montée de niveau. Moins de bricolage local, plus de contrat, plus d’architecture explicite, plus de vérification outillée.

C’est une journée moins spectaculaire qu’une nouvelle feature visible, mais probablement plus importante pour la bêta. Sans cette clarification, le sujet texte aurait continue à absorber du temps sans jamais vraiment se calmer.

Point roadmap du soir

Le point roadmap ressort plus net ce soir :

  • le sujet bloc texte simple est mieux compris ;
  • le sujet blocs textes lies devient un chantier noyau a part entière ;
  • il ne faut pas rouvrir d’autres fronts texte avant d’avoir stabilise cette base.

La lecture du moment est donc :

  1. finir le noyau des blocs texte lies autour du document canonique ;
  2. valider proprement resize live, suppression, retour ligne, puis 3 blocs ou plus ;
  3. seulement ensuite reprendre les couches UX ou les autres sujets editoriaux adjacents.

Pour la roadmap bêta postcard, c’est un point de realisme utile : mieux vaut un système texte plus restreint mais cohérent qu’un pseudo-chaînage qui regresse à chaque correction.

Ce que la journée laisse ouvert

La journée ne clot pas le sujet. Elle le remet dans un cadre traitable.

Les prochains retests utiles sont maintenant très concrets :

  • resize live du bloc 1 avec styles mixtes ;
  • suppression du bloc 2 avec retour du texte ;
  • ajout de retours ligne dans le bloc d’origine ;
  • chaîne sur 3 blocs ou plus ;
  • ergonomie réelle d’entrée en édition.

Le gain du jour est simple : on ne repart plus demain d’un tas de patches contradictoires. On repart d’un contrat clair et d’un noyau qui commence enfin a ressembler à une architecture.
