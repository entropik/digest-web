Day 77 – The text becomes a production contract

Text stabilisation whilst zooming, rich text normalisation for PDFs, more secure WooCommerce duplication, and KEREDIT-GOF alignment with regard to typographic rendering.

Session timetable

  • Software used: Codex
  • Date: Sunday 7 June 2026.
  • Environments: Krampouz/KEREDIT at dépôt local krampouz, GOF at dépôt local gof.
  • KEREDIT branch: dev.
  • End-of-day KEREDIT SHA: be785d6.
  • End-of-day KEREDIT version: 0.6.75.
  • GOF SHA observed at the end of the day: c66e826.
  • KEREDIT commit amplitude: 10:10 -> 20:03.
  • GOF commit amplitude: 10:33 -> 20:15.
  • Minimum cumulative time since the start of the log: approximately 417h58+.

Brief conclusion

The day centred on a topic that may seem narrow but which affects the entire workflow: the text. As long as the publisher, the JSON project, the local PDF and GOF do not speak exactly the same typographical language, a postcard may look good on screen but turn out poorly in production.

So, on 7 June, the text moved from being an editor’s representation to a production contract. Rich text becomes the canonical source, internal text margins are explicitly defined, the old ‘styleRanges’ no longer control the rendering when rich content exists, and GOF learns not to retain obsolete renderings as if they were still current.

Morning: fine-tuning the entry, then holding the zoom

The first commit of the day (0d33377) follows on from 6 June: the editor’s launch screen has been visually tweaked. It’s not the day’s major task, but it’s the gateway the client sees when they switch from WooCommerce to KEREDIT.

The first real functional milestone comes next with ef2aa47: keeping the text stable whilst zooming in the editor. This is a classic issue with a canvas: if resizing, calculated dimensions and live editing do not follow the same logic, the text can shift, change size or appear to float.

The fix affects:

  • EditorCanvas.tsx ;
  • TextFrameEditor.tsx ;
  • useCanvasDimensions.ts ;
  • text frame helpers;
  • a dedicated test for canvas dimensions.

This work is important for the beta: the customer must not feel that their text is changing when they zoom in to inspect it.

WooCommerce: duplicating without losing the basket context

The commit 9adc98c addresses a specific scenario: when a client project that has already been ordered is duplicated, the copy must become editable again, but it must not lose the WooCommerce metadata that allows us to understand where it came from.

The fix adds a real integration test and preserves:

  • wc_product_id ;
  • wc_variation_id ;
  • wc_context_fingerprint ;
  • wc_context.

The aim is not to silently recommend the same project. It is to enable clean duplication: a new draft on the KEREDIT side, with the commercial context still readable on the WooCommerce side.

Reference commit: 9adc98c (fix: preserve Woo metadata on customer duplicates).

Rich text becomes the PDF truth

The major KEREDIT pivot is 2b47806: rich text becomes the canonical contract for the PDF. Until now, the old model styleRanges could still act as a competing ‘truth’. This is dangerous: two representations of the same text always end up diverging.

Today’s decision is clear:

  • if `richText` exists, it controls the rendering;
  • the backend routes normalise and validate this contract;
  • PDF exports convey this truth;
  • the architecture documentation no longer suggests that several equivalent models coexist.

The tests cover the page validator, the export payload and the relevant rendering paths. It’s less spectacular than a new interface, but it’s more valuable: it’s the sort of decision that prevents incorrect PDFs from being produced.

Reference commit: 2b47806 (fix: make rich text the canonical PDF contract).

GOF is following suit

At the same time, GOF is receiving a series of closely related fixes:

  • 0a89b70 renders styled rich text runs correctly in PDFs;
  • f4f8d8e fully embeds print fonts;
  • 31401c1 aligns GOF’s rich text rendering with the KEREDIT specification;
  • 4028077 adds text geometry diagnostics;
  • c4487d9 ignores ‘styleRanges’ metadata when ‘richText’ is canonical;
  • f0e16b6 aligns text insets with the KEREDIT contract.

The chain becomes more consistent: KEREDIT cannot simply export clean JSON; GOF must read it using the same physical conventions.

Duplicate GOF renderings no longer obscure the text

Another production issue: obsolete GOF renderings must not remain visible as if they were still validated. The GOF commits 0bf1f43, 68865a1, 1afa8b5 and c66e826 define the concepts of current rendering, revision and supersede.

The expected outcome is straightforward for the operator: a project must have a readable current version, with its history behind it, not a pile of competing PDFs that forces one to guess which one to send.

This is a key workshop topic. The correct version of the PDF must be obvious.

In the evening: aligning the contract text with the payload

Today’s final KEREDIT commit (be785d6) brings everything together: backend validation, PDF renderer, export payload, management routes, asset routes, WooCommerce, docs, frontend helpers, Fabric object factory, shared types and text layout utilities.

In particular, this commit adds shared/src/utils/textLayout.ts and its tests. It transforms the text into a shared calculation rather than an implicit convention specific to a particular screen.

What’s stable tonight

  • KEREDIT ends the day at be785d6, version 0.6.75.
  • Rich text is the canonical source for the PDF contract.
  • Legacy styleRanges files must no longer contradict rich content.
  • The text remains more stable during editor zooming.
  • GOF now renders styles, fonts, insets and rendering revisions more accurately.
  • Duplicating a commissioned Woo project retains the relevant commercial context.

What remains problematic

The text issue is not yet resolved. The contract has been finalised, but each engine retains its pitfalls: Fabric on-screen, local PDFs, GOF, font embedding, ligatures, line-height, insets, and font substitution. The right approach is not to add more typographical options; it is to continue comparing screen, JSON and PDF outputs using simple but rigorous test cases.

The beta is progressing, but it is now moving forward with a more mature requirement: what the client sees must become what the production environment produces.
