Jour 66 - Fermer le P1 backend sans regonfler les routes

Clôture du premier gros chantier P1 backend : admin/pricing devient un routeur d'assemblage, assets sépare pur/runtime, print-jobs centralise la queue PDF, et le tout reste documente/teste.

  • Version repo : 0.6.29
  • Amplitude observée par les commits : 12:07 -> 16:28, soit 4 h 21 minimum
  • Temps actif estime : environ 4 h 45 a 5 h 30, en comptant les lectures d’audit, validations, rapport HTML et reprises de contexte
  • Commits pousses :
    • 9ad14b0 - refactor: split admin pricing route domains

  • Volume visible sur ces commits : 3266 insertions, 1821 suppressions sur les trois lots La journée a continue le chantier commence la veille : remettre le backend KEREDIT dans une architecture lisible, sans repartir dans une vague de refactorisation abstraite. Le fil directeur était simple : une route doit rester un controleur HTTP. Les décisions métier, Prisma, les effets de bord et les queues doivent vivre dans des services nommes, testables, et stables. Hier, ce principe a été applique sur trois points P1.

Admin pricing : la route géante devient un assemblage

Le plus gros gain visuel de la journée est sur backend/src/routes/admin/pricing.ts.

Au départ du P1, cette route faisait 2598 lignes avec 128 accès prisma.*. Elle mélangeait trop de domaines : attributs atelier, papiers, matrices, liaisons produit, simulation, MISKISS, overview.

Le chantier a termine l’extraction par domaines :

  • workshop-attributes.ts pour les bases, catégories et attributs atelier ;
  • papers.ts pour le référentiel papier et fournisseurs ;
  • matrices.ts pour les grilles tarifaires et import/export ;
  • bindings.ts pour les liaisons produit-grille et la simulation ;
  • miskiss.ts pour les modèles de coût, processus et recettes ;
  • overview.ts pour la synthèse pricing.

Le résultat est net : admin/pricing.ts est tombe a 16 lignes et 0 accès Prisma.

Ce n’est pas juste une réduction de taille. C’est une clarification de responsabilité. La route racine assemble les sous-domaines, elle ne doit plus redevenir un monolithe.

Cette règle a été documentée explicitement : les prochains developpements pricing doivent entrer dans un sous-domaine existant ou créer un nouveau sous-domaine clair. Il ne faut pas regonfler pricing.ts.

Un rapport HTML pour voir le gain

Un rapport visuel a été créé dans docs/rapports/p1-admin-pricing-refactor.html.

Son but est humain : rendre visible le gain d’architecture. Marc voulait pouvoir comprendre le chantier en quelques slides, avec les chiffres, les fichiers modifies, les checks et les risques restants.

Le rapport montre notamment :

  • 2598 -> 16 lignes dans la route racine ;
  • 128 -> 0 accès Prisma dans la route racine ;
  • 6 sous-domaines pricing explicites ;
  • URLs API inchangees ;
  • séparation route/service/tests.

C’est un format à conserver pour les gros chantiers : après un vrai refactor, le code ne suffit pas toujours. Il faut aussi une synthèse lisible qui explique ce qui a été gagné.

Assets : séparer helpers purs et runtime

Le deuxième P1 était moins spectaculaire, mais important.

backend/src/services/asset-service.ts mélangeait deux natures différentes :

  • des helpers purs ou quasi-purs : détection MIME, SVG, hash, metadata raster, normalisation kind/scope ;
  • des dépendances runtime : storage S3/R2 et jobs BullMQ assets.

Le problème n’était pas fonctionnel a court terme. Le problème était architectural : importer un helper apparemment simple pouvait charger des dépendances de queue ou de storage.

La correction a créé backend/src/services/asset-helpers.ts pour le pur, et a réduit asset-service.ts a assetRouteDeps.

Un test de frontière vérifie que asset-helpers.ts ne reimporte pas ../queues/, ../lib/storage ou assetRouteDeps.

C’est exactement le type de garde qui évite les régressions silencieuses : le code peut évoluer, mais la frontière pur/runtime est maintenant explicite.

Print jobs : un service unique pour la queue PDF

Le troisième P1 a traité backend/src/routes/print-jobs.ts.

Avant le chantier, la route publique portait elle-même :

  • la vérification projet/utilisateur ;
  • la création idempotente du PrintJob ;
  • la détection de conflit actif ;
  • l’enqueue BullMQ ;
  • la génération d’URL signée ;
  • le package de production ;
  • la livraison hot-folder.

La même intention existait aussi cote WooCommerce, avec un autre chemin de création/enqueue PDF. C’était le risque principal : deux chemins qui finissent par diverger.

La correction a créé backend/src/services/print-job-service.ts.

Ce service centralise maintenant :

  • createPrintJobIfAbsent() ;
  • createAndEnqueuePrintJob() ;
  • startUserPrintJob() ;
  • startAdminPrintJob() ;
  • reconcileOrphanPrintJob() ;
  • statut, download, package production et livraison utilisateur.

backend/src/routes/print-jobs.ts est passé de 423 lignes a 240 lignes, avec 0 accès Prisma direct.

WooCommerce n’importe plus pdfQueue directement. Le webhook de commande confirmée appelle createAndEnqueuePrintJob().

admin/pdfs.ts utilise aussi le service pour la génération admin et la réconciliation des jobs orphelins.

Ce que cela change vraiment

Le gain du jour n’est pas seulement “moins de lignes”.

Le vrai gain est que les zones critiques ont maintenant des frontières :

  • pricing : domaines explicites, route racine minuscule ;
  • assets : helpers purs separes du runtime ;
  • PDF jobs : queue BullMQ concentree dans un service ;
  • WooCommerce : premier decouplage fait sur la partie PDF.

Le backend reste gros, mais il devient plus navigable. On sait mieux ou chercher, ou tester, et ou ne pas remettre de logique.

Pour assets :

Une commande de test plus large avec filtre -- print-job-service à lance beaucoup plus que le fichier cible et a été interrompue après avoir montre de nombreux tests verts. Le test cible a ensuite été relance proprement avec teardown Redis/queue explicite.

Auto-critique

Le chantier s’est bien termine, mais il y a deux points a garder en tête.

D’abord, il faut continuer a se mefier des grosses routes qui semblent “juste un peu longues”. Elles finissent par cacher des contrats implicites : queue, storage, Prisma, droits, status codes. La bonne découpe est celle qui sort un domaine stable, pas celle qui déplacé du code au hasard.

Ensuite, il faut garder la discipline documentaire. Le rapport HTML et le blog ne sont pas accessoires : ils rendent le chantier compréhensible après coup. Sans eux, le gain de maintenabilite reste visible pour l’agent qui vient de coder, mais moins pour l’humain qui reprend le projet le lendemain.

État pour la suite

Le prochain lot logique reste WooCommerce.

La route backend/src/routes/woocommerce.ts a perdu l’import direct de pdfQueue, mais elle porte encore trop de workflow métier : intégration auth, création/consommation de token, checkout, webhook, reprise de projets client, duplication et suppression.

La bonne suite n’est pas de tout exploser d’un coup. Il faut extraire une facade par use case :

  • createCheckoutOrderFromProject
  • consumeWooLaunchToken
  • handleWooOrderWebhook

assets/upload.ts reste volontairement hors prochain lot immédiat. C’est une zone bêta critique : upload, confirm, checksum, dedup, cleanup storage, previews et jobs async. Avant de l’extraire, il faudra verrouiller le comportement par tests upload/confirm/dedup.

La règle centrale de fin de journée : ne pas regonfler les routes racines. Chaque nouvelle logique doit rejoindre le bon domaine ou créer un domaine explicite.
