Day 136 – Finalising orders before delivery

Day 136 of the log: KEREDIT is locking backups, the checkout, assets and PDF permissions ahead of preparing version 0.23.1.

Session timetable

  • Tool used: Codex
  • Main environment: VS Code WSL, Codex plugin on the left, code in the centre, Codex terminal on the right, GitHub Actions for PR validations
  • Date covered: Tuesday 25 August 2026
  • Main branches: codex/issue-458-save-concurrency, codex/issue-458-test-discovery, codex/release-0.23.1 and codex/issue-458-discovered-test-fixtures, all merged into dev
  • Window selected for the minimum: 00:10 – 09:59 CEST, from the first production lock to the merge of the final test isolation
  • Minimum observed duration: approximately 9 hours 48 minutes+
  • Version prepared: KEREDIT 0.23.1 and WordPress plugin 0.1.100; no evidence of runtime deployment observed today
  • Main traces: PR #485, #477, #490 and #491; stale backups, checkout/assets concurrency, web PDF permissions, exhaustive test discovery and isolation of the Google Photos queue
  • Minimum cumulative time since the start of the log: approximately 884h35+ (874h47+ as at 24 August, + 9h48+ today)

Quick read

The day begins ten minutes past midnight and feels less like a release than a long process of closing things down. The discovery of previously overlooked tests reveals a real-world issue: a client backup can still overwrite a field modified by an internal writer when that writer has not incremented the project version. Fixing this issue triggers a much broader review of concurrent writes relating to projects, assets, the WooCommerce checkout and web PDF permissions.

By the morning, four PRs have been merged. KEREDIT 0.23.1 is ready, but the log does not show it as deployed: the latest VPS version explicitly listed in the documentation remains 0.22.9. Today’s result is, firstly, a persistence contract that is harder to bypass, and secondly, a suite of tests that finally recognises all the files it needs to run.

A single version is not enough when several writers share the project

The first safeguard prohibits modifying a project whilst it is in active production . The core fix goes further: a versioned backup locks the project line, re-reads the fields it is about to write whilst under this lock, and returns ‘409 project_version_conflict’ if any of them have changed since the client snapshot. An internal update without a version bump can therefore no longer be silently overwritten by a save that has become stale.

The same requirement then extends to the other write paths. Asset mutations and the final checkout are fenced; the order of the deduplication locks is standardised; and storage deletions gain persistent intentions. Variants whose processing was interrupted can be resumed without losing their clean-up, and quotas are no longer adjusted based on a state that has become obsolete during the transaction.

This is a substantial undertaking because a process never operates in isolation. An administrative task, an import, a deletion or a job queue may all affect the same project with legitimate intent. The useful approach is not to assume a single writer; it is to make their order visible and to refuse the write when the freshness proof is no longer valid.

The checkout and web PDF are designed to fail safely

The WooCommerce workflow is hardened around the attempt ID, the ordered version and the expected payload. A divergent payload is rejected; a submitted order can be retrieved by its attempt ID; and an active reservation remains exclusive. Reconciliations are time-limited so that an old scan cannot arbitrarily link to a recent order.

Access to the web PDF follows the same logic. Authorisation for sharing becomes atomic; a disabled option is rejected and the deferred policy is locked before execution. When a repair fails and is then resumed, its dispatch line and commercial rights remain linked to the correct version of the project. The PDF is no longer merely an artefact to be produced: it remains the consequence of an explicit right, verified at the moment the system acts.

Tests now find files they previously overlooked

PR #477 replaces fragile globs with a recursive and portable detection method. The evidence attached to the PR counts 126 out of 126 backend files and 84 out of 84 frontend files, including two suites—photo_print—which were not being executed. The command `test:list` makes this inventory visible and any new file `*.test.ts` is automatically included in the contract.

This comprehensive check then reveals a residual dependency on the Redis queue shared in a Google Photos scenario. PR #491 replaces the actual BullMQ write with a local stub that checks the name, payload and jobId, then restores the original descriptor. The CI runs for all four PRs complete successfully; the comprehensive suite does not pass by masking the test that has just caused a problem.

Preparing 0.23.1 without reinventing the production process

The four application manifests pass at 0.23.1, the preparation documentation is aligned and the plugin remains ready at 0.1.100. Typecheck, lint, build, OKF validations and CI are reported as green in the relevant PRs.

However, no evidence has been found to confirm a VPS deployment of 0.23.1 today. This post maintains this distinction: the code has been merged and the release is prepared; the ‘live’ status should only be confirmed after checking the SHA and the version served by production.

Status at the end of the ticket

KEREDIT emerges from the night with a more explicit concurrency model, a checkout that rejects ambiguities, PDF permissions more firmly tied to their versions, and comprehensive test coverage. The number of fixes also highlights the cost of a review carried out right up to the transactional boundaries. The next useful step is not to add a new product promise: it is to keep this evidence accessible and to verify separately the release of the prepared version.
