Day 100 – Making simple what the code has made complicated

Day 100 of the journal: KISS approach to simplifying the notebook entries, an overview, local actions, a brief history and the battle against UI entropy.

Overall summary

The hundredth day of the log.

This figure marks a day that is very representative of the project: the code may generate quickly, but the product doesn’t become good simply because it has lots of features. It becomes good when the user understands what’s happening, when unnecessary choices disappear, and when the interface stops creating entropy.

Today’s task focuses on filling the notebook quickly.

Initially, the workflow can do a lot of things: select pages, process the cover, add pages, sort, filter, alternate, choose styles, select templates, preview, apply. On paper, it’s powerful. In user testing, it’s too much.

So today’s task is to do the opposite of over-engineering: remove the visible options, retain the internal power, and transform the quick mode into a KISS experience.

What does KISS mean here?

KISS doesn’t mean ‘poor’.

KISS means:

  • a clear primary purpose;
  • settings that match the client’s vocabulary;
  • a preview that truly shows the notebook;
  • simple, reversible actions with no surprises;
  • technical options hidden unless they are needed to make a decision.

Quick form-filling must be guided by a simple principle:

placer mes photos dans mon carnet et me laisser essayer autre chose sans stress

Anything that forces the user to understand the engine’s internal terminology becomes suspect.

The quick workflow simplifies

The modal window is gradually reduced to just a few choices:

  • sorting photos;
  • number of pages;
  • photos per page;
  • margins;
  • spacing;
  • layout: regular, alternating, occasional full-page spreads;
  • Global action: Reorganise all;
  • local action: Reorganise on one page.

The ‘Quick’ and ‘Wizard’ buttons disappear from the header of this modal. Quick mode is now the default mode. The narrative wizard remains in the codebase, but it does not need to be displayed in this workflow until it has a clear product specification.

The main button remains result-oriented:

Placer X photos dans le carnet

This is clearer than “Start auto-fill”.

Global preview: what is seen must be what is applied

The preview becomes the centrepiece of the workflow.

It shows the notebook after simulated filling, without modifying the store until the user applies the changes. It includes existing pages, pages that have been added, the cover where included, and retains the current position when changing style or rhythm.

Several UI details have been refined:

  • the unnecessary preview counter has been removed;
  • the ‘page modified’ borders have been removed;
  • the arrows have been moved closer to the notebook;
  • the controls are grouped on the left;
  • the help section has been transformed into a reassuring, overlay panel;
  • the close button is more visible, without any unnecessary tooltips;
  • the page backgrounds before thumbnails load are replaced by a paper-like grey;
  • the sliders use a terracotta colour consistent with the buttons.

The preview is no longer just for decoration. It serves to reassure users.

Reorganise everything, then just one page

The ‘Reorganise All’ button maintains the selected layout. If the user is set to ‘regular’, it remains in ‘regular’ mode. It changes the compatible templates, not the client’s overall logic.

A major bug has been fixed: with one photo per page, the engine was still forcing full-width display. This was consistent with a previous contract, but contrary to actual usage: if the local ‘Reorganise’ button can suggest other templates for a photo, ‘Reorganise All’ must be able to do so as well.

The cover is given the same trial feature: when it contains a photo, the local ‘Reorganise’ button appears on the front cover, centred on the right-hand half, not in the middle of the spread.

Undo without creating a second editor

The Undo button becomes a mini composition history.

It retains up to 5 states, but only for:

  • ‘Reorganise All’;
  • Reorganise a page.

Manual adjustments such as margins, spacing, rhythm or photos per page reset this history. This is intentional: the aim is to undo a visual exploration, not to create a parallel history system within the modal.

Here again, KISS does not mean a lack of convenience. It is a refusal to add a mechanism whose scope the user would no longer understand.

Local seed: the trust reminder

Today’s work is also marked by the fear of losing locally stored data.

The day before, anti-seed protection was put in place. Today, the issue remains relevant: a local database intended to serve as a mirror must not be treated as a disposable database. The Zine product, visible on the VPS but absent locally, served as a very concrete reminder.

An AI tool can execute a command quickly. The project, however, requires a slow and non-negotiable rule:

ne jamais ecraser silencieusement des donnees metier vivantes

What Day 100 reveals about the project

Code generates quickly. Sometimes too quickly.

In an hour, you can get an auto-fill feature with dozens of parameters. But it then takes two days to organise the semantic and visual chaos: which words to keep, which controls to hide, which preview to trust, which action cancels what, which page is really the target, which option builds trust and which creates confusion.

Day 100 therefore does not mark a major functional expansion. It marks a discipline:

puissance interne, simplicite externe

And that is probably a good definition of KEREDIT at this stage: a ‘workshop-first’ product that must hide a great deal of complexity without deceiving the user.
