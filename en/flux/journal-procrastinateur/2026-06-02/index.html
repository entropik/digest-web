Références PDF

La matinée a commencé par un ajout documentaire autour de la génération PDF.

Le repo gardé maintenant des références plus solides pour l’analyse du futur rendu :

  • ajout d’une analyse HTML dans ;
  • ajout d’une référence GWG dans docs/analyse/références/pdf-specs/ ;
  • raccord dans BIBLIOTHEQUE.md et docs/HOME.md.

Ce n’est pas encore le chantier renderer lui-même. C’est la couche de préparation qui évite de faire du PDF “au feeling”.

Le contexte reste le même : KEREDIT doit produire un payload complet et versionne, et GOF doit devenir la forge capable de transformer ce payload en PDF de production. Pas de retour à Puppeteer comme réflexe par défaut. Pas de capture géante quand on peut garder un document de page.

Journal rétrospectif du 1er juin

Le billet du 1er juin a été créé rétrospectivement.

Son rôle était simple : dire qu’il ne s’était rien passé côté atelier ce jour-la.

C’est moins spectaculaire qu’une fonctionnalité, mais c’est important pour la mémoire projet. Une journée blanche non documentée devient vite un trou dans la chronologie. Une journée blanche documentée devient une information : le plan bêta a été gardé, sans mouvement caché, sans validation implicite.

Logo imprimeur : le détail qui se voit tout de suite

Le gros sujet visible de la journée a été le logo imprimeur.

La demande paraissait cosmétique : le logo devait être dans un rond. En pratique, le sujet touchait plusieurs surfaces :

  • sidebar backoffice ;
  • preview admin ;
  • login ;
  • reset password ;
  • barre de l’éditeur ;
  • page Personnalisation ;
  • export/import et persistance du thème tenant.

La première version était trop naïve : elle affichait parfois un carré dans une surface qui devait être ronde, ou un rond qui ne correspondait pas vraiment au cadrage final. Le problème à fini par pointer une cause plus intéressante : dans KEREDIT, les rayons UI sont volontairement verrouilles à 0px, et rounded-full dépendait aussi du token radiusFull.

Conclusion : pour ce cas précis, le rond n’est pas un style générique. C’est une contrainte de rendu métier du logo.

La correction finale a donc ajouté :

  • logoTransform dans le thème tenant (x, y, scale) ;
  • un BrandLogo centralise qui masque vraiment le rendu final en rond ;
  • un outil de cadrage après upload ;
  • un plateau de cadrage commun entre preview et rendu final ;
  • un guide rond explicite qui ne dépend plus des tokens de radius ;
  • des tests Playwright dédiés au flux logo.

Le point important est la cohérence : ce que l’admin voit dans le cercle de cadrage doit être ce qui apparaît ensuite dans le logo final.

Ce n’est plus seulement une note d’intention. GOF a maintenant un socle applicatif.

Socle technique GOF

Le dossier GOF contient une app Node gof-forge-app en CommonJS, avec :

  • bullmq et ioredis pour la file de jobs ;
  • pg et une base Postgres pour tracer les travaux ;
  • pdf-lib et sharp pour un premier rendu PDF natif et la normalisation image ;
  • SDK S3 AWS pour lire les assets R2 ;
  • pdfjs-dist pour visualiser les PDF générés dans le dashboard.

Le docker-compose.yml posé une stack atelier complète :

  • Postgres 16 ;
  • Redis 7 avec append-only ;
  • dashboard GOF sur 8080 ;
  • worker de rendu séparé ;
  • Nginx Proxy Manager ;
  • Dozzle en profil ops ;
  • volumes persistants data/, fonts/ et espaces NVMe cache, work, tmp, output-staging.

Le script scripts/sync-to-forge.sh prépare la synchronisation vers [compte]@[hôte]:/opt/[chemin privé], en excluant .env, data/, node_modules, les captures Playwright, les backups et .git.

Backoffice Flux

docs/backoffice-gof.md documente une vraie interface atelier, servie par app/src/server.js :

  • dossiers par état : réception, file, génération, succès, échecs, annulations, validations ;
  • table de jobs triable et cherchable ;
  • panneau de détail avec payload JSON, rapports, assets, artefacts, événements et actions opérateur ;
  • viewer PDF.js pour ouvrir l’artefact local ;
  • actions opérateur : annuler, relancer, approuver pour impression.

Les routes GOF existent côté app :

  • POST /api/render-jobs pour créer un job ;
  • GET /api/render-jobs pour lister ;
  • GET /api/render-jobs/:id pour consulter ;
  • POST /api/render-jobs/:id/cancel ;
  • POST /api/render-jobs/:id/retry ;
  • POST /api/render-jobs/:id/approve ;
  • endpoints pour URLs signées assets et lecture d’artefacts locaux.

La base créé les tables render_jobs, render_assets, render_artifacts, render_events et operator_actions. C’est exactement le bon vocabulaire pour une forge : travail, assets, artefacts, événements, actions humaines.

Renderer PDF v1

Le premier renderer vit dans app/src/pdf-renderer.js.

Il ne lancé pas Chromium. Il créé un PDF avec pdf-lib, convertit les dimensions mm en points PDF, posé MediaBox, BleedBox et TrimBox, dessine :

  • fonds de page ;
  • textes en objets texte PDF avec fallback Helvetica ;
  • rectangles vectoriels ;
  • images et cliparts résolus depuis assets[].storage_key via R2 puis normalises avec sharp.

Le renderer produit aussi :

  • render-report.json ;
  • print-validation-report.json ;
  • checksum SHA-256 du PDF ;
  • warnings pour les assets absents, polices fallback, SVG vectoriel non encore pris en charge.

Ce n’est pas encore le moteur prepress final, et le billet doit le dire clairement. Mais c’est une première forge exécutable : un payload entre, un job est trace, un PDF maître sort, un rapport explique ce qui a été fait.

Doctrine PDF

Les docs GOF consolident aussi la direction :

  • docs/inspiration-dalim-twist-forge-pdf.md traduit la logique DALIM/TWiST en pipeline GOF : ingestion, prevol, normalisation, display list, rendu natif, post-traitement, contrôle final ;
  • docs/moteur-pdf-bas-niveau.md fixe le principe du writer PDF natif, sans Puppeteer/Playwright/Chromium dans le chemin nominal ;
  • docs/preparation-pdf.md est maintenant marqué comme brouillon historique, avec une note d’autorité indiquant que les pistes Puppeteer ne sont plus la direction ;
  • docs/backoffice-gof.md relie cette doctrine à une surface opérateur concrète.

Le point de fond est sain : GOF n’est pas “un export PDF de plus”. C’est une chaîne de production. KEREDIT gardé l’autorité du projet, de la commande, des templates et des assets ; GOF consomme un payload PDF autonome, fabrique des artefacts et rend ses décisions auditables.

GOF dans le backoffice KEREDIT

Le commit de fin de journée a aussi embarqué les premiers éléments d’exposition GOF côté admin Krampouz.

Les fichiers ajoutés et modifiés montrent le raccord côté KEREDIT :

  • backend/src/routes/admin/gof.ts ;
  • backend/src/services/gof-service.ts ;
  • raccord dans backend/src/routes/admin/index.ts ;
  • appel API côté frontend ;

Le sens produit est cohérent : GOF commencé a sortir du simple dossier local pour devenir un flux visible depuis KEREDIT, sans pour autant déplacer l’autorité métier. KEREDIT reste le backoffice, GOF reste la forge.

Il faudra reprendre ce sujet prudemment : il touché à l’exploitation PDF, donc à la frontière entre éditeur, admin, payload, worker et machine atelier.

Ce que cela dit de la bêta

La bêta n’a pas besoin d’un logo parfait pour exister.

Mais elle a besoin que les petites choses visibles ne donnent pas une impression de bricolage. Un logo carré quand l’interface promet un rond, ce n’est pas grave techniquement ; c’est mauvais comme signal produit.

Le 2 juin a donc été utile pour une raison simple : il a remis de la cohérence dans les surfaces visibles, tout en continuant a préparer le terrain PDF/GOF.

La cible reste la même :

  • ne pas regonfler le scope avant clients amis ;
  • garder postcard comme produit bêta prioritaire ;
  • stabiliser ce que l’utilisateur voit vraiment ;
  • laisser le PDF avancer par contrat et par preuves, pas par improvisation.

Reprise

Priorités recommandées après cette journée :

  1. vérifier que la personnalisation logo reste correcte après reload et sur toutes les surfaces ;
  2. ne pas rouvrir la thématisation générale sous prétexte du logo ;
  3. versionner ou sauvegarder proprement GOF, puisque dépôt local gof porte maintenant du code applicatif sans dépôt Git actif ;
  4. reprendre GOF par un contrat clair entre KEREDIT et la forge ;
  5. rejouer le parcours postcard complet avant invitation externe ;
  6. garder les tests E2E comme filet bêta, pas comme un chantier cosmétique permanent.

La journée a commencé par de la documentation et s’est terminée par un détail visible corrigé. C’est souvent ça, l’approche bêta : rendre moins fragile ce qui va se voir en premier.
