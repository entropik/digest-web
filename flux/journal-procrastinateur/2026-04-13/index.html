Jour 30 — Le deploy VPS passe a GHCR et SSH

Sortir le build du VPS

6 commits, tous concentres sur un même sujet : fiabiliser enfin le déploiement VPS. Après le diagnostic du 8 avril sur les limites de Dockhand comme chaîne de build, la journée acte un pivot propre : build dans GitHub Actions, publication d’images immuables sur GHCR, puis redéploiement du VPS via SSH sur un checkout Git contrôle.

Le commit principal pose presque tout d’un coup : nouveau workflow .github/workflows/deploy.yml, script deploy/ghcr-deploy.sh, compose VPS adapte, env exemple, et guide de déploiement remis a plat. Les commits suivants raffinent le flux manuel : répétition a blanc du deploy, choix explicite d’un image_tag déjà publie, puis choix de la ref cible pour les exécutions manuelles. Un correctif répond ensuite à une review sur le script et le workflow, avant le merge de la PR #26 dans main.

La fin de journée est plus calme mais importante : README, guides poste/dev et mémoire projet sont réalignés avec cette nouvelle vérité opérationnelle. On ne laisse pas un deploy changer sans remettre le cadre documentaire au propre.

La production ne doit plus découvrir les erreurs

La décision structurante est claire : le VPS ne doit plus être l’endroit ou l’on “découvre” si le build marche. Il doit seulement recevoir des images déjà construites et identifiées. C’est la bonne réponse au flottement observe avec Dockhand, les clones Git locaux fragiles et les rebuilds opaques.

Autre arbitrage utile : le workflow manuel ne sert pas juste a “forcer un deploy”. Il devient un outil de répétition et de vérification, avec deux garde-fous concrets :

  • pouvoir sauter temporairement validate pour un exercice de déploiement quand le CI global est bruite
  • pouvoir redéployer un image_tag existant sans rebuilder tout le monde

Le repo garde quand même un checkout Git sur le VPS. Ce n’est pas un retour au vieux mode “build sur serveur” : ce checkout sert à versionner la stack Compose et le script de deploy, pas a produire les images applicatives.

Un pipeline invisible enlève une dette mentale

Ce genre de journée n’ajoute aucune feature visible dans l’éditeur, mais elle retire une dette mentale énorme. Tant que le déploiement restait mélange entre supervision Dockhand, checkout Git distant et build plus ou moins implicite, chaque vérification produit était suspecte : est-ce qu’on regarde le bon code, la bonne image, le bon conteneur ?

Le choix GHCR + SHA + SSH n’a rien de spectaculaire, mais il remet une chaîne de preuve simple au centre : commit -> image -> deploy. Pour un projet atelier-first qui doit valider des usages réels, cette lisibilité vaut largement une “solution magique” de plateforme.

La préproduction gagne en confiance

On reste hors du chemin critique visible de la bêta postcard, mais on traite un verrou indispensable : pouvoir croire ce qu’on voit en preprod. Sans déploiement fiable, impossible d’interpreter correctement les tests réellement menes sur l’éditeur, l’upload ou la production PDF.

Repères : GHCR, SSH et VPS

  • GHCR — GitHub Container Registry, le registre d’images Docker de GitHub.
  • SSH — connexion sécurisée a distance pour administrer un serveur.
  • VPS — serveur prive virtuel loue chez un hébergeur.
  • CI — intégration continue : vérification automatique du code à chaque push ou PR.
  • SHA — identifiant unique d’un commit Git ou d’une image taguee par commit.
  • Dockhand — outil de supervision et de déploiement de stacks Docker utilise dans notre infra.
