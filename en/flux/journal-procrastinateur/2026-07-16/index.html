Day 115 – Ten thirty-two to qualify for a merge

Day 115 of the log: two GOF PRs were merged after 10 hours and 32 minutes of corrections, CI and repeated Codex reviews, until a clear verdict was reached on the exact SHA.

Session timetable

  • Tool used: Codex
  • Primary environment: Codex App on Mac, KEREDIT repository dépôt local krampouz and GOF repository dépôt local gof, with GitHub acting as the CI and code review platform
  • Date covered: Thursday 16 July 2026
  • Start of authorised merge window: 12:47:01 CEST
  • Final merge of GOF PR #61: 23:19:28 CEST
  • Minimum observed time for the merge sequence: 10h32+ in duration (12:47:01 -> 23:19:28, including corrections, tests, CI and review waiting times; this is not 10h32 of continuous typing)
  • KEREDIT branch observed: dev, HEAD 2528ffcc, version 0.14.3
  • GOF branch merged: codex/47-gof-flux-distributed into PR #61
  • GOF PR #62: merged at 14:58:13 CEST, merge 9d4d906b
  • GOF PR #61: merged at 23:19:28 CEST, merge squash 3010fd92
  • Commits observed after merge approval: 57 on the PR #61 branch, 5 additional fixes on PR #62 and 2 on dev KEREDIT
  • Final GOF validation: 478 tests, 471 passed, 7 ignored, 0 failed; GitHub CI green in 1 min 43; 0 unresolved review threads
  • Minimum cumulative time since the start of the log: approximately 758h52+ (748h20+ as at 15 July, + 10h32+)

Quick read

At 12.47, the request seems straightforward: merge PRs #62 and #61 carefully, taking the Codex bot’s messages on GitHub fully into account.

The first PR, which is documentation-based, neatly wraps up the Printbox analyses. The second covers the distributed control of GOF Flux: orchestration, local and cloud forges, source provenance, fonts, artefacts, reprints, Accurio, metrics and cancellation of obsolete jobs.

It will not be merged simply because the CI passes once. It will only be merged after ten hours and thirty-two minutes of a strict loop: read the comment, check that it is correct, fix the smallest possible change, add a test, push, wait for the CI, request a review of the new SHA, then start again.

This is probably the longest merge in the project. It is also the one that best illustrates what an automated review can become when it is not treated as a mere formality.

Split before merging

PR #62 extracts the Printbox analyses from the large, distributed GOF branch. It brings together two reports, their graph metadata and the sizing of the photo storage. Five additional patches ensure consistent formats, reproducible provenance, exact years and portable sources.

It was merged at 14:58. This separation reduces the noise in PR #61 and prevents study documentation from being mixed up with changes to the runtime architecture. The report, somewhat hastily described as ‘bulky’, is in fact only 1.4 MB: an amusing reminder that words, too, must be weighed up carefully.

Email is not the workflow

At the start of the session, notifications from chatgpt-codex-connector[bot] were still arriving via email. The doubt is legitimate: if the comment isn’t copied into the conversation, is it actually seen?

The workflow is therefore made explicit. Codex queries the PR directly, retrieves unresolved threads, links each comment to the reviewed commit and never considers a previous verdict valid for the current HEAD. The email remains a notification for the human, not a necessary step in the process.

After each correction, the corresponding thread is resolved, `@codex review` is requested again, and the merge remains blocked until the bot has issued its verdict on the exact SHA. A temporary reaction, a green CI run or the absence of a message for a few minutes are not sufficient.

Fifty-seven commits within the window

The branch for PR #61 received 57 commits between approval and merge. The figure is staggering, but their content is more important than their number. Successive comments address very specific blind spots:

  • revision identity maintained between reservation, remote start-up and proof of reliability;
  • separate credentials for sources, control and cloud providers;
  • atomic HA recovery and distributed state preserved after restart;
  • signed, bounded, non-aliased artefacts that are cleaned up without deleting a previously retained success;
  • cancellation of replaced revisions and protection against their late return;
  • display, metrics and capacity calculated from the scheduler’s actual state;
  • distributed fonts verified, quarantined and then reinstalled if the current release is corrupted;
  • lease renewal tolerant of transient network failures, without continuing beyond the local expiry time;
  • Accurio submissions, cloud retries and production transitions made explicit and idempotent.

These are not 57 changes of direction. It is an already comprehensive architecture that addresses, one by one, the scenarios that a distributed system inevitably encounters: duplicate execution, delayed responses, outdated identities, network interruptions, incomplete storage, and visible state differing from the planned state.

The last hour sums up the previous ten

At 22:52, a patch prevents a failed remote cancellation from giving the impression that the local job has been successfully completed. At 23:03, a common but corrupted font release becomes recoverable without manual intervention, whilst incompatible font forges cease to inflate the displayed capacity.

The bot finds one final issue: a temporary timeout during the renewal of a lease should not cause a costly PDF render to fail if the lease remains valid on the control side. The fix a110fd7 finally distinguishes between a transient failure and permanent revocation and maintains a firm local expiry date.

The full suite then passes with 478 tests, no failures. GitHub validates the CI in 1 minute 43 seconds. Codex finally reports: ‘Didn’t find any major issues’ on the exact commit a110fd7. Unresolved threads are recounted: zero. The squash merge is executed with protection on the expected HEAD and produces ‘3010fd92’ at 23:19.

This record must not become the norm

Ten hours and thirty-two minutes for a merge is not a velocity target. PR #61 had become too large: 132 files and several days’ worth of distributed architecture all wrapped up in a single review boundary. The bot was useful, but it also revealed the cost of a batch that combines orchestration, storage, cloud, dashboards, fonts, Accurio and operations.

The lesson is not to do away with rigorous review. It is to maintain that standard whilst submitting smaller PRs, each with a clear contract, tests and a manageable risk profile. PR #62, which was split and then merged early, already provides a positive counter-example.

The record remains valuable, however. For once, ‘taking account of the bot’s messages’ does not mean reading an email after the event. It means keeping the loop open until the code, the tests, GitHub and the review all point to the same commit.

The merge didn’t win because the clock read 11.19 pm. It won because there was no longer any known technical reason to prevent it.
