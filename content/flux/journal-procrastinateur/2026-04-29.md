## Ce qui devait fonctionner

Le comportement produit attendu pour les cadres est simple :

1. sélectionner un bloc image ;
2. glisser un asset `Cadre` depuis le panneau décorations ;
3. si le drop tombe sur une photo, demander confirmation : `Lier ce cadre au bloc photo ?` ;
4. si l'utilisateur confirme, le cadre devient un asset lie au bloc photo ;
5. le cadre suit le déplacement, la taille et la rotation de la photo ;
6. le cadre apparaît autour du bloc, pas enferme dans l'image ;
7. le panneau calques indique clairement le cadre lie, avec une couleur orange ;
8. si l'utilisateur refuse ou depose hors photo, le cadre reste un élément libre.

Ce contrat est différent de celui du masque :

- le masque agit comme une géométrie interne de decoupe ;
- le cadre est une décoration externe liée au bloc ;
- le cadre peut aussi rester libre, comme un clipart raster.

La confusion entre ces trois statuts a été une cause directe de régression.

## Ce qui a casse

Plusieurs problèmes se sont enchaines :

- le cadre a été traite comme un `clipart` dans le payload de drag ;
- la liaison `cadre -> bloc image` a disparu lors des retours arriere ;
- les resets Git ont replace le code sur un commit ou le backoffice et le catalogue frames existaient, mais pas le comportement éditeur complet ;
- la rotation de l'overlay image est revenue sur un ancien calcul base sur `left/top`, alors que Fabric doit être lu via ses coins runtime réels ;
- le frontend a d'abord typechecke contre des declarations `shared/dist` stale, ce qui a donne l'impression que le type `ImageElement` n'avait pas été modifie ;
- les services locaux ont du être redemarres proprement pour éviter de tester un runtime qui ne correspondait plus au code.

Le point le plus important : revenir à un ancien commit n'est pas une preuve que l'application revient exactement à l'état mental attendu si une partie du comportement n'avait jamais été committee, ou si le runtime sert encore un ancien bundle.

## Autocritique de l'agent

La perte de temps vient d'abord d'une mauvaise discipline de contexte.

Ce qui aurait dû être fait plus tôt :

- vérifier immédiatement que `frame` était encore un type de payload distinct au lieu de chercher d'abord cote rendu ;
- inspecter `editorAssetDrag.ts`, `ImageElement` et `fabricObjectFactory.ts` comme triangle de contrat avant de patcher l'UI ;
- refuser de conclure à une régression Fabric avant d'avoir prouve si le cadre était encore dans le modèle persistant ;
- reconstruire l'état fonctionnel depuis les commits et le reflog avant de continuer a modifier ;
- relancer `pnpm --filter @krampouz/shared build` des qu'un type partage changeait.

Ce qui a été mal gere :

- trop de corrections successives ont été tentees en gardant une partie du contexte en mémoire conversationnelle plutôt que dans le code et les tests ;
- la distinction "cadre libre" / "cadre lie" / "clipart" a été redecouverte au lieu d'être formalisee tout de suite ;
- les resets ont été utilises comme solution de récupération, mais ils ont aussi efface des morceaux non commités ou non stabilises du comportement attendu ;
- la documentation disait déjà que Fabric `left/top` n'était pas une vérité après transformation, mais aucun test ne bloquait le retour de l'ancien calcul.

Conclusion methodologique : une doc de contrat ne suffit pas. Sur le canvas, chaque contrat géométrique sensible doit avoir un test minimal qui echoue si l'ancien chemin revient.

## Correction remise en place

Le code de clôture remet un contrat explicite :

- `EditorFrameDragPayload` existe séparément de `clipart` et `mask` ;
- `ImageElement` porte `decorativeFrameAssetId` et `decorativeFrameVisible` ;
- le drop d'un cadre sur une photo ouvre une confirmation de liaison ;
- confirmer lie le cadre au bloc image ;
- annuler ajoute le cadre librement ;
- le rendu Fabric du bloc image ajoute le PNG cadre autour du bloc photo, avec une taille externe ;
- le panneau calques colore le bloc photo en orange quand un cadre lie existe et affiche une sous-ligne `Cadre lie` ;
- le backend extrait aussi `decorativeFrameAssetId` comme référence d'asset projet ;
- la suppression d'un asset cadre detache le cadre du bloc au lieu de supprimer la photo.

Le correctif d'overlay rotation a aussi été verrouille :

- les objets Fabric non texte utilisent `obj.getCoords()` pour l'overlay de sélection ;
- le test `pnpm --filter frontend test:image-clipart-helpers` couvre un objet Fabric tourne dont `left/top` mentent.

## Règle de reprise

Avant de retoucher aux cadres, reprendre dans cet ordre :

1. vérifier le payload `frame` dans `editorAssetDrag.ts` ;
2. vérifier les champs `decorativeFrameAssetId` / `decorativeFrameVisible` dans `ImageElement` ;
3. vérifier le rendu Fabric du bloc image dans `fabricObjectFactory.ts` ;
4. tester le drop sur photo avec confirmation ;
5. tester le drop hors photo ;
6. tester déplacement, rotation, resize du bloc photo avec cadre lie ;
7. vérifier le panneau calques et la couleur orange.

La prochaine fois qu'une régression de ce type revient, il ne faut pas commencer par patcher l'apparence. Il faut d'abord prouver si le contrat modèle existe encore.
