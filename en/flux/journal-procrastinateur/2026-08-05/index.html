Day 124 – The ‘Synchronise’ button is being retired

Day 124 of the blog: a product listing tested too hastily, an unfair setback, then the KEREDIT synchronisation with WooCommerce became automatic and was successfully tested in production.

Session timetables

  • Agent used: Kimi CLI code for Woo synchronisation, Codex running in parallel on the Products & Prices workspace
  • Main environment: Mac, KEREDIT repository dépôt local krampouz, VPS [nom privé], server [nom privé] (ooblik.com)
  • Date covered: Wednesday 5 August 2026
  • Main branch prior to the log: dev, PRs #387 to #393 merged
  • Observed windows: approximately 16:30 → 19:45 CEST for end-to-end Woo synchronisation
  • Minimum observed duration: approximately 3 hours+
  • Main releases: Products & Prices workspace 0.17.0, automatic product synchronisation KEREDIT → WooCommerce, plugin 0.1.89, deployment 0.17.1
  • Minimum cumulative time since the start of the log: approximately 807h37+ (804h37+ as at 4 August, + 3h00+ today)

Quick read

The day began with a minor scare: a product listing edited in KEREDIT wasn’t displaying correctly on the WooCommerce side. Immediate frustration. Then it all came back to me: the WooCommerce listing had never been resynchronised — I needed to open the product in WooCommerce and click ‘Synchronise’. The bug wasn’t in the code, it was in the action.

Rather than getting used to the process, the day puts an end to it. In the evening, a backup in the KEREDIT admin panel updates the WooCommerce listing all by itself, in just a few seconds, as demonstrated on ooblik.com.

Diagnosis before the code

The investigation first confirms what’s already in place: the synchronisation is a ‘pull’ operation; the WordPress plugin retrieves the product configuration via the KEREDIT API. Two automatic triggers already exist — the save of the Woo listing and a lazy refresh on display, limited to one hour. The gap is clear: editing the listing in the KEREDIT admin panel doesn’t notify anyone.

Three options are on the table: a real-time webhook push, a simply hardened pull, or a WordPress price list cron job. The choice falls on the push, because the scenario we’re dealing with is exactly ‘I’ve just made a change, I’ll test it straight away’.

The decisions that matter

First decision: no Prisma migration for the secret. The backend only stores the hash of the integration secret, so it can never send it back to the plugin. The environment variables WOO_SITE_URL, WOO_INTEGRATION_KEY and WOO_INTEGRATION_SECRET follow the precedent AUTH_EMAIL_WEBHOOK_* — duplication assumed, single-tenant architecture required.

Second decision: the notification is ‘fire-and-forget’. Five-second timeout, error logged as a ‘warn’, failures are never escalated to the admin dashboard. An unreachable WooCommerce site must not cause a product page to fail.

Third decision: on the plugin side, the HTTP response is sent immediately and the actual synchronisation is scheduled via wp_schedule_single_event. The backend does not wait for WordPress.

The usual stress of ‘doing things properly’

The configuration requires production credentials. These are stored in the plugin settings on the ooblik.com server. WP-CLI with PHP 8.3 explicitly — the default binary points to a PHP version that’s too old and misrepresents the versions — allows you to read them properly, to enter the local .env and that of the VPS, and to validate the Compose output before any restart. The backend is not restarted straight away: the old code is still running, so the variables will have to wait until deployment.

Deployment follows its own procedure: version 0.17.0 is already live, so we need a 0.17.1, which means a release branch, a PR, a successful CI run, and a merge. Then the nominal script runs, the served SHA is verified, and only after that does the test run.

Proof, twice

The first end-to-end test fails — the meta _keredit_connector_synced_at doesn’t change. A few seconds of doubt, then the obvious realisation: the test backup ran during redeployment, on the old code. The channel is manually verified from within the container (200, scheduled: true), the user re-registers, and the meta updates automatically. Second time lucky.

The ‘Synchronise’ button remains visible in WooCommerce. It’s no longer needed, but you don’t remove an emergency ramp on the day you install the lift.
