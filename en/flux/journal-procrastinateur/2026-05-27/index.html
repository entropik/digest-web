Jour 68 - Le parcours commerce KEREDIT devient testable

Quantités : KEREDIT reprend la main

Le premier bloc a corrigé une erreur de contrat importante.

WooCommerce lançait encore des projets avec une quantité 1, alors que le produit KEREDIT Carte postale commencé à 8 exemplaires. Le prix échouait donc logiquement avec des 400 Bad Request.

La correction a aligné le flux :

  • le produit WooCommerce lit les quantités autorisées depuis KEREDIT ;
  • l’éditeur démarre sur une quantité valide ;
  • le panier WooCommerce affiche la quantité imprimée KEREDIT ;
  • la quantité WooCommerce classique est verrouillée pour les lignes KEREDIT ;
  • le client peut revenir éditer son projet depuis le panier, changer format ou quantité, puis recommander.

Ce point est central pour la bêta. Il évite une divergence dangereuse entre fiche produit, éditeur, prix et panier.

Données produit : export/import pour ne plus confondre code et base

Le test live à mis en évidence une autre confusion : le déploiement embarqué le code, pas les données locales de prix, formats, papiers et attributs atelier.

Sur ooblik.keredit.com, certains produits étaient donc vides ou incomplets même si le local était correctement paramétré.

Le backoffice Produits & Prix dispose maintenant d’un flux d’export/import pour transférer les données produit et atelier :

  • export du produit local ;
  • import sur le VPS ;
  • correction du rafraîchissement admin après import ;
  • hydratation correcte des attributs atelier dans la fiche produit ;
  • compatibilité avec l’ancien paramètre paper=invercote_300.

Après import et redéploiement, le prix est revenu en live. C’était le premier vrai verrou commerce de la journée.

Intégrations Woo : le client pourra configurer ses clés

Le backoffice Intégrations a été renforcé pour que l’intégration WooCommerce soit exploitable par un client KEREDIT.

Ce qui a changé :

  • credentials Woo REST configurables côté admin KEREDIT ;
  • chiffrement des secrets via INTEGRATION_SECRET_ENCRYPTION_KEY ;
  • test de connexion Woo ;
  • activation explicite de la commande Woo ;
  • distinction UX entre clés REST obligatoires et secret webhook optionnel.

Le point important : KEREDIT ne doit pas dépendre d’une manipulation invisible faite par nous en SSH. Le backoffice doit expliquer et porter la configuration.

Panier WooCommerce : le premier cycle client fonctionne

Le bouton Commander de l’éditeur appelle maintenant KEREDIT, qui ajouté la ligne au panier WooCommerce puis redirige vers OOBLIK.

Le parcours validé en live :

  1. ouvrir un produit OOBLIK ;
  2. lancer l’éditeur KEREDIT ;
  3. créer/modifier une carte postale ;
  4. calculer le prix ;
  5. commander ;
  6. arriver dans le panier OOBLIK ;
  7. voir la ligne KEREDIT avec projet, format, quantité imprimée et papier ;
  8. cliquer sur éditer depuis le panier ;
  9. modifier format ou quantité ;
  10. revenir au panier avec prix mis à jour.

Le panier ne doit plus exposer le sélecteur de quantité WooCommerce sur ces lignes. La quantité métier appartient à KEREDIT.

Commandes admin et correction support

La page Commandes du backoffice KEREDIT est devenue utilisable pour suivre les projets ayant une commande WooCommerce.

Ajouts du jour :

  • recherche ;
  • filtres ;
  • tri ;
  • pagination ;
  • recherche dynamique sans appuyer sur Entrée ;
  • correction du bug de focus qui empêchait de taper plus d’une lettre ;
  • ouverture du projet en mode correction support.

Le mode support a aussi été sécurisé côté assets.

Problème rencontré : en ouvrant un projet client depuis l’admin, certaines images donnaient :

/api/assets/:id/url 404 Asset non trouvé

Cause : l’admin de support pouvait ouvrir le projet, mais pas forcément résoudre l’URL de l’asset client attaché au projet.

Correction :

  • accès admin/editor autorisé pour les assets liés à un projet du même tenant ;
  • vérification live d’une URL asset en 200 ;
  • bouton Commander masqué en mode correction support ;
  • conservation de Sauvegarder et Régénérer PDF.

Décision produit : quand l’atelier corrige un projet client, il ne doit pas repasser une commande à la place du client.

Un warning frontend connu reste à nettoyer autour de UsersPage.tsx, mais il n’a pas bloqué les parcours du jour.

Incidents utiles

La journée à surtout révélé des trous de contrat :

  • quantité Woo 1 contre quantité KEREDIT 8 ;
  • données produit locales non présentes en prod ;
  • intégration Woo pas assez explicite dans le backoffice ;
  • panier Woo qui voulait encore modifier une quantité métier ;
  • correction support qui ouvrait le projet mais pas toujours les assets ;
  • filtre commandes qui perdait le focus à chaque frappe.

Ces incidents sont de bons signaux avant bêta : ils sont apparus sur un vrai parcours client, pas dans une abstraction. Et ils ont été corrigés dans le sens du produit, pas par contournement.

Avis bêta au soir du 27 mai

Oui, on est nettement mieux pour la bêta du 1er juin.

On n’est pas en situation de lancement public large. En revanche, une bêta clients amis contrôlée devient crédible :

  • le parcours commerce produit -> éditeur -> prix -> panier existe ;
  • le client peut revenir éditer depuis le panier ;
  • l’atelier voit les commandes dans KEREDIT ;
  • le support peut ouvrir et corriger un projet client ;
  • les quantités et prix sont maintenant pilotés par KEREDIT ;
  • les données produit peuvent être transférées proprement entre local et VPS.

Ce qui reste à valider avant ouverture :

  • rejouer un parcours complet propre, du produit OOBLIK jusqu’à la commande Woo ;
  • vérifier la régénération PDF support sur un projet réel ;
  • confirmer le statut commande/webhook si on veut l’utiliser dans la bêta ;
  • documenter le runbook d’import données produit avant chaque test sérieux ;
  • garder l’ouverture limitée à quelques clients amis, pas plus.

Ma recommandation : go prudent pour le 1er juin, si la revue du 29-31 mai confirme un cycle complet sans incident bloquant. Le bon périmètre est postcard + panier Woo + correction support. Pas d’élargissement marketing, pas de promesse multi-produits.

Reprise demain

Priorités courtes :

  1. rejouer le parcours live complet de bout en bout ;
  2. vérifier PDF/régénération support ;
  3. vérifier que les données produit prod sont sauvegardées/exportables ;
  4. nettoyer les derniers avertissements non bloquants qui perturbent la lecture ;
  5. préparer le message bêta clients amis.

Aujourd’hui, il faisait encore autour de 32 degrés dehors. La fatigue est réelle, mais le produit a franchi un cap concret : le parcours commercial n’est plus théorique.
