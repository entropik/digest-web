## KEREDIT : rendre la bêta moins fragile

Le premier axe KEREDIT de la journée est l'upload direct et le diagnostic.

Le commit `6ed046c` a ajouté un script de probe R2, deux configurations CORS de référence, des notes de deploy et une spécification upload plus explicite. Le bouton de rapport de bug a aussi été nettoyé pour mieux capturer ce qui compte au lieu de produire du bruit.

C'est un sujet discret, mais central pour la bêta : si un client ou un testeur importe une photo et que l'asset n'apparaît pas, il faut savoir si le problème vient du navigateur, de R2, du backend, du poll frontend, du worker ou de la miniature. Sans diagnostic, chaque test ressemble à une panne générale.

## Assets : voir rapidement ce que l'on vient d'importer

La suite de la journée à tourne autour du contrat asset.

Les commits `1d4f0e0`, `652b68a` et surtout `40bbab6` ont resserre plusieurs couches :

- rafraîchissement de preview après upload ;
- création de clé preview pour les photos importees ;
- helpers backend de contrat asset ;
- scripts d'audit et de réparation ;
- tests backend sur le contrat asset ;
- corrections du pipeline worker ;
- formatage frontend des assets ;
- miniatures dans les panneaux d'options ;
- cohérence entre statut upload, preview et affichage éditeur.

Le point important est le suivant : pour la bêta, `uploaded` puis `preview_ready` sont les états qui doivent donner confiance côté utilisateur. Le `print_ready` reste une preoccupation de production, mais il ne doit pas bloquer la visibilité dans l'éditeur.

Cette journée a donc remis l'accent au bon endroit : l'utilisateur doit voir son image, comprendre qu'elle est disponible, et continuer son édition sans attendre que tout le pipeline de production ait fini de respirer.

## Sauvegarde, autosave et geste visible

Le commit `f1a25b6` a termine le déplacement du bouton de sauvegarde vers le header global.

Ce détail avait déjà été affiné par captures : taille, trait, lisibilité, absence de doublon dans la toolbar. Ce n'est pas seulement du polish. Pour un éditeur client, la sauvegarde doit être à l'endroit où l'œil la cherche naturellement, et elle ne doit pas entrer en concurrence avec les contrôles de style.

Le commit `b97124c` a traite un problème plus profond : les freezes d'autosave pendant le drag.

La bêta postcard à besoin que les gestes de base restent fluides. Déplacer une photo, un texte ou un élément décoratif ne doit pas donner l'impression que l'application se bloqué parce qu'elle persiste trop agressivement au mauvais moment. La correction va dans le bon sens : moins de friction pendant l'interaction, persistance au bon niveau de rythme.

## Texte et contrôles d'édition

Le commit `6548090` a corrigé les contrôles de style texte.

Il a ajouté des composants communs pour les swatches couleur et le choix de police, des helpers dédiés aux styles texte, et des tests sur le catalogue de polices et les contrôles. Le panneau texte et la toolbar ont été réalignés.

Ce sujet compte parce que le texte n'est pas le chantier principal à rouvrir avant bêta, mais il doit rester stable. Un outil de texte qui perd sa police, qui présente mal ses couleurs, ou qui diverge entre panneau et toolbar donne tout de suite une impression d'éditeur inacheve.

La journée n'a donc pas relance une ambition typographique. Elle a consolide l'existant pour que les contrôles déjà exposes restent cohérents.

## Lancement Woo et logo rond

La fin d'après-midi a aussi corrigé des détails visibles autour du lancement Woo et du logo.

Les commits `ddabd28` et `341540f` ont poli le chargement de lancement, la requête utilisateurs admin et le logo rond dans la page de lancement. Le commit `7e12d3e` à ajuste l'icône de fit du cadre photo.

La logique reste la même que les jours precedents : les petites incohérences visuelles ne sont pas de simples détails quand on prépare une bêta fermée. Elles sont des signaux. KEREDIT doit donner l'impression d'un outil tenu, même si tout le flux production n'est pas encore ferme.

## Runtime local : adapter le poste

Le dernier commit KEREDIT de la journée, `1e71664`, a adapte le runtime local au Mac.

Il a touché les scripts de dev, le bootstrap DB local, le reset backend, le status, le start/stop et les guides de reprise de poste. Un helper `scripts/dev-runtime-lib.sh` a été ajouté pour centraliser une partie de cette logique.

C'est moins produit, mais très important pour la suite : une bêta ne se prépare pas bien si le poste de développement ment sur ce qu'il sert. Le 3 juin a donc aussi été une journée de fiabilisation de l'environnement.

## GOF : naissance propre de la forge

Côté GOF, le 3 juin est encore plus net.

À 08:34, le commit `ccfb2d6` posé le baseline initial de la forge : app Node, Dockerfile, Docker Compose, Postgres, Redis, worker, dashboard, stockage, queue, renderer PDF, scripts d'installation et documentation d'exploitation.

Le dossier GOF cesse alors d'être seulement un ensemble de notes. Il devient un dépôt.

Les pièces principales sont la :

- une app `gof-forge-app` ;
- un worker de rendu ;
- une file BullMQ ;
- une base Postgres ;
- un stockage local et R2 ;
- un premier renderer PDF bas niveau avec `pdf-lib` et `sharp` ;
- un dashboard opérateur ;
- des docs d'installation, de sécurité, d'exposition HTTPS et d'opérations ;
- un script de synchronisation vers la machine atelier.

Le commit `8f9dcc8` nettoie ensuite le dépôt en ignorant les backups locaux et artefacts Playwright. C'est un commit de hygiène, mais il compte : une forge atelier ne doit pas commencer sa vie Git avec des sauvegardes locales comme source de bruit.

## Reverse proxy client et exposition atelier

Le commit `621f1a1` documente l'installation reverse proxy client.

Il ajoute `docs/reverse-proxy-installation-client.md` et raccorde `README.md`, `docs/exposition-https-autonome.md` et le runbook Ubuntu. Le sujet est déjà celui du monde réel : GOF doit vivre dans l'atelier, mais certains services doivent être joignables proprement depuis l'extérieur ou depuis KEREDIT, selon les flux.

Ce n'est pas encore le pairing du 4 juin. C'est la préparation de l'exposition : comment rendre la forge joignable sans transformer chaque client en administrateur système.

## Backoffice GOF : voir les jobs

Le commit `3c6c49c`, en fin de journée, ajoute l'affichage des détails de job en modal plein écran.

Il modifié `app/src/server.js`, met à jour les dépendances et enrichit les docs opérations/runbook. C'est un signal produit fort pour GOF : l'opérateur ne doit pas seulement savoir qu'un job existe, il doit pouvoir l'ouvrir, lire son payload, ses artefacts et ses événements dans une surface confortable.

Une forge PDF n'est pas une boîte noire. Elle doit expliquer ce qu'elle a reçu, ce qu'elle a produit, et où elle a échoué.

## Ce que le 3 juin dit du 4 juin

Le billet du 4 juin raconte le flux complet :

```text
WooCommerce -> KEREDIT -> GOF -> Accurio Flux -> atelier
```

Le 3 juin raconte plutôt la préparation de ce flux.

KEREDIT travaille sur les entrees utilisateur : upload, assets, autosave, texte, lancement, runtime local.

GOF travaille sur la machine atelier : dépôt Git, stack Docker, worker, renderer, dashboard, reverse proxy, opérations.

Le lendemain, ces deux mondes commencent à se parler plus franchement autour d'Accurio. Mais sans le 3 juin, le 4 juin aurait moins de sens. Il fallait d'abord que chaque côté ait un peu plus de tenue.

## Ce qui tient

En fin de journée, plusieurs choses sont plus solides :

- les uploads ont de meilleurs diagnostics ;
- les previews assets ont un contrat plus clair ;
- les miniatures reviennent plus vite dans l'interface ;
- l'autosave gene moins les interactions ;
- les contrôles texte sont mieux factorises et testes ;
- la sauvegarde vit dans le header global ;
- le runtime local est mieux adapte au poste ;
- GOF existe comme dépôt Git et comme stack atelier ;
- le backoffice GOF commencé à donner de la visibilité opérateur.

Le dépôt `keredit-site`, lui, ne montre pas d'activité Git le 3 juin. La journée KEREDIT visible dans les traces est donc portée par le monorepo Krampouz/KEREDIT, pas par le site vitrine ou WordPress séparé.

## Ce qui reste fragile

La fragilité principale reste le parcours complet.

Chaque brique avancé, mais l'ensemble n'est pas encore un flux bêta tranquillement rejouable. Les assets doivent rester visibles sans attendre la production. L'autosave doit rester fluide sous interaction. GOF doit être joignable depuis les bons endroits, pas seulement depuis le poste de dev. Et le futur lien Accurio ne doit pas faire perdre la répartition des responsabilités : KEREDIT pour le projet et la commande, GOF pour la forge et l'opérateur, Accurio pour la production.

## Reprise

La reprise logique après le 3 juin est courte :

1. rejouer un import photo et vérifier que la preview devient visible sans attendre `print_ready` ;
2. tester un drag long avec autosave actif ;
3. vérifier les contrôles texte exposes dans la toolbar ;
4. confirmer que les scripts dev indiquent bien le runtime charge ;
5. ouvrir GOF, créer ou inspecter un job, et vérifier que le détail opérateur est lisible ;
6. préparer le pont KEREDIT -> GOF sans faire de GOF une dépendance opaque.

Le 3 juin n'était pas une journée spectaculaire par un seul gros livrable. C'était mieux que ça : une journée de serrage. L'éditeur devient moins nerveux, les assets deviennent plus prévisibles, et GOF passé du brouillon au début de machine.
