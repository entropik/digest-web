Jour 54 - Le tirage photo devient le troisième pilier

Journée dense sur le nouveau produit Tirages photo : atelier de lot, import explicite, vignettes fidèles, preview agrandie, PDF repete par quantité, fond perdu corrige, et projection vers le lancement bêta.

Horaires de session

  • Agent utilisé : Codex, transition depuis Claude Code
  • Branche de travail : dev-photo-print-workshop
  • SHA de départ visible après merge KEREDIT : fe457cd (Merge pull request #44 from [compte GitHub]/dev-keredit)
  • Dernier SHA pousse avant les corrections de fin de journée : 5a6b426 (feat: improve photo print preview controls)
  • Version applicative locale : 0.6.26
  • Commits du jour déjà poses sur le chantier tirages photo : 4
  • État de clôture : WIP local non encore commité, en test manuel cote utilisateur
  • Objectif du jour : transformer photo_print en vrai atelier de tirages, pas en sous-mode bancal de l’éditeur canvas Ce soir, la journée à une forme assez nette : KEREDIT n’a pas seulement change de nom hier, il a récupéré aujourd’hui un morceau essentiel de son métier. Les tirages photo ne sont pas un bonus. C’est un pilier d’atelier. Dans la vraie activité OOBLIK, les clients ne commandent pas uniquement des cartes, des carnets ou des objets composes. Ils envoient aussi des lots de photos, parfois beaucoup, avec une attente simple en apparence : choisir un format, vérifier les cadrages, ajuster quelques images, commander un ensemble propre. Simple en apparence seulement. Le produit photo_print oblige à poser une autre logique que celle du canvas libre. Il ne faut pas donner au client un éditeur complet. Il faut lui donner une planche de tirages fiable.
  • Temps cumulé :264h+

Une nouvelle famille produit

La journée a commencé par une prise de conscience produit : il manquait une famille importante.

Le site actuel de Print Ooblik possède déjà ce geste : importer beaucoup d’images, les voir sous forme de cartes, choisir une quantité par photo, appliquer un mode de recadrage, puis produire un PDF page par page.

Mais les captures historiques n’étaient pas une référence de design. Elles étaient une référence métier.

La direction retenue pour KEREDIT :

  • garder le shell existant ;
  • garder la barre d’actions à gauche ;
  • garder l’identité visuelle KEREDIT ;
  • ne pas créer un second éditeur ;
  • ne pas ajouter texte, decos, templates ou calques ;
  • faire de la surface centrale une vraie planche de tirages.

Cette distinction a été importante. Le tirage photo n’est pas une page blanche. C’est un lot.

Importer d’abord, manipuler ensuite

Le premier gros ajustement UX a été de séparer clairement l’étape d’ajout.

Au lieu d’un panneau latéral qui mélangeait bibliothèque client et photos du lot, le bouton PHOTOS ouvre maintenant une modale explicite :

  • Importer des images ;
  • Depuis mon telephone ;
  • Mes photos ;
  • Google Photos.

La planche centrale reste le seul endroit ou les photos du lot sont visibles.

C’est beaucoup plus sain mentalement. Le client ne se demande plus s’il est dans une bibliothèque, un panier, un canvas ou une sélection. Il ajoute des photos, puis il travaille son lot.

La modale a été agrandie, le fond floute, et le comportement a été ajusté : si le client ouvre une source secondaire puis revient sans avoir ajoute de photo, la première modale reste disponible. Pas de cul-de-sac, pas de confusion.

Une barre de progression a aussi été ajoutée pour l’upload ordinateur. C’est un détail en taille, mais pas en perception : quand on importe 20, 50 ou 100 photos, le temps doit être raconté.

La planche doit montrer le tirage, pas une miniature

Le cœur de la journée a été la géométrie.

Au début, les vignettes affichaient des images. Ce n’était pas suffisant.

Une vignette de tirage doit montrer :

  • le format choisi ;
  • le mode de recadrage ;
  • la rotation ;
  • les marges quand elles sont volontaires ;
  • le cadrage réel ;
  • la quantité ;
  • l’état de sélection.

Il a fallu corriger plusieurs choses visibles :

  • supprimer les labels inutiles sous les vignettes ;
  • supprimer les doubles cadres parasites ;
  • garder une feuille de tirage identique pour un même format ;
  • afficher la photo dans la feuille, clippee proprement ;
  • appliquer la rotation à l’image, pas à la carte ;
  • ajouter la rotation individuelle directement sur chaque carte ;
  • centrer les contrôles ;
  • rendre le déplacement de cadrage decouvrable avec un effet hover et une petite croix de déplacement.

Le contrat est devenu plus clair :

la carte n’est pas une miniature de fichier, c’est une miniature du tirage final.

C’est la bonne abstraction.

Le grand aperçu devient cohérent

Le grand format a ensuite été remis au même contrat que les vignettes.

Au lieu d’avoir une géométrie différente entre la carte et la preview, les deux surfaces utilisent le même rendu partage. Le client peut ouvrir une photo, naviguer à gauche/droite, régler rapidement :

  • luminosité ;
  • contraste ;
  • saturation ;
  • rotation gauche/droite ;
  • mode de recadrage ;
  • bordure blanche quand le mode le permet ;
  • reset de l’image.

La saturation descend maintenant jusqu’au noir et blanc, ce qui est beaucoup plus naturel : si un curseur de saturation existe, le bout gauche doit permettre le noir et blanc.

La barre d’outils du grand aperçu a été simplifiée plusieurs fois : moins de pictos inutiles, moins de rouge, plus de tonalite KEREDIT, puis une grille claire de sliders et d’actions.

Ce n’est pas seulement plus joli. C’est plus calme. Et dans un atelier de lots, le calme est une fonctionnalité.

Bordure blanche réglable

Une demande client très concrète est revenue : choisir la taille de la bordure blanche.

Le choix V1 :

  • uniquement pour le mode Bordure blanche ;
  • pas de modification de Polaroid ;
  • minimum 1 cm pour éviter les problèmes de coupe ;
  • maximum 5 cm ;
  • pas de 0 cm, parce que ce serait une fausse bordure blanche ;
  • valeur persistée par page via photoPrintBorderMm.

La géométrie partagée calcule maintenant la bordure en millimètres physiques, pas en pourcentage arbitraire. Un 10x15 avec 1 cm de bordure donne donc un cadre image différent d’un 20x20 avec 2 cm, comme il se doit.

C’est exactement le genre de détail qui transforme une démo en outil d’atelier.

PDF : répétition, cohérence, fond perdu

Le PDF a progresse lui aussi.

Le contrat principal est posé :

  • une photo avec quantité 3 produit 3 pages PDF identiques ;
  • l’ordre du PDF suit l’ordre de la grille ;
  • le rendu PDF utilise la même normalisation photo_print que l’export ;
  • selected_quantity et pages_count représentent le total de tirages, pas le nombre de photos uniques.

En test manuel, le PDF correspond maintenant à l’éditeur.

Un dernier point de production est apparu ce soir : le fond perdu.

Pour les tirages photo, le fond perdu doit être de 2 mm, et en mode Plein format, l’image doit aller jusqu’au bord du fond perdu. Il ne doit pas y avoir un liseré blanc exporte autour de la photo.

La correction est en WIP local ce soir :

  • fond perdu effectif photo_print force à 2 mm ;
  • seed produit tirages-photo aligne ;
  • payload PDF/export aligne ;
  • image Plein format étendue au fond perdu ;
  • modes avec blanc volontaire conserves tels quels.

Checks déjà passes sur cette correction :

  • pnpm --filter @krampouz/shared test:photo-print
  • pnpm --filter backend test -- pdf-renderer project-export-payload
  • pnpm --filter @krampouz/shared typecheck
  • pnpm --filter backend typecheck
  • pnpm --filter frontend typecheck
  • git diff --check

Le test manuel final reste en cours cote utilisateur.

Upload rapide, dimensions lentes

Un bug important a aussi été identifie : certaines photos pouvaient être ajoutées trop tôt au projet, avant que le backend ait calcule leurs dimensions réelles.

Symptôme : une image deformee ou mal homothétique, parce que le projet avait récupéré un asset-coquille avec width_px=0, height_px=0, aspect_ratio=1.

La solution retenue est plus subtile qu’un simple blocage :

  • affichage immédiat d’une carte temporaire avec l’objet local navigateur ;
  • lecture locale des dimensions pour un aperçu fluide ;
  • pas de persistence dans pages_data tant que le serveur n’a pas les vraies dimensions ;
  • /api/assets/status remonte maintenant dimensions et orientation ;
  • l’auto-ajout au lot attend un asset serveur fiable.

C’est le paradoxe du temps présent applique au web-to-print : il faut que le client voie vite quelque chose, mais il ne faut pas sauvegarder trop vite quelque chose de faux.

Navigation et simplification

La colonne gauche a aussi été simplifiée.

Le menu LOT a disparu comme entrée séparée. Les actions de lot sont maintenant dans Reglages, avec :

  • sélection ;
  • quantité de sélection ;
  • rotations ;
  • recadrage de sélection ;
  • suppression avec confirmation.

La suppression a été déplacée et sécurisée, parce qu’un bouton poubelle trop proche d’une action de deselection est un piège. Le produit doit éviter ce genre de confusion avant même que le support client ne le découvre.

La barre supérieure inutile a été supprimée. Le zoom n’est plus affiché sur ce produit. La session garde le bouton bug, mais le reste se retire.

Less is more, surtout quand la grille contient beaucoup de photos.

Sauvegarde et fermeture

Un autre garde-fou global a été remis sur la table : prevenir l’utilisateur quand il ferme l’onglet.

Le comportement attendu est volontairement strict : même si une sauvegarde a eu lieu, fermer l’éditeur doit afficher un avertissement. Pas parce que tout est forcément perdu, mais parce que l’éditeur est un espace de travail, et que la fermeture accidentelle est trop facile.

Le warning navigateur est maintenant actif dans l’éditeur.

Ce n’est pas spectaculaire. Mais le jour ou un client ferme par erreur un onglet après 80 photos, ce genre de garde-fou devient invisible parce qu’il a fait son travail.

État d’esprit

La journée a été intense.

Pas intense au sens “on ajoute une feature après l’autre”. Intense parce que le produit a resiste. Les vignettes n’étaient pas bonnes. Le cadrage n’était pas juste. Le PDF avait encore un bord blanc. Le grand aperçu n’avait pas le même contrat que la grille. L’upload voulait être rapide mais pouvait sauvegarder trop tôt.

Et pourtant, le fil s’est clarifié.

Le bon modèle est apparu :

un atelier de tirages n’est pas une bibliothèque photo, pas un canvas, pas une galerie. C’est une planche de production.

Quand cette phrase tient, beaucoup de choix deviennent plus simples.

Prospective bêta

On commence à voir le jour de la bêta.

Pas comme un feu d’artifice. Plutôt comme une ouverture d’atelier un matin : quelques clients réels, des produits limites mais compréhensibles, des exports que l’on peut imprimer, des bugs que l’on sait nommer, et une interface qui ne promet pas plus qu’elle ne sait faire.

Le lancement bêta devra probablement ressembler a cela :

  • un flux carte postale solide ;
  • un flux tirages photo utilisable sur un vrai lot ;
  • un flux carnet suffisamment cadre pour ne pas piéger le client ;
  • WooCommerce capable de reprendre un projet et de porter la commande ;
  • Google Photos et téléphone disponibles comme options de bêta, pas comme promesses marketing absolues ;
  • un PDF que l’atelier peut vérifier sans deviner ce que le client voulait ;
  • un support interne qui sait lire l’état d’un projet.

Le plus important ne sera pas d’avoir “toutes les features”.

Le plus important sera que le premier client bêta puisse dire :

J’ai compris quoi faire, j’ai vu ce que j’allais recevoir, et l’atelier peut produire ce que j’ai commandé.

Si KEREDIT atteint ce contrat-la, la bêta aura le droit d’exister.

État final

État à la clôture :

  • branche dev-photo-print-workshop active ;
  • PR KEREDIT mergée en amont ;
  • produit tirages-photo cree et déjà largement fonctionnel ;
  • modale d’ajout explicite en place ;
  • grille de tirages en place ;
  • vignettes fidèles au format et au cadrage ;
  • recadrage rapide par déplacement ;
  • preview agrandie harmonisee ;
  • bordure blanche réglable ;
  • PDF cohérent avec l’éditeur ;
  • fond perdu photo-print en cours de validation manuelle ;
  • documentation produit déjà mise à jour ;
  • billet du jour ajoute ;
  • pas de commit de clôture encore pose sur ce WIP.

Demain, il faudra finir ce qui doit être fini : test manuel complet, éventuelles corrections PDF, commit propre, push, puis probablement PR de consolidation.

Mais ce soir, le sentiment est bon.

Fatigue présente, oui. Mais pas une fatigue de dispersion.

Plutôt la fatigue d’une journée ou un troisième pilier produit a commencé à prendre sa vraie forme.

Rideau.
