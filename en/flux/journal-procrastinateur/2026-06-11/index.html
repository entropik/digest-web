Day 81 – Observe the beta before expanding it

VPS clean-up, beta observability, release 0.7.0, OpenReplay fix and refinement of the WooCommerce client projects area.

This commit was reconstructed on Friday 12 June 2026 from the Git history and the repository’s files. The end-of-day state corresponds to KEREDIT 0.7.3 locally, with several intermediate milestones: 0.6.103, 0.7.0 and 0.7.2.

Brief conclusion

Today transformed the beta into a more observable and usable system. The morning was spent addressing operational issues: VPS disk pressure, Docker retention and the observability stack. The evening saw the resolution of another critical issue: making the beta launch more user-friendly, updating OpenReplay with the correct tracker version, and then streamlining the WooCommerce client project area.

The common thread is simple: before expanding the beta, KEREDIT must provide a clearer picture of what is happening, and the client must be able to find their projects without having to navigate a technical interface.

VPS and Docker retention

The commit 5e899e9 formalises the post-deployment clean-up of Docker artefacts. This isn’t a product change, but it addresses a very real risk: a functioning stack can still become fragile if images, layers and the BuildKit cache saturate the disk.

The right decision was to schedule retention after a successful deployment, as a best-effort clean-up task, without affecting volumes or business data. The documentation also maintains the distinction between the nominal GHCR path and the local fallback.

Observability beta

The first major technical phase is observability.

The commits in the `feature/observabilite-beta` branch, merged by 5b80bd5, add or stabilise:

  • VictoriaMetrics, VictoriaLogs and Grafana on the [serveur de production] side;
  • node-exporter, cAdvisor, postgres-exporter, redis-exporter, vmagent and Vector on the KEREDIT VPS;
  • Docker logs sent to VictoriaLogs;
  • backend, worker and BullMQ queue metrics;
  • initial front-end product events to track launch, autosave, upload, checkout and errors.

The 39c1e46 commit marks this phase at 0.6.103.

Two operational fixes followed swiftly: 96f3f3f and db5bb3c ensure that data collection begins upon deployment and that the ‘message’ field in Pino logs is correctly mapped to VictoriaLogs. 44d5366 and 6bb4b10 also document Hetzner’s SMTP configuration: you must use port 587, not the blocked outgoing ports.

Beta release 0.7.0

The commit 88f677a moves KEREDIT to 0.7.0.

This is not a major marketing roll-out. It is a clear signal: the friends’ beta can begin, with a controlled scope, priority given to postcard and active workshop support still very much in place.

The key point is not to confuse ‘0.7.0’ with general stability. Rather, this version signifies that the product is consistent enough to start exposing the workflow to close clients and learning from real-world feedback.

Customer catalogue and hidden options

The commits ‘916f523’, ‘cd2b79e’, ‘2760f2a’ and ‘0aa224a’ enhance the customer area:

  • decorative assets become visible to clients when they need to be;
  • customer catalogues remain available even if a backfill queue fails;
  • Accurio technical options no longer clutter the customer summary;
  • the list of client projects is now easier to read.

These are minor changes, but they mitigate a common beta risk: exposing clients to internal concepts when the production team should be managing that complexity.

OpenReplay: correcting actual compatibility

The evening also highlighted a limitation of observability: simply integrating a tool is not enough if the compatibility matrix is incorrect.

The commits 441352e, 116300d, the merge b79687c, and the release c1887d1 fix the OpenReplay tracker. The self-hosted v1.23 backend did not support tracker 18: sessions appeared to start but the batches failed silently. The fix therefore reverts to the compatible line ~17.2.11 and documents this constraint in the changelog.

The expected result is much more useful for the beta: if a client freezes, the support team must be able to understand the sequence of events rather than having to guess.

WooCommerce client projects

The end of the day sees a return to the customer-facing interface.

The commit 8c554bb consolidates actions and thumbnails in the project lists, then b59acdb applies the same changes to the WordPress plugin. The aim is to keep key actions visible without turning every project line into a technical specification.

The buttons Modifier, Dupliquer and Supprimer remain front and centre. Project details, options and technical information remain available, but are less intrusive.

Verification and limitations

Today’s commits mainly indicate domain-specific validations: CI, releases, changelog, UI fixes and plugin publication. The reconstructed log is not intended to replace current CI logs or GitHub checks.

The key point to monitor following today’s work is the consistency across three areas:

  • the client project area in KEREDIT;
  • the client project area in WooCommerce;
  • the WordPress plugin published via its private manifest.

A visual improvement on the repository side is only valid if the plugin’s publish and the live WordPress installation are indeed running the same version.

Closure decision

11 June points us in the right direction: do not expand the beta without proper monitoring, and do not expose clients to the technical inner workings of the development environment.

KEREDIT is becoming more observable, more cautious with its releases, and more streamlined in its client interface. This is exactly the kind of consolidation that makes a beta useful: less noise, more traceability, and a more comprehensible client interface.
