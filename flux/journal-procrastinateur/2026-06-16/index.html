Le Zine sort du flou

La journée commence par un produit qui cesse d’être seulement une intention : le Zine devient un produit vendable, tarifable, raccordable a WooCommerce et transmissible à l’atelier.

Le premier mouvement concerne les quantités. Un zine ne se vend pas comme une carte postale a quantités fixes. Il a besoin d’une plage continue, avec un minimum, un maximum et un pas, sans créer artificiellement un attribut pour chaque quantité possible. Les travaux des 15 et 16 juin convergent donc vers un mode range dans la fiche produit, puis vers un affichage et une validation cote WooCommerce.

Aujourd’hui, le sujet devient surtout tarifaire : les paliers ne sont plus traites comme de simples remises abstraites, mais comme des prix unitaires par palier. C’est plus proche de la réalité atelier : à partir d’une quantité, le prix unitaire change. Le devis KEREDIT et l’affichage Woo doivent donc parler le même langage.

Le Zine gagne aussi un workflow CPD/release local via .codex-skills/cpd/ et .codex-skills/quick-vps-release/. Ce n’est pas le cœur produit visible par le client, mais c’est important : un produit éditorial demande des gestes repetables, pas seulement un correctif de prix dans l’admin.

Le prix devient plus atelier

Le lot prix a continue de quitter le bricolage. Le commit 3004f00 introduit plusieurs modes d’impact pour les attributs de fabrication :

  • montant fixe ;
  • montant par quantité ;
  • pourcentage ;
  • pourcentage par quantité.

Ce détail est très concret pour un atelier. Un papier, une finition, une reliure ou un traitement ne se comporte pas toujours comme une surcharge fixe. Certaines options doivent suivre la quantité, d’autres le total, d’autres encore une logique de matrice.

Le commit 393c645 corrige ensuite un point sensible : les paliers de quantité doivent être lus comme des prix unitaires, pas comme une réduction mal interpretee. C’est le genre de correction qui évite une catastrophe silencieuse : un prix peut sembler cohérent à l’écran tout en étant faux dans la logique commerciale.

WooCommerce est aussi ramené dans le même flux. Le total KEREDIT apparaît directement sur la fiche produit Woo, avant l’ouverture de l’éditeur, et le connecteur accepte des options vides comme une vraie absence d’option. Ce n’est pas spectaculaire, mais cela rend le parcours client moins magique et moins fragile.

Couverture, cahier, tranche : le livre devient un contrat

Le gros nœud technique du jour est le contrat livre/zine entre KEREDIT et GOF.

Jusqu’ici, le risque était de penser “un projet = un PDF”. Pour un zine ou un livre, ce n’est plus assez précis. L’atelier doit distinguer :

  • la couverture ;
  • le cahier ;
  • la tranche quand elle existe ;
  • les formats physiques ;
  • les pièces a envoyer vers Accurio.

Le commit c2e615f exporte donc un contrat plus explicite pour le livre : surface de couverture, largeur de tranche, épaisseur papier, indexes de couverture, hints de production. Le retour de review sur bc5a504 a corrigé un point important : dans le modèle actuel, la couverture a plat est editee sur la page 0, y compris la zone de quatrième de couverture. Pointer le dos vers la dernière page aurait fait perdre du contenu aux rendus GOF/atelier.

Ce correctif est typique du passage d’un éditeur visuel à une chaîne de production. L’interface peut montrer une surface unique, mais le contrat doit expliquer comment cette surface sera decoupee, lue et produite.

Accurio cesse d’être un simple champ

La fin d’après-midi pousse le sujet plus loin : Accurio n’est plus seulement un nom de produit ou une imprimante dans un champ _accurio. Il faut mapper la production par format et par pièce.

Le commit KEREDIT 22d6044 introduit cette logique :

  • mappings Accurio par produit ;
  • jobs de production par artifact_kind ;
  • rôles de pièce print_master, cover, cahier ;
  • choix de services Accurio visibles et normalises ;
  • backoffice KEREDIT capable de configurer ces correspondances.

Cote GOF, le commit 9ed9932 répond au même besoin : support des mappings scindes et synchronisation du catalogue. GOF lit le catalogue Accurio dans le réseau atelier, KEREDIT le consomme via GOF, puis le produit KEREDIT peut associer la bonne pièce au bon produit Accurio.

Le correctif KEREDIT 6cde819 remet la synchronisation du catalogue Accurio d’aplomb : l’UI admin et l’API ne doivent pas se desaccorder sur la forme du catalogue. C’est petit en nombre de lignes, mais central pour le flux : si le catalogue ne remonte pas correctement, toute la promesse “client-first sans terminal” retombe.

GOF devient un cockpit de dossiers

GOF a pris un vrai virage aujourd’hui.

Le commit 2988888 pivote le backoffice vers un cockpit de dossiers. Ce n’est plus seulement une liste technique de jobs PDF. GOF commence à devenir l’écran atelier qui regroupe les rendus, les pièces, les états courants, les sorties livre, les actions Accurio et le suivi de production.

Ce changement est logique avec le Zine. Un livre ou un zine n’est pas une seule image finale. C’est un dossier de production : couverture, cahier, version courante, historique, validation, envoi Accurio.

Le dernier commit GOF, cb56ce4, augmente aussi la durée du verrou BullMQ pour les rendus longs. C’est un détail d’exploitation, mais il compte : plus les produits deviennent réels et lourds, moins le worker peut supposer que tout se rend vite. Le système doit tenir un rendu long sans le considérer a tort comme perdu.

Le detour VPS et la réparation du workflow

La journée a aussi eu son episode très opérationnel : le deploy VPS.

Le VPS a été remis sur la version 0.7.31 au SHA c4d6cc6, mais ce deploy a d’abord du passer par le fallback manuel. La raison était bete et coûteuse : GitHub expose les workflows manuels depuis la branche par défaut main, alors que le bon workflow Deploy Beta VPS vivait sur dev. Cote utilisateur, cela a donne l’impression légitime de perdre du temps pour rien.

La correction a été de porter l’infrastructure de deploy sur main, sans merger le code applicatif. La PR #54 a finalement ajouté aussi deux garde-fous utiles :

  • quand image_tag est vide, le workflow build/push les images GHCR taggees avec le SHA avant de vérifier et déployer ;
  • les variables d’observabilité ne bloquent plus l’interpolation Compose quand l’app peut démarrer sans elles.

Le résultat est simple : le prochain deploy normal doit pouvoir repartir depuis GitHub Actions, workflow Deploy Bêta VPS, avec ref=dev, sans rebuild manuel sur le VPS.

Ce que raconte la journée

Le fil de la journée n’est pas “on a ajouté le zine”. C’est plus large :

Produit vendable -> prix correct -> contrat PDF livre -> mapping Accurio -> dossier GOF -> deploy reproductible

Le Zine oblige KEREDIT a devenir plus précis. Il force les quantités libres, les prix unitaires par palier, les options atelier qui modulent vraiment le prix, la séparation couverture/cahier, et le mapping Accurio par pièce.

GOF, de son cote, cesse d’être seulement un moteur de rendu. Il devient progressivement le poste atelier qui comprend les dossiers, les artefacts et les actions de production.

Accurio n’est plus “le truc au bout”. Il devient un contrat de nommage, de services, de pièces et de catalogue. Et comme il vit dans le réseau atelier, la bonne architecture reste : KEREDIT orchestre le métier, GOF parle a Accurio, l’atelier produit.

Suite logique

Demain, la bonne suite n’est pas de rajouter encore une couche.

Il faut rejouer un chemin complet et étroit :

  1. produit Zine dans KEREDIT ;
  2. quantité libre et prix Woo lisible ;
  3. projet édite ;
  4. export GOF avec couverture/cahier ;
  5. mapping Accurio par pièce ;
  6. dossier visible dans GOF ;
  7. rendu long tenu par le worker ;
  8. deploy via GitHub Actions, pas via fallback manuel.

Le produit commence à ressembler à une chaîne. La prudence maintenant, c’est de la faire tourner bout a bout sans changer trois contrats en même temps.
