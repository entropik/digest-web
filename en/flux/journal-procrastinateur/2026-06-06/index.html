Day 76 – WooCommerce becomes a genuine KEREDIT gateway

Google Photos has been properly reconnected, page previews have been restored, and the WooCommerce plugin has been redesigned to allow KEREDIT to control quantities, formats and options.

Session timetable

  • Date: Saturday 6 June 2026.
  • Provider: Codex.
  • Environments: Krampouz/KEREDIT, WordPress/WooCommerce connector, KEREDIT VPS, Woo test site.
  • Source branch: dev.
  • Source status at the end of the day: e64994f, application version 0.6.70.
  • KEREDIT WordPress plugin: 0.1.34, private manifest aligned with updates.ooblik.com.
  • Application VPS checked during the day: version 0.6.69 on bb0128a, prior to the latest plugin and splash screen adjustments.
  • Time range observed via KEREDIT commits: 10:16 – 20:25.
  • Minimum cumulative time since the start of the log: approximately 407h53+.

Brief conclusion

The day began with a visible regression in the editor: Google Photos did not clearly tell the client what to do when its authorisation had expired. It ended much further down the line: WooCommerce can now display a product listing driven by KEREDIT, without letting Woo invent a quantity, format or ‘Add to basket’ button alongside the creation workflow.

The guiding principle is simple: KEREDIT remains the industry standard, WooCommerce becomes the commercial gateway, and the printer must be able to configure this integration without having to decipher cryptic fields.

Google Photos: breaking the loop

The first symptom was on the publisher’s side: the Google Photos import would return with a ‘401’ on /api/google-photos/picker-sessions, then the interface would display a status that was too vague. The customer would mainly see ‘Try again’, click it, and end up back in the same loop.

The fix distinguished between two scenarios:

  • the KEREDIT session may still be valid;
  • the Google Photos link, however, may have expired, been revoked or be invalid.

The button has therefore become more explicit: the user must reconnect Google Photos. The workflow discards the old Google link, re-initiates OAuth and avoids giving the impression that a simple network retry can fix an invalid external authorisation.

Reference commit: 805fbf0 (fix: make Google Photos reconnect explicit).

Page previews: bringing reality back into view

Second visible fix: page previews should no longer remain as placeholders when the actual images are available. The page browser and overview now use more reliable preview areas, with asset URLs resolved, dedicated tests and expanded footer controls to prevent buttons from being too close together.

It’s not spectacular, but it’s exactly the sort of detail that builds trust in the editor: if a page exists, the interface must show that page, not an empty square that makes you doubt whether it’s been saved.

Reference commits:

  • 5008672 (fix: show real page previews by default) ;
  • 5ad4acb (fix: widen bottom preview controls).

WooCommerce: no longer buying before creating

The main task of the afternoon was the WooCommerce product page when a product is managed by KEREDIT.

Previously, WooCommerce still displayed its native controls: WooCommerce quantity, ‘Add to basket’ button, standard e-commerce logic. For a KEREDIT product, this is risky: the customer must not purchase a generic item before going through the editor and creating a customised project.

The connector now replaces this block with the expected workflow:

  • the direct WooCommerce controls are removed for KEREDIT products;
  • the creation button becomes the main action;
  • the quantity displayed is taken from the values authorised by KEREDIT;
  • launching the editor carries over the quantity, format and selected options.

Reference commit: 788557e (Fix KEREDIT Woo product purchase controls).

KEREDIT remains the master reference

Today’s key decision: WooCommerce must not invent product attributes. Quantities, formats and options come from KEREDIT. WooCommerce can choose what it displays to the customer, in what order, with what labelling and what tooltips, but it does not become the business data source.

The backend therefore exposes a product configuration that is readable by Woo. The plugin synchronises this data with the product page, keeps track of the last synchronisation, and provides a “Synchronise now” button to quickly push through any changes made in KEREDIT.

What is now covered:

  • permitted quantities;
  • available formats;
  • options from the KEREDIT product, for example paper or Accurio;
  • customisable customer labels;
  • visible customer descriptions;
  • visibility by attribute;
  • display order on the product details page.

Reference commit: bb0128a (Add KEREDIT Woo product options UI).

The admin UX was iterated live

The first version worked, but it was constrained by the WooCommerce “Product Data” panel: fields were too small, checkboxes were hard to read, accordions were poorly suited, and space was truncated. It was functional, but not acceptable for a printer who has to configure products all day long.

The KEREDIT configuration was therefore moved to a dedicated metabox, with a clearer structure:

  • a configuration header;
  • a synchronisation status;
  • an ‘Instant Sync’ button;
  • three tabs: login, customer view, advanced;
  • clear toggle switches;
  • full-width fields;
  • a client description by attribute;
  • an explicit display order;
  • an ‘Advanced’ mode reserved for technical constraints.

The client profile followed the same logic: the attributes are stacked, not aligned in a row, and then right-aligned to match the layout of the Woo theme observed.

Plugin versions released during this phase:

  • 0.1.29 : removal of native Woo controls and the KEREDIT Creation block;
  • 0.1.30 : manual synchronisation and initial KEREDIT attributes;
  • 0.1.31 : more user-friendly tabs, toggles and fields;
  • 0.1.32 : dedicated metabox outside the restrictive Woo panel;
  • 0.1.33 : stacked attributes and display order;
  • 0.1.34 : right-alignment of attributes on the product page.

Key commits:

Final polish: Amiga-style editor interface

The day ended with a deliberately stylised loading screen, in the style of Amiga Workbench: pixel art, an animated grid, a solid panel with sharp shadows, cyan/magenta/yellow/black, a workshop sheet, cutting marks, a ruler, a craft knife, a magnifying glass and loading indicators in discrete steps. This isn’t just a simple spinner placed in the middle of the page: it’s a buffer between WooCommerce and the editor.

The behaviour is also technically well-defined. The splash screen is handled by a dedicated store, cached in sessionStorage during launch, visible for at least two seconds to prevent overly rapid flashing, then animated out of view once the editor is ready. After 8.5 seconds, it switches to a long-wait state and offers to reload. If the launch fails, it displays an error message rather than leaving the customer facing a blank screen.

The work also addresses accessibility and validation: the overlay at role="status" reports its status via aria-live, complies with prefers-reduced-motion, and the Playwright smoke test now waits for the splash screen to appear and then disappear before validating the editor shell.

Reference commit: e64994f (feat: add editor launch splash).

What’s stable tonight

  • dev is aligned with origin/dev at e64994f.
  • The application versions are aligned at 0.6.70.
  • The KEREDIT WordPress connector is available at 0.1.34.
  • The WooCommerce product feed no longer offers direct purchase for a KEREDIT product.
  • The attributes displayed on the client side come from KEREDIT, but remain configurable within WooCommerce for order, labelling and visibility.
  • Reconnecting to Google Photos is now an explicit action.
  • Page previews now have a more concrete representation.
  • Launching the editor now features a proper loading screen, consistent with KEREDIT’s visual identity.

What remains to be monitored

The project has moved from a technical integration to a fully-fledged product interface. We will now need to test with products that are more complex than the test postcard: different paper types, different formats, workshop options, Accurio specifications, and customer descriptions that are short enough to remain legible on mobile devices.

The main point of focus is no longer “does Woo call KEREDIT?”. Rather, it is: can a printer configure ten different products without getting lost, and does a customer still understand what they are choosing before opening the editor?

This evening, the answer began to take shape.
