FOCUS - Software Factory: code is no longer the bottleneck

Seven videos all point to the same idea: automating the build, code, testing, review and pull request pipeline shifts the bottleneck to human attention.

Il y a des tendances que l’on reconnaît à un produit. Celle-ci se reconnaît à une phrase soudain répétée partout. En quatre mois, Boundary, Tessl, Mastra, Matt Pocock, IndyDevDan et Owain Lewis ont tous publié leur version de la software factory. Cinq des sept vidéos de cette sélection sont sorties au mois d’août 2026.

Après les assistants, les agents autonomes, les fermes d’agents et les ADE, voici donc l’usine. Le mot est chargé de promesses un peu trop parfaites : on dépose un ticket à une extrémité, une pull request testée et révisée ressort à l’autre. Entre les deux, des agents trient, planifient, codent, lancent les tests, commentent le diff, corrigent leurs propres erreurs et préparent le commit. L’humain n’entre plus dans chaque conversation. Il surveille la ligne.

La tendance est réelle. Son nom est ancien. Et son enjeu n’est déjà plus de produire davantage de code, mais de décider ce qui mérite d’être produit et de prouver que l’on peut le livrer.

Une idée de 1968, avec enfin des ouvriers logiciels

La software factory n’est pas née avec Claude Code. Dans le rapport de la conférence de l’OTAN de 1968, Robert W. Bemer décrivait déjà un environnement de production contrôlé par la machine, réunissant fichiers, compilation, assemblage, tests et distribution. Hitachi inaugura dès 1969 une organisation explicitement baptisée Software Works. NEC, Toshiba et Fujitsu suivirent dans les années 1970. Microsoft relança encore l’expression au début des années 2000 autour des lignes de produits, des modèles et de la génération de code.

Chaque époque cherchait à faire passer le logiciel de l’artisanat à l’industrie par la standardisation, la réutilisation et l’outillage. Chaque époque se heurtait aussi à la même différence avec une chaîne automobile : le logiciel n’est pas la répétition d’un objet stabilisé. Le besoin bouge, chaque projet transporte son histoire et un programme peut être syntaxiquement parfait tout en résolvant impeccablement le mauvais problème.

Les participants de 1968 avaient même anticipé le piège. Dans les discussions du rapport, Fraser observe que l’automatisation peut cacher les informations qu’une supervision humaine adaptative aurait perçues, tandis que Ross avertit du danger d’automatiser un processus que l’on ne comprend pas encore. Cinquante-huit ans plus tard, la mise en garde n’a pas pris une ride.

Ce qui change en 2026 n’est donc pas le rêve d’usine. C’est l’arrivée d’un composant capable de lire un ticket en langage naturel, d’explorer un dépôt, d’utiliser ses outils et de réagir aux résultats. Les anciennes factories automatisaient surtout l’environnement autour du programmeur. Les nouvelles tentent d’automatiser le parcours de la décision jusqu’au changement validé.

La matière première n’est plus une spécification formelle. C’est une issue imparfaite. Le produit fini n’est plus un paquet de code. C’est une proposition de changement accompagnée de ses preuves.

La factory est une boucle, pas une foule

Les sept vidéos montrent des implémentations différentes — Machinist, encore présenté sous son ancien nom Factory dans la vidéo de juillet, Kikimora, Sandcastle, Mastra Factory ou une collection de scripts — mais leur architecture converge :

Issue → triage → plan → environnement isolé → implémentation → tests → revue → révision → PR → décision humaine

Le gestionnaire de tickets devient le plan de contrôle. Un label GitHub, une colonne Linear, un message Slack ou une tâche planifiée déclenche le travail. Un agent de triage transforme la demande en critères d’acceptation, choisit un dépôt et évalue si le sujet peut être délégué. Un worker crée ensuite un worktree, une VM ou une sandbox jetable, installe le projet et confie l’implémentation à Codex, Claude Code ou un autre harnais.

Ces trois isolations ne sont pas équivalentes. Un worktree empêche surtout deux branches de se marcher dessus ; il ne protège ni les secrets, ni le réseau, ni le reste du disque. L’exécution réellement autonome exige une frontière de sécurité en plus d’une frontière Git.

Les tests, linters et règles d’architecture forment les premiers postes de contrôle. Un échec renvoie automatiquement la pièce vers l’agent qui l’a produite. Une session distincte relit ensuite le diff, avec un autre contexte et parfois un autre modèle. Ses objections alimentent une nouvelle révision. La PR n’apparaît dans la file humaine qu’après plusieurs tours de cette boucle.

Ce découpage est plus important que le nombre d’agents. Un essaim peut produire beaucoup de bruit en parallèle. Une factory transforme le travail en états explicites, conserve les artefacts entre les étapes, impose des transitions et sait pourquoi une tâche est bloquée. Elle remplace le tête-à-tête avec un agent par un système reproductible.

IndyDevDan formule au passage une règle saine : le code propose la structure, les agents proposent le travail, le code tranche et valide. Il est absurde de louer un modèle pour redécouvrir qu’une commande de test a réussi. Les contrôles déterministes doivent rester des programmes rapides, inspectables et bon marché. Le raisonnement probabiliste intervient là où une règle ne suffit plus.

Le goulot d’étranglement remonte la chaîne

Le premier goulot des agents de code était leur surveillance. Il fallait ouvrir une session, répondre aux permissions, rappeler le contexte, constater l’échec et relancer. Les sandboxes, les worktrees et les permissions préconfigurées permettent désormais à plusieurs agents de travailler pendant que leur opérateur fait autre chose.

Cette victoire crée immédiatement le goulot suivant : l’attention. L’expérience de Harness engineering chez OpenAI est spectaculaire — environ un million de lignes et 1 500 PR produites sans code saisi manuellement — mais sa leçon la plus durable est ailleurs. Quand le débit de code a augmenté, la capacité humaine de QA est devenue la contrainte fixe. L’équipe a dû rendre l’interface, les logs, les métriques et les traces directement lisibles par les agents pour qu’ils puissent reproduire et vérifier davantage de problèmes eux-mêmes.

Puis le goulot s’est encore déplacé. Avec Symphony, le tableau de tickets distribue automatiquement chaque tâche disponible à un agent permanent. OpenAI rapporte jusqu’à cinq fois plus de PR fusionnées dans certaines équipes, tout en expliquant que le problème devenu critique était le changement de contexte humain : examiner un résultat, retrouver l’intention, décider, puis passer au suivant.

Tessl raconte la même rupture avec Kikimora. L’entreprise affirme déléguer plus de 90 % du travail et améliorer régulièrement sa vitesse. Mais la question qui subsiste dans son propre récit est la meilleure de toute cette sélection : peut-on apposer son nom sur une PR que l’on n’a pas écrite ? Ce témoignage reste celui d’un éditeur présentant son produit, pas une mesure indépendante. Il décrit néanmoins très bien le passage d’un goulot de production à un goulot de confiance.

La revue automatique tente à son tour d’absorber cette contrainte. GitHub annonçait en mars avoir dépassé 60 millions de revues Copilot. Une étude récente, SWE-Review, transforme la revue en boucle générer → examiner → réviser : sur SWE-bench Verified, elle améliore fortement plusieurs agents générateurs de PR. Le résultat porte sur un benchmark, pas sur une organisation en production, mais il montre pourquoi la revue agentique est plus qu’un commentaire décoratif. Elle peut devenir le signal qui ramène automatiquement un changement défectueux vers l’atelier.

Automatiser la revue ne supprime pas le jugement

Si l’agent écrit, qu’un deuxième agent révise et qu’un troisième accepte, le goulot a-t-il disparu ? Non. On l’a rendu moins visible — et parfois plus dangereux.

Deux agents fondés sur les mêmes modèles, les mêmes documents et les mêmes hypothèses peuvent partager le même angle mort. Une suite de tests ne prouve que ce qu’elle a été chargée de tester. Une spécification ambiguë peut conduire à une implémentation, une revue et une validation parfaitement cohérentes entre elles, mais toutes fausses. L’automatisation multiplie alors une erreur de cadrage avec une efficacité industrielle.

La recherche commence à formaliser le problème. Rethinking Code Review in the Age of AI décrit une revue devenue manuelle, irrégulière et cognitivement coûteuse à mesure que les agents augmentent le volume de code. Ses auteurs proposent des agents spécialisés, mais conservent les humains aux décisions où comptent responsabilité, compréhension collective, biais, confidentialité et risque d’automatisation complaisante.

Les travaux de DORA invitent à la même prudence. Leur rapport 2025 sur le développement assisté par IA décrit l’IA comme un amplificateur : elle renforce les qualités d’une organisation bien structurée et accélère aussi les dysfonctionnements d’une équipe confuse. Le temps gagné à générer est souvent réinvesti dans l’audit et la vérification ; davantage de débit peut s’accompagner de davantage d’instabilité. La factory de fonctionnalités inutiles reste une feature factory, simplement beaucoup plus rapide.

Même la mesure de productivité résiste. L’étude contrôlée de METR avait observé en 2025 un ralentissement de 19 % chez seize mainteneurs expérimentés travaillant sur leurs propres grands dépôts. Sa mise à jour de février 2026 suggère que les outils récents accélèrent probablement davantage le travail, mais reconnaît ne plus pouvoir produire une estimation fiable : les développeurs refusent plus souvent la condition sans IA et l’usage simultané de plusieurs agents rend le temps humain difficile à isoler. Compter les tokens, les commits ou les PR ne suffit pas. Il faut mesurer les changements utiles, les incidents, le coût de reprise et la valeur livrée.

Ce que signifie vraiment « auto-améliorante »

Une factory devient intéressante lorsqu’elle apprend de ses défauts, pas lorsqu’un agent annonce avoir amélioré son propre prompt.

Chaque exécution produit une trace : durée, coût, commandes, erreurs, attentes, résultat des tests, commentaires de revue, refus humain et comportement en production. Ces données permettent de comparer un modèle, un harnais ou une stratégie sur un corpus stable. Surtout, chaque échec utile peut devenir une contrainte durable : un test de régression, une règle d’architecture, un exemple de PR attendue, une permission retirée ou un document rendu accessible dans le dépôt.

Le système s’améliore lorsque le jugement humain ponctuel est transformé en garde-fou réutilisable. La connaissance cesse de rester dans la tête du reviewer et rejoint la machine. C’est moins magique qu’une IA qui se réécrit seule, mais beaucoup plus proche de l’amélioration continue d’une vraie chaîne industrielle.

Cette boucle impose aussi une hygiène sévère. Les environnements doivent être isolés et reproductibles. Les secrets et le réseau suivent le principe du moindre privilège. Chaque action reste attribuable, chaque budget plafonné, chaque changement réversible. Les opérations risquées — migration de données, accès à la production, changement de permissions, fusion d’un diff sensible — exigent une validation proportionnée à leur impact. Les analyses d’Anthropic sur le confinement de Claude et le retour d’OpenAI sur l’exécution sûre de Codex convergent sur ce point : davantage d’autonomie réclame des frontières plus explicites, pas moins de gouvernance.

Le nouveau métier : concevoir la ligne

Dans cette organisation, l’ingénieur ne disparaît pas. Il change d’échelle. Il choisit les travaux admissibles, rend l’intention lisible, découpe les lots, dessine les interfaces, encode les invariants, construit les tests, observe les dérives et décide du niveau de preuve exigé avant la fusion.

La compétence rare n’est plus seulement de savoir écrire la fonction. C’est de construire un environnement dans lequel une fonction correcte est plus facile à produire qu’une fonction plausible. Le bon dépôt devient une machine à guider le travail : documentation navigable, architecture vérifiable, commandes prévisibles, données de test, observabilité locale et critères d’acceptation explicites.

Une factory mature ne promet donc pas « zéro humain ». Elle protège l’attention humaine en l’utilisant aux endroits où elle a le plus de valeur : choisir le problème, arbitrer l’ambiguïté, juger l’expérience, évaluer le risque et assumer la responsabilité de ce qui part en production.

Le code est en train de cesser d’être le goulot d’étranglement. C’est une excellente nouvelle pour les bons systèmes et une très mauvaise pour les organisations qui confondaient déjà mouvement et progrès. L’usine logicielle ne nous dispense pas de penser. Elle rend simplement beaucoup plus coûteux le fait de penser trop tard.

Quinze projets open source pour construire la ligne

Il n’existe pas encore de « Kubernetes de la software factory » qui réunirait orchestration, agents, isolation, revue, observabilité et gouvernance avec une maturité incontestable. Les projets les plus populaires résolvent souvent une seule couche ; les implémentations réellement complètes sont beaucoup plus jeunes.

Le classement ci-dessous est ordonné par nombre d’étoiles GitHub relevé le 2 septembre 2026. Ce nombre mesure l’attention, pas la fiabilité. La maturité est donc évaluée séparément sur quatre niveaux : 4 — établi, avec versions régulières, documentation et usage large ; 3 — adoptable, utilisable mais encore jeune ou partiel ; 2 — preview, à expérimenter dans un environnement maîtrisé ; 1 — prototype, intéressant pour son architecture, pas encore pour une chaîne critique.

Les plus étoilés ne sont pas les plus complets

OpenHands fournit un excellent ouvrier, E2B un poste de travail isolé et PR-Agent un contrôleur qualité, mais aucun des trois n’est à lui seul une factory. Paperclip orchestre une organisation entière sans imposer le détail du SDLC. Orca et Emdash sont d’excellents cockpits humains, mais leur valeur tient précisément à la supervision qu’ils rendent possible.

Symphony est le dessin le plus net de la chaîne complète. Son WORKFLOW.md versionne la politique, son daemon lit les tickets, borne la concurrence, crée un workspace par issue et remet le travail dans un état comme « Human Review ». Mais OpenAI le présente explicitement comme une engineering preview pour environnements de confiance. Ses 26 997 étoiles et son numéro de version 0.0.2 racontent deux histoires très différentes.

Sandcastle est aujourd’hui la boîte à outils programmable la plus convaincante pour construire sa propre ligne en TypeScript. Ses templates couvrent déjà les exécutions séquentielles ou parallèles, avec planning et reviewer. Il faut toutefois examiner la stratégie de branche et le fournisseur de sandbox : un conteneur qui monte le workspace hôte n’offre pas la même frontière qu’une VM éphémère.

Machinist est plus proche d’un atelier d’exploitation : control plane, workers, commandes approuvées, événements, coûts et métriques. Son statut early access et sa version 0.4 invitent encore à l’expérimentation. Super Simple Software Factory est le meilleur schéma pédagogique du lot — code déterministe propriétaire du graphe, agents limités aux étapes de raisonnement — mais ne fournit pas encore les branches isolées, la sandbox, le cloud ou le merge attendus en production.

Une pile raisonnable aujourd’hui

Pour un premier montage sérieux, je partirais de la spécification de Symphony pour le plan de contrôle, de Sandcastle ou Machinist pour l’exécution, d’OpenHands pour un agent open source ou des CLI Codex et Claude existantes, d’E2B pour les tâches nécessitant une isolation distante, puis de PR-Agent et des contrôles déterministes du dépôt pour la première revue. La fusion resterait humaine et les droits seraient limités par construction.

Pour une équipe qui veut surtout piloter plusieurs agents sans bâtir immédiatement un service permanent, Orca ou Emdash constituent une étape intermédiaire plus réaliste. Pour Kubernetes, Kube Foundry montre la bonne primitive — une tâche devient un pod jetable — mais reste trop jeune pour être adopté sans travail important de sécurité et d’exploitation.

Le projet décisif n’existe peut-être pas encore. Le choix le plus durable consiste donc à garder les interfaces remplaçables : ticket, workspace, harnais, preuves, revue et décision de fusion. La factory doit survivre au prochain modèle à la mode.
