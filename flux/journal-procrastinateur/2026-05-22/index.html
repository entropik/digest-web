Jour 63 - Le pricing quitte les vieux rails

Une journée de nettoyage profond du pricing produit : formats integres aux attributs, quantités conditionnelles, remises panier famille, defaults par BD, runtime éditeur et garde-fous contre les vieux champs.

Horaires de session

  • Agent utilisé : Codex, transition depuis Claude Code
  • Branche de travail : feat/miskiss-pricing-v0
  • État de départ : le cœur du pricing commençait a tenir, mais il restait des restes dangereux : anciens formats de fiche produit, prix par quantité, options de prix, champs numériques fragiles et runtime encore capable de reveiller l’ancien modèle.
  • État de clôture : les formats, quantités, papiers et autres choix atelier sont gérés comme attributs produit actifs, avec impacts prix/poids dans l’onglet Prix et attribut par défaut par BD pour l’ouverture de l’éditeur
  • Version repo : 0.6.29
  • Travail local final : refonte fiche produit, runtime pricing, éditeur, Woo/export/PDF, remises panier famille, documentation et migration is_default
  • Temps de session estime : environ 8h00
  • Objectif du jour : tester un vrai prix avec Claire et supprimer les logiques qui rendaient le calcul incohérent. La journée finit fatiguee, mais elle finit mieux qu’elle n’a commencé. Le chantier prix a encore mordu. On pensait avoir stabilise le cap hier, puis le test métier avec Claire a révélé le loup : les formats existaient comme onglet a part, mais ils n’avaient pas le même statut que les autres choix atelier. Donc ils ne pouvaient pas naturellement peser sur le prix. Dit autrement : on avait commencé à faire simple, puis un vieux rail historique continuait a tirer le modèle ailleurs.
  • Temps cumulé :317h30+

Le vrai declic : tout ce qui se choisit est un attribut

La décision du jour est nette :

Un format est un attribut. Une quantité est un attribut. Un papier est un attribut. Un attribut peut impacter le prix ou le poids quand il est choisi, sinon il vaut 0.

Cette phrase paraît simple, mais elle a nettoyé beaucoup de confusion.

Avant, on avait plusieurs modèles qui cohabitaient :

  • formats dans un onglet special ;
  • quantités dans un champ libre ;
  • anciens prix directs par quantité ;
  • options de prix séparées ;
  • attributs atelier dans une autre logique ;
  • remises produit ;
  • remises panier famille.

Chaque morceau était défendable seul. Ensemble, c’était trop fragile.

La fiche produit a donc été recadree :

  • l’onglet Formats disparaît ;
  • Formats revient dans Attributs, comme les autres BD atelier ;
  • les formats actifs d’un produit sont les attributs Formats coches ;
  • leurs dimensions viennent de la BD atelier Formats ;
  • leurs impacts prix/poids se reglent dans Prix > Attributs de fabrication ;
  • l’éditeur public lit les formats depuis ces attributs actifs.

C’est plus cohérent, et surtout c’est explicable a Claire.

Les quantités ne sont pas additionnelles

Le gros signal d’alarme de la journée a été une carte postale a plus de 200 euros.

La cause était claire : les impacts de quantité étaient additionnes comme si choisir 8, 16, 24, 48, etc. voulait dire prendre toutes ces quantités en même temps.

C’est faux.

Une quantité est conditionnelle :

  • si le client choisit 8, seul l’attribut 8 peut impacter le prix ;
  • si le client choisit 16, seul l’attribut 16 peut impacter le prix ;
  • les autres quantités actives servent à remplir le menu, pas a additionner des montants.

La correction importante est donc dans le moteur, pas dans l’affichage. Le runtime distingue maintenant :

  • les attributs formats : impact seulement si le format du projet correspond ;
  • les attributs quantités : impact seulement si la quantité choisie correspond ;
  • les autres BD atelier : impact seulement si l’option correspondante est selectionnee dans l’éditeur.

La règle métier devient :

Un attribut = une option qui peut impacter le prix ou non quand elle est choisie par le client.

Nettoyer les vieux champs avant qu’ils ne reviennent

On a aussi fait une passe de vigilance sur les scories du pricing.

Les anciens champs quantity_prices et format_modifiers étaient encore acceptés pour compatibilité, mais ils ne doivent plus influencer un produit gere par attributs. C’était exactement le genre de dette silencieuse qui peut ressurgir trois jours plus tard avec un prix incompréhensible.

Le runtime a donc été purifie :

  • le prix actif lit base, extra_page, les remises de ligne et les attributs actifs ;
  • les anciens prix directs par quantité ne pilotent plus le calcul produit ;
  • les anciens modificateurs de format ne pilotent plus le calcul produit ;
  • les formats publics sont dérives des attributs actifs Formats ;
  • les quantités publiques sont derivees des attributs actifs Quantite ;
  • les options atelier publiques sont derivees des autres BD actives ;
  • un produit sans format actif est signale comme incomplet au lieu d’ouvrir un éditeur casse.

Ce nettoyage est moins visible qu’un bouton, mais il est probablement plus important.

Fiche produit : moins d’onglets, plus de sens

La fiche produit est maintenant plus lisible :

  • Resume garde l’identité catalogue ;
  • Attributs choisit les BD atelier utiles au produit ;
  • PDF porte les réglages d’export ;
  • Prix règle le calcul ;
  • Woo / Integration garde les identifiants et raccords.

Le bouton Actif inutile du résume a disparu, parce qu’il doublonnait le statut.

L’onglet PDF a remplace les cases techniques perdues dans le résume. Les champs couverture, fond perdu, zone sûre, gouttière, reliure, espace couleur et politique ICC sont maintenant dans un endroit compréhensible : ce sont des paramètres d’export, pas des informations catalogue.

L’onglet Prix a lui aussi été nettoyé :

  • suppression du bloc Prix par quantite ;
  • suppression des anciennes Options de prix ;
  • conservation du prix de base et du prix page supplémentaire ;
  • conservation des remises par quantité de ligne produit ;
  • affichage des attributs actifs avec impact prix/poids ;
  • suppression des cartes Impact prix total et Impact poids total, qui donnaient une fausse impression de total global.

La présentation a été compactee plusieurs fois, parfois dans la douleur. Les champs étaient trop grands, les tuiles n’étaient pas alignées, la barre sticky laissait un trou, et le moindre mauvais décalage donnait l’impression d’un écran encore bricolé. Ce sont des détails, mais dans un outil de prix ils comptent.

Remises : ligne produit et panier famille

Une confusion importante a été clarifiée avec WooCommerce.

Une remise par quantité dans la fiche produit ne veut pas dire “le client a achète plusieurs visuels différents de cartes postales”. Elle s’applique à une même ligne/configuration produit.

Exemple :

  • 8 exemplaires du même projet carte A : logique de ligne produit ;
  • 8 exemplaires carte A + 16 exemplaires carte B : logique panier famille.

Pour ce deuxième cas, on a ajouté la logique Remises panier famille catalogue dans la sidebar des familles catalogue. Elle se règle au niveau de la famille, pas du produit.

Cela évite de tordre la fiche produit pour un cas qui appartient au panier WooCommerce : cumuler les quantités de plusieurs lignes d’une même famille catalogue.

Attribut par défaut

Dernière brique du jour : pouvoir choisir un attribut par défaut par BD et par produit.

Dans l’onglet Attributs, une colonne Defaut permet maintenant de dire :

  • ce format doit ouvrir l’éditeur par défaut ;
  • cette quantité doit être preselectionnee ;
  • ce papier ou cette option atelier doit être choisi au démarrage.

La règle reste simple :

  • un seul défaut par BD et par produit ;
  • Defaut implique Utilise ;
  • désactiver un attribut retire aussi son défaut ;
  • si rien n’est defini, on garde le comportement actuel : premier attribut actif selon l’ordre.

Le backend porte le champ is_default avec une migration append-only et un index partiel PostgreSQL pour éviter deux defaults actifs sur la même BD produit.

Les champs numériques : règle durcie

Il y a eu une vraie régression de confort sur les champs numériques : perte de focus, impossibilite de taper deux chiffres sans recliquer, virgule difficile, valeurs négatives penibles.

La règle est maintenant documentée et durcie :

Pas de champ numérique “intelligent” contrôle par React dans les formulaires métier.

Concrètement :

  • pas de remount lie à la valeur ;
  • pas de type="number" par défaut dans l’admin ;
  • pas de formatage pendant la frappe ;
  • accepter ``, -, 20,, 2,5, -5 ;
  • normaliser seulement au blur, Enter, bouton Enregistrer ou submit.

Ce n’est pas du confort secondaire. Si Claire doit saisir des prix et se battre contre les inputs, l’outil a perdu.

Frictions et autocritique

La journée a été utile parce qu’elle a expose des confusions, mais elle a aussi montré une faiblesse : on a parfois corrige localement des symptômes UI sans nommer assez vite la règle métier derrière.

Le pire exemple était la quantité additionnee. Il ne fallait pas seulement “corriger le total”. Il fallait rappeler la règle :

un choix client active un attribut, il n’additionne pas toute une BD.

Autre point : les vieux champs de compatibilité sont dangereux. Les garder en base est prudent, mais les laisser influencer le runtime produit est une porte ouverte aux régressions. La compatibilité doit rester au bord, pas dans le cœur du calcul.

Enfin, la densité UI reste un sujet sensible. Trop de vide fatigue, des champs trop grands fatiguent, des cartes qui bougent fatiguent. Le backoffice doit être compact, stable, et prévisible.

État pour demain

Demain, il faudra tester le produit complet sans rouvrir l’architecture :

  1. créer/vérifier une carte postale avec formats, quantités et papier actifs ;
  2. choisir les defauts utiles ;
  3. tester l’éditeur puis le prix ;
  4. vérifier le cas panier famille dans WooCommerce ;
  5. commencer a raccorder les vraies recettes atelier sans casser le contrat simple : attribut choisi = impact applique.

Le chantier reste gros. Mais ce soir, le prix a quitte une bonne partie de ses vieux rails.

Et c’est une bonne chose pour dormir.
