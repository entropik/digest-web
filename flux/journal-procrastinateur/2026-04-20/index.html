Jour 37 — Restaurer la prod et reprendre pied

La journée a bascule en gestion d'incident : prod seedee, assets clients disparus, backup du 2 avril restaure, schéma recale et cutover prudent vers une base à nouveau exploitable.

Reconstituer l’incident avant de restaurer

Ce billet est reconstruit à partir des traces d’exploitation, des commandes executees sur le VPS et du diagnostic formule pendant l’incident. Il n’y a pas de commit représentatif de cette journée : le travail s’est fait presque entièrement en investigation et en restauration.

La production servait une base seedée

La journée a été monopolisee par un constat brutal : la prod krampouz.ooblik.com ne servait plus les vraies données métier. Les assets clients avaient disparu de l’interface, et l’état de la base active ressemblait à une base seedee plutôt qu’à une base de production vivante.

Le diagnostic fini par tomber sans ambiguïté :

  • assets = 0
  • users = 2
  • projects = 1
  • présence typique des comptes seed ([compte OOBLIK retiré], [compte OOBLIK retiré])

Autrement dit : la prod ne pointait plus vers une vraie base métier, mais vers une base reconstruite/bootstrappee après les ennuis Prisma. Le deploy “réussi” visible dans GitHub n’était pas la cause directe de la disparition ; le dommage était déjà la, dans la séquence de régularisation precedente.

La journée a ensuite changé de nature. Il ne s’agissait plus d’améliorer le workflow, mais de sauver les données. Un backup du 2026-04-02 a été retrouvé sur le VPS. Il contenait encore les vraies données :

  • assets: 1562
  • users: 1525
  • projects: 547

La restauration a d’abord été faite dans une base témoin. Cette base restaurée n’avait pas _prisma_migrations et ne pouvait pas simplement repartir en migrate deploy. Il a fallu :

  1. mesurer le diff exact avec le schéma courant ;
  2. appliquer uniquement le diff additif nécessaire ;
  3. enregistrer l’historique Prisma ;
  4. vérifier ensuite que prisma migrate deploy ne voulait plus rien changer.

Une fois la base témoin rendue compatible, le cutover réel a été fait vers la vraie base krampouz. Les comptes, projets et assets du backup ont alors reapparu en prod, y compris le compte [compte OOBLIK retiré] et ses données liées.

Les faits établis avant le cutover

  • la prod active était bien tombée sur une base seedee
  • le volume Docker Postgres n’avait pas simplement été recréé “par hasard”
  • aucune preuve d’un DELETE assets dans les migrations elles-mêmes
  • le problème venait d’un chemin d’exploitation trop dangereux autour de Prisma et du seed
  • la restauration depuis backup était possible
  • la base restaurée pouvait être rendue compatible avec le schéma courant

Restaurer d’abord, expliquer ensuite

La décision la plus importante n’est pas seulement la restauration. C’est la remise en question du workflow lui-même. à partir de ce moment-là, plusieurs règles deviennent évidentes :

  • plus de seed possible en prod sans action explicite exceptionnelle ;
  • plus de régularisation Prisma “intelligente” dans le flux nominal ;
  • un deploy doit échouer si la base est ambiguë, pas tenter de la “réparer” tout seul ;
  • la prod client ne doit plus jamais servir de terrain de régularisation legacy.

Une journée entière en gestion d’incident

Cette journée ne produit aucune feature. Elle consomme presque tout son temps a :

  • vérifier la base active ;
  • retrouver le backup sain ;
  • restaurer en base separée ;
  • corriger la compatibilité schéma ;
  • valider le cutover ;
  • confirmer le retour des comptes et assets essentiels.

Le sentiment de temps perdu est réel, mais la sortie utile l’est aussi : les données clients reviennent et la dette Prisma cesse d’être une abstraction.

La fenêtre du retour en production

  • Activité dominante : ops / SQL / restauration / vérification
  • Commits representatifs sur le repo : aucun
  • État final de la journée : prod restaurée sur une base métier à nouveau exploitable

Retrouver durablement la confiance dans les données

La restauration sauve la situation immédiate, mais elle ne règle pas encore la cause racine de fond : une procédure de deploy trop complexe, trop ambiguë, trop capable de dériver hors du chemin nominal.

Le lendemain devra donc faire plus que “continuer” : il faudra remettre a plat la provenance du runtime lui-même.
