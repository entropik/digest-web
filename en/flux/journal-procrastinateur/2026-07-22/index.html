Day 119 – The order is double-checked; sharing is made easier

Day 119 of the log: ordering and sharing have been tightened up, and KEREDIT and GOF have adopted the regenerations, immutable iterations and server locks that were missing from the Production v2 contract.

Session times

  • Tools used: Codex for pull requests, Kimi Code CLI (K3) for maintaining this log
  • Main environment: Codex App on Mac, then Kimi Code CLI, KEREDIT repository dépôt local krampouz
  • Date covered: Wednesday 22 July 2026 (no commits were made on Tuesday 21 July: assumed break)
  • Observation window: 22 July 17:12:43 → 23:53:45 CEST for KEREDIT commits, with GOF active from 19:04:18 to 21:33:24
  • Minimum observed duration: approximately 7 hours 11 minutes+ (6 hours 41 minutes of continuous KEREDIT/GOF activity, plus the initial log-keeping session)
  • Merged branches: 8 KEREDIT PRs to dev, versions 0.16.3 → 0.16.9, and GOF PRs #83/#85, versions 0.7.3 → 0.8.0
  • Main releases: Woo REST re-verification, web PDF sharing, Google Photos OAuth, 100-megapixel limit, template locks, GOF v2 regenerations and iterations
  • Minimum cumulative time since the start of the log: approximately 786h11+ (779h00+ as at 20 July following historical correction, + 7h11+ observed)

Quick read

Following Tuesday’s break, Wednesday evening saw eight KEREDIT pull requests and two GOF pull requests consolidated in just under seven hours. The overarching principle: what the user sees when sharing or placing an order must be exactly what the production environment expects.

Meanwhile, this log is changing hands. The catch-up entries for days 117 to 119 are being written using Kimi Code CLI, installed on Monday morning: the first proper session using the tool on the repository, three days after the release of Kimi K3.

Never take an order at face value

PR #328 tightens up the WooCommerce pipeline. KEREDIT orders are re-verified via the Woo REST API before going into production, and an unreadable status is rejected rather than interpreted. The items in the re-validated order are also validated, and their role — main product or add-on — is compared with what the webhook had announced. The original order is no longer set in stone: it is re-validated at the moment it is processed by the workshop.

Public sharing becomes a real achievement

Three PRs follow one another on the public reader. #329 enables the GOF v2 web PDF to be downloaded from the share, with a trusted status reader injected into the Woo feed test and vulnerable dependencies fixed in the process. #330 removes the blank tab that used to open with the public link. #332 prevents opening the link from triggering a new GOF rendering: viewing a share should never resemble a command.

Two infrastructure safeguards

PR #333 rewrites the Google Photos OAuth callback: no more code injection into the redirect page, and a response compliant with the Content Security Policy. Logging into the client’s photo account remains seamless, but the redirect page can no longer be used as a script vector.

PR #335 blocks images larger than 100 megapixels from the asset pipeline: rejection occurs before decoding, goes through the standard business logic rejection, properly rejects catalogues that are too large at the upload confirmation stage, and the ` ASSET_PIPELINE_MAX_INPUT_PIXELS` limit has been extended all the way to the VPS composer, without duplication in the worker.

The evening wasn’t over yet

The first version of this post ended here, at 19:06. However, Git shows that the second half of the session was even more substantial than the first.

KEREDIT first learnt to regenerate an existing Production v2 without losing its product families. The bindings now follow an explicit rendering iteration; the web PDF download uses the current artefact, and WooCommerce replays recognise this new lineage. Polling remains read-only: checking the GOF status must never overwrite the production environment it is monitoring.

Templates are also locked on the server

At the same time, a long series of fixes has hardened the exact variants of templates. The format change preserves the proven geometry; permissions and visual identity are compared against a canonical baseline; cross-page movements are controlled; and late writes are locked out.

The key point is simple: a client may modify what the template permits, but must not silently reconstruct the contract from a more permissive payload.

GOF 0.8.0 makes iterations immutable

GOF begins the sequence at 0.7.3 with the Accurio auto-submission, bounded by a timestamped activation. Then PR #85 introduces 0.8.0 and the Production v2 rendering iterations.

A regeneration now creates an immutable candidate. The current PDF remains available until its atomic promotion; incidents and resubmissions remain linked to their iteration; and a previous iteration can no longer initiate an Accurio action. Rendering and delivery become two separate decisions, with a usable history rather than a current file being overwritten.

Kimi keeps the log

Last piece of news for today, and by no means the least important for this log: the documentation catch-up itself is carried out using Kimi Code CLI. The tool reads the repository, retrieves the evidence from Git, follows the blog skill procedure and produces posts 117, 118 and 119 in the usual format. Claude Code kicked off the venture, Codex has carried it this far; Kimi K3 is cutting its teeth on the project’s history, and it is this log that will remember it.

Correction of 4 August

This post was revised with Codex on 4 August 2026 following a comparison of the KEREDIT and GOF Git histories. The time window, versions, minimum time and cumulative total were recalculated to include the second half of the evening.
