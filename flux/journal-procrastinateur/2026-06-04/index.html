Le flux réel apparaît

Le cœur de la journée tient en une ligne :

WooCommerce -> KEREDIT -> GOF -> Accurio Flux -> atelier

Jusqu’ici, chaque morceau avait déjà de la substance.

KEREDIT savait recevoir un projet, garder un contexte client, exposer un backoffice, envoyer un travail vers une forge PDF. GOF savait devenir la forge locale, générer des artefacts, garder une trace de production. Accurio était le monde industriel à rejoindre, avec son API, son catalogue, ses imprimantes, ses services, ses contraintes réseau.

Aujourd’hui, le travail a été de faire passer des informations réelles à travers ces frontières.

Ce n’est pas un petit raccord UI. C’est un changement de nature : on ne teste plus seulement un éditeur, on teste une chaîne d’atelier.

Accurio entre dans le contrat

Le premier chantier KEREDIT de la journée a étendu le payload d’export GOF pour Accurio.

Le payload ne se contente plus de dire “voici un projet à rendre”. Il transporte maintenant les indices de production attendus :

  • contexte client ;
  • contexte commande ;
  • nom de produit Accurio ;
  • imprimante cible ;
  • préfixe de commande ;
  • type de livraison ;
  • services Accurio sélectionnés depuis les options KEREDIT.

Côté GOF, le commit 729c4ba a ajouté le connecteur de production Accurio. Le flux documente dans GOF fixe une règle importante : Accurio reçoit un POST /api/createOrder déjà conforme. Pour ce flux, aucun script de transformation Accurio ne doit devenir la rustine centrale.

C’est exactement le bon sens de responsabilité :

  • KEREDIT reste l’autorité métier : client, commande, produit vendu, options, mapping.
  • GOF prépare le PDF, le gardé disponible et soumet la commande.
  • Accurio pilote la production et l’impression.

La difficulté commence là où les mots doivent devenir des noms exacts : produit Accurio, imprimante Accurio, services Accurio, URL de PDF accessible depuis le serveur Accurio.

GOF devient configurable

GOF a beaucoup bouge aujourd’hui.

La forge n’est plus seulement une app locale avec un pipeline PDF. Elle gagne une surface de configuration exploitable :

  • connecteur Accurio ;
  • UI de configuration client ;
  • login de backoffice par session au lieu d’une auth navigateur brute ;
  • aide de configuration intégrée ;
  • documentation client ;
  • simplification du parcours de synchronisation KEREDIT ;
  • suppression propre des anciens jetons API automatiques ;
  • lecture complète du catalogue Accurio depuis GOF ;
  • erreurs API renvoyees de manière lisible.

La documentation GOF produite aujourd’hui est aussi un signal important :

  • docs/flux-keredit-gof-accurio.md posé le contrat technique ;
  • docs/procedure-client-configuration-keredit-gof-accurio.md donne une procédure client non technique ;
  • docs/architecture-gof-memo-2026-06-04.html et .pdf fixent l’intention d’architecture ;
  • docs/operations-gof.md et docs/backoffice-gof.md gardent le côté exploitation.

GOF prend donc son rôle d’atelier : pas une librairie cachée, mais une machine locale configurée, visible, testable, avec un opérateur au milieu.

KEREDIT apprend à se connecter à GOF

Cote KEREDIT, le backoffice GOF Flux est devenu beaucoup plus concret.

Deux migrations ont été ajoutées :

  • 20260604113000_add_gof_integration_config ;
  • 20260604124500_add_gof_pairing_code.

Elles permettent de stocker la configuration GOF, puis un code temporaire de connexion. Le principe est simple pour le client :

  1. KEREDIT généré un code de connexion.
  2. GOF reçoit ce code dans son écran de configuration.
  3. GOF créé un jeton technique.
  4. GOF envoie ce jeton a KEREDIT.
  5. KEREDIT le stocke chiffré et teste la connexion.

C’est beaucoup mieux qu’un champ “collez un token secret quelque part”, parce que le geste client devient compréhensible : connecter deux outils, pas manipuler une clé technique.

Le backoffice KEREDIT affiche aussi plus clairement l’état de connexion, les tests GOF et la lecture du catalogue Accurio.

Un point de doctrine a été corrigé dans l’après-midi : KEREDIT ne doit pas lire Accurio directement. Le catalogue Accurio est lu par GOF, parce que GOF est installé dans l’atelier et peut joindre le serveur Accurio Flux. KEREDIT consomme ensuite cette lecture via GOF.

Ce détail paraît petit, mais il évite une architecture bancale. Accurio appartient au réseau atelier, pas au VPS KEREDIT.

WooCommerce resserre la boucle

La fin de journée a ramené WooCommerce dans la boucle.

Ce n’est pas un sujet séparé. Le flux GOF/Accurio à besoin du contexte commande et du contexte client. Sans cela, la production reçoit un PDF, mais pas assez de métier autour du PDF.

Les commits de fin de journée ont donc traite :

  • le contexte client Woo prefere pour les exports GOF ;
  • la réutilisation du verrou panier Woo pour les mises à jour depuis l’éditeur ;
  • l’automatisation de la configuration webhook WooCommerce ;
  • la réparation checkout depuis l’admin.

On sent ici la même logique que pour GOF : les tests réels font apparaître les contrats caches. Un projet éditeur ne vit pas seul. Il doit rester cohérent avec le panier, la commande, les webhooks et l’identité client.

Les bugs ne sont pas du bruit

La phrase du jour pourrait être : “je lève des problèmes de partout en testant”.

Oui. Et c’est probablement bon signe, même si c’est fatiguant.

Les problèmes apparaissent partout parce que le test traverse maintenant les frontières du système :

  • frontière navigateur / backoffice ;
  • frontière KEREDIT / GOF ;
  • frontière VPS / machine atelier ;
  • frontière URL publique / URL LAN ;
  • frontière token lisible / token technique chiffré ;
  • frontière catalogue Accurio / mapping produit KEREDIT ;
  • frontière projet éditeur / commande WooCommerce ;
  • frontière PDF généré / commande imprimable.

Tant que chaque brique était testée seule, ces problèmes restaient invisibles. Le test live les met au jour. Ce n’est pas une régression unique avec une cause simple. C’est la découverte progressive du vrai contrat de production.

La bonne réaction n’est donc pas de tout reouvrir. C’est de transformer chaque surprise en contrat :

  • qui est l’autorité de cette donnée ?
  • qui a le droit d’appeler quel service ?
  • quelle URL doit être joignable depuis quelle machine ?
  • quel état doit être visible par le client ou par l’opérateur ?
  • quelle erreur doit arrêter le flux au lieu de laisser croire que tout va bien ?

Ce qui tient déjà

Ce soir, il y a des choses solides.

KEREDIT et GOF sont tous les deux sur dev, propres, poussés, avec une activité cohérente de commits. Les versions KEREDIT sont réalignées en 0.6.61. Le backoffice a maintenant un vrai début de surface GOF Flux. Le pairing par code donne une expérience client plus défendable. GOF lit Accurio depuis le bon endroit. Les docs client et opérateur existent. WooCommerce continue de se rapprocher de la chaîne de production.

Le plus important : l’architecture gardé la bonne répartition.

KEREDIT ne devient pas une machine Accurio distante. GOF ne lit pas les tables internes KEREDIT comme contrat principal. Accurio ne devient pas le lieu où l’on corrige les données KEREDIT. Chaque outil commence à avoir sa place.

Ce qui reste fragile

La fragilité n’est pas encore dans un seul fichier. Elle est dans le parcours complet.

Il faut encore rejouer calmement un flux minimal :

  1. Vérifier que le VPS KEREDIT sert bien le SHA attendu avant tout test live.
  2. Ouvrir GOF et valider sa configuration Accurio.
  3. Depuis le serveur Accurio, vérifier que l’URL GOF des PDF est joignable.
  4. Connecter KEREDIT a GOF par code temporaire.
  5. Tester GOF depuis KEREDIT.
  6. Lire le catalogue Accurio via GOF.
  7. Mapper un seul produit KEREDIT vers un seul produit Accurio.
  8. Envoyer un projet connu vers GOF.
  9. Contrôler le PDF dans GOF.
  10. Envoyer à Accurio.
  11. Noter chaque erreur avec sa frontière exacte.

Ce replay doit rester petit. Un produit, une commande, un PDF, une imprimante. Pas toute la boutique, pas tous les formats, pas tous les cas métiers.

Ce que cela dit de la bêta

La bêta postcard n’est plus seulement une question d’éditeur joli et stable.

Elle devient une question de confiance atelier :

  • est-ce que le client peut commander ?
  • est-ce que KEREDIT gardé le bon contexte ?
  • est-ce que GOF fabrique un artefact controlable ?
  • est-ce qu’Accurio reçoit une commande exploitable ?
  • est-ce que l’opérateur sait où regarder quand ça casse ?

La journée a été impressionnante parce qu’elle a fait apparaître ce niveau-là.

Il y a encore beaucoup de pièces en mouvement, mais elles commencent à former une chaîne. Ce n’est pas confortable, mais c’est plus réel que rassurant. Et pour un projet atelier-first, c’est probablement la bonne étape.

Reprise demain

Demain, ne pas chercher à “tout tester”.

Chercher à tester une seule histoire de bout en bout :

un produit postcard -> une commande Woo -> un projet KEREDIT -> un job GOF -> un PDF contrôle -> un envoi Accurio

Si cette histoire passe, même avec des ajustements, la journée d’aujourd’hui aura changé de statut : elle ne sera plus une dispersion impressionnante, mais le moment où les morceaux ont commencé à devenir un flux.
