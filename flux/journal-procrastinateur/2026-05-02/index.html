Jour 45 - Bugs bêta, slots photo et règles d'atelier

La journée transforme les premiers retours bêta en outils exploitables : rapports de bug indexes avec contexte, slots photo remplissables, placeholders propres, règles en cm et guides d'alignement.

Fil directeur

Le fil rouge a été la bascule entre usage client et travail de production interne.

Cote client, le bouton de bug doit capturer assez de contexte pour éviter les allers-retours inutiles : navigateur, OS, horaires, référence stable du rapport, capture de l’état au bon moment. Cote édition, le bloc photo vide doit devenir un vrai slot de template, pas un objet provisoire fragile. Cote opérateur, les règles et guides doivent permettre de caler une maquette comme dans un outil de PAO simple.

Le résultat n’est pas une seule grosse feature, mais un ensemble cohérent : mieux remonter un problème, mieux remplir un template, mieux aligner les blocs.

Rapports de bug bêta

La première partie de la journée a consolide le flux de rapports de bug.

Le besoin était simple : quand un testeur clique sur Bug, il ne faut pas lui demander ensuite son navigateur, son OS ou l’heure exacte. Ces données doivent être embarquées automatiquement. Le schéma, les routes publiques et admin, l’export backend et le frontend ont donc été enrichis pour transporter ce contexte.

Un autre point est apparu immédiatement : deux rapports anonymes dans le backoffice sont difficiles a designer en conversation. Le système ajoute maintenant une référence publique lisible, du type BUG-0002, pour pouvoir dire “regarde le rapport 0002” sans ambiguïté. Le filtre de recherche admin a été corrigé dans la foulée pour retrouver ces références.

La fermeture de la modale après envoi a aussi été ajustée. Le signalement confirme l’envoi, puis rend la main proprement au client.

Enfin, la question de la capture a été tranchee de façon pragmatique : la capture doit représenter l’état au moment ou l’utilisateur clique sur le bouton de bug. Si elle est prise trop tard, le client peut avoir supprime ou masque l’élément fautif. Le bouton capture donc le contexte visuel au declenchement, puis le rapport suit ce snapshot.

BUG-0003 et slots photo

Le rapport BUG-0003 a servi de vrai cas bêta : un bloc photo vide était visuellement présent, mais pas vraiment utilisable. Déposer une image dedans pouvait créer une nouvelle photo à cote au lieu de remplir le bloc existant.

Le correctif a clarifié le contrat des slots photo :

  • un ImageElement avec assetId: null est un slot photo ;
  • déposer une photo sur ce slot doit remplir ce slot ;
  • déposer une photo hors slot garde le comportement de création d’une image libre ;
  • déposer sur un bloc déjà rempli ne remplace pas automatiquement l’image.

Ce contrat prépare directement le futur bouton “remplir le carnet” : les slots vides pourront être parcourus par page, ordre visuel et pile de calques, puis recevoir les fichiers client automatiquement.

Le calcul de drop a aussi été corrigé. Le hit-test ne doit pas se baser sur le conteneur scrollable global, mais sur le rectangle réel du canvas imprime. Sur écran large, quand la page est centrée, cette différence suffit a rater le bloc cible.

Placeholder photo

Le bloc photo vide a ensuite été retravaille visuellement.

L’objectif n’était pas de créer un nouveau type d’objet, mais de rendre le slot immédiatement compréhensible dans un template. Le rendu Fabric garde donc le même cadre, les mêmes dimensions, la sélection, le déplacement et le resize qu’un bloc image normal, mais affiche un fond neutre, un repère discret et une icône claire.

Une leçon importante est sortie de l’itération sur l’icône : les icones Lucide choisies pour l’app doivent être utilisées depuis leur SVG source ou via l’import lucide-react, pas redessinees à la main. Le rendu HTML de référence et le rendu Fabric ne peuvent pas être identiques si on reconstruit approximativement les traits. Cette obligation a été ajoutée dans AGENTS.md.

Le choix final s’est stabilise autour de ImageUp, en SVG, avec une taille légèrement réduite. Le dernier ajustement de la journée retire aussi le pointillé du bloc vide au profit d’un trait fin continu, pour éviter une confusion visuelle avec les guides d’alignement.

Règles et guides

La fin de session a ouvert un nouveau chantier d’atelier : les règles en centimetres dans l’éditeur.

La demande était précise : les règles ne doivent pas encadrer la page comme une décoration, mais vivre dans l’interface de travail, sous le menu et à gauche de la barre d’outils. Le zéro part du bord superieur gauche de l’éditeur, pas d’une origine cachée du document.

Les règles peuvent maintenant être affichées ou masquees depuis le même bouton que les informations de grille/fond perdu. Leurs chiffres utilisent un token de couleur terracotta, pas une valeur CSS hardcodee, afin de garder la thématisation modifiable.

Ensuite, les règles sont devenues actives : cliquer sur une règle principale cree un guide horizontal ou vertical. Les guides peuvent être déplacés, sélectionnes, supprimes individuellement, supprimes tous en une fois, et modifies depuis le panneau de propriétés. Le panneau liste les guides de façon compacte, avec séparation simple, hover et état sélectionne.

Plusieurs détails d’ergonomie ont été corrigés au passage :

  • les chiffres des règles ne doivent pas être selectionnables ;
  • le menu des formats doit passer au-dessus des règles ;
  • masquer les règles masque aussi les guides, sans ajouter de nouveau bouton ;
  • les guides doivent être visibles mais discrets.

Le style retenu à la clôture est un guide terracotta en tirets assez espaces, avec une transparence moderee. Un essai de masquage sous le bloc sélectionne a été abandonné car il compliquait trop le rendu et ne fonctionnait pas assez bien.

Saisie negative dans les propriétés

Un correctif important pour les templates a été ajouté : les champs X et Y du panneau de propriétés acceptent maintenant les valeurs négatives.

C’est utile pour caler un bloc légèrement hors page, par exemple a -3 mm, notamment pour des fonds, debords ou compositions qui doivent anticiper la coupe.

Le premier correctif gardait un état brouillon local dans le champ numérique, mais synchronisait ce brouillon via un useEffect. La CI GitHub a refusé ce pattern avec la règle React react-hooks/set-state-in-effect. Le dernier commit du jour corrige proprement le composant : le brouillon n’existe que pendant le focus, et la valeur affichée hors édition est derivee directement des props.

Déploiement et CI

La version 0.6.0 a été préparée puis déployée sur le VPS après le lot règles/guides et placeholder.

Le déploiement manuel local vers krampouz.ooblik.com a reconstruit les images backend/frontend, vérifie les migrations Prisma, relance backend, frontend et worker, puis valide les smoke checks :

  • API health ;
  • endpoint thème ;
  • frontend local ;
  • frontend public.

Une fois le deploy termine, la PR #42 a signale un échec du job lint. Le problème ne venait pas du build ou du typecheck, mais du composant de saisie numérique dans RightPanel. Le correctif 2420d3a a été poussé dans la foulée et la CI est repassée verte : lint, typecheck, prisma_contract et build.

Reprise demain

Ordre recommande :

  1. tester les guides sur plusieurs formats et plusieurs niveaux de zoom ;
  2. vérifier que les guides restent lisibles sans gener les contours de blocs ;
  3. continuer l’itération sur le rendu du placeholder photo si le trait continu se confirme mieux que le pointillé ;
  4. tester un template réel avec positions négatives, slots photo et guides ;
  5. décider quand lancer le chantier “remplir le carnet” à partir des slots ImageElement vides.

La journée a transformé des retours bêta très concrets en outils de production. C’est exactement le bon type d’avancement à ce stade : moins spectaculaire qu’une grande feature, mais beaucoup plus proche de ce qui rend un éditeur utilisable tous les jours.
