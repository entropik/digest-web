Le fil de la journée

Le chantier partage a commencé avec une idée simple : depuis l’espace Mes projets du client WooCommerce, ouvrir une version publique, légère, persistante et partageable d’un carnet, zine ou livre photo.

Sur le papier, cela ressemble à une petite action de service : un bouton Partager, une URL publique, un lecteur web, un téléchargement PDF web plus tard. En pratique, c’est un vrai morceau de produit, parce qu’il touche à la fois :

  • le projet KEREDIT comme source de vérité ;
  • la commande et les options client ;
  • le rendu web public ;
  • le lien WooCommerce ;
  • la frontière avec GOF ;
  • l’expérience de lecture d’un objet imprime.

Le point important de ces deux jours, c’est que le partage n’est pas reste un aperçu technique. Il a commencé à prendre le geste du produit : une couverture, des doubles pages, une table des matières, un lien copiable, un plein écran, un téléchargement conditionnel, et surtout un vrai effet de page.

Sortir du faux lecteur

Le premier piège a été de confondre “afficher les pages” avec “feuilleter un carnet”.

Un rendu image plat peut dépanner, mais il ne donne pas l’objet. Les pages restent séparées, l’effet de volume disparaît, et l’utilisateur ne comprend pas pourquoi on lui vend un carnet si le lecteur ressemble à une galerie.

Le commit f52269a introduit donc StPageFlip dans le lecteur public. C’est le bon choix pragmatique : ne pas perdre du temps a coder un moteur 3D maison, mais utiliser une librairie spécialisée qui sait déjà faire le pli, l’ombre, le drag, le clic, le clavier et le mobile.

La première intégration n’était pas suffisante. Le lecteur était la, mais l’effet ne ressemblait pas encore au modèle attendu. Les pages ne se touchaient pas assez, certains chemins retombaient sur un affichage simple, et le chargement ne donnait pas l’impression d’un objet fini.

Le commit 9ae6d83 améliore la scène : dimensions, centrage, ombre, navigation, table des matières, footer, contrôle du slider. Mais la vraie correction arrive ensuite.

HTML StPageFlip, pas seulement des images

Le point décisif est b5f4148.

Au lieu d’attendre que GOF fabrique un artefact image pour donner une expérience de lecture, KEREDIT peut reconstruire une version HTML des pages à partir du projet lui-même. C’est exactement le bon découpage pour le partage public :

KEREDIT projet JSON -> rendu HTML leger -> StPageFlip -> URL publique
GOF                  -> PDF web optimise / artefacts pre-presse quand necessaire

Le partage devient donc utilisable même quand les images GOF ne sont pas encore prêtes. GOF garde son rôle de forge PDF et d’optimisation web/PDF. KEREDIT garde la capacité de montrer le projet, maintenant, à partir de sa source de vérité.

Le rendu HTML est moins noble qu’un PDF final, mais il est cohérent avec le besoin : feuilleter rapidement, partager une URL, vérifier le rythme, montrer le contenu a quelqu’un. Pour un client, c’est beaucoup plus utile qu’un bouton qui attend un pipeline complet.

Le moment utile : quand l’effet devient l’objet

La validation produit est arrivée quand le rendu a enfin ressemble au modèle StPageFlip attendu : pages jointives, pli visible, mouvement fluide, sensation de carnet.

Ce n’est pas un détail cosmétique. Dans ce type de produit, l’interface doit faire sentir l’objet physique. Une carte postale peut se montrer comme une face. Un zine, lui, doit se feuilleter. La différence est décisive.

Le chantier a aussi montré ce qui ne marche pas :

  • un rendu trop plat ;
  • des pages qui flottent séparément ;
  • des fallbacks “aperçu image simple” qui cassent l’effet ;
  • des artefacts de debug visibles en public ;
  • des indications de hover ajoutées à la main qui se melangent avec le moteur StPageFlip.

Ces erreurs ont été utiles parce qu’elles ont force une règle : le lecteur public doit être un lecteur StPageFlip, pas un empilement de modes de secours visibles par l’utilisateur.

Nettoyage et artefacts

Le commit f0b851b nettoie le rendu public.

Il factorise les réglages StPageFlip dans projectShareFlipBook.ts, retire le vieux mode image plat, supprime les classes CSS mortes et coupe les indications de coin ajoutées par notre propre CSS. Il desactive aussi l’aperçu de coin au survol cote StPageFlip, parce qu’il produisait des plis parasites alors que l’effet de page au clic/drag suffit.

Le dernier residu venait d’un autre endroit : les placeholders d’assets non résolus dans PagePreviewSurface. Sur des micro-éléments, leur bordure de debug apparaissait comme un petit “L” gris dans la page publique. C’est utile dans l’éditeur ou les previews internes ; c’est mauvais dans un partage client.

La correction est donc limitée :

  • en variante share, un clipart sans URL ne rend plus de placeholder ;
  • en variante share, une image sans asset ni cadre décoratif ne rend plus de placeholder ;
  • les aperçus internes gardent leurs placeholders de diagnostic.

Ce choix évite de masquer des vrais contenus dans l’éditeur tout en gardant le partage public propre.

Le service prend forme

La fonctionnalité n’est pas terminée au sens large. Le service complet doit encore lier proprement :

  • l’option WooCommerce télécharger le PDF web ;
  • l’entitlement pdf_web_enabled par commande/client ;
  • la génération GOF du PDF web allège ;
  • le backoffice KEREDIT dédié au service ;
  • la persistance longue des artefacts par share.

Mais la base produit existe maintenant :

Projet client -> Partager -> URL publique -> lecteur StPageFlip

Ce socle est important. Tant que le lecteur public n’était pas convaincant, discuter du PDF web, du panier WooCommerce ou du backoffice aurait été abstrait. Maintenant, on a l’expérience cible : un client peut ouvrir un zine et le feuilleter.

à cote du chantier partage

Le commit f8f4316 ajoute aussi une compétence locale improve sous .agents/skills/improve/SKILL.md, avec son skills-lock.json. Ce n’est pas le cœur produit du jour, mais c’est dans le même mouvement d’outillage : garder des workflows d’audit et de plans exécutables dans le repo, au lieu de les laisser vivre uniquement dans la conversation.

Un document HTML hors-série est aussi présent dans docs/roman/500-heures-avec-elle.html. Il transforme la mémoire de ces centaines d’heures avec l’IA en objet narratif pagine A5. Ce n’est pas une fonctionnalité KEREDIT, mais c’est une trace directe de la période : le journal de développement commence à produire sa propre matiere.

Risques encore ouverts

Le lecteur web est maintenant convaincant, mais plusieurs risques restent ouverts.

Le rendu HTML public n’est pas un PDF. Il faut donc garder la distinction produit claire : c’est la version de consultation et de partage, pas l’artefact pre-presse. Le PDF web allège devra venir de GOF, avec ses propres garanties de poids, pages, images et téléchargement.

Il faudra aussi vérifier la durée de vie des URLs et des assets. Un partage public qui montre un projet doit rester stable, même si le projet original evolue ou si les URLs signées d’assets expirent. Le modèle frozen_project_snapshot existe pour cela ; il faudra continuer a le traiter comme un contrat, pas comme un cache accidentel.

Enfin, le choix StPageFlip est bon, mais il faudra rester attentif aux comportements mobile, aux couvertures seules, aux livres courts et aux cas ou le nombre de pages est impair.

Suite logique

La suite courte est claire :

  1. tester le partage sur un vrai zine long, un carnet court et une carte postale ;
  2. vérifier les URLs d’assets dans la durée ;
  3. brancher l’option WooCommerce PDF web sur l’entitlement share ;
  4. lancer la génération GOF du PDF web allège quand l’option est achetee ;
  5. ajouter le backoffice KEREDIT du service partage ;
  6. garder le lecteur StPageFlip comme expérience publique principale.

La journée se termine sur un point concret : le partage n’est plus seulement une route ou un token. C’est une expérience qui ressemble enfin au projet.
