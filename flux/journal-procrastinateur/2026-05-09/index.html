Jour 50 - Auth, Woo et le connecteur WordPress

La journée a commencé par le bruit Graphify autour d'editorStore, puis a bascule sur le socle dev-auth, le lancement WooCommerce signe, le QR mobile et un premier plugin WordPress deploye sur ooblik.com.

Horaires de session

  • Agent utilisé : Codex, transition depuis Claude Code
  • Branche de travail : dev-auth
  • SHA de départ observe : b2abf78 (refactor: isolate editor store toolbar surfaces)
  • SHA distant de référence avant clôture : origin/dev = b2abf78
  • Commit cree en clôture : a venir dans cette session
  • Amplitude minimale observée : journée longue, environ 7h30 de travail effectif documente
  • Commits déjà présents au départ du billet : 0 nouveau commit sur dev-auth depuis b2abf78
  • Création / complétion du billet : 2026-05-10 pour la clôture de la journée du 2026-05-09
  • Objectif produit du jour : sécuriser l’accès bêta depuis WooCommerce et préparer les imports photo sans ouvrir trop vite Google Photos Cette entrée couvre le travail du samedi 9 mai, clôture le lendemain matin. C’est une journée charnière : elle a commencé comme une suite de refactor frontend guidée par Graphify et elle s’est terminée avec une vraie passerelle WordPress/WooCommerce installée sur ooblik.com. Le fil commun reste la mise en production bêta. Il ne suffit plus que l’éditeur soit agréable : il doit pouvoir être ouvert proprement depuis une boutique, authentifier un client sans bricolage, recevoir des images rapidement et rester maintenable.
  • Temps cumulé :241h23

Graphify et editorStore

La première partie de la journée a repris les questions Graphify sur les connexions surprenantes du frontend.

Le signal utile n’était pas que editorStore est central : il doit l’être. Le problème était plutôt que plusieurs surfaces de chrome UI lisaient le store directement via de gros useEditorStore(), ce qui rendait le graphe plus bruyant et mélangeait trop facilement responsabilités UI et état éditeur.

La décision a été de ne pas découper le store lui-même. Pour l’instant, on isole les dépendances par surface avec des hooks contrôleurs courts, plus faciles à vérifier et moins risques pour la bêta.

Première tranche :

  • EditorBottomRightControls, CheckoutPanel, FixedLeftMenu, FloatingLayersPanel, FloatingImageEnhancementPanel, TemplatesPanel, UploadZone et les outils formes du Toolbar ont reçu des hooks dédiés.
  • Les rapports Graphify ont ensuite montré que les premières connexions surprenantes avaient disparu.

Deuxième tranche :

  • PageNavigator a été extrait vers usePageNavigatorState.
  • PageOverviewDialog a été extrait vers usePageOverviewDialogState.
  • RightPanel a été extrait vers useRightPanelState.
  • Toolbar a été extrait vers useToolbarState pour son état principal.

Après cette passe, il ne reste plus de useEditorStore() global dans frontend/src/components et frontend/src/hooks.

Les useEditorStore.getState() restants sont volontairement laisses hors de cette tranche : ils vivent surtout dans des zones imperatives ou runtime (EditorCanvas, persistence, raccourcis clavier, debug, builder). Les toucher demandera une analyse séparée, car ce ne sont pas les mêmes risques.

Socle dev-auth

La deuxième partie de la journée a bascule sur le gros chantier de sécurisation bêta.

Le diagnostic de départ était simple : le JWT en localStorage était acceptable pour un MVP local, mais insuffisant pour une bêta exposée et pour des connecteurs OAuth/commerce propres.

Le socle pose dans dev-auth ajoute :

  • sessions navigateur serveur via user_sessions ;
  • cookies HttpOnly avec compatibilité Bearer temporaire ;
  • CSRF double-submit pour les mutations cookie ;
  • logout, refresh, révocation et expirations cote serveur ;
  • credentials d’intégration tenant pour les appels serveur-a-serveur ;
  • tokens WooCommerce one-shot, hashes, expirable en 10 minutes ;
  • sessions QR mobile courtes ;
  • tables de préparation pour connexions provider et imports externes.

La logique produit est volontairement progressive : le plugin WooCommerce passe avant Google Photos. On valide d’abord le flux boutique -> Krampouz -> session éditeur, puis seulement ensuite on ouvre les connecteurs photos externes.

Woo launch et QR mobile

Le contrat WooCommerce est maintenant exécutable :

  • le plugin appelle POST /api/woocommerce/launch cote serveur ;
  • les headers X-Krampouz-Integration-Key et X-Krampouz-Integration-Secret identifient le tenant ;
  • return_url est vérifiée contre l’allowlist du credential ;
  • Krampouz cree un token aléatoire stocke seulement en hash ;
  • le frontend ouvre /woo/launch?token=... ;
  • Krampouz consomme le token, cree ou retrouve le client, pose la session et retourne le contexte.

Le QR mobile a aussi son premier parcours local :

  • desktop connecte cree une session via POST /api/mobile-upload-sessions ;
  • la page mobile /mobile-upload?token=... fonctionne sans login téléphone ;
  • l’upload mobile reutilise le pipeline asset existant ;
  • les routes publiques par token restent limitees et expirables.

Ce n’est pas encore le produit final du QR, mais la fondation est importante : pas de pipeline parallèle pour les photos, pas de token long, pas d’accès général au compte.

Plugin WordPress / WooCommerce

Le chantier secondaire est devenu très concret : un plugin prive krampouz-connector a été créé dans wordpress-plugin/krampouz-connector/.

Fonctions livrées :

  • header WordPress propre, Update URI, Requires Plugins: woocommerce ;
  • intégration native WooCommerce ;
  • réglages techniques : API URL, key, secret, test connexion, manifest update ;
  • onglet produit Krampouz pour activer le bouton Creation ;
  • mapping produit/template/formats ;
  • bouton front qui respecte produit simple, variation et client invite avec email ;
  • appel serveur-a-serveur via wp_remote_post() ;
  • update prive via manifest JSON et ZIP.

Le plugin a été packagé, installe puis corrige directement sur ooblik.com.

Chronologie :

  • 0.1.0 : premier plugin installable, mais pre-requis PHP initial trop haut pour WP-CLI par défaut.
  • 0.1.1 : ajout d’une entrée visible WooCommerce > Krampouz, parce que l’accès dans les réglages était trop cache.
  • 0.1.2 : correction décisive : WooCommerce 10.7 ne rend pas les simples filtres woocommerce_get_settings_integration dans l’onglet Intégration ; il attend une vraie classe WC_Integration. Le plugin declare maintenant Krampouz_Connector_WC_Integration, et les champs apparaissent.

Le point PHP était aussi instructif :

  • CloudPanel sert bien ooblik.com en PHP 8.3 via php-fpm8.3 ;
  • wp en ligne de commande utilise par défaut PHP 8.0.30 ;
  • la commande SSH sûre pour ce site est donc php8.3 /usr/bin/wp --path=/home/[compte]/[chemin privé] ... ;
  • le plugin reste compatible PHP 8.0+, ce qui évite de bloquer inutilement.

État serveur vérifie :

  • krampouz-connector active 0.1.2 ;
  • WooCommerce voit Krampouz_Connector_WC_Integration ;
  • le rendu admin contient bien les champs API et intégration key ;
  • manifest 0.1.2 accessible sur ooblik.com ;
  • ZIP 0.1.2 publie dans wp-content/uploads/krampouz-updates/krampouz-connector/.

Direction produit du plugin

Une décision de produit importante a été prise après avoir vu le plugin dans le backoffice.

Garder uniquement WooCommerce > Integration > Krampouz serait trop limite. C’est propre pour les secrets, mais pas pour piloter demain :

  • les produits ;
  • les options ;
  • les formats ;
  • les variantes WooCommerce ;
  • la personnalisation du bouton ;
  • les diagnostics ;
  • les futures synchronisations avec Krampouz ;
  • la personnalisation de l’éditeur.

La direction retenue :

  • garder WooCommerce > Reglages > Integration > Krampouz pour l’API, la key, le secret et le test connexion ;
  • ajouter plus tard une vraie entrée WordPress de premier niveau, provisoirement Editor ;
  • y construire un mini tableau de bord sobre, moderne et opérationnel ;
  • éviter l’esthétique des vieux plugins WordPress : pas de page surchargee, pas de blocs de blabla, pas de table molle sans hiérarchie.

Onglets proposes pour ce futur dashboard :

  • Vue d'ensemble
  • Produits
  • Options & formats
  • Editeur
  • Mises à jour
  • Diagnostic

Le nom public reste ouvert. Krampouz est confirme comme nom de code interne, pas comme nom final. Les pistes trop évidentes comme Printforge, Printflow, Imprimo ou Printlane sont déjà prises ou trop proches. La meilleure piste encore fragile issue de la discussion est Imprixio, mais elle devra être vérifiée juridiquement et commercialement avant tout engagement.

Documentation

La documentation a été alignée autour de ce nouveau chantier :

  • docs/specifications/auth-api-imports.md cadre le socle auth/API, Woo launch, QR mobile et Google Photos après plugin ;
  • docs/guides/plugin-wordpress-woocommerce.md documente l’installation, le packaging, WP-CLI PHP 8.3, le manifest et l’état 0.1.2 ;
  • docs/guides/commandes-dev.md ajoute les commandes plugin et dev-auth ;
  • docs/produit/roadmap.md place le plugin-first avant Google Photos ;
  • BIBLIOTHEQUE.md référence le plugin, les routes dev-auth et la stratégie de surface admin.

Décision de propreté : les ZIP sous wordpress-plugin/releases/*.zip sont des artefacts generes. Le code, le manifest exemple et le script pnpm plugin:build sont versionnes ; les ZIP se regenerent.

Conversations et décisions

Sujets abordes

  • Audit de sécurisation avant bêta.
  • Retour des tests CI et sécurisation de Prisma.
  • Questions Graphify sur editorStore, get(), post() et les surfaces frontend.
  • Refactor frontend par hooks contrôleurs.
  • Auth cookie, CSRF, sessions serveur et compat Bearer.
  • Plugin WooCommerce prive.
  • QR mobile et Google Photos.
  • Stratégie d’update WordPress depuis manifest.
  • Installation sur ooblik.com.
  • Correction du faux problème PHP : web en 8.3, WP-CLI par défaut en 8.0.
  • Nom public du produit et abandon de Krampouz comme nom commercial.

Décisions prises ensemble

  • Ne pas toucher encore a Google Photos tant que le plugin WooCommerce n’est pas valide en live.
  • Garder WooCommerce comme adaptateur, pas comme cœur produit.
  • Garder les secrets dans une vraie intégration WooCommerce.
  • Construire ensuite une surface admin dédiée pour le pilotage métier.
  • Traiter les ZIP plugin comme artefacts de release, pas comme code source.
  • Ne pas forcer un nom public avant vérification domaine/marque.

État de clôture

État fonctionnel :

  • le chantier frontend Graphify est proprement termine pour cette tranche ;
  • le socle dev-auth existe et passe les tests locaux attendus ;
  • le plugin WordPress existe, se package, s’installe et s’affiche dans WooCommerce ;
  • ooblik.com porte déjà le plugin 0.1.2 ;
  • le prochain grand chantier fonctionnel est le dashboard plugin Editor, puis Google Photos.

État a ne pas oublier :

  • la stack Krampouz VPS n’a pas été redeployee depuis cette branche ;
  • pour tester le bouton Creation en live, il faudra un backend Krampouz dev-auth déployée avec un credential Woo autorisant https://ooblik.com/* ;
  • le plugin actuel sait ouvrir la porte, mais le flux complet produit -> éditeur -> retour panier reste à enrichir ;
  • le nom public reste à choisir.

Reprise

Ordre recommande :

  1. finaliser commit + push de dev-auth ;
  2. ouvrir le backoffice ooblik.com et renseigner les réglages API uniquement quand le backend correspondant est prêt ;
  3. concevoir le mini dashboard WordPress Editor avec une UI sobre et moderne ;
  4. tester un produit Woo simple avec bouton Creation ;
  5. seulement ensuite rouvrir Google Photos.

La journée a été dense. Elle a transformé une inquiétude abstraite - “comment va-t-on mettre ça en bêta sans casser la boutique ?” - en pièces concrètes : sessions, credentials, launch token, plugin, manifest, QR mobile. Ce n’est pas encore la fin du chantier auth, mais c’est la première fois que le pont WooCommerce -> éditeur ressemble à un vrai produit.
