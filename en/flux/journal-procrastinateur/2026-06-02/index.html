Printer logo: the detail that catches the eye straight away

The main visible topic of the day was the printer logo.

The request seemed cosmetic: the logo had to be in a circle. In practice, the issue affected several areas:

  • back-office sidebar;
  • admin preview;
  • login;
  • password reset;
  • editor bar;
  • Personnalisation page;
  • export/import and persistence of the current theme.

The first version was too simplistic: it would sometimes display a square where an area was supposed to be round, or a circle that didn’t quite match the final framing. The problem eventually pointed to a more interesting cause: in KEREDIT, UI radii are deliberately locked to 0px, and rounded-full also depended on the token radiusFull.

Conclusion: in this specific case, the circle is not a generic style. It is a business-specific rendering constraint for the logo.

The final correction therefore added:

  • logoTransform in the parent theme (x, y, scale);
  • a centralised ‘BrandLogo’ that effectively masks the final circular rendering;
  • a cropping tool available after upload;
  • a common cropping canvas shared between the preview and the final render;
  • an explicit circular guide that no longer depends on radius tokens;
  • Playwright tests dedicated to the logo workflow.

The key point is consistency: what the admin sees within the cropping circle must be what subsequently appears in the final logo.

GOF technical framework

The GOF folder contains a Node app gof-forge-app written in CommonJS, with:

  • bullmq ioredis for the job queue;
  • pg and a Postgres database for tracking jobs;
  • pdf-lib sharp for initial native PDF rendering and image normalisation;
  • AWS S3 SDK to read R2 assets;
  • pdfjs-dist to view the generated PDFs in the dashboard.

The webdocker-compose.ymls a complete development stack:

  • Postgres 16;
  • Redis 7 with append-only;
  • GOF dashboard on 8080;
  • separate rendering worker;
  • Nginx Proxy Manager;
  • Dozzle in ops profile;
  • persistent volumes data/, fonts/ and NVMe storage spaces cache, work, tmp, output-staging.

The script scripts/sync-to-forge.sh prepares synchronisation to [compte]@[hôte]:/opt/[chemin privé], excluding .env, data/, node_modules, Playwright captures, backups and .git.

Backoffice Flux

docs/backoffice-gof.md documents a real workshop interface, served by app/src/server.js:

  • folders by status: received, queue, generation, success, failures, cancellations, validations;
  • sortable and searchable job table;
  • detail panel with JSON payload, reports, assets, artefacts, events and operator actions;
  • PDF.js viewer to open the local artefact;
  • operator actions: cancel, retry, approve for printing.

GOF routes exist on the application side:

  • POST /api/render-jobs to create a job;
  • GET /api/render-jobs to list;
  • GET /api/render-jobs/:id to view;
  • POST /api/render-jobs/:id/cancel ;
  • POST /api/render-jobs/:id/retry ;
  • POST /api/render-jobs/:id/approve ;
  • endpoints for signed asset URLs and reading local artefacts.

The database creates the following tablesrender_jobsrender_assetsrender_artifactsrender_events and operator_actions. This is exactly the right terminology for a forge: work, assets, artefacts, events and human actions.

PDF Renderer v1

The first renderer is located at app/src/pdf-renderer.js.

It does not launch Chromium. It creates a PDF using pdf-lib, converts the dimensions from mm to PDF points, sets MediaBox, BleedBox and TrimBox, and draws:

  • page backgrounds;
  • text as PDF text objects with Helvetica as the fallback font;
  • vector rectangles;
  • images and clipart rendered from assets[].storage_key via R2, then normalised using sharp.

The renderer also produces:

  • render-report.json ;
  • print-validation-report.json ;
  • an SHA-256 checksum for the PDF;
  • warnings for missing assets, fallback fonts, and vector SVGs not yet supported.

This is not yet the final pre-press engine, and the blog post must make that clear. But it is a first working build: a payload is input, a job is tracked, a master PDF is output, and a report explains what has been done.

PDF Doctrine

The GOF documentation also reinforces the approach:

  • docs/inspiration-dalim-twist-forge-pdf.md translates the DALIM/TWiST logic into a GOF pipeline: ingestion, pre-volumisation, normalisation, display list, native rendering, post-processing, final check;
  • docs/moteur-pdf-bas-niveau.md establishes the principle of a native PDF writer, without Puppeteer/Playwright/Chromium in the nominal pipeline;
  • docs/preparation-pdf.md is now marked as a historical draft, with an official note stating that the Puppeteer approaches are no longer the preferred direction;
  • docs/backoffice-gof.md links this doctrine to a concrete operational interface.

The underlying principle is sound: GOF is not ‘just another PDF exporter’. It is a production pipeline. KEREDIT retains control over the project, the order, the templates and the assets; GOF consumes a standalone PDF payload, produces artefacts and ensures its decisions are auditable.

What this tells us about the beta

The beta doesn’t need a perfect logo to exist.

But it does need to ensure that the small, visible details do not give the impression of being cobbled together. A square logo when the interface promises a round one is not a technical issue; it sends the wrong message about the product.

So 2 June was useful for one simple reason: it restored consistency to the visible interfaces, whilst continuing to lay the groundwork for PDF/GOF.

The goal remains the same:

  • not to expand the scope before we have any client partners;
  • to keep postcard as the priority beta product;
  • to stabilise what the user actually sees;
  • let the PDF project move forward through contracts and evidence, not through improvisation.
