## Lecture globale

Centieme jour du journal.

Le chiffre tombe sur une journée très representative du projet : le code peut
générer vite, mais le produit ne devient pas bon parce qu'il a beaucoup de
fonctions. Il devient bon quand l'utilisateur comprend ce qui se passe, quand
les choix inutiles disparaissent, et quand l'interface arrête de produire de
l'entropie.

Le chantier du jour porte sur le **remplissage rapide du carnet**.

Au départ, le flux sait faire beaucoup de choses : choisir des pages, traiter
la couverture, ajouter des pages, trier, limiter, alterner, choisir des styles,
choisir des modèles, previsualiser, appliquer. Sur le papier, c'est puissant.
En test client, c'est trop.

Le travail du jour consiste donc a faire l'inverse de l'over-engineering :
retirer les options visibles, garder la puissance interne, et transformer le
mode rapide en expérience KISS.

## KISS, ici, veut dire quoi ?

KISS ne veut pas dire pauvre.

KISS veut dire :

- une intention principale visible ;
- des réglages qui correspondent au vocabulaire client ;
- une preview qui montre vraiment le carnet ;
- des actions simples, reversibles, et sans surprise ;
- des options techniques cachees tant qu'elles ne servent pas a décider.

Le remplissage rapide doit répondre à une phrase simple :

```text
placer mes photos dans mon carnet et me laisser essayer autre chose sans stress
```

Tout ce qui oblige l'utilisateur à comprendre les termes internes du moteur
devient suspect.

## Le flux rapide simplifie

La modale est progressivement ramenee a quelques choix :

- tri des photos ;
- nombre de pages ;
- photos par page ;
- marge ;
- écart ;
- rythme : régulier, alterne, pleine page ponctuelle ;
- action globale : **Tout réorganiser** ;
- action locale : **Réorganiser** sur une page.

Les boutons **Rapide** et **Assistant** disparaissent de l'en-tête de cette
modale. Le mode rapide est maintenant le mode. L'assistant narratif reste dans
le codebase, mais il n'a pas a être expose dans ce flux tant qu'il n'a pas un
contrat produit clair.

Le bouton principal reste oriente résultat :

```text
Placer X photos dans le carnet
```

C'est plus clair que "Lancer le remplissage".

## Preview globale : ce qui est vu doit être ce qui sera applique

La preview devient le centre du flux.

Elle montre le carnet après remplissage simule, sans modifier le store tant que
l'utilisateur n'a pas applique. Elle reprend les pages existantes, les pages
ajoutées, la couverture quand elle est incluse, et conserve la position courante
quand on change de style ou de rythme.

Plusieurs détails UI ont été affines :

- le compteur de preview inutile est supprime ;
- les bordures de "page modifiee" sont retirées ;
- les chevrons sont rapproches du carnet ;
- les controles se regroupent à gauche ;
- l'aide devient un panneau superpose et rassurant ;
- la croix de fermeture est plus visible, sans tooltip superflu ;
- les fonds de page avant chargement des vignettes sont remplaces par un gris papier ;
- les sliders utilisent la couleur terracotta cohérente avec les boutons.

La preview ne sert plus a faire joli. Elle sert à rassurer.

## Tout réorganiser, puis une page seulement

Le bouton **Tout réorganiser** garde le même rythme choisi. Si l'utilisateur est
sur "régulier", il reste en régulier. Il change les templates compatibles, pas
la logique globale du client.

Un bug important a été corrige : en **1 photo par page**, le moteur forcait
encore le plein format. C'était cohérent avec un ancien contrat, mais contraire
à l'usage : si le bouton local **Réorganiser** sait proposer d'autres templates
pour une photo, **Tout réorganiser** doit pouvoir le faire aussi.

La couverture reçoit le même droit d'essai : quand elle contient une photo, le
bouton local **Réorganiser** apparaît sur la 1re de couverture, centre dans la
moitié droite, pas au milieu du spread.

## Annuler sans inventer un deuxième éditeur

Le bouton **Annuler** devient un mini historique de composition.

Il garde jusqu'a **5 états**, mais uniquement pour :

- **Tout réorganiser** ;
- **Réorganiser** une page.

Les réglages manuels comme marge, écart, rythme ou photos par page
reinitialisent cet historique. C'est volontaire : l'objectif est d'annuler une
exploration visuelle, pas de créer un système d'historique parallèle dans la
modale.

La encore, le KISS n'est pas une absence de confort. C'est le refus d'ajouter
un mécanisme dont l'utilisateur ne comprendrait plus la portée.

## Seed local : le rappel de confiance

Le chantier du jour reste aussi marque par la peur de perdre des données
produit locales.

La veille, la protection anti-seed a été posée. Aujourd'hui, le sujet reste
present : une base locale qui devait servir de miroir ne doit pas être traitée
comme une base jetable. Le produit Zine visible sur le VPS mais absent en local
a servi de rappel très concret.

Un outil IA peut appliquer une commande vite. Le projet, lui, a besoin d'une
règle lente et non negociable :

```text
ne jamais ecraser silencieusement des donnees metier vivantes
```

## Ce que le Jour 100 raconte du projet

Le code genere vite. Parfois trop vite.

En une heure, on peut obtenir un remplissage automatique avec des dizaines de
paramètres. Mais il faut ensuite deux jours pour organiser le chaos semantique
et visuel : quels mots garder, quels controles cacher, quelle preview croire,
quelle action annule quoi, quelle page est vraiment ciblee, quelle option
cree de la confiance et laquelle cree de la confusion.

Le Jour 100 ne marque donc pas une grande extension fonctionnelle. Il marque
une discipline :

```text
puissance interne, simplicite externe
```

Et c'est probablement une bonne définition de KEREDIT a ce stade : un produit
atelier-first qui doit cacher beaucoup de complexité sans mentir a
l'utilisateur.
