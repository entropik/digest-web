Cette journée n'est pas une victoire. C'est un avertissement.
Elle commence comme une continuation logique du chantier prix. Elle finit comme une journée de confusion technique, de branches qui se croisent, de refactorisation trop large, de CLI qui travaillent en même temps sur le même sol, et d'un état personnel qui aurait dû imposer d'eteindre l'ordinateur.
Il faut l'écrire clairement : hier, j'ai percute une biche sur la route. Ce genre d'accident laisse une trace bizarre. Pas seulement parce que la voiture prend, ou parce que l'image reste dans la tête. Mais parce que le corps continue ensuite comme si tout devait rester normal, alors que quelque chose a déjà bascule. J'aurais probablement du ne pas toucher au code dans ces conditions.
Je l'ai fait quand même.
- Temps cumulé minimal depuis le début du journal : **environ 327h30+**

## Le matin : finir le pricing proprement

La première partie de la journée était encore dans la continuité des jours precedents.

Deux commits cadrent le matin :

- `5fe57c3` - `fix(pricing): use current editor format in quote`
- `d11f08d` - `fix(pricing): remove empty workshop option choice`

Le sujet était sain : le devis devait utiliser le format réel choisi dans l'éditeur, et les options atelier ne devaient plus inventer un faux choix vide du type "Aucun" quand un seul vrai choix existe.

C'est exactement le genre de correction utile avant bêta :

- ne pas afficher un prix calcule sur un format qui n'est plus celui du projet ;
- ne pas polluer l'interface client avec des options artificielles ;
- garder le pricing lisible et explicable ;
- protéger la logique atelier déjà reconstruite cette semaine.

La branche `feat/miskiss-pricing-v0` a été fast-forwardee dans `dev` vers 09:39. à ce moment-là, la journée pouvait rester simple : pricing stabilise, vérification, documentation, repos.

Elle n'est pas restée simple.

## L'après-midi : le refactor qui s'étend

Vers 10:02, le travail bascule sur `feat/simplification`.

L'intention n'était pas absurde. Le codebase avait de vraies zones lourdes :

- routes backend trop volumineuses ;
- logique WooCommerce difficile a isoler ;
- route assets massive ;
- PDF renderer en gros bloc ;
- services a extraire ;
- schémas partages a remettre au bon endroit ;
- tests a remettre en face des nouveaux decoupages.

Le commit `9623df3` résume cette première phase :

> `refactor: simplify codebase, split fat routes and extract services`

Sur le papier, l'orientation est défendable. Les routes monolithiques sont un vrai problème, et le projet a besoin de services testables. Mais le volume est énorme : `assets.ts`, `woocommerce.ts`, `projects.ts`, `pdf-renderer.ts`, schémas partages, bootstrap frontend, constantes shared. Ce n'est plus une correction. C'est une chirurgie d'architecture.

Et une chirurgie d'architecture ne se fait pas bien dans une journée déjà fragile.

## Le moment dangereux : Codex et Gemini CLI en même temps

Le vrai incident du jour est la collision d'outils.

Codex et Gemini CLI ont travaille dans le même repo, au même moment, avec des changements de branche au milieu. Les traces Git le montrent :

- checkout de `dev` vers `feat/simplification` ;
- reset local ;
- retour vers `dev` ;
- stash WIP ;
- retour vers `feat/simplification` ;
- puis reset vers `origin/dev` ;
- puis nouveaux commits sur `dev`.

Il existe encore deux stashes du 23 mai autour de 18:52 et 18:55 :

- `On feat/simplification: wip-retour-dev`
- `WIP on dev: d11f08d fix(pricing): remove empty workshop option choice`

C'est exactement le genre d'état qui devient illisible quand plusieurs assistants manipulent les mêmes fichiers sans verrou humain clair. Un outil croit sauver une branche. L'autre croit reprendre `dev`. Un reset remet une base propre, mais un stash contient encore un morceau de monde parallèle. Puis une partie du refactor arrive quand même dans `dev`.

Le résultat mental est violent : on ne sait plus immédiatement si le code courant est la bonne suite du chantier, une réparation partielle, ou une greffe mal refermee.

## Ce qui a vraiment casse la journée

Techniquement, le problème n'est pas seulement "Gemini a fait un gros patch" ou "Codex a switche".

Le problème est le mélange de cinq risques :

1. une journée emotionnellement abimee par l'accident ;
2. un chantier pricing déjà lourd la veille ;
3. une refactorisation transversale sur des fichiers critiques ;
4. deux CLI agissant dans le même repository ;
5. des changements de branche, reset et stash pendant que le sens du travail n'était plus clair.

Chaque risque pris seul peut se gérer. Ensemble, ils creent un brouillard.

Dans ce brouillard, on peut facilement confondre :

- code simplifie et code simplement déplacé ;
- suppression de dette et suppression de comportement ;
- test qui passe et contrat produit encore cohérent ;
- branche propre et workspace réellement récupérable ;
- documentation generee et décision validée.

Le plus dangereux est la sensation de devoir finir quand même. Elle pousse a accepter un commit parce qu'il calme l'angoisse, pas parce qu'il ferme vraiment le sujet.

## Auto-critique

Il y à une erreur de méthode.

Un refactor global ne devait pas être lancé en parallèle d'une reprise de branche déjà en cours. Encore moins avec deux assistants. Encore moins après un accident.

La bonne discipline aurait été :

- geler `dev` ;
- créer une seule branche de refactor ;
- interdire les switchs automatiques pendant que l'autre CLI travaille ;
- faire un commit de sauvegarde ou un patch exporte avant toute exploration ;
- limiter le refactor à un seul axe : routes, ou PDF, ou workers, mais pas tout ;
- valider chaque axe avant de passer au suivant ;
- documenter le refactor après validation, pas pendant le chaos.

La seconde erreur est emotionnelle : croire que continuer a coder allait remettre de l'ordre. Parfois, continuer ne remet pas de l'ordre. Parfois, continuer ajoute de la dette au moment précis ou il faudrait dormir.

Hier, il aurait fallu s'arrêter plus tôt.

## Ce qui reste sauvable

Tout n'est pas a jeter.

Le matin a produit deux corrections pricing utiles. Elles sont claires, petites, et rattachées au besoin bêta.

Le refactor contient probablement de bonnes idées :

- découper les routes `projects`, `assets`, `woocommerce` ;
- isoler les services ;
- rendre les workers testables ;
- modulariser le rendu PDF ;
- centraliser les contrats queues ;
- réduire les imports morts ;
- clarifier le bootstrap frontend.

Mais ces idées doivent maintenant repasser par une revue froide.

La question n'est pas "est-ce que le refactor est beau ?". La question est :

> est-ce que le produit bêta est plus fiable après ce refactor qu'avant ?

Si la réponse n'est pas prouvable localement, le refactor doit rester suspect.

## Reprise recommandee

Demain, il ne faut pas reprendre en mode production de code.

Il faut reprendre en mode diagnostic.

Ordre recommande :

1. Ne rien commiter du WIP courant avant lecture.
2. Sauvegarder l'état local si nécessaire avec un patch ou une branche de secours.
3. Comparer `dev@e9016cd`, `feat/simplification`, `rescue/feat-simplification-wip` et les stashes du 23 mai.
4. Lister les fichiers critiques modifies par le WIP actuel.
5. Lancer d'abord les checks de compilation et tests workers/PDF ciblés, mais seulement après avoir decide quelle base tester.
6. Vérifier l'auth, les routes projets, WooCommerce, upload assets, workers et PDF comme surfaces prioritaires.
7. Décider ensuite : continuer depuis `dev`, cherry-pick des morceaux, ou repartir d'un SHA plus ancien.

Le critère doit être simple : si une modification ne peut pas être expliquee et testée, elle ne rentre pas.
