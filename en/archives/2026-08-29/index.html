FOCUS - After the IDE, here comes the ADE

For thirty years, the development environment was designed around a developer working with files. Claude Code and Codex have changed this unit of work. A new generation of tools — Orca, Superset, Emdash — no longer seeks to help us write code: it organises agents to write it for us.

The traditional IDE organises files, an editor, a terminal and a debugger. The ADE now organises agents. This shift in terminology signals a more profound transformation: the unit of work is no longer simply the file opened by a developer, but the task entrusted to an agent in an isolated environment.

The central argument of this edition can be summed up in a single sentence: the next essential tool for AI developers may be neither the model nor the editor. It will be the orchestrator.

From the IDE to the ADE

For thirty years, the integrated development environment (IDE) has brought together in a single window everything a human needs to programme: file tree, editor, terminal, debugger, search and version control. Code assistants first found their place within this architecture in the form of smarter autocomplete or a conversation panel.

Claude Code, Codex, OpenCode and other terminal agents are now shifting the centre of gravity. They read the repository, modify multiple files, run tests, inspect errors and sometimes even prepare the commit or pull request themselves. Humans no longer handle every line of code: they assign tasks, monitor execution and assess the results.

The dominant workflow therefore takes on a different form:

Project → tasks → Git worktrees → independent agents → supervision → diff and review → merge

The IDE — Agentic Development Environment — becomes less of an editor and more of a control centre. Its role is to launch multiple agents, provide them with the correct context, isolate their changes, flag those awaiting a decision and present their proposals in a comparable manner.

The worktree as a common primitive

Most of these tools converge on the same building block: the Git worktree. A task is assigned a separate branch and a separate working directory. Claude Code can fix a regression whilst Codex prepares a feature and OpenCode explores a third solution, without their changes immediately mixing.

This isolation does not solve everything. Contributors may still modify the same concepts on different branches, fail to set up the project, or produce incompatible changes at the time of merging. But the worktree transforms a cacophony of concurrent processes into observable, comparable and, if necessary, disposable units.

It becomes to the ADE what the file was to the IDE: the concrete object around which the interface organises the work.

The stable layer above the models

Models will remain uneven. Claude will excel at one task, Codex at another, and Gemini or a local model at a third. Their performance, pricing and context windows will evolve rapidly. Betting the entire workflow on just one of them is tantamount to confusing the engine of the moment with the vehicle.

The ADE offers a more stable layer: project + context + worktrees + agents + supervision + validation + history. The model becomes an interchangeable executor that one chooses according to the problem, cost or confidentiality constraints.

This promise remains partly to be proven. Not all agents expose the same events, session formats or recovery mechanisms. Changing models does not yet mean cleanly transferring their memory and reasoning. But the direction is clear: the environment seeks to absorb these differences to offer the developer a consistent workflow.

Three projects that define the category

Orca — the most comprehensive cockpit

Orca embodies the concept of a fleet most directly. It runs CLI agents side by side, each in its own worktree, then brings together terminals, files, diffs, GitHub, Linear, remote machines and notifications into a single interface. Its mobile companion also allows you to monitor or restart a run whilst away from your workstation.

Its most revealing feature is the ability to send the same problem to several isolated agents and then compare their solutions. Development becomes almost like concurrent experimentation: multiple implementations are produced, tested and compared before a human chooses or merges them.

Licensed under the MIT licence and driven by a very strong community, Orca is currently the best starting point for understanding what a general-purpose IDE could become.

Emdash — the vendor-agnostic open-source choice

Emdash explicitly defines itself as an open-source agent-based development environment. Its Apache 2.0 licence and vendor independence make it the clearest candidate for building a sustainable workflow without tying it to a single agent.

Its approach follows the actual development pipeline: a ticket from GitHub, GitLab, Linear, Jira or Asana is assigned to an agent in an isolated environment; this is followed by changes, review, testing, the pull request and CI. Agents can also work on a remote machine via SSH whilst the interface remains local.

Emdash is less spectacular than Orca, but its neutrality and integration with project tools probably make it the most coherent open-source choice in this selection.

Superset — the integrated agent-based IDE

Superset uses the same basic building blocks — a task, an isolated workspace, an agent — with an ambition closer to that of a direct successor to the IDE. It maintains sessions via a daemon, flags agents requiring attention, displays diffs and allows workspaces to be opened in other editors.

The project claims to be able to orchestrate over a hundred agents. This figure primarily describes an architectural capacity: no human can reasonably examine a hundred complex workflows at once. It nevertheless raises the right question: that of attention. When ten agents are running simultaneously, the problem is no longer launching them but knowing which one is blocked, which one has finished and which one requires a decision.

An editorial distinction is essential: Superset releases its code under the Elastic Licence 2.0. It can be used, modified and self-hosted, but this licence is not recognised as open source in the strict sense by the OSI. Superset is therefore source-available, not strictly open source.

The alternative approach: staying in the terminal

Agent Deck rejects the idea that an agent dashboard must necessarily become a large graphical application. Written in Go and built around tmux, it brings together sessions, their statuses, notifications, groups and worktrees within a terminal interface.

This approach tackles the same problem using existing Unix primitives. It will appeal more to developers who already work in tmux and want to monitor multiple agents without installing a new Electron-based IDE. Above all, Agent Deck demonstrates that an IDE is a function first and a graphical interface second.

Two up-and-coming projects to watch

OpenADE, licensed under the MIT licence, advocates a more structured workflow: plan, review, then execute. Plans can be compared across multiple agents before a single agent applies the changes. The environment remains local and brings together the terminal, files, search, diff, process management and Git snapshots centred around Claude Code and Codex.

ADE literally takes its name from the category. Still in its infancy, this AGPL project comprises a macOS application, a CLI, a persistent local runtime — the ‘brain’ — and an iOS companion. Each task resides in its own worktree, and the various interfaces connect to the same execution state. Its adoption remains limited, but its architecture clearly illustrates the idea of a sustainable environment to which multiple interfaces are attached.

After orchestration, the project’s memory

Frame shifts the focus to a problem that cockpits do not yet solve effectively: how do we preserve the software’s intent? Running five agents in parallel is pointless if each one has to rediscover the architecture, past decisions and acceptance criteria.

Its spec-driven approach transforms planning, architecture notes, structure and tasks into a persistent context, readable by future agents and versioned alongside the project. Frame is less a fleet manager than an attempt to build the collective memory that this fleet will require.

This approach could become just as important as orchestration itself. A mature ADE will need to answer not only ‘which agent is working on which branch?’, but also ‘what do they know about the project, why was this decision made, and how can they prove that their work adheres to the original intention?’

Agent, ADE, organisation: three distinct layers

Confusion with ‘agent-based operating systems’ disappears if we separate the layers:

Agent — Claude Code, Codex, OpenCode, Gemini CLI: to execute a development task.

IDE — Orca, Emdash, Superset: isolating, launching, supervising, comparing and validating multiple agents.

Organisational orchestration — Paperclip and multi-agent systems: distributing objectives, responsibilities, budgets and governance across an organisation.

Paperclip aims to become the operating system for an enterprise of agents. Orca and Emdash aim to become the operating system for its software workshop. They are closely related, sometimes required to connect, but they do not solve the same problem.

My editorial ranking

Orca is currently the most comprehensive suite and the project that best defines the category. Emdash is the cleanest open-source choice for a workflow-agnostic solution. Superset perhaps embodies the product vision closest to the future IDE, with the significant caveat of its source-available licence.

Next come Agent Deck for terminal-based development, OpenADE for planning, Frame for memory and context, and then ADE for its local, persistent and mobile architecture – which is still at an experimental stage.

The real test, however, will not be the number of agents displayed in an interface. It will be the ability to make them replaceable, to resume their work after a failure, to preserve the project’s intent, and to narrow down a hundred competing proposals to a verifiable human decision.

The IDE helped the developer to write code. The ADE must now help them to manage those who write it.
