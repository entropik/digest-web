Jour 126 - Le produit se montre, le panier se souvient

Jour 126 du journal : l'aperçu produit dynamique arrive, les projets du panier deviennent indestructibles, la grille tarifaire gagne sa matrice et le Builder commence à centraliser l'authoring.

Session timetables

  • Tool used: Codex, with several automated work sessions and reviews
  • Primary environment: Mac, KEREDIT repository dépôt local krampouz, GitHub Actions and KEREDIT VPS for the relevant releases
  • Date covered: Friday 7 August 2026, including the night shift starting on 6 August
  • Main branch: dev, PRs #412, #414 to #417 and #425 to #427 merged; Builder work continued at the end of the session
  • Observed windows: 03:06 → 04:33 and 17:07 → 22:12 CEST
  • Minimum observed duration: approximately 6h32+
  • Milestone commits: ba8245c4, 73b66942, 01dfe415, 2d942516, 663636b1, 54b1a54e, 5a3e853c
  • Versions used: 0.20.1, 0.21.0, 0.21.1 and 0.21.2; plugin 0.1.96 then 0.1.97
  • Minimum cumulative time since the start of the log: approximately 825h08+ (818h36+ as at 6 August, + 6h32+ today)

Quick read

The day begins by tidying up the loose ends from the previous day: the WooCommerce synchronisation is now recoverable, compatible with the old endpoint and capable of handling a change received whilst a batch is running. Then KEREDIT changes gear. The product can finally feature a dynamic presentation without cluttering its print file; the basket protects the projects it references; the pricing grid accepts a free value for each format × quantity combination; the Builder is starting to become the sole authoring tool for templates.

These are not four isolated functions. They are beginning to form a single contract: a marketable product links a composition, an appearance, a price and a project without confusing their sources of truth.

Finishing the Woo synchronisation properly

The night-time session processes Codex feedback from catalogue synchronisation. The backend falls back to /product-synced when a site is still using an older plugin. The plugin maintains its lock throughout the processing of batches, then symmetrically re-checks the pending generation before exiting. A merged burst must not lose either legacy products or the latest update received.

The security fix js-yaml is included in the same release. Version 0.20.1 and plugin 0.1.96 are prepared, documented and then merged at 4.33 am, following the return of GitHub Actions. The night finally draws to a close with a publishable state rather than just a successful restart.

Showcasing the product without rendering its background

The dynamic product preview, introduced the day before, is merged into 0.21.0. The references in the workshop library can provide a colour or a physical texture; the Builder links these appearances to a family of options and adds conditional backgrounds. Layers follow the layout in the canvas, page thumbnails and project previews.

The key principle can be summed up in one sentence: the presentation is not the composition. It remains separate from the print JSON and the PDF. A single template can therefore be used for several products or colourways without duplicating its pages, whilst the appearance assets remain protected as long as they are referenced.

A project viewed in the basket is no longer disposable

The second major benefit stems from a more subtle risk. A WooCommerce line item may still point to a project that the client subsequently deletes in KEREDIT. ` cart_seen_at` becomes the minimal record of the project’s passage through the basket: for 90 rolling days, all deletion interfaces — client, application and admin, whether individual or batch — refuse to delete this project. Revenue projects test_flux remain unaffected, but only via their persistent and tenant-scoped identity.

Plugin 0.1.97 can also account for an old line that has already become orphaned. The guard does not repair the pass; above all, it prevents it from being reproduced.

The price becomes an explicit matrix

The historical additive mode can start from a base price and apply tiered pricing or surcharges. It cannot simply express that each format × quantity combination has its own price. The product listing therefore gains a matrix_v1 grid, embedded in the Product.pricing contract, validated before saving and utilised by the server, the editor and WooCommerce.

Review has revealed a legacy issue: the VAT rate has existed in several different formats. The runtime standardises the old values and guarantees a default rate; otherwise, the basket discount would be calculated on an inconsistent basis. Version 0.21.2 brings together the matrix, its VAT compatibility and the Builder’s first atomic guarantees.

The Builder becomes the control centre

Multi-format saving can no longer promote one variant whilst others are still being written. Ambiguous normalisations and migrations are detected, variants are compared semantically, pages are realigned after saving, and promotion remains locked until the operation is complete. This first batch corresponds to issue #418 and closes the main atomicity flaw.

Late in the evening, the next task begins: removing the templates list’s role as a concurrent editor and centralising the reference product, assignments, publication and transfers within the Builder. The commit 5a3e853c establishes this new control centre, but its PR and final patches will be merged after midnight. Day 126 therefore ends with a clear boundary and work still in progress, not at a false finish line.
