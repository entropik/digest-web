Day 70 – When the job itself becomes a risk

A day of disruptions and decisions: three power cuts, an order for a Mac mini M4 Pro, and a cautious decision to postpone the beta for friends and family by a week.

It becomes a project risk.

Three outages

The workstation suffered three interruptions:

  • a general power cut linked to the electricity grid;
  • two outages caused by the machine overheating.

It’s not just a nuisance. On KEREDIT, a workstation outage can disrupt far more than just concentration:

  • Codex sessions cut short;
  • lost debug contexts;
  • browser, terminal, backend or worker that needs to be checked again;
  • risk of mistaking a local glitch for a genuine application bug;
  • extra fatigue at precisely the moment when the beta requires a clear head.

The project already has enough real issues to deal with: e-postcards, shopping basket recovery, workshop support, PDFs, assets, the WordPress plugin and product data. Adding an unstable machine to the beta cycle would be counterproductive.

Hardware decision

The result was concrete: an order for a Mac mini M4 Pro.

This isn’t a matter of fancying a fancy setup. It’s a decision regarding local infrastructure. The workstation has become part of the critical path, just like the VPS or the WordPress plugin.

Next week will therefore involve migrating the environment:

  • development tools;
  • local repositories and secrets;
  • Docker / pnpm / Node;
  • VPS and GitHub access;
  • Codex configuration;
  • personal skills and project skills;
  • working habits relating to VS Code, the terminal, the browser and screenshots.

Between excitement and added stress, we need to accept that this transition will take up some time. Treating it as a simple ‘in-between’ task would be the surest way to ruin the beta.

GOF: the future PDF forge

The other important thread from 29 May wasn’t in the Krampouz repo itself. It was in:

dépôt local gof

GOF, which is beginning to take shape as the future PDF workshop forge for KEREDIT.

The proposal has already set out several key structural choices:

  • workshop machinegof with a static IP[adresse LAN];
  • Target installation: Ubuntu Server + Docker Compose;
  • local dashboard at 8080;
  • Local Redis to manage a job queue;
  • Nginx Proxy Manager for secure HTTPS access via forge.keredit.com;
  • persistent volumes for logs, Redis, proxy, fonts and data;
  • Dedicated NVMe for fast storage at cache, work, tmp and output-staging;
  • Node.js base ready for a native Cairo/Fabric PDF renderer, without Puppeteer.

The GOF documents created or consolidated also describe the implementation:

  • README.md : GOF’s role as a local PDF forge;
  • docs/runbook-installation-ubuntu.md : Ubuntu reinstallation, bootstrapping, deployment, checks;
  • docs/securite-atelier.md : firewall, LAN-only, blocked ports;
  • docs/exposition-https-autonome.md : DNS, Freebox Pro NAT, HTTPS, Basic Auth;
  • docs/operations-gof.md : control commands;
  • docs/dns-lan-stock2.md : LAN DNS incident with STOCK2 and cache NXDOMAIN;
  • docs/audit-truenas-[adresse LAN].md : treating the old TrueNAS as a storage appliance, not as a practical application host.

This is a key principle for KEREDIT: GOF must not read the internal tables directly. KEREDIT remains the authority for commands, projects, templates and assets. GOF must consume a complete, versioned PDF payload, then produce the rendered artefacts.

PDF processing is also moving in a more sound direction: no large PNG images pasted into a PDF, no Puppeteer eating up all the RAM. What is needed is a genuine production-quality PDF, with text and shapes preserved where possible, HD images rendered from R2, fonts embedded, and vector rendering via Cairo/Fabric. Put simply: the PDF must remain a page-based document, not a giant screenshot.

Blog decision: we must not start a second blog for GOF. As long as GOF exists as KEREDIT’s PDF forge, its progress must be reported here, in the Krampouz/KEREDIT blog, with an explicit link to dépôt local gof.

Beta decision

Today’s decision is therefore:

No-Go for opening up to partner clients on 1 June 2026. A cautious one-week postponement, with Wave 1 now targeted for 8 June 2026.

This postponement does not change the product itself. It changes the timetable.

The scope remains deliberately narrow:

  • postcard as a priority product;
  • WooCommerce for product listings, the shopping basket and payment;
  • KEREDIT as the business authority for prices, formats, quantities and options;
  • possible workshop support adjustments;
  • photo_print and fine_art_print will provide support in the background, without making any broad promises.

1 June can remain a symbolic date and an internal milestone. But it must no longer be the date on which partner clients are brought into an environment that we know will need to be migrated shortly afterwards.

What this changes in the plan

The week of 1 to 7 June becomes a week of stabilisation and workstation migration:

  1. moving the development environment to a reliable machine;
  2. migrate Codex, the skills and access rights;
  3. check that the repository, the local runtime and the VPS are all in sync;
  4. re-run the full ‘postcard’ workflow after migration;
  5. only invite beta testers once local support has returned to normal.

The delay is frustrating, but sensible. A beta for friends and family doesn’t need a perfect product. It needs a reliable ability to respond when something goes wrong.

Yesterday, the signal was clear: it’s not yet the right time to bring in external testers.

Resumption

Recommended priorities:

  1. document the postponement in the beta plan;
  2. prepare a short checklist for the migration of workstations, Codex and skills;
  3. version control or, at the very least, properly back up GOF before expanding it;
  4. explicitly link the future Krampouz PDF payload to the GOF consumer;
  5. check the current status of dev before starting any new work;
  6. run the ‘postcard’ cycle again once the new environment is ready;
  7. keep 8 June as the new target date, unless a genuine obstacle is identified.

The day did not advance the editor’s development, but it did prevent a mistake: forcing a beta release out of a desire to stick to a deadline, when the local working infrastructure first needed to be secured.
