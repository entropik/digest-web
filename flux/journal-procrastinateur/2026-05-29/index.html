Jour 70 - Quand le poste devient lui-même un risque

Journée de coupures et de décision : trois interruptions du poste, commande d'un Mac mini M4 Pro et report prudent de la bêta clients amis d'une semaine.

Horaires de session

  • Agent utilisé : Codex
  • Environnement principal : VS Code WSL, plugin Codex à gauche, code au centre, terminal Codex à droite
  • Date : vendredi 29 mai 2026
  • Branche : dev
  • Version application en fin de journée : 0.6.49
  • Version plugin WordPress/WooCommerce de référence : 0.1.27
  • Dernier SHA connu sur dev : 69c914b
  • Amplitude observée par les commits : aucun nouveau commit applicatif observé ce jour-la ; dans dépôt local gof, fichiers de forge PDF modifiés entre 11:09 et 18:04
  • Temps actif estimé : non mesurable proprement dans les traces git, mais la journée a combine interruptions, arbitrage planning et première structuration de GOF
  • Commits principaux poussés : aucun commit applicatif le 29 mai ; GOF n’est pas encore un dépôt Git local Le 29 mai devait être une journée de revue Go / No-Go. Elle l’a été, mais pas comme prévu. Au lieu d’un replay calme du parcours bêta, la journée à surtout rappele un point simple : quand le poste de travail coupe, chauffe et interrompt le fil trois fois dans la même journée, ce n’est plus un bruit de confort. Cela devient un risque projet.
  • Temps cumulé :368h48+, inchange faute de trace commit utile

Trois coupures

Le poste a subi trois interruptions :

  • une coupure générale liée au réseau electrique ;
  • deux coupures liées à la surchauffe de la machine.

Ce n’est pas seulement pénible. Sur KEREDIT, une interruption de poste peut casser beaucoup plus qu’une concentration :

  • sessions Codex coupees ;
  • contextes de debug perdus ;
  • navigateur, terminal, backend ou worker à vérifier à nouveau ;
  • risque de confondre une panne locale avec un vrai bug applicatif ;
  • fatigue supplémentaire au moment précis où la bêta demande de la lucidité.

Le projet à déjà assez de sujets réels : commerce postcard, reprise panier, support atelier, PDF, assets, plugin WordPress, données produit. Ajouter une machine instable dans la boucle bêta serait une mauvaise économie.

Décision matérielle

La conséquence a été concrète : commande d’un Mac mini M4 Pro.

Ce n’est pas une coquetterie de setup. C’est une décision d’infrastructure locale. Le poste de travail est devenu une partie du chemin critique, au même titre que le VPS ou le plugin WordPress.

La semaine prochaine devra donc absorber une migration d’environnement :

  • outils de dev ;
  • repo et secrets locaux ;
  • Docker / pnpm / Node ;
  • accès VPS et GitHub ;
  • configuration Codex ;
  • skills personnels et skills projet ;
  • habitudes de travail autour de VS Code, terminal, navigateur et captures.

Entre excitation et stress supplémentaire, il faut accepter que cette transition prenne de la place. La traiter comme une simple installation “entre deux tickets” serait le meilleur moyen d’abîmer la bêta.

GOF : la future forge PDF

L’autre fil important du 29 mai n’était pas dans le repo Krampouz lui-même. Il était dans :

dépôt local gof

GOF commencé à prendre forme comme future forge PDF atelier pour KEREDIT.

Le dossier posé déjà plusieurs choix structurants :

  • machine atelier gof en IP fixe [adresse LAN] ;
  • installation cible Ubuntu Server + Docker Compose ;
  • dashboard local sur 8080 ;
  • Redis local pour préparer une file de jobs ;
  • Nginx Proxy Manager pour une exposition HTTPS protégée sur forge.keredit.com ;
  • volumes persistants pour logs, Redis, proxy, polices et données ;
  • NVMe dédié aux espaces rapides cache, work, tmp et output-staging ;
  • socle Node prêt pour un renderer PDF natif Cairo / Fabric, sans Puppeteer.

Les docs GOF créés ou consolidées racontent aussi l’exploitation :

  • README.md : rôle de GOF comme forge PDF locale ;
  • docs/runbook-installation-ubuntu.md : reinstallation Ubuntu, bootstrap, deploy, checks ;
  • docs/securite-atelier.md : firewall, LAN-only, ports interdits ;
  • docs/exposition-https-autonome.md : DNS, NAT Freebox Pro, HTTPS, Basic Auth ;
  • docs/operations-gof.md : commandes de contrôle ;
  • docs/dns-lan-stock2.md : incident DNS LAN avec STOCK2 et cache NXDOMAIN ;
  • docs/audit-truenas-[adresse LAN].md : lecture de l’ancien TrueNAS comme appliance de stockage, pas comme hote applicatif pratique.

Le point de doctrine est important pour KEREDIT : GOF ne doit pas lire directement les tables internes. KEREDIT reste l’autorité des commandes, projets, templates et assets. GOF doit consommer un payload PDF versionne et complet, puis produire les artefacts de rendu.

La recherche PDF avancé aussi dans une direction plus saine : pas de grosse image PNG collee dans un PDF, pas de Puppeteer qui mange toute la RAM. Le besoin est un vrai PDF de production, avec textes et formes conserves quand c’est possible, images HD résolues depuis R2, polices enregistrées, et rendu vectoriel via Cairo/Fabric. En clair : le PDF doit rester un document de page, pas une capture d’écran géante.

Décision de journal : il ne faut pas ouvrir un deuxième blog pour GOF. Tant que GOF existe comme forge PDF de KEREDIT, ses avancées doivent être racontees ici, dans le journal Krampouz/KEREDIT, avec un lien explicite vers dépôt local gof.

Décision bêta

La décision du jour est donc :

No-Go pour une ouverture clients amis le 1er juin 2026. Report prudent d’une semaine, avec Vague 1 ciblée au 8 juin 2026.

Ce report ne change pas le produit ouvert. Il change le calendrier.

Le scope reste volontairement petit :

  • postcard en produit prioritaire ;
  • WooCommerce pour fiche produit, panier et paiement ;
  • KEREDIT comme autorité métier pour prix, formats, quantités et options ;
  • correction support atelier possible ;
  • photo_print et fine_art_print en second rideau accompagne, pas en promesse large.

Le 1er juin peut rester une date symbolique et un jalon interne. Mais ce ne doit plus être la date d’entrée de clients amis dans un environnement que l’on sait devoir migrer dans la foulée.

Ce que cela change dans le plan

La semaine du 1er au 7 juin devient une semaine de stabilisation et de migration poste :

  1. remettre l’environnement de dev sur une machine fiable ;
  2. migrer Codex, les skills et les accès ;
  3. vérifier que le repo, le runtime local et le VPS racontent la même histoire ;
  4. rejouer le parcours postcard complet après migration ;
  5. n’inviter les clients amis qu’une fois le support local redevenu calme.

Le report est frustrant, mais sain. Une bêta clients amis n’a pas besoin d’un produit parfait. Elle a besoin d’une capacité de réaction fiable quand quelque chose coince.

Hier, le signal était clair : ce n’est pas encore le bon moment pour ajouter des testeurs externes.

Reprise

Priorités recommandées :

  1. documenter le report dans le plan bêta ;
  2. préparer une checklist courte de migration poste / Codex / skills ;
  3. versionner ou au minimum sauvegarder proprement GOF avant de le faire grossir ;
  4. relier explicitement le futur payload PDF Krampouz au consommateur GOF ;
  5. vérifier l’état courant dev avant tout nouveau chantier ;
  6. rejouer le cycle postcard une fois le nouvel environnement prêt ;
  7. garder le 8 juin comme nouvelle date cible, sauf blocage réel constate.

La journée n’a pas fait avancer l’éditeur, mais elle a évite une erreur : forcer une bêta par fidélité à une date alors que l’infrastructure de travail locale demandait d’abord à être sécurisée.
