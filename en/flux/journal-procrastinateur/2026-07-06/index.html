WooCommerce observability incident

The Grafana alert “5xx errors > 2%” did not indicate a widespread outage. The VPS probes showed a healthy backend, and the metrics indicated that the 500 errors were concentrated on POST /api/woocommerce/webhook.

The diagnosis traced the issue back to the WooCommerce webhook 13, active on ooblik.com, topic order.updated, KEREDIT URL woo_ooblik_live. This webhook is legitimate: it links WooCommerce orders to KEREDIT. The noise stems from the native deliver_ping(), which sends a non-JSON body of the type webhook_id=13. KEREDIT expects a signed JSON order and therefore responded with a 500 status code to this ping. Genuine order webhooks continued to go through.

Operational conclusion: no global backend incident, but a fix is required. KEREDIT remains useful for handling this ping via 200 or by rejecting it, without cluttering up the 5xx alerts.

Moving forward

There are two points to bear in mind:

  • properly fix the WooCommerce ping to eliminate this 5xx error message noise;
  • check in the editor that snapping, guides and multi-block alignment remain user-friendly, not just covered by tests.
