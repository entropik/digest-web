Jour 79 - Images plus nettes, projets plus prudents, contrat JSON réparé

Amélioration du rendu image dans l'éditeur, confort de zoom, projets WooCommerce plus prudents, puis correction GOF 0.1.49 du contrat JSON/rendu image KEREDIT.

Billet finalisé après correction GOF 0.1.49 du bug de correspondance image entre le JSON KEREDIT et le rendu PDF GOF.

Horaires de session

  • Agent utilisé : Codex
  • Environnements observés : Krampouz/KEREDIT dans dépôt local krampouz, GOF dans dépôt local gof
  • Date : mardi 9 juin 2026
  • Branche KEREDIT : dev

  • Version KEREDIT observée : 0.6.92
  • Branche GOF : dev
  • Version GOF observée après correction : 0.1.49
  • SHA GOF observé après correction : 347a563

Conclusion courte

La journée a d’abord cherché à rendre l’éditeur plus crédible visuellement : meilleure résolution de preview, image de lancement configurable, photos originales mieux chargées, raster adaptatif plus net, puis déplacement et survol moins coûteux dans le canvas.

Elle a ensuite glissé vers un sujet plus produit : les projets client WooCommerce doivent être plus prudents. Un projet déjà commandé ne doit pas être réédité comme un brouillon libre ; la duplication devient le chemin normal pour reprendre sans abîmer l’historique de commande.

La fin de journée a fermé le point le plus dur : la correspondance image entre KEREDIT et GOF. KEREDIT avait renforcé son contrat de fraîcheur de rendu ; GOF 0.1.49 sait maintenant rendre les ajustements image KEREDIT avec la bonne origine de rotation et le même sens de rotation que l’éditeur.

Le matin : rendre l’éditeur plus net

Le premier fil du jour est très visible : l’éditeur devait arrêter de donner une impression floue ou fragile dès que l’on regarde une vraie photo.

Les commits de référence côté KEREDIT montrent la progression :

  • a569076 ajoute un écran de lancement configurable ;
  • 89c395e ajoute des effets configurables sur cet écran ;
  • 411039c augmente la résolution des previews éditeur ;
  • b6962fe puis 67e32f2 rendent l’image de preview de lancement plus fiable ;
  • 8402bf3 améliore le zoom de confort dans l’éditeur postcard.

Ce n’est pas un simple vernis. Pour la bêta, le client doit comprendre qu’il travaille sur un objet imprimable, pas sur une miniature approximative. Le zoom, la netteté, le temps de chargement et la stabilité du canvas font partie de la confiance produit.

Photos : garder l’original comme vérité, accélérer l’écran

Le gros chantier technique autour des images a ensuite repris le contrat déjà documenté : l’original reste la vérité de production, le raster adaptatif reste un cache écran temporaire.

KEREDIT charge maintenant mieux les photos originales dans le canvas (44905a2), garde les photos attachées pendant le drag (272fd34 / 35d99e6), rend les rasters adaptatifs plus nets (be46fcf), garde leur fit correct (7881b03), puis décale le travail coûteux pour ne pas bloquer les interactions (5eb7146).

Le point important est le compromis : l’éditeur doit répondre immédiatement quand on déplace ou redimensionne une photo, mais il ne doit pas sacrifier la qualité de ce qui sera exporté. La journée a donc séparé davantage les responsabilités :

  • feedback écran rapide pendant l’interaction ;
  • cache navigateur pour éviter de relire l’original à chaque geste ;
  • contrat persistant qui continue de parler de l’image source, pas du cache.

Overlay et gestes éditeur

Le commit b865919 polit les interactions d’overlay. C’est cohérent avec le reste de la journée : une fois les images plus lourdes et plus nettes, il faut éviter que les guides, sélections et toolbars donnent une sensation de collage ou de retard.

Ce travail reste dans le cap bêta : ne pas rouvrir le chantier typographie stable, mais enlever les frottements visibles autour de la manipulation d’images.

WooCommerce : reprendre sans casser la commande

L’autre moitié de la journée touche le parcours client et le plugin WooCommerce.

Le commit 854f288 impose une règle prudente : un projet déjà commandé doit passer par une duplication avant reprise. C’est un point métier important. Une commande passée est une trace commerciale et production ; la rouvrir comme un brouillon modifiable serait dangereux.

La suite améliore le confort de consultation :

  • 281d7ac charge les projets client progressivement ;
  • c379067 simplifie les contrôles ;
  • 456b5c4 clarifie la sélection en masse ;
  • fbfbd09 polit les actions groupées.

Le résultat attendu côté client est plus simple : retrouver ses projets, comprendre lesquels sont commandés, dupliquer quand il faut repartir, et éviter les actions ambiguës.

Bug corrigé : KEREDIT et GOF relisent le même contrat image

La fin de journée était le point de tension.

KEREDIT à un commit explicite, 0beb905 (Fix image render contract freshness), qui touche la validation de pages, le payload GOF, les routes PDF/print jobs, l’admin PDF et la persistance projet. Le signal est clair : le contrat de rendu image devait être rafraîchi et rendu plus explicite avant l’envoi ou la réutilisation de rendus.

Côté GOF, la correction s’est faite en trois temps :

  • 9f33865 (Render Keredit image adjustments in GOF) ajoute le rendu des ajustements image KEREDIT dans app/src/pdf-renderer.js avec test associé ;
  • 7756fb5 (Fix GOF image block rotation origin) corrige l’origine de rotation des blocs image ;
  • 347a563 (Mirror editor image rotation in GOF PDFs) aligne le sens de rotation GOF avec celui de l’éditeur.

Le bug n’était donc pas une simple différence visuelle PDF. C’était un bug de contrat entre :

  • le JSON persistant de l’éditeur ;
  • le payload exporté par KEREDIT ;
  • l’interprétation GOF ;
  • le rendu PDF final.

GOF 0.1.49 documente la sortie de ce blocage : les ajustements image KEREDIT, l’origine de rotation et le sens de rotation sont maintenant rendus du même côté de la chaîne.

Décision de clôture

La journée se termine mieux qu’elle n’était partie : l’éditeur image gagne en confort, le parcours projet WooCommerce devient moins dangereux, et le pont KEREDIT → GOF ferme une divergence concrète entre JSON et PDF.

Point à garder pour la suite : dès qu’un rendu PDF ne correspond pas à l’éditeur, le bon réflexe reste de suivre le contrat complet plutôt que de patcher le rendu final par intuition. La chaîne doit être vérifiée dans cet ordre : JSON persistant, payload exporté, interprétation GOF, PDF produit.
