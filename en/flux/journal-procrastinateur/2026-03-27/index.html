Huit CPU, quatre workers et seize visiteurs

3 commits qui bouclent les sprints d’amélioration upload. Le sprint 6 a déjà été diagnostique : upgrade VPS vers 8 CPU / 16 Go, et surtout passage du worker assets a concurrency 4 (c’était le vrai goulot). Le sprint 7 est gèle avec une campagne multi-utilisateurs validée : 16 VUs, 2 minutes, 517 assets preview_ready, 0 échec.

Le sprint 8 ajoute du trafic métier autour du flux photo : création de projets, autosave, navigation API. Le scénario atelier-mixte est valide : 418 itérations, 418/418 assets OK, project update p95 ~82ms.

Le VPS passe enfin au banc de charge

  • VPS upscale 8 CPU / 16 Go

  • Campagne 16 VUs validée sans échec
  • Scénario atelier-mixte valide (upload + projets + autosave)
  • Décision : geler les sprints benchmark, revenir aux features

La file de prévisualisation était le goulot

La découverte clé : le goulot n’était pas le frontend ni le swap mémoire, c’était la file de preview du worker. Avec concurrency: 2, le worker ne pouvait traiter que 2 images à la fois — le reste attendait dans la queue. Passer a 4 a changé la donne.

Même après l’upgrade infra, le frontend a 6 uploads parallèles reste moins performant que 4. Le navigateur n’est pas fait pour saturer la bande passante.

Huit sprints pour trouver un réglage simple

8 sprints d’amélioration upload pour arriver à une conclusion simple : “worker 4, frontend 4, VPS 8 CPU / 16 Go”. Mais le chemin pour y arriver a construit une compréhension profonde du système. Chaque sprint a été documenté, chaque décision est traçable. C’est du vrai engineering, pas du bricolage.

Décision importante : on arrête les benchmarks et on revient aux features client. L’upload fonctionne, c’est le moment de l’utiliser.

L’upload se fige, la photo revient au centre

Le pipeline upload est gèle et valide. On pivote vers l’expérience photo dans l’éditeur (insertion, recadrage, manipulation).
