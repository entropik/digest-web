Day 82 – Make the documentation less likely to be forgotten, then take a look at the finished product

Contrast between WooCommerce project actions, documentation made auditable, a polished publisher’s wordmark, and the Final Preview mode enabled to view the map without bleed.

This post was written on Friday 12 June 2026 whilst updating the repo’s documentation, and then continued during a night session at around 1.30 am. I’m clearly tired, but the session has resolved two important issues: the documentation is now less reliant on gut feeling, and the editor can finally display the finished document without bleed.

Brief conclusion

The session began by fixing a client-side detail in the WordPress plugin: project actions had been condensed, but the deletion prompt needed to remain sufficiently clear to prevent a dangerous action resulting from a misreading.

It then turned a recurring oversight into a workflow: a versioned documentation skill in the repo can now audit versions, HEAD, changelog, roadmap, guides and log before correcting the documentation.

The end of the night was spent on visual improvements: refining the branding in the editor header, then adding a proper ‘Final Preview’ mode. It’s a small button in Affichage, but it represents a real boost to customer confidence: users can view the card exactly as it will appear in their hands, without seeing the bleed area.

WordPress plugin: contrasting project actions

The commits a0ae6e3 and 239a5c0 build on yesterday’s work on the WooCommerce client projects area.

This is not merely an aesthetic issue. In a project list, Modifier, Dupliquer and Supprimer do not carry the same weight. Streamlining the interface must not make deletion too subtle or ambiguous.

The fix affects the plugin’s front-end CSS, the version header, readme.txt and the example manifest. This is in line with a rule in the repository: any change under wordpress-plugin/keredit-connector/ constitutes a plugin release, not a simple local tweak.

Documentation: no longer relying on memory

The commit 536ef3c introduces the actual method change.

The .codex-skills/doc skill already existed, but it was too general. It can now trigger a brief audit, then direct the agent to the correct files:

  • AGENTS.md for the repository status and working rules;
  • CHANGELOG.md for versioned milestones;
  • BIBLIOTHEQUE.md and docs/HOME.md for the repo map;
  • product documentation for the roadmap, beta and objectives;
  • recovery guides and commands;
  • the daily log when a significant day does not yet have an entry.

The script node .codex-skills/doc/scripts/audit-docs.mjs provides the facts before writing: branch, HEAD, versions of the four packages, any drift, latest commits, latest issue and cumulative timeline.

Why this is important

The problem wasn’t a lack of documentation. The repository has plenty of it. The problem was consistency: after a live fix, a version bump, a VPS deployment or a plugin tweak, it’s all too easy to forget the documentation part.

Skill is no substitute for judgement. It simply forces you to take the first useful step:

  • check the current facts;
  • see if any documentation is out of date;
  • make minor corrections;
  • state explicitly when no version bump, roadmap or changelog is required.

Night session: branding and final preview

The commits 6f3f3b1 and c2b42e0 tweak the KEREDIT wordmark in the editor. This isn’t a major product overhaul, but a finishing touch: the header must convey a sense of stability, not a cobbled-together look, especially as the interface begins to be shown outside the development environment.

The commit 5734f11 adds the ‘Final Preview’ mode to the Affichage menu.

Until now, the ‘Fond perdu’ button mainly controlled a visual cue. The canvas itself remained built across the full page, with bleed. The new mode changes the actual display area:

  • in edit mode, the area remains in ‘format + fond perdu’ view;
  • in final preview, the area becomes the finished size, with bleed=0;
  • the project coordinates remain relative to the trim size;
  • the preview is deliberately read-only: no selection, no handles, no grid, no rulers, no drag-and-drop, no inline text editing.

This approach avoids creating a second editing geometry. You do not modify the project JSON to view the finished product. You only change the rendering surface.

Closure decision

The key takeaway from this session is twofold.

If a task recurs frequently and is discipline-specific, it must be encoded in the repository.

If a client needs to understand what they are going to receive, you must be able to show them the finished product without the production marks.

The Krampouz documentation now has a concrete starting point. When the version, roadmap, changelog or log are at risk of drifting, the agent can launch an audit rather than relying on gut feeling.

And the postcard editor takes on a more human feel: less workshop, more finished product. At 1.30 am, that’s a good cut-off point.
