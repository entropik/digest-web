Jour 52 - Tarifs, tableurs et fatigue utile

Une journée plus courte mais structurante : QR mobile stabilise, Google Photos valide en live, garde-fou desktop, puis début du chantier prix avec grilles tarifaires et question ouverte sur les changements de carnet.

Horaires de session

  • Agent utilisé : Codex, transition depuis Claude Code
  • Branche de travail : dev
  • SHA de départ du jour : ed7a472 (feat: confirm customer project deletion)
  • Dernier SHA pousse avant clôture : 87e42f8 (fix: raise google photos import limit for testing)
  • Version applicative locale : 0.6.25
  • Version plugin WordPress connue du jour : 0.1.15
  • Commit de clôture prévu : 1 commit de synthèse prix / tarifs / documentation
  • Amplitude minimale observée : journée de code plus courte, avec fatigue encore présente
  • Objectif produit du jour : finir les imports photo live, puis ouvrir proprement le chantier prix sans fabriquer une usine a gaz Ce soir, pas de grande nuit de code. Et c’est plutôt une bonne nouvelle. Après les grosses avancées du week-end sur WooCommerce, l’auth, les projets clients et Google Photos, la journée avait besoin d’être moins spectaculaire et plus structurante. Un projet peut mourir d’une absence de features, mais il peut aussi mourir d’une accumulation de features qui ne savent plus se parler. Le sujet du jour, derrière les boutons et les imports, c’était donc celui-ci : comment garder Krampouz simple pour le client, alors que le métier de l’imprimeur est combinatoire par nature ?
  • Temps cumulé :253h+

Ce qui a avancé concrètement

La première partie de la journée a continue le fil commerce déjà ouvert.

Le flux WooCommerce est maintenant plus propre :

  • le client connecte peut lancer Creation depuis ooblik.com ;
  • l’éditeur s’ouvre dans le même onglet ;
  • les projets sont persistants et repris depuis le compte Woo ;
  • la proposition Reprendre un projet ? évite de créer des dizaines de projets vides ;
  • le plugin a récupéré son cycle d’update prive plus fiable ;
  • les sessions admin et client peuvent cohabiter dans le même navigateur sans se voler la place.

Ensuite, le chantier photo a franchi deux marches importantes.

Le QR mobile fonctionne comme un vrai pont de terrain : on scanne, on envoie des photos depuis le téléphone, les aperçus remontent dans l’éditeur sans recharger la page, et les barres de progression racontent quelque chose de compréhensible.

Google Photos a lui aussi passe le test live :

  • OAuth Google Cloud configure ;
  • popup Google ouverte hors iframe ;
  • Picker Google Photos disponible ;
  • images choisies explicitement ;
  • import dans le pipeline assets existant ;
  • limite montée a 100 photos pour test ;
  • videos ignorées en V1 ;
  • pas de promesse trompeuse sur le GPS, puisque Google et les navigateurs peuvent ne pas transmettre ces métadonnées.

Ce n’est pas encore un flux de production grand public, car Google affiche encore les avertissements d’application non vérifiée tant que la validation n’est pas faite. Mais pour une bêta contrôlée, le connecteur est vivant.

Enfin, un garde-fou simple a été ajouté : l’éditeur client n’est pas responsive en V1, donc il l’assume. Sur petit écran, il affiche un message clair Editeur disponible sur ordinateur avec un bouton Retour. C’est beaucoup plus sain que de laisser une interface complexe se casser visuellement.

Le chantier prix change de nature

La deuxième partie de la journée a ouvert le gros morceau : le prix.

La première intuition était de partir des fichiers Excel OOBLIK. C’est logique : l’atelier a déjà des grilles, des coûts, des formules, des habitudes. Mais après analyse, une direction plus forte est apparue :

Krampouz doit devenir le moteur prix maître. WooCommerce doit rester le canal boutique, panier et paiement.

Cela veut dire :

  • ne plus dupliquer les champs entre Woo, Advanced Product Fields et Krampouz ;
  • éviter de renseigner deux fois les formats/options ;
  • ne pas laisser le navigateur envoyer un prix libre au panier ;
  • conserver WooCommerce pour ce qu’il fait bien : client, commande, paiement, coupons, taxes, panier ;
  • faire calculer le devis par Krampouz, cote serveur, à partir du projet réel.

Le menu Tarifs a donc été lancé dans le backoffice.

Première version technique :

  • familles tarifaires globales ;
  • grilles versionnees ;
  • liaisons produits ;
  • simulateur ;
  • import/export.

Puis première correction d’usage immédiate : le mot “matrice” est trop nucleaire. Personne n’a envie de piloter une centrale pour vendre un carnet.

L’interface devient donc Grilles tarifaires.

Le stockage peut garder pricing_matrices en interne, mais l’humain doit manipuler une table proche Excel :

  • Format ;
  • Quantite min ;
  • Quantite max ;
  • Pages incluses ;
  • Prix base TTC ;
  • Prix page supp. ;
  • Mode page supp. ;
  • colonnes dynamiques comme Papier, Reliure, Coins ronds, Finition.

Une cellule vide signifie : règle générique. Une cellule remplie signifie : condition. Si plusieurs lignes correspondent, la plus spécifique doit gagner.

C’est moins impressionnant qu’un moteur abstrait, et c’est précisément l’objectif.

La vraie question : options ou variantes ?

La fatigue du soir sert parfois a poser les bonnes limites.

Il ne faut pas transformer chaque produit en silo :

  • Carnet classique ;
  • Carnet Singer ;
  • Carnet spirale ;
  • Carnet dos colle ;
  • Carte postale ;
  • Tirage photo.

Si ces surfaces deviennent hermetiques, le client sera bloqué dans un choix initial. Or, dans un éditeur web-to-print, un client change d’avis. Il commence un carnet classique, puis comprend qu’il veut un Singer. Il change de format. Il ajoute des pages. Il veut un papier différent.

L’idée forte pour la suite :

un client doit pouvoir changer de type de carnet comme il change de format, tant que le métier peut l’accepter.

Mais il faut le faire avec des alertes intelligentes.

Exemple très concret :

  • carnet classique : 60 pages possibles ;
  • carnet Singer : 44 pages max ;
  • le client a déjà construit 60 pages ;
  • il choisit finalement Singer.

Mauvaise solution : bloquer sans explication.

Encore pire : supprimer silencieusement 16 pages.

Bonne solution cible : autoriser l’intention, mais afficher une alerte claire :

Ce changement est possible, mais le carnet Singer accepte 44 pages maximum. Vous devez retirer 16 pages avant de valider ce choix.

Cela veut dire qu’il faudra probablement une couche de compatibilité produit, distincte du calcul prix pur :

  • ce format est compatible ;
  • cette reliure impose un nombre de pages ;
  • ce papier est indisponible avec cette finition ;
  • cette option ajoute un coût ;
  • ce changement demande une correction du projet ;
  • ce changement est impossible.

Le prix ne doit donc pas tout porter. Il calcule. Mais il ne doit pas devenir le juge unique de la validite produit.

La bonne architecture semble être :

  1. Catalogue produit : ce que l’on vend et comment l’éditeur se comporte.
  2. Grilles tarifaires : comment le prix se calcule.
  3. Compatibilités métier : ce qui est autorisé, averti ou refuse.
  4. Quote serveur : le prix final signe pour WooCommerce.
  5. WooCommerce : panier, paiement, commande.

Si on garde cette séparation, on évite à la fois les silos et l’usine a gaz.

Documentation ajustée

La spécification Pricing Matrix V1 a été recalée :

  • l’interface parle de Grilles tarifaires, pas de matrices ;
  • le JSON reste un détail technique serveur ;
  • l’édition normale passe par un tableur métier ;
  • l’import CSV cree une grille en brouillon ;
  • l’activation reste manuelle ;
  • une nouvelle section documente les changements de configuration produit.

La roadmap ajoute maintenant un point explicite :

éviter les silos de produits et préparer une couche de compatibilité pour les changements métier en cours d’édition.

C’est probablement l’un des sujets les plus importants avant le retour panier complet. Si le prix est mal pensé, tout le reste devient fragile : éditeur, panier, production, devis, support client.

Vérifications

Checks effectues sur le chantier tarifs :

  • pnpm --filter backend typecheck
  • pnpm --filter frontend typecheck
  • pnpm --filter backend test -- project-pricing
  • pnpm --filter backend lint
  • pnpm --filter frontend lint
  • pnpm build
  • git diff --check
  • pnpm dev:status
  • vérification locale de /api/admin/pricing/overview : réponse 401 non connecte, donc route montée et plus de 404.

Le build complet passe. Le seul avertissement notable reste le warning Vite habituel sur certains chunks lourds, déjà connu sur l’éditeur.

État final

État à la clôture :

  • QR mobile upload utilisable ;
  • Google Photos Picker V1 utilisable en bêta contrôlée ;
  • desktop-only guard en place ;
  • produits admin plus compacts ;
  • menu Tarifs en place ;
  • grilles tarifaires editees comme tableur ;
  • liaisons produit-tarif posées ;
  • simulateur serveur disponible ;
  • docs alignées ;
  • XLS prives proteges par .gitignore.

Ce n’est pas encore le moteur prix final. Mais c’est le bon début : assez concret pour tester, assez structure pour ne pas coincer le futur.

Et ce soir, c’est aussi un bon endroit pour fermer l’atelier. Fatigue présente, mais fatigue utile. Pas la fatigue d’un mur. Plutôt celle d’une journée ou l’on a posé les rails avant d’envoyer le train plus vite.

Rideau.
