Le fil de la journée

La journée a commencé comme une journée de correction bêta, mais elle a fini par toucher presque toute la chaîne :

OpenReplay / Grafana -> editeur -> JSON KEREDIT -> GOF -> PDF -> impression -> partage client

Le point important n’est pas seulement le nombre de commits. C’est la nature du travail : on a arrête de raisonner à partir d’une intention abstraite de produit, et on a recale plusieurs comportements sur des faits observés.

Les guides poses dans l’éditeur doivent être globaux. Le dos d’un zine pique métal ne doit pas être calcule comme un dos carré colle. GOF peut terminer un rendu alors que KEREDIT garde un statut stale si le suivi n’est pas rattache au bon job. Un PDF peut être validé dans GOF mais invalide cote KEREDIT si le projet source a changé après l’envoi. Et un partage public ne peut pas dépendre d’un artefact GOF si l’objectif est simplement de montrer le projet au client.

Cette journée a donc été moins une journée d’ajout linéaire qu’une journée de réalité.

Les guides deviennent vraiment globaux

Premier bug visible : les règles ou guides poses sur une page ne suivaient pas les autres pages. Pour un utilisateur, ce comportement est incompréhensible. Un guide sert justement de repère global de composition, pas de note locale perdue dans une page.

Le commit c7ba6cb corrige cette attente :

  • les guides passent dans la persistance projet comme structure globale ;
  • la sauvegarde/reprise conserve ces guides ;
  • l’éditeur les applique sur les pages au lieu de les limiter à la page active ;
  • les tests de persistance verrouillent le comportement.

C’est une petite correction UX, mais elle compte beaucoup pour les zines et carnets. Quand on cale des marges, des alignements ou une ligne de pli, on a besoin que le repère survive au changement de page.

Audit bêta : rendre les signaux exploitables

La session Grafana/OpenReplay des trois derniers jours a aussi joue son rôle. Elle n’a pas révélé un effondrement général. Le vrai signal exploitable était beaucoup plus précis : les erreurs 500 sur PUT /api/projects/:id.

Le point important, c’est qu’on a trie :

  • ce qui était du bruit de navigation ou d’interface ;
  • ce qui venait de vieux états de projet ;
  • ce qui indiquait une faiblesse de contrat backend ;
  • ce qui devait devenir actionnable dans les logs et la télémétrie.

Le commit f6f5944 va dans ce sens. Il ajoute des erreurs GOF serialisees proprement, enrichit la télémétrie frontend avec un contexte produit/session, rend certains échecs de sauvegarde plus lisibles, et transforme le backoffice bêta en outil de tri plutôt qu’en mur de signaux rouges.

Ce n’est pas spectaculaire, mais c’est exactement ce qu’une bêta doit produire : des signaux que l’on peut traiter, pas seulement des replays que l’on regarde en se demandant si tout va mal.

Le contrat Zine / GOF devient explicite

Le chantier central de la journée reste le Zine A5.

La comparaison Printbox, les exports GOF et les mesures sur objet réel ont force une clarification : KEREDIT doit rester l’autorité du contrat, et GOF ne doit pas redeviner la géométrie du livre. Le payload doit dire explicitement :

  • quelle est la surface de couverture a plat ;
  • quel est le dos technique ;
  • quelles sont les zones 4e de couverture, dos, 1re de couverture ;
  • quelles pages partent dans cover_pdf et dans cahier_pdf ;
  • quelle formule de dos a été utilisée.

Le commit 5ad1c5b ajoute les rôles de pages livre dans le payload GOF. Ce n’est pas un champ décoratif : il donne a GOF une lecture production claire. Une page n’est pas seulement page 0, page 1, page 2. Elle peut être couverture extérieure, 2e de couverture, cahier page 1, 3e de couverture, etc.

La première correction de formule, 2713443, s’est alignée sur les valeurs Printbox disponibles à ce moment-là :

base 2 mm + ((pages + couverture equivalente) / 2) * epaisseur papier

Pour un A5 24 pages en papier 0.150, cela donnait 3.95 mm et une couverture bleed/média proche de Printbox.

Mais l’atelier a ensuite donne une information plus forte que l’écran Printbox : la mesure physique.

La régression du dos a 2,4 mm

Après le premier deploy, l’éditeur affichait encore Dos 2,4 mm sur un zine 32 pages. Le calcul 2.4 = 32 / 2 * 0.15 trahissait l’ancienne logique.

Le problème n’était pas seulement un bundle stale. Le projet lui-même pouvait garder une ancienne surface.width_mm persistée dans pages_data. Et un onglet déjà ouvert pouvait continuer a reenregistrer cette ancienne surface.

Le commit 2f8e2b6 corrige ce piège :

  • normalisation de la surface couverture à la création, lecture, duplication et sauvegarde projet ;
  • prise en compte de workshop:reliures avant l’ancien binding libre ;
  • alignement de l’éditeur, des previews, du navigateur de pages et du payload export ;
  • prévention de la re-persistance d’une ancienne couverture 298.4 mm quand la formule courante donne autre chose.

Ce commit est une vraie correction de régression : la formule avait été corrigée, mais le système permettait encore à une ancienne surface de survivre et de revenir par autosave. La correction porte donc sur le cycle complet, pas seulement sur le calcul.

Mesure physique : le dos n’est pas un dos carré colle

Le vrai recalage est arrivé après impression et mesure.

Mesure atelier :

  • environ 2.80 mm pour le cahier + couverture sur le bord droit ;
  • environ 3.60 mm au pli, avec le renflement du cahier, de la couverture et des agrafes ;
  • usage réel vise : un dos technique autour de 3 mm, pas une zone texte fiable.

Cela change la doctrine. Pour un zine pique métal, on ne veut pas “vendre” un dos imprimable. On veut calculer correctement la largeur nécessaire à la couverture, tout en evitant que le client croit pouvoir composer un titre sur une tranche de 3 mm.

Le commit 111acb2 pose donc la nouvelle formule :

spine_width_mm =
  ((pages / 2) + cover_page_equivalent_count) * sheet_thickness_mm
  + saddle_stitch_fold_allowance_mm

Avec les valeurs par défaut :

cover_page_equivalent_count = 2
saddle_stitch_fold_allowance_mm = 0.3 pour pique metal / agrafe
base_spine_width_mm = 0

Pour le golden zine A5 32 pages, papier 0.15 :

((32 / 2) + 2) * 0.15 + 0.3 = 3.0 mm

La couverture trim devient donc :

148 + 3 + 148 = 299 mm

Et cote éditeur, on simplifie volontairement : le libellé n’affiche plus Dos 3 mm. Il affiche simplement Dos. Le calcul reste présent pour la fabrication ; la promesse client est retirée.

C’est une bonne correction produit. On ne trompe pas le client, mais on ne l’encourage pas non plus a faire une chose que l’objet ne permet pas vraiment.

KEREDIT et GOF se recollent sur les jobs

Un autre décalage est apparu dans GOF Flux : GOF disait OK, KEREDIT affichait encore PDF obsolete.

La cause était double :

  1. KEREDIT marquait trop tôt un job comme termine, parfois au moment ou GOF acceptait le dossier, pas quand GOF avait fini le rendu.
  2. Le bouton manuel Envoyer a GOF créait bien un job dans GOF, mais ne créait pas toujours une trace print_jobs exploitable par KEREDIT.

Le commit 16909af corrige ce suivi :

  • l’envoi manuel GOF cree maintenant un vrai print_job KEREDIT ;
  • le worker garde le statut processing tant que GOF n’a pas fini ;
  • la page GOF Flux relit l’état GOF via forge_job_id avant d’afficher le badge ;
  • l’obsolescence compare la date d’export du payload avec project.updated_at, pas seulement la date de fin GOF.

Le point subtil est important. Si le projet change après l’envoi a GOF, même si GOF termine ensuite, le PDF reste obsolète. Ce n’est pas KEREDIT qui est “en retard” ; c’est KEREDIT qui refuse de faire passer un PDF construit sur un ancien état comme PDF courant.

GOF a avancé de son cote dans le même sens. Les commits 04a5baa et 0f2d5ab ameliorent le suivi de progression et le routage des debordements de couverture. 5aa52b4 aligne les fixtures GOF sur les dimensions KEREDIT. La frontière reste la même que la veille : KEREDIT calcule et décrit, GOF forge et valide.

Le golden Zine devient un repère

GOF a aussi archive un golden A5 sur la commande 1075781.

Le commit cf00354 ajoute :

  • un dossier docs/golden-samples/1075781-zine-a5/ ;
  • les rapports render, prepress, print-validation et inspection PDF ;
  • des checksums ;
  • une documentation de baseline.

Ce golden est utile parce qu’il transforme une intuition en référence. Quand on parle de couverture, cahier, poids PDF, DPI, médias, zones et pages, on peut revenir à un dossier concret. Le billet d’hier parlait de l’optimisation massive du poids PDF ; aujourd’hui, ce golden devient une brique de non-régression.

Export livre : ownership des éléments de spread

Le commit c99afa1 corrige un autre point de rendu livre : certains éléments visuellement places sur une page voisine de spread pouvaient rester possedes par la mauvaise page au moment de l’export.

Ce genre de bug est discret dans l’éditeur, mais dangereux en production. Visuellement, l’utilisateur voit une double page. Contractuellement, GOF reçoit des pages séparées. Si un élément est complètement hors page mais reste rattache à la mauvaise page source, le rendu peut diverger.

La correction normalise cette propriété d’élément pour l’export. C’est un autre exemple de la règle du jour : ce que l’écran montre doit être traduit explicitement dans le contrat.

Partage public : de la forge au lecteur HTML

La fin de journée change de sujet, mais pas de logique : rendre le projet exploitable hors de l’éditeur.

Le commit a676e90 ajoute le partage public projet :

  • schéma Prisma project_shares ;
  • token public hashe et token propriétaire récupérable ;
  • routes publiques /api/project-shares/:token ;
  • routes projet pour créer/ouvrir un partage ;
  • intégration WooCommerce dans Mon compte > Projets ;
  • lecteur public /partage/:token/html ;
  • première logique d’artefacts web GOF.

Puis les commits suivants resserrent le flux :

  • d705692 expose l’action Partager dans les listes admin Commandes et Projets Clients ;
  • d4dd7a1 déclenche la génération web partagée avant d’ouvrir le lecteur public ;
  • ca801e4 bascule le lecteur vers un rendu HTML direct depuis les données KEREDIT, avec assets signes, pour ne pas dépendre des artefacts GOF quand l’objectif est simplement de montrer le projet ;
  • bd2ce46 stabilise les liens de partage existants : cliquer sur partager ne doit pas invalider un onglet déjà ouvert ;
  • c1df664 borne les pages partagées a pages_count, afin d’éviter des pages fantômes issues d’un historique pages_data trop long.

C’est un vrai nouveau pan produit. GOF reste la forge de production, mais le partage client n’a pas besoin d’attendre un PDF de production. KEREDIT peut rendre une lecture web du projet depuis sa propre source de vérité.

Cela donne une séparation saine :

Partager / relire / valider visuellement = KEREDIT HTML
Produire / preflight / imprimer          = GOF PDF

Régressions et corrections du jour

La journée contient plusieurs régressions ou quasi-régressions traitees :

  • Guides page-locales : corrige en guides globaux persistants.
  • Ancienne surface couverture : corrige par normalisation backend à la lecture/sauvegarde/duplication.
  • Calcul dos trop “livre colle” : corrige après mesure atelier vers une formule pique métal.
  • Affichage Dos X mm trompeur : corrige en libellé simple Dos.
  • GOF OK mais KEREDIT obsolète : corrige par suivi print_jobs et synchronisation forge_job_id.
  • GOF termine après modification projet : clarifie comme vrai cas stale, pas comme retard KEREDIT.
  • Élément de spread exporte depuis la mauvaise page : corrige dans le payload livre.
  • Partage public dependant de GOF : corrige vers rendu HTML KEREDIT.
  • Lien de partage instable : corrige, un lien actif est réutilisé.
  • Pages fantômes partagées : corrige par bornage a pages_count.

Ce n’est donc pas une journée “sans bug”. C’est une journée ou les bugs ont force les bonnes frontières.

Ce qui reste fragile

Le dos pique métal reste une estimation d’atelier, pas une promesse industrielle absolue. La mesure physique montre déjà que l’objet n’est pas uniforme : environ 2.80 mm sur le bord droit, environ 3.60 mm vers le pli. Le 3.0 mm est donc un compromis technique pour la couverture, pas une zone de composition fine.

Le partage public vient d’entrer dans le produit. Il faudra le tester sur des projets réels avec beaucoup d’assets, des pages en trop dans l’historique, des projets commandes, des projets non commandes et des liens ouverts avant/après régénération.

Le suivi GOF est plus propre, mais il faut continuer a distinguer trois dates :

date de modification projet
date d'envoi payload GOF
date de fin rendu GOF

Si la première passe après la seconde, le PDF doit rester obsolète, même si GOF finit correctement plus tard.

Suite logique

La suite courte :

  1. régénérer un Zine A5 32 pages avec la formule 3.0 mm ;
  2. vérifier dans GOF couverture, cahier, zones et validation ;
  3. imprimer et mesurer à nouveau la couverture a plat ;
  4. tester le partage HTML sur ce même projet ;
  5. vérifier que le lien reste stable quand on reclique Partager ;
  6. comparer le rendu partage HTML avec l’éditeur et avec le PDF GOF.

La journée a fait avancer le produit sur deux axes qui paraissent différents mais se rejoignent : la fabrication et la confiance. Il faut imprimer juste, mais aussi montrer juste.
