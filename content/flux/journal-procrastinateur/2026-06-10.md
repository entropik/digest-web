## Conclusion courte

La journée a commencé par une question de contrat : pourquoi l'éditeur KEREDIT, le JSON transmis, GOF et le PDF peuvent encore diverger alors que les champs semblent exister quelque part ?

Elle s'est terminée sur un autre contrat, plus métier : un template ne peut plus être pensé comme un seul layout que l'on étire entre formats. Un template devient une famille éditoriale, avec une variante par format, et le client peut passer de `10x15` à `10x10` sans perdre la photo déjà posée.

Entre les deux, la journée a aussi corrigé un point sécurité TLS, rendu le placeholder photo plus net, puis suivi plusieurs bugs live WordPress -> WooCommerce -> KEREDIT jusqu'à leur vrai endroit : non pas le plugin, mais la continuité entre variante template, projet créé, permissions client, changement de format et contenu client.

## Le matin : auditer le contrat JSON KEREDIT -> GOF

Le premier commit KEREDIT du jour, `298cde9`, pose un audit complet du contrat JSON KEREDIT -> GOF.

Ce travail part d'un constat pénible mais utile : deviner champ par champ ne suffit plus. Les blocs image, texte, clipart et shape doivent avoir une décision explicite :

- champ persisté et rendu ;
- champ volontairement ignoré ;
- champ non supporté mais reporté ;
- champ absent du payload et donc à corriger.

L'audit ajoute une documentation traçable dans `docs/audits/keredit-gof-json-contract-2026-06-10.md`, renforce les tests backend du payload d'export et vérifie que les champs importants survivent jusqu'à `KereditPdfForgePayloadV1.pages`.

Côté GOF, `4249b81` complète la même logique : le renderer sait mieux auditer les champs canvas KEREDIT et les fixtures des commandes sensibles `1075752` et `1075753` deviennent des garde-fous.

Le point de méthode est important : quand l'éditeur et le PDF ne correspondent pas, le problème doit être traité comme un bug de contrat, pas comme une retouche de rendu à l'aveugle.

## Sécurité : retirer le bypass TLS GOF

Le commit `8feb9ef` corrige un point de sécurité ciblé dans le client GOF côté KEREDIT.

Le helper de configuration GOF désactivait la validation TLS via `rejectUnauthorized: false`. Même si la configuration live actuelle passe par un GOF HTTP LAN, ce défaut était dangereux pour toute instance HTTPS future : bearer token GOF, catalogue Accurio et réponses persistées ne doivent pas transiter par un canal qui accepte silencieusement un certificat invalide.

La correction est volontairement petite :

- suppression du bypass TLS inconditionnel ;
- ajout d'un test empêchant sa réintroduction silencieuse ;
- maintien du comportement HTTP LAN actuel ;
- pas de nouveau flag de contournement global.

Le résultat est plus sain : si un GOF HTTPS à un mauvais certificat, il faudra réparer le certificat, pas affaiblir KEREDIT.

## Placeholder photo : première impression plus nette

Le commit `ea77ae1`, puis une partie de `ac5e85f`, traitent un détail très visible : le placeholder photo vide.

Avant correction, le pictogramme et le texte "Ajouter une photo" pouvaient donner une impression floue ou se désynchroniser du cadre pendant les manipulations. Ce n'est pas seulement esthétique : c'est la première surface que voit un client avant d'ajouter sa photo.

Le rendu placeholder reste maintenant vectoriel, non mis en cache en bitmap flou, et ses sous-éléments sont tagués pour suivre le cadre pendant resize et drag :

- fond du placeholder ;
- icône ;
- libellé ;
- bordure du bloc.

Le test `test:photo-placeholder` verrouille ce comportement. Le but est simple : avant même l'image client, le slot doit paraître propre.

## Le vrai chantier : les templates multi-formats

Le commit `3bbe914` fait basculer le modèle template.

L'ancien raisonnement implicite était trop pauvre : un template avait un `pages_data`, puis on adaptait ce layout à un autre format. Cela marche pour des cas simples, mais cela ne respecte pas le métier. Un `10x15`, un `10x10`, un `13x18` ou un `20x20` peuvent nécessiter des compositions différentes.

Le nouveau modèle introduit `TemplateFormatVariant` :

- `template_id` ;
- libellé et dimensions du format ;
- `pages_data` propre à ce format ;
- vignette éventuelle ;
- marqueur `is_default`.

`Template.pages_data` reste une compatibilité temporaire, mais les variantes deviennent la source nominale. Le builder sait charger la variante exacte, en créer une nouvelle par adaptation quand elle n'existe pas, puis sauvegarder seulement la variante du format courant.

La création de projet classique depuis template suit la même règle : variante exacte si disponible, sinon adaptation depuis la variante par défaut.

## WordPress -> WooCommerce -> KEREDIT : suivre la trace réelle

Les tests live ont ensuite montré que le front client n'était pas synchronisé avec les variantes pourtant enregistrées.

Le premier réflexe aurait pu être d'accuser le plugin WordPress. Les logs ont montré autre chose :

- WordPress envoyait bien `template_id`;
- il envoyait aussi le format demandé dans le contexte KEREDIT ;
- le backend créait un projet attaché au bon template ;
- mais certains chemins lisaient encore `Template.pages_data` ou adaptaient localement les pages.

Le commit `ac5e85f` corrige la création projet depuis lancement WooCommerce. `backend/src/services/woocommerce-service.ts` résout maintenant les pages de template via `TemplateFormatVariant`, exactement comme la route projet classique.

Le test d'intégration réel vérifie qu'un launch Woo avec template utilise la variante exacte, pas le vieux `pages_data` legacy.

## Le piège suivant : changer de format dans l'éditeur client

Une fois la création Woo corrigée, un autre écart est apparu dans l'éditeur.

Le projet était bien issu du template, mais le frontend ne conservait pas assez d'information pour savoir qu'un changement de format devait demander la variante exacte. Il faisait simplement :

```text
pages courantes -> adaptPagesToFormat(...)
```

Le commit `7469656` ajoute donc la mémoire minimale nécessaire : un projet issu d'un template garde son `sourceTemplateId` côté store éditeur. Quand le client change de format, `RightPanel` appelle l'API `/templates/:id` avec le format cible.

Si l'API répond `variant_source: "exact"`, l'éditeur applique cette variante. Sinon, il garde le fallback adaptatif existant.

Ce correctif a fermé le bug principal visible en live : le passage au format `10x10` charge enfin le layout `10x10` enregistré dans le builder, au lieu d'étirer le layout `10x15`.

## La question oubliée : garder la photo du client

La dernière découverte du jour est la plus métier.

Oui, le layout doit changer quand on passe de `10x15` à `10x10`. Mais si le client a déjà posé une photo dans le slot, cette photo ne doit pas disparaître. La variante cible doit remplacer la composition, pas remettre le projet à blanc.

Le commit `e041449` ajoute cette fusion :

- la variante cible fournit la géométrie, la position et les permissions du bloc ;
- le projet courant fournit le contenu client déjà posé ;
- pour un bloc photo de même `id`, KEREDIT conserve `assetId`, ratio original, crop, pan, zoom, rotation interne, flip et améliorations image ;
- pour un bloc texte de même `id`, KEREDIT conserve le contenu texte riche.

Le test `test:template-format-variant` vérifie explicitement ce cas : une variante `10x10` avec placeholder vide récupère la photo client posée en `10x15`, tout en gardant la géométrie `10x10`.

C'est probablement la règle produit la plus importante de la journée : les variantes portent le design, mais le projet porte le travail du client.

## La contradiction des permissions template

Après le déploiement multi-format, un bug très concret est apparu sur le produit `Carte postale`, thème `Postal` : en `10x15`, le bloc affichait bien "Ajouter une photo", mais le client ne pouvait pas y déposer de photo. En passant sur d'autres formats, le comportement semblait redevenir normal.

La cause n'était pas un problème de drag-and-drop, ni un problème WooCommerce. Le template portait deux messages contradictoires :

- le bloc image était un placeholder vide, éditable et non verrouillé ;
- les permissions globales du template interdisaient `canReplaceAsset`.

Le front respectait donc la permission globale et refusait silencieusement le remplacement, alors que l'interface promettait un slot photo utilisable.

Les commits `0052ab0` et `afcd1d3` ferment ce piège. Côté backend, un projet dérivé d'un template ne peut plus sortir avec un bloc photo vide éditable mais non remplaçable. La règle est appliquée à la création projet classique, à la création depuis lancement WooCommerce, puis à la sauvegarde projet pour éviter qu'un onglet déjà ouvert réintroduise l'ancien état via autosave.

La donnée live a aussi été réparée pour `tpl_postcard_postal` : le template est revenu à des permissions client cohérentes, et le brouillon touché a récupéré `canReplaceAsset: true` sans rouvrir les autres actions.

## Remplacer une photo doit être un geste naturel

Dernier ajustement UX de la journée : une fois qu'un bloc image contient déjà une photo, le client doit pouvoir la remplacer sans supprimer le bloc, sans recréer un layout et sans perdre le cadre.

Le commit `4efe897` ajoute ce comportement :

- drop d'une photo sur un bloc vide : remplissage immédiat ;
- drop d'une photo sur un bloc déjà rempli : confirmation "Remplacer la photo ?" ;
- clic sur une photo avec un bloc image rempli sélectionné : même confirmation ;
- même photo que celle déjà présente : aucune action ;
- bloc non remplaçable : aucune action silencieuse, pas d'ajout ailleurs.

Après confirmation, KEREDIT conserve la géométrie du bloc : position, taille, rotation, permissions, masque et cadre décoratif. En revanche, la nouvelle photo repart proprement en `cover`, avec crop, pan, zoom, rotation interne et améliorations image remis à zéro. C'est le bon compromis pour un service client : le bloc reste le contenant éditorial, la photo remplacée repart d'un état lisible.

## Décision de clôture

La journée renforce une ligne de produit importante : KEREDIT ne peut pas être seulement un éditeur qui adapte des rectangles. Il doit préserver une intention métier.

Pour les templates multi-formats, cette intention est maintenant plus claire :

- l'atelier peut préparer une composition par format ;
- le client peut changer de format dans le même produit ;
- le projet récupère la variante exacte quand elle existe ;
- le contenu déjà posé par le client survit au changement.

Ce n'est pas un détail de confort. C'est ce qui rend le changement de format acceptable commercialement : le client explore un autre format sans avoir l'impression que KEREDIT lui retire son travail.

Point de vigilance pour la suite : cette logique doit rester valable au-delà du bloc photo simple. Les textes riches, cliparts recolorisés, cadres et masques devront suivre la même philosophie : variante pour le layout, projet pour le contenu client.

Autre vigilance : chaque permission template doit être pensée comme une promesse d'interface. Si l'écran dit "Ajouter une photo", le contrat projet doit rendre cette action possible. Sinon, le client voit un bug, même si techniquement le code "respecte" une permission.
