Jour 78 - Verrouiller la bêta avant d'élargir

Reconnexion éditeur, durcissement sécurité WooCommerce, audit bêta publique et verrouillage strict du contrat texte PDF entre KEREDIT et GOF.

Horaires de session

  • Agent utilisé : Codex
  • Date : lundi 8 juin 2026.
  • Environnements : Krampouz/KEREDIT dans dépôt local krampouz, GOF dans dépôt local gof, VPS KEREDIT.
  • Branche KEREDIT : dev.
  • SHA KEREDIT de fin de journée : 6eeb30a.
  • Version KEREDIT de fin de journée : 0.6.78.
  • SHA GOF observé en fin de journée : 6c9ffd7.
  • Amplitude commits KEREDIT : 08:59 -> 17:49.
  • Amplitude commits GOF : 10:36 -> 18:15.
  • Temps cumulé :427h14+.

Conclusion courte

Le 8 juin était la date repère de la bêta clients amis. La journée n’a pas consisté à ouvrir largement. Elle a plutôt resserré les verrous : accès éditeur plus récupérable, splash durci, webhook WooCommerce protégé, audit sécurité écrit, et surtout contrat texte PDF rendu beaucoup plus strict entre KEREDIT et GOF.

La conclusion pratique est prudente : la bêta peut avancer, mais pas en laissant des zones grises dans les flux de commande, les webhooks ou les PDF.

L’entrée éditeur doit permettre de se reconnecter

Le matin commence avec 2b719d8 : l’écran de lancement de l’éditeur doit permettre de se reconnecter. Ce point vient d’un cas très réel : un client peut arriver depuis WooCommerce, avoir une session expirée, ou croiser un état intermédiaire pendant le lancement.

L’ancien comportement pouvait laisser l’utilisateur face à un splash qui attend, sans action claire. Le correctif ajoute une sortie plus propre :

  • le splash distingue mieux attente, erreur et reconnexion ;
  • ProtectedRoute et le bootstrap applicatif coopèrent mieux ;
  • le wording évite de parler de détails techniques inutiles ;
  • les versions packages sont alignées pour le déploiement.

Commit de référence : 2b719d8 (fix: allow reconnect from editor launch splash).

Splash : durcir la récupération, pas seulement l’apparence

Le commit f99b27e continue ce sujet avec un durcissement plus large de la récupération. L’application reçoit une vraie RouteErrorBoundary, le bootstrap devient plus explicite, et le store de lancement garde mieux l’état nécessaire pour sortir des erreurs.

C’est une correction de confiance : une bêta ne peut pas demander à un client de comprendre si un écran bloqué vient d’une session, d’un chunk frontend, d’une route, ou d’un lancement Woo. Elle doit proposer une action simple : recharger, se reconnecter, reprendre.

Sécurité : le webhook WooCommerce ne doit pas être public

Le commit 48f5f1d est le verrou sécurité le plus visible du jour : le webhook WooCommerce exige maintenant une clé. Ce n’est pas un détail. Une route webhook qui accepte des événements de commande doit être authentifiée, même en bêta fermée.

Le correctif :

  • retire la résolution implicite dangereuse côté credentials ;
  • impose une clé webhook côté route ;
  • ajoute des tests d’intégration ;
  • documente le comportement dans le guide plugin ;
  • écrit l’audit docs/audits/2026-06-08-audit-securite-beta-publique.md.

Le message produit est simple : on peut tester avec peu de clients, mais les surfaces publiques ne doivent pas rester ouvertes par confort.

Commit de référence : 48f5f1d (fix(security): require WooCommerce webhook key).

Texte PDF : le contrat devient strict

La plus grosse masse technique du jour est encore le texte. Le 7 juin a posé le contrat ; le 8 juin le rend plus strict.

KEREDIT ajoute d’abord c23432a, une documentation plus nette du contrat texte KEREDIT-GOF. Puis d4616fb verrouille ce contrat côté backend :

  • validation des pages plus stricte ;
  • diagnostics des champs texte ;
  • payload d’export enrichi ;
  • schéma projet JSON mis à jour ;
  • tests sur le validateur et le payload.

Ensuite aa22062 émet un contrat de layout texte strict dans l’export PDF. shared/src/utils/richText.ts porte plus clairement la normalisation, et les tests rich text couvrent les cas qui ne doivent plus dépendre d’interprétations locales.

Enfin 6eeb30a déclare explicitement la politique de synthèse de police PDF. C’est un point fin mais important : si le système synthétise de l’italique ou du gras faute de variante exacte, cela doit être une décision visible dans le contrat, pas un comportement caché du moteur de rendu.

Commits de référence :

  • c23432a (docs: verrouiller le contrat texte KEREDIT GOF) ;
  • d4616fb (fix(pdf): verrouille le contrat texte GOF) ;
  • aa22062 (fix: emit strict PDF text layout contract) ;
  • 6eeb30a (fix: declare PDF font synthesis policy).

GOF : du glyph au garde-fou de régression

GOF avance au même rythme :

  • b0b16ca corrige le rendu déterministe des ligatures ;
  • ebfdfcc corrige le shaping texte au niveau glyph ;
  • 0df3422 ajoute des diagnostics de contrat texte ;
  • 526e221 affiche le guide de fond perdu dans la preview PDF ;
  • f6688c3 et dd778fc ajoutent le téléchargement PDF et des noms de fichiers liés aux commandes ;
  • f9e49c1 applique le contrat de layout texte KEREDIT ;
  • c98d3f4 synthétise l’italique pour les variantes exactes ;
  • 2de371b respecte le line-height compact du rich text ;
  • 4d9d48b inclut la version renderer dans la réutilisation de job ;
  • 6c9ffd7 documente les garde-fous de régression PDF.

Ce n’est plus seulement “faire un PDF”. C’est rendre le PDF inspectable, téléchargeable, versionné, et suffisamment déterministe pour que la comparaison écran/production devienne possible.

La bêta du 8 juin devient une ouverture contrôlée

La mémoire produit disait déjà que le 8 juin devait rester une vague clients amis, pas une ouverture large. Le travail du jour confirme cette ligne.

Ce qui a été renforcé :

  • lancement éditeur plus récupérable ;
  • webhook WooCommerce protégé ;
  • audit sécurité bêta écrit ;
  • contrat texte PDF documenté et testé ;
  • GOF mieux armé pour diagnostiquer les écarts de rendu ;
  • version KEREDIT avancée en 0.6.78.

Ce qui n’est pas encore un feu vert large :

  • chaque chemin Woo -> éditeur -> panier doit rester testé avec un vrai contexte produit ;
  • les projets ouverts hors fiche produit peuvent exister, mais ne doivent pas être confondus avec des projets commandables ;
  • les PDF doivent continuer à être comparés sur des cas texte réalistes ;
  • les messages client doivent rester compréhensibles sans vocabulaire technique.

Ce qui est solide ce soir

  • KEREDIT termine la journée à 6eeb30a, version 0.6.78.
  • Le webhook WooCommerce est protégé par clé.
  • L’audit sécurité bêta publique du 8 juin est documenté.
  • Le splash de lancement éditeur propose des sorties plus propres.
  • Le contrat texte PDF est plus strict, documenté et partagé.
  • GOF ajoute diagnostics, preview fond perdu, téléchargements PDF et garde-fous de régression.

Ce qui reste à surveiller

Le danger n’est plus seulement le bug évident. Il est dans les états intermédiaires : session expirée, projet repris depuis “Mes projets”, fichier PDF réutilisé alors que le renderer a changé, police exacte absente, webhook mal configuré. La journée a réduit ces zones grises, mais elle montre aussi que la bêta doit rester accompagnée.

Le bon cap reste : peu de clients, de vrais parcours, et une vérification attentive des transitions entre WooCommerce, KEREDIT, GOF et l’atelier.
