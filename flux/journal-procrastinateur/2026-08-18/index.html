Jour 130 - Sauver avant de sortir, choisir avant de migrer

Jour 130 du journal : l'éditeur durcit sauvegarde, checkout et responsive pendant qu'un audit remet en cause la migration instinctive de R2 vers Hetzner.

Horaires de session

  • Agent utilisé : Codex, avec le workflow de critique et durcissement Impeccable pour l’éditeur
  • Environnement principal : Mac, plusieurs worktrees KEREDIT, GitHub Actions et recherche fournisseur
  • Date couverte : mardi 18 août 2026
  • Branches principales : codex/impeccable-editor-hardening fusionnée dans dev par la PR #443 ; audit stockage conservé non commité dans codex/vrifier-ltat-de-la-branche
  • Fenêtre retenue pour le minimum : 17:44 → 19:00 CEST, de la création de l’analyse stockage au snapshot du worktree
  • Temps minimal observé : environ 1h16+
  • Version livrée : 0.22.4, merge PR #443 f2b46361
  • Traces principales : analyse stockage créée à 17:44, sept commits de durcissement, CI et journey vertes, revue Codex finale sans problème majeur, snapshot a276f248
  • Temps cumulé :842h53+ (841h37+ au 15 août, + 1h16+ ce jour)

Lecture courte

Deux formes de confiance sont travaillées dans la même fenêtre. Dans l’éditeur, KEREDIT doit savoir avec certitude qu’un projet est sauvé avant de laisser l’utilisateur sortir ou commander. Dans l’infrastructure, une envie de quitter Cloudflare R2 ne doit pas devenir une migration vers le premier fournisseur européen venu.

Le premier lot est livré en 0.22.4. Le second reste une analyse locale, encore non commitée. Les deux appliquent pourtant la même règle : ne pas confondre une interface rassurante avec une garantie prouvée.

La sauvegarde devient une frontière

L’éditeur bloque désormais la sortie et la commande tant qu’une sauvegarde stricte n’est pas confirmée. Les conflits de version restent différents des erreurs transitoires : les premiers exigent une décision, les secondes doivent pouvoir être remises en file et retentées.

Le checkout explique mieux pourquoi il est indisponible. Les statuts de sauvegarde, le clavier et les états ARIA sont alignés. À largeur intermédiaire, l’éditeur, le Template Builder et son test client ne laissent plus deux panneaux latéraux se disputer l’espace ; la coque large conserve son comportement.

La PR #443 est courte dans le temps mais dense dans les retours. Plusieurs revues sont demandées sur des HEAD successifs pour corriger le contrôle de sécurité CI, la couverture responsive, la cohérence des panneaux et la remise en file de l’autosave. La CI et le parcours journey passent, puis la revue finale ne trouve plus de problème majeur. Le merge arrive à 18h47.

Sortir de R2 sans sauter dans une autre panne

L’audit stockage part d’un constat encourageant : KEREDIT est déjà largement S3-compatible. Les objets sont référencés par clé, les URLs sont signées à la volée et le backend masque le fournisseur. La migration peut donc rester une bascule de configuration et de données.

La recherche retire toutefois Hetzner du hot path. L’Object Storage traverse une dégradation de capacité longue, sans SLA adapte à un flux d’upload synchrone. OVH 1-AZ et Scaleway montrent eux aussi des incidents récents. L’analyse fait émerger OVH Standard 3-AZ Paris comme candidat principal et IONOS Francfort comme alternative à tester, mais aucune décision de migration n’est encore exécutée.

Le vrai résultat du jour n’est pas un logo de fournisseur. C’est la nécessité de retries avec backoff, d’un suivi propre des erreurs 5xx et d’une copie chez un second acteur. Changer de bucket sans ces protections ne ferait que déplacer la fragilité.

Le rythme se fissure

Le journal est déjà interrompu depuis dix jours. Pourtant le code continue à avancer par lots denses, avec des revues répétées et une nouvelle décision d’infrastructure a porter. Le contraste devient difficile : les preuves techniques s’accumulent, mais la sensation de progrès ne suit plus. Ce jour ne porte pas encore les mots les plus francs sur l’épuisement ; il en montre les conditions.
