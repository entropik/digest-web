Jour 65 - Remettre l'architecture sur des rails

Une journée de reprise après le chaos des branches croisées : tests backend stabilises, audit Service/Controller, Graphify à jour, puis début du vrai découpage P1 de admin/pricing.ts.

Horaires de session

  • Agent utilisé : Codex
  • Date : dimanche 24 mai 2026
  • Branche de reprise : dev
  • Branche de clôture chantier : refactor/admin-pricing-workshop-attributes
  • Version repo : 0.6.29
  • Commits de stabilisation visibles avant le chantier P1 :
    • 62399b4 - docs: audit backend service controller architecture
    • 72e099c - test: fix backend Redis teardown warning
    • fc314b0 - refactor: extract pricing attributes and beta bug triage
  • Amplitude observée par les commits : 09:29 -> 21:35, soit 12 h 06 minimum
  • État de clôture attendu : branche de refactor poussée, reprise demain sur le même chantier P1 La journée d’hier avait laisse une odeur de fumee. Pas seulement parce que le code avait souffert. Aussi parce que les conditions humaines étaient mauvaises : l’accident de voiture, la fatigue, les branches croisées, Codex et Gemini CLI sur le même dépôt, puis cette impression très desagreable de ne plus savoir si le code courant était une base solide ou un montage de secours. Aujourd’hui, l’objectif n’était donc pas d’ajouter une grande fonction. C’était de reprendre le contrôle. Reprendre le contrôle, dans un projet comme KEREDIT, ce n’est pas faire semblant que tout va bien. C’est vérifier, nommer les zones douteuses, remettre les tests au vert, puis avancer par decoupes courtes.
  • Temps cumulé :339h36+

Le warning qui disait vrai

La première vraie correction du jour a été le MaxListenersExceededWarning pendant test:backend.

Il était non bloquant, puisque la suite passait. Mais ce genre de signal ne doit pas rester indéfiniment dans le bruit de fond. Il finit toujours par cacher une vraie fuite ou par habituer l’œil a ignorer les alertes.

La cause a été isolée : les tests fermaient plusieurs fois le singleton Redis via ioredis.quit(). à chaque tentative de fermeture sur une socket déjà dans un état fragile, ioredis ajoutait des listeners close, jusqu’au warning Node.

La correction a été simple et propre :

  • lancer la suite backend en NODE_ENV=test ;
  • désactiver le logger Fastify en test ;
  • centraliser la fermeture Prisma/Redis dans un helper de teardown idempotent ;
  • fermer Redis une seule fois par process avec redis.disconnect().

Résultat : pnpm test:backend est repasse au vert avec 75 tests, sans warning.

C’est une petite victoire d’hygiène. Pas spectaculaire, mais importante : un test vert doit être silencieux quand il n’a rien a dire.

L’audit Service/Controller

Le deuxième bloc a été l’audit d’architecture backend.

La question n’était pas : “est-ce qu’on jette le refactor d’hier ?”

La bonne question était : “est-ce que l’idée Service/Controller est saine, et quelles surfaces ne la respectent pas encore ?”

La réponse est claire : l’idée est saine et doit être conservée.

Le modèle cible reste :

  • routes/controllers : validation HTTP, orchestration, status codes, réponse ;
  • services : logique métier, Prisma, effets de bord, décisions d’atelier ;
  • libs : calculs purs, parsing, transformations sans runtime lourd ;
  • shared : types, constantes et contrats partageables.

L’audit a confirme que les workers avaient été remis dans un bon état : contrats de queues importables sans Redis, processeurs purs testables sans BullMQ, workers runtime separes.

Il a aussi confirme les vrais P1 :

  • admin/pricing.ts, encore énorme ;
  • asset-service.ts, encore mélange entre helpers purs et dépendances queues ;
  • WooCommerce, encore trop route-métier ;
  • print-jobs.ts, encore trop couple à la queue PDF.

Mais aucun P0.

C’était important. Après une journée de chaos, on peut être tente de tout rollback par peur. L’audit a permis de ne pas confondre “refactor incomplet” et “refactor a jeter”.

Et sans surprise, admin/pricing.ts ressortait comme un gros point de dette.

Comprendre le piège de admin/pricing.ts

Au début, j’ai failli prendre le bloc papier comme premier sous-domaine a extraire : papiers, fournisseurs, offres, paliers, options papier produit.

Techniquement, c’était défendable. Mais Marc a corrigé le tir : le futur client ne doit pas être enferme dans des concepts figes comme “papier” ou “fournisseur”. Il doit pouvoir créer ses propres bases de données d’atelier et ses propres attributs.

C’est une remarque structurante.

Dans le code actuel, deux mondes cohabitent :

  • le monde générique futur : WorkshopLibraryDatabase, WorkshopLibraryCategory, WorkshopLibraryAttribute, ProductWorkshopAttribute ;
  • le monde papier specialise : PaperReference, PaperSupplier, PaperOffer, PaperPriceTier, ProductPaperOption.

Le premier doit être le socle.

Le second reste utile, surtout pour le tirage d’art et le catalogue papier, mais il ne doit pas devenir la metaphysique du pricing KEREDIT.

Cette distinction a changé le plan.

Premier sous-lot P1 : les attributs atelier generiques

Le premier vrai découpage P1 a donc vise le socle client-configurable :

  • bases de données atelier ;
  • catégories ;
  • attributs ;
  • liaison d’attributs aux produits.

Le travail a créé :

  • backend/src/services/admin-pricing-workshop-service.ts
  • backend/src/routes/admin/pricing/workshop-attributes.ts
  • backend/src/services/admin-pricing-workshop-service.test.ts

Les URLs publiques n’ont pas changé. Le frontend continue d’appeler /api/admin/pricing/....

Mais la responsabilité a changé :

  • la route parse, orchestre et répond ;
  • le service porte Prisma, les règles de tenant, les erreurs métier et la serialisation ;
  • admin/pricing.ts n’a plus a contenir ce morceau entier du monde.

Les tests couvrent les points importants :

  • création de bases et attributs libres ;
  • isolation tenant ;
  • validation stricte des defaults pour la base reservee formats ;
  • un seul attribut par défaut actif par base pour un produit ;
  • archivage des attributs retirés d’un produit.

Ce point est central pour demain : le futur configurable de KEREDIT est la, dans ce socle générique, pas dans un catalogue papier code en dur.

Deuxième sous-lot P1 : le papier comme spécialisation

Une fois le socle générique sorti, le bloc papier pouvait être extrait sans confusion conceptuelle.

Le papier n’est pas le modèle universel. C’est une spécialisation utile.

Le deuxième sous-lot a donc cree :

  • backend/src/services/admin-pricing-paper-service.ts
  • backend/src/routes/admin/pricing/papers.ts
  • backend/src/services/admin-pricing-paper-service.test.ts

Ce service porte :

  • les papiers ;
  • les fournisseurs ;
  • les offres ;
  • les paliers tarifaires ;
  • les options papier rattachées à un produit.

Les règles existantes ont été conservées :

  • suppression physique quand l’objet n’est pas lié ;
  • archivage quand un papier ou fournisseur est déjà référence ;
  • rejet des références hors tenant ;
  • remplacement des options papier produit avec archivage des entrées retirées.

La encore, les URLs ne changent pas. On nettoie l’intérieur sans casser le contrat visible.

Le chiffre qui rassure

Au début de l’audit, admin/pricing.ts faisait environ 2598 lignes et 128 accès prisma.*.

Après le premier sous-lot, il est tombe a 1831 lignes et 93 accès Prisma.

Après le deuxième sous-lot, il tombe a 1265 lignes et 54 accès Prisma.

Ce n’est pas encore parfait. Mais ce n’est plus le même animal.

Surtout, le mouvement est bon : on ne fait pas des micro-patchs qui ajoutent de la rustine dans le fichier geant. On sort des domaines cohérents, un par un, avec tests, sans changer les routes publiques.

Les vérifications

Les vérifications du jour ont été larges :

  • pnpm typecheck : OK ;
  • pnpm lint : OK ;
  • pnpm test:backend : OK, 81 tests ;
  • pnpm build : OK ;
  • pnpm exec knip : OK, seulement les hints de configuration connus ;
  • git diff --check : OK.

Le build frontend garde ses warnings Vite habituels sur de gros chunks. Ce n’est pas un nouveau problème du chantier pricing.

Ce qui reste pour demain

Le chantier P1 n’est pas fini.

admin/pricing.ts porte encore :

  • processus MISKISS ;
  • recettes MISKISS ;
  • overview pricing ;
  • livres et matrices tarifaires ;
  • activation/duplication de matrices ;
  • bindings produit ;
  • simulateur quote ;
  • import/export.

Le prochain lot logique est probablement matrices/import/export, parce qu’il est proche de pricing-import.ts et du contrat PricingMatrixV1.

Mais il faudra rester discipline :

  • un seul sous-domaine ;
  • pas de changement d’URL ;
  • service d’abord ;
  • route mince ;
  • tests ciblant les règles existantes ;
  • vérification complète avant commit.

État d’esprit

Aujourd’hui n’a pas été une journée brillante. Elle a été une journée de remise en ligne.

Après hier, c’était nécessaire.

Il y avait encore la fatigue, encore cette sensation d’avoir trop ouvert le ventre du code, encore le doute sur ce qu’il fallait conserver ou non. Mais la méthode est revenue : lire, auditer, mesurer, extraire petit, tester, documenter.

C’est probablement ça, la bonne leçon du week-end.

Ne pas confondre vitesse et reprise de contrôle.

Ne pas confondre refactorisation et architecture.

Ne pas confondre un gros patch avec une avancée durable.

Demain, on reprend le même fil : continuer P1 sur admin/pricing.ts, sans rouvrir toute la maison.
