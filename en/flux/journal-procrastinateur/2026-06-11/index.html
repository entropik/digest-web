Jour 81 - Observer la bêta avant de l'élargir

Nettoyage VPS, observabilité bêta, ouverture 0.7.0, correction OpenReplay et polissage de l'espace projets client WooCommerce.

Billet reconstruit le vendredi 12 juin 2026 depuis l’historique Git et les documents du repo. L’état de fin de journée correspond a KEREDIT 0.7.3 en local, avec plusieurs jalons intermédiaires 0.6.103, 0.7.0 et 0.7.2.

Horaires de session

  • Agent utilisé : Codex
  • Environnement principal : VS Code WSL, plugin Codex à gauche, code au centre, terminal Codex à droite
  • Date : jeudi 11 juin 2026
  • Branche de travail : dev
  • Versions traversées : 0.6.103 -> 0.7.0 -> 0.7.2 -> 0.7.3
  • Amplitude commits observée : 08:18 -> 23:52
  • Temps minimal observé : 15h34+
  • Commits principaux : 39c1e46, 88f677a, c1887d1, 8c554bb, b59acdb
  • Temps cumulé :461h28+

Conclusion courte

La journée a transformé la bêta en système plus observable et plus exploitable. Le matin a servi a traiter l’exploitation : pression disque du VPS, rétention Docker et stack d’observabilité. Le soir a fermé un autre sujet critique : rendre l’ouverture bêta lisible, corriger OpenReplay avec la bonne version de tracker, puis rendre l’espace projets client WooCommerce plus compact.

Le fil commun est simple : avant d’élargir la bêta, KEREDIT doit mieux montrer ce qui se passe, et le client doit retrouver ses projets sans lire une interface d’atelier.

VPS et rétention Docker

Le commit 5e899e9 formalise le nettoyage post-déploiement des artefacts Docker. Ce n’est pas un changement produit, mais il répond à un risque très concret : une stack qui fonctionne peut quand même devenir fragile si images, layers et cache BuildKit saturent le disque.

Le bon choix a été de placer la rétention après un déploiement réussi, comme passe de ménage best-effort, sans toucher aux volumes ni aux données métier. La documentation garde aussi la distinction entre le chemin nominal GHCR et le fallback local.

Observabilité bêta

La première grosse phase technique est l’observabilité.

Les commits de la branche feature/observabilite-beta, mergés par 5b80bd5, ajoutent ou stabilisent :

  • VictoriaMetrics, VictoriaLogs et Grafana côté [serveur de production] ;
  • node-exporter, cAdvisor, postgres-exporter, redis-exporter, vmagent et Vector cote VPS KEREDIT ;
  • logs Docker envoyés vers VictoriaLogs ;
  • métriques backend, worker et files BullMQ ;
  • premiers événements produit frontend pour suivre launch, autosave, upload, checkout et erreurs.

Le commit 39c1e46 marque cette phase en 0.6.103.

Deux corrections d’exploitation suivent rapidement : 96f3f3f et db5bb3c assurent que la collecte démarre au déploiement et que le champ message des logs Pino est bien mappe vers VictoriaLogs. 44d5366 puis 6bb4b10 documentent aussi la réalité SMTP Hetzner : il faut passer par le port 587, pas par les ports sortants bloques.

Ouverture bêta 0.7.0

Le commit 88f677a fait passer KEREDIT en 0.7.0.

Ce n’est pas une bascule marketing large. C’est une marque claire : la bêta amis peut commencer, avec un périmètre contrôle, le postcard prioritaire et un support atelier encore très présent.

Le point important est de ne pas confondre 0.7.0 avec une stabilité générale. La version dit plutôt : le produit est assez cohérent pour commencer a exposer le flux a des clients proches et apprendre des retours réels.

Catalogue client et options cachées

Les commits 916f523, cd2b79e, 2760f2a et 0aa224a renforcent l’espace client :

  • les assets décoratifs deviennent visibles cote client quand ils doivent l’être ;
  • les catalogues client restent disponibles même si une file de backfill échoue ;
  • les options techniques Accurio ne polluent plus le récapitulatif client ;
  • la liste des projets client gagne en lisibilité.

Ce sont des changements petits, mais ils réduisent un risque bêta classique : laisser voir aux clients des concepts internes alors que l’atelier devrait absorber cette complexité.

OpenReplay : corriger la compatibilité réelle

La soirée a aussi montré une limite de l’observabilité : brancher un outil ne suffit pas si la matrice de compatibilité est fausse.

Les commits 441352e, 116300d, le merge b79687c, puis la release c1887d1 corrigent le tracker OpenReplay. Le backend self-hosted v1.23 n’acceptait pas le tracker 18 : les sessions semblaient démarrer mais les batches echouaient silencieusement. La correction revient donc à la ligne compatible ~17.2.11 et documente cette contrainte dans le changelog.

Le résultat attendu est beaucoup plus utile pour la bêta : si un client se bloque, l’atelier doit pouvoir comprendre le parcours au lieu de deviner.

Projets client WooCommerce

La fin de journée revient à l’interface visible du client.

Le commit 8c554bb compacte les actions et les vignettes dans les listes de projets, puis b59acdb applique le même mouvement cote plugin WordPress. L’objectif est de garder les actions fortes visibles sans transformer chaque ligne projet en fiche technique.

Les boutons Modifier, Dupliquer et Supprimer restent au premier plan. Les détails projet, les options et les informations techniques restent disponibles, mais moins envahissants.

Vérification et limites

Les commits du jour indiquent surtout des validations ciblées par domaine : CI, releases, changelog, corrections d’interface et publication plugin. Le journal reconstruit ne prétend pas remplacer les traces de CI ni les checks GitHub du moment.

Le point a surveiller après cette journée est la cohérence entre trois surfaces :

  • l’espace projets client dans KEREDIT ;
  • l’espace projets client dans WooCommerce ;
  • le plugin WordPress publie via son manifest prive.

Une amélioration visuelle cote repo ne vaut que si le plugin publie et l’installation WordPress live voient bien la même version.

Décision de clôture

Le 11 juin donne une direction saine : ne pas élargir la bêta sans instrumentation, et ne pas exposer aux clients les coutures techniques de l’atelier.

KEREDIT devient plus observable, plus prudent sur ses releases, et plus sobre dans son interface client. C’est exactement le type de consolidation qui rend une bêta utile : moins de bruit, plus de traces, et une surface client plus compréhensible.
