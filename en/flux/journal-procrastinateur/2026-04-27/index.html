Jour 41 — Rendre les blocs texte lies testables avant la bêta

La journée a été consacrée au chantier le plus sensible avant la bêta du 3 mai : les blocs texte lies. Le travail a alterne corrections, tests utilisateur, régressions assumees et verrouillage e2e pour stabiliser le flux texte sans casser l'édition locale.

Point de départ du jour

La journée a repris sur le sujet central de la bêta fermée du 3 mai : la gestion fine des blocs texte lies.

Le besoin produit est clair : le bloc texte ne doit plus être un empilement de patches. Pour que l’éditeur carte postale soit défendable en bêta, il faut que le texte puisse :

  • être colle dans un bloc sans changer sa géométrie ;
  • déborder proprement vers un second bloc lie ;
  • reagir aux retours ligne volontaires ;
  • revenir dans l’autre sens avec Backspace et Delete ;
  • garder l’édition locale riche : gras, typo, taille, couleur, sélections partielles ;
  • rester manipulable quand les poignées de resize se chevauchent.

Le fil de la journée a été très concret : coder, pousser, tester dans l’application, remonter les régressions, corriger, puis verrouiller avec des tests navigateur.

Les retours utilisateur qui ont pilote la journée

Les retours manuels ont été plus utiles que n’importe quelle lecture théorique du code.

Premier problème fort : un clic dans un bloc texte pouvait provoquer une boucle React Maximum update depth exceeded. Ce symptôme indiquait que le store et le composant TipTap se repondaient en boucle au lieu de converger vers un état stable.

Ensuite, le collage dans un second bloc lie a révélé un bug de géométrie : le bloc cree à droite revenait parfois sur l’emplacement du premier bloc et s’etirait anormalement. La correction a porté sur le respect de la frame d’origine au moment du paste et de la redistribution.

Un autre retour important a concerne les poignées de resize : quand deux blocs se chevauchent, certaines poignées horizontales devenaient impossibles a attraper. La logique de priorité/z-index des handles a été revue pour que la manipulation reste possible sans casser l’édition du texte.

La suite a été le vrai cœur du sujet : l’édition riche.

Deux régressions ont été identifiées par test manuel :

  • sélectionner une portion de texte puis appliquer le gras ne modifiait plus le texte ;
  • changer une typo ou un style local pouvait être écrase par la resynchronisation du document TipTap ;
  • des espaces ou retours ligne artificiels pouvaient apparaître pendant un resize ou une édition structurelle.

Le point le plus sensible est arrivé ensuite : les retours ligne volontaires. Le premier Enter poussait correctement du texte dans le second bloc, mais le deuxième Enter cassait la chaîne et faisait remonter le titre au mauvais endroit. C’était le signal que le reflow live et le curseur TipTap n’étaient pas encore cohérents.

Ce qui a été corrigé

La journée a été decoupee en commits courts pour garder une reprise possible à chaque étape.

Corrections principales :

  • stabilisation initiale des blocs texte lies (4684ded) ;
  • conservation de la frame du bloc au collage (6b597e2) ;
  • priorisation des poignées de resize sur le canvas (3c590d3) ;
  • maintien de l’édition texte au-dessus de l’overlay de resize (4d047ba) ;
  • préservation des bornes de texte riche pendant les éditions liées (ea37353, puis ee4b877) ;
  • reflow live des retours ligne et suppressions structurelles (0a6194c) ;
  • restauration du curseur TipTap après reflow live (22f587c) ;
  • couverture e2e de Backspace et Delete (a3a7629) ;
  • préservation des éditions de style locales dans une chaîne liée (dde8f3f).

Le changement technique important du soir est celui-ci : le reflow live ne doit pas devenir un aspirateur qui réécrit tout à chaque action. Les modifications structurelles (Enter, Backspace, Delete, paste) peuvent déclencher une redistribution. Les modifications de style local doivent, elles, être préservées et commitees sans être ecrasees par un ancien sourceDoc.

Pourquoi la dernière régression est arrivée

La régression “je ne peux plus éditer localement” venait d’un conflit entre deux garde-fous.

D’un cote, il fallait recharger TipTap depuis le document source quand la chaîne liée est redistribuee, sinon le rendu local et le store divergent.

De l’autre, cette resynchronisation pouvait se déclencher pendant une édition locale de style. Dans ce cas, TipTap appliquait bien le gras ou la police, puis le composant reinjectait un document source plus ancien et annulait l’action.

Le correctif final sépare mieux les cas :

  • si la source n’a pas réellement change, on ne reinjecte pas setContent inutilement ;
  • si une édition de style ne change pas le texte brut mais change le document riche, elle est committee immédiatement dans la chaîne ;
  • si une action structurelle modifie le flux, on garde le reflow live mais on restaure la sélection pour que le deuxième Enter ou Delete parte du bon endroit.

Ce point est important pour la suite : on ne peut pas stabiliser les blocs lies en ignorant TipTap. Le curseur, le document riche et les fragments de chaîne doivent rester alignés.

Vérifications effectuées

La validation du jour s’est faite par retours utilisateur et par tests outilles.

Vérifications e2e principales :

La spec linked-text couvre maintenant :

  • conservation du document complet sur création de blocs lies ;
  • resize sans lignes blanches synthétiques ;
  • édition partielle en gras sans perte du texte canonique ;
  • application de police pendant l’édition active ;
  • Enter x2 avec redistribution de la chaîne ;
  • Backspace puis Delete dans l’autre sens.

Lecture produit du soir

La bonne nouvelle du jour n’est pas que les blocs texte lies sont magiquement finis. La bonne nouvelle est qu’on a transformé une zone floue en matrice de comportements testables.

Pour la bêta du 3 mai, le bloc texte lie reste probablement le sous-système le plus risqué de l’éditeur. Mais il est maintenant possible de le retester avec une grille simple :

  • insertion d’un bloc texte simple ;
  • collage long ;
  • création d’un second bloc ;
  • resize horizontal et vertical ;
  • Enter, Backspace, Delete ;
  • gras et typo sur sélection partielle ;
  • vérification que le texte ne bouge pas de cadre sans action explicite.

La stratégie pour demain doit rester la même : ne pas ouvrir un autre gros front texte tant que cette base n’a pas été retestee manuellement sur plusieurs scénarios réels.

Reprise conseillée

Demain, reprendre par un test manuel court, dans cet ordre :

  1. hard refresh de l’application locale ;
  2. création de deux blocs texte lies ;
  3. collage long dans le bloc 1 ;
  4. deux Enter au début ;
  5. Backspace, puis Delete ;
  6. sélection partielle + gras ;
  7. sélection partielle + changement de police ;
  8. resize des deux blocs quand les poignées se chevauchent.

Si ce parcours tient, le chantier pourra passer de “stabilisation noyau” a “validation bêta”. Sinon, les prochains bugs devront être ajoutés à la spec e2e avant toute nouvelle correction.
